# 6주차 과제 회고

기존에 했던 4주차 과제에서 많은 것이 바뀌어서 시간이 많이 걸렸다.

## entity 간의 관계

먼저, erd 작성 했을 때 만든 post, user, comment, attach, post_like, comment_like 과 report 테이블로 나누어 진행 하고자,

각각의 entity를 만들어 관계를 만들어줬다.

이 과정에서 각각의 Id들은 증가 할 수 있도록 IDENTITY 방식을 사용 하였다.

수업에서 배웠던 것 처럼 1대다, 다대1 등 N쪽이 외래키를 가질 수 있도록

@ManyToOne 과 지연로딩을 기본으로 잡기 위해 fetchType을 lazy로 지정했다.

Post entity와 Post Like, Attach entity, Comment entity간의 관계에서 

post(부모 엔티티)가 없어지면 attach(자식 엔티티)도 없어지도록 설정하는게 좋아보여, 양방향 관계 매핑을 통해 수업에서 배웠던 orphanRemoval을 직접 사용해보았다.

### Repository

어렵지는 않았다. optional (있거나 없거나)과 List(0또는 여러개 리스트 반환)의 사용 기준 등 스스로 재정립 할 수 있었다.

쿼리 메소드 수업에서 findByPostId 등으로 ai한테 질문 했다가 스네이크 표기법을 넣는 것이 JPA 입장에서 확실해진다, postId 같은 필드가 있으면 post.id와 헷갈릴 수 있다는 것이 기억에 남아 쿼리 매소드 작성도 수월 했다.

### Controller

많이 ai를 사용한 부분이다. 코드를 작성하고 틀린 부분이나 오류를 잡아달라고 요청 하였고, 이 과정에서 엔드포인트 매핑 피드백이랑, RequestParam, 과 Pathvariable, RequestBody의 작동 원리랑,

RequestBody에서 내용과 제목등 빈칸이 되어서는 안될 @NotBlank를 넣었음에도 수행 해줄 @Valid가 없어서 작동하지 않았던 이유를 알게 되었다. 

### DTO

post테이블과 attach테이블을 분리하다보니 postResponse에서 imageurl을 따로 넣는 것보다 post에 포함된 attachResponse를 넣는 것이 적절한것 같다고 생각했으나 내부 구현 감이 잡히지 않아서 ai의 도움을 받았다.

`this.attaches = post.getAttaches().stream()        .map(AttachResponse::new)        .toList();`

나중에 Service 쪽에서 ai 도움 받을 때, PostService에서 getposts 목록 조회 할 때도 똑같이 사용되는 방법 이었다.

### Service

각각의 테이블에 findPostById 등 메소드를 선언해서 repository에서 id를 통해 꺼내오는 메소드를 작성 했다. 이 전에는 getid()등을 사용하면서 null 일때의 예외를 다 처리 해줬는데 JPA 연동을 하고 만약 null이면 알아서 예외를 던져준다는 점이 편리했다.

service 코드 구현에서 막히는 부분들은 ai를 활용하였습니다. 물론 처음부터 끝까지 코드를 짜달라고 하진 않았고 처음에는 힌트 제공으로, 그래도 구현이 안되는 건 코드 생성을 맡겼습니다. (getPosts 제외.. repository에서 어떻게 가져올지 감이 안잡혔습니다, 결과적으로는 stream()문법을 알게 됨)

### 오류 해결

처음에는 @Transactional을 아예 붙히지 않았다가 AI에게 의도치 않게 붙히는게 좋다고 도움을 받아 서비스의 수정, 삭제, 추가 메소드에 transactional을 붙혀줬다.

나중에는 다른 트랙잭션과 충돌하게 되면 잘못된 값을 읽거나 불러오게 될 때를 방지해서 추가 한 이유이다.

조회 메소드는 충돌에 대해서 가볍게 생각해 transactional을 붙히지 않았는데 posts, comment, attach 등을 조회할때 콘솔에서

[Request processing failed: org.hibernate.LazyInitializationException: Could not initialize proxy [com.homework4.workapi.entity.User#1] 오류가 떠서 살펴 보았다.

LazyInit 오류는 영속성 컨텍스트가 닫힌 후 엔티티를 불러올때 생기는 오류로 알고 있는데 값을 엔티티도 아니고 dto로 반환하니 영속성 컨텍스트가 닫혀서 생긴 오류 였다. 

원인은 getposts()메소드에서 findAll()이 자동으로 repository의 작은 트랜잭션을 실행시켜서 post엔티티를 영속 상태로 만들고 값들을 반환하고 종료. 

그 이후에 PostResponse에서 post.getUser().getId()등을 가져오려고 할때, post와 user의 연관 관계가 lazy로 되어 있어서 값을 가져오지 못하는 것이었다.

→ 결국 서비스 getposts()메소드에도 transactional을 붙혀 영속성 컨텍스트를 닫히지 않게 해결.
