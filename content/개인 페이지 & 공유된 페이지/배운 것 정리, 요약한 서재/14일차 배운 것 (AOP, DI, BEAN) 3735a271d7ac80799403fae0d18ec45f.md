**DI**

1. 사용자가 브라우저나 앱에서 버튼을 누르면 백엔드 서버로 HTTP Request를 보냄.
2. Spring Boot로 도착하고 Controller로 도착함
3. controller는 요청 받아서 해석을 하고 핵심 비즈니스 로직을 처리하는 Service 클래스로 넘김
4. Service는 계산이랑 로직 처리하고 데이터를 Repository 계층에 남김.
5. Repository는 db접속해서 데이터를 기록하거나 조회 함
6. 처리가 끝나면 다시 서비스로 전달하고 controller에게 전달해서 프론트 엔드에게 응답까지 감.

IoC가 제어권을 외부로 넘기는 제어 역전이라는 거시적인 설계 철학이면

DI가 그것을 구현 해내는 실질적인 기술 -> 프레임워크가 이미 만들어줬고 우리는 그걸 가져다 쓰는 것에 가까움.

의존성 주입하면 변수만 선언하고 알맞은 객체를 안으로 밀어넣어 줌.

실제 웹서비스는 클래스가 수만개까지 될 수 있다.

- > 이 클래스들이 서로 얽히고 설켜서 의존 할 수 있다.
- > 이것들을 전부 new 키워드로 조립하고 하는 건 복잡하고 하나라도 틀리면 문제가 되기 좋다.
- >이걸 개발자가 신경 쓰는게 아닌 spring 에서 관리해주는것임.

이걸 왜 사용하나? -> 결합도를 낮추고 변경에 강한 구조를 만들고 테스트와 확장이 쉬운 코드를 유지한다.

만약에 new 키워드 써서 객체를 직접 만들면? ->

- > 자바 소스 코드 파일 안에 notification service 가 new emailsender라는 구체적인 클래스 이름을 작성하게 됨
- > 컴파일러가 이 코드를 기계가 읽을 수 있는 바이트코드로 변환 (컴파일 시점)
- > 이때 두 클래스 간의 관계를 굳힌것처럼 확정이됨
- > 컴파일 타임의 의존성과 런타임의 의존성이 동일 하다는 뜻.
- > 강한 결합

스프링 부트 켜면 콘솔창 로그 찍히고 실행이 되는데 -> 이때 ApplicationContext라는 컨테이너 생성.

- > IoC Container 컨테이너는 어떤 역할을 하는 가?
- > 스프링이 코드 스캔, 객체를 미리 만들어 AplicationContext에 저장하는 것임.

컴파일과 런타임에서의 의존성은 서로 다르다.

- > 이렇게 쓴다면 테스트 코드 돌릴 때마다 외부 이메일 API 호출하는 게 됨.

**Bean**

개발자가 직접 new 키워드 사용해서 객체 만들고 조립하는게 아니라 스프링 이용해서 제어 권한 넘기고 알아서 객체 의존성 주입하게 만들어줌.

- > 스프링 컨테이너가 객체를 만들고 하는 단위가 Bean

자바 프로그램 돌아가면 힙 영역에 수많은 객체들이 생긴다. 만들고 사라짐.

- > 프론트엔드에서 사용자가 로그인 할 때 폼 데이터로 API 서버에 요청하는 JSON 데이터 담기 위해서 생성되는 Request 객체, 데이터 베이스에 조회해서 가져온 주문 객체 -> 자바 객체
- > 스프링 빈에 해당되는가?
- >ㄴㄴ
- > 스프링 빈이 되기 위해서는 조건이 필요하다.
- > 객체를 그냥 만들었다고 자동으로 빈이 되지는 않는다. 컨테이너의 관리 대상이 되려면. annotation을 붙이든, 별도의 클래스를 통해서 스프링에게 알려줘야함. “이 클래스는 bean 대상” 이라고 알려줘야함.
- > 컨테이너가 어플리케이션 시작 지점에 객체 생성하고 객체가 필요한 곳에 의존성 주입을 해주고 어플리케이션 셧다운 될 때 안전하게 자원 반납하고 파기 하는 -> 생명주기를 통제함.

그치만

- > 프론트엔드와 통신하기 위해 만든 데이터 객체(DTO)나 데이터 베이스의 한 row를 표현하기 위한 객체들은 bean으로 등록하지 않음.
- >즉, 일회성 소모품은 bean으로 등록하지 않는다.
- > 일회성 소모품을 스프링 컨테이너에 일일히 다 관리하고 추적하려고 한다면 성능저하..

그럼 어떤 걸?

- > 주문 처리하는 OrderService나 회원가입 로직 행하는 UserService, Controller, repository 같은 클래스들은 계속 new로 만들 필요가 없음.
- > 시스탬 구성하는 핵심 처리 로직의 뼈대 역할을 하는 객체들만 스프링 컨테이너에 올리면 됨

사용 이유 :

객체를 컨테이너가 관리하도록 해 의존성 관리, 생명 주기, 구성 변경을 일관되게 처리하고 애플리케이션의 확장성과 안정성을 높이기 위해서

1. 의존성 관리 자동화
    1. 객체는 복잡하게 의존하고 얽혀있음.
    2. 컨트롤러에 서비스가 필요하고 서비스는 페이먼트 클라이언트나 레포지토리, 알람 서비스등 객체에 의존.
    3. 만약 이런 복잡한 의존성을 빈 시스템이 없으면 우리가 스스로 조립하고 나열 해야함. New 키워드….
2. 일관된 생명 주기
    1. 실제로 일하다 보면 어떤 객체가 생성되자마자 즉시 실행되어야 하는 무조건 로직이 필요한 경우가 있다.
    2. 외부 서버와 통신을 하기 위해 보안 TCP 커넥션 또는 어플리케이션 켜질때. 데이터베이스에서 자주 쓰는 공통 코드를 읽어와 메모리 캐시에 올리거나 해야 할 수 잇음.
    3. 개발자가 직접 제어하면 순서 맞추기가 너무 힘듬
3. 구성 변경 및 유연한 확장
    1. 로컬이나 개발 환경에서는 돈이 빠져나가면 안되니 가짜 결제 빈을 써야하고 운영에서는 실제로 결제되는 진짜 결제 빈을 써야 한다.

**Singleton Scope**

기본값임

싱글 톤이라는 것 자체가 단어 뜻 그대로 “스프링 컨테이너 라는 공간 안에 이 타입의 빈 객체 인스턴스는 하나만 만들어진다.

어플리케이션 전체가 이 단 하나의 객체를 돌려가면서 공유해서 쓴다.”

- > 기본적으로 설정 빈으로 등록을 하면 객체 한번만 초기에 생성, 그 후에는 돌려서 씀.

빈클래스 자체는 싱글톤으로 생성되고 사용 될 수 있다는 가정하에 클래스 레벨에서 데이터를 관리하지 않고 요청 파라미터를 활용하거나 내부의 분리된 지역변수를 사용하는 무상태 설계로 써야함.

- > 지역 변수는 쓰레드별로 독립적인 스택 메모리에 쌓여서 동시성 문제에서 안전하다.

정리 :

- 거대한 매니저인 컨테이너(IoC)가 객체들을 빈이라는 관리대상으로 묶고 통제하면서 일하면서 필요한 관계를 DI로 엮어준다
- Bean은 new로 만들어 내는 일반 자바 객체랑 다르게 컨테이너에 의해서 생명주기가 철저히 관리되고 Di를 통해 조합되는 객체
- 어노테이션 이용한 컴포넌트 스캔으로 등록할 수 있고 설정 클래스 기반으로도 가능.
- 99% 싱글톤으로 동작함. -> 하나의 객체를 여러명이 동시에 요청하는 스레드가 공유하면서 사용하기 때문에 내부에서는 절대 요청별로 달라지는 상태값을 저장해서는 안됨.

**AOP (Aspect-Oriented Programming)**

실무에서 개발하다보면 프로젝트 규모가 커지다보면 계층을 쪼개도 공통적으로 나타나는 요구사항들이 있다.

- > 사소한 요구사항들은 주문이나 결제나 특정 비즈니스 도메인에 속하는 것은 아님.
- > 이런 기능들은 주문이나 결제나 특정 비즈니스 도메인에 속하는 것이 아니다.
- > 애플리케이션 전체를 횡단하면서 필요하다 라는 표현을 씀.
- > 즉, 이런 공통 코드를 다른 관심사로 묶어서 처리하는 역할을 한다.

이미 스프링 프레임 워크 안에서 내부적으로 사용 되고 있는 개념이다.

정의

핵심 비즈니스 로직과 공통 관심사를 분리해, 공통 기능을 코드 수정 없이 일관되게 적용하도록 하는 프로그래밍 방식

핵심 비즈니스 로직

우리가 보통 서비스 계층에 짜는 코드.

- > 예를 들면 장바구니에 담긴 상품의 총액을 계산한다 or VIP회원들에게 10% 할인을 적용한다 같은 것들

공통 관심사(횡단 관심사)

- > 로그 기록, 보안 검사, 트랜잭션 관리 등등…
- > 각 컨트롤러, 서비스, 레포지토리 등등을 횡단하면서 공통으로 나타나는 요구사항.
- > 그래서 생긴게 AOP.
- > 공통 기능들을 비즈니스 로직 안에 섞지 말고 아예 바깥으로 빼내서 하나의 독립된 모듈로 뭉쳐버리자. 그리고 나중에 프로그램이 실행 될 때 지정한 규칙에 맞춰 살짝 끼워넣자.
- > 관점 지향이라는 철학의 핵심
- > 관점 자체를 핵심 기능과 부가 기능으로 쪼개서 보겠다.

비즈니스 로직에 관한 것과 그 외 공통 기능을 나누자

OrderService 클래스

- > 신규 개발자이고 로직 이해하는 것이 목적. 업무 흐름을 알아야함.
- > 코드 열어보니 로그 로직 들이 많이 있고 다른 검사 코드도 많다고 가정.
- > 이러면 비즈니스 의도 자체를 파악하기 힘들음
- > 그래서 별개로 분리를 하는 것이 AOP

사용 이유

공통기능을 한곳에 모아 코드 중복을 줄이고, 비즈니스 로직을 건드리지 않고도 기능 변경과 확장이 가능하도록 만들기 위해서

비즈니스 로직을 건드리지 않고

- > 무슨 이야기냐?
- > AOP를 쓰면 서비스 클래스를 건드리지 않고 별도의 Aspect 클래스를 만들어서 “실행 시간 측정 하라”는 공통 로직을 작성. 그 후 모든 Service 라는 이름이 붙은 모든 클래스의 모든 메소드의 앞뒤에 적용 하라는 규칙 적용 가능.

사용 방법

1. Aspect로 공통 기능 분리
2. 포인트컷으로 적용 대상으로 지정
3. 언제 무엇을 할 것인가? -> advice 정함. @before, @after, @around 등등

실제로 동작하는 시점

- > DI배울 때 스프링이 구동될 때 controller안에 orderservice객체를 주입을 하는데.. 컨트롤러가 서비스 메소드 부를 때 aop로직이 알아서 앞뒤로 끼어드는게 어떻게 되는거인가?
- > 프록시 객체를 몰래 만들어서 치환하는 방법
- > 스프링은 진짜 orderService 빈을 바로 컨테이너에 내놓지 않음 -> 내부에는 aspect공통 로직이 추가로 발려있는 가짜 대리인 객체(proxy 객체)를 몰래 하나 만들어냄.

OOP vs AOP

OOP가 우리가 살게 될 집을 나누는 설계도

AOP는 그 건물 전체를 가로지르면서 들어가는 전기 배선, 수도 파이프, 이런 느낌

정리

- 어플리케이션의 핵심 비즈니스 로직을 더럽히는 횡단 관심사(로그, 권한, 테스트, 트랜잭션)을 깔끔하게 분리해내는 방법, 철학, 도구를 Aop라고 부른다.
- 3가지 구성요소이다. Aspect, point cut, advice 3가지 역할로 나뉘어져 있음.
