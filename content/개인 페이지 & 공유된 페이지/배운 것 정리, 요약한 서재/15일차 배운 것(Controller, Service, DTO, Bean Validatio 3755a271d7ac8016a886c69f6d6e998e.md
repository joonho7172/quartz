**Controller**

Controller. 화면에 무언가를 띄우고 프론트엔드 개발자와 실제로 데이터를 주고 받는 API라는 것을 만들어 볼 수 있다.

컨트롤러는 외부 입력을 처리 흐름에 맞게 정리하고, 실제 비즈니스 처리는 서비스 계층에 위임함.

- > controller가 중개자 역할이 아닌 다른 역할까지 하면 컨트롤러 자체가 비대해질 수 있음.

사용 이유 : 웹 요청과 응답 처리 책임을 비즈니스 로직과 분리해 변경 범위를 줄이고, 요청 흐름을 일관되게 관리하기 위해서.

- > 기획이 바뀌고 요구사항이 바뀌어서 백엔드쪽에서 내려주는 응답 필드명을 바꾸거나 기획상 페이지 순서나 구조가 바뀌어서 URl도 같이 바뀌어야하는 상황
- >계층 분리가 되어있으면 고쳐야 할 지점이 나뉘어져 있고 명확한데 불필요하게 서비스 계층이 바뀔 수가 있다.

사용 방법

클래스에 @controller나 @restcontroller 선언하고 요청에 메서드 매칭.

@RestController라는 어노테이션 하나 붙으면 Bean으로 등록해줌

- > 클래스 내부에 메소드 만들고 @GetMapping(“/users”) 같은거 붙여두면 디스패처 서블릿이나 핸들러 매핑이 정보를 수집해서 가져감
- > 클라이언트가 get방식으로 오면 이 메소드를 실행시켜야지 라고 정해줌

@Controller와 @RestController의 차이

둘 다 붙으면 해당 클래스가 컨트롤러 역할을 한다.

- > 스프링 MVC 내부에서 응답을 만들어내는 매커니즘은 완전히 다름.
- > 예전에는 서버에서 HTML 까지 같이 렌더링 해서 브라우저로 전달을 해줬고, 이 과정에서 JSP나 thyme leaf 같은걸 사용함.
- > 이럴때 사용하는게 @Controller.
- > 백엔드는 데이터 jSON만 프론트로 던져줌
- > 이 상황에서 백엔드 서버는 REST API 서버의 역할만 한다.
- > REst api 서버를 만들기 위해 사용하는 컨트롤러가 @RestController
- > @Controller + @ResponseBody의 결합
- > 컨트롤러 메소드에서 return new UserResponse 순수한 자바 객체를 반환하면 뷰 리졸버가 관여를 안하고 대신 MessageConverter가 개입함.
- controller는 화면을(view, html) 리턴하기 위한 목적
- restcontroller는 데이터(json)를 리턴하기 위한 목적

@RequestMapping -> 클래식하고 범용적. 클래스 레벨과 메소드 레벨 둘 다 붙일 수 있다.

- > 클래스 맨 위에 붙여줌. @RequestMapping(“/users”)
- > 이 컨트롤러 안에 있는 모든 API 기본 시작 주소는 /users 다 라고 공통 경로를 묶어줌
- > 그 위에서 get mapping, post mapping 붙여주는거임

DTO -> 데이터 전송하는 객체

일회용 택배 상자 느낌이라고 보면 됨

- > 복잡한 비즈니스 로직이나 데이터 설정.. 아예 단순하게 선언해서 쓰는 객체. (getter나 setter만)

왜 이렇게 까지 하냐? DTO 클래스는 응답에도 사용이 되기 때문. 응답은 어디서 오냐? DB에서 옴.

DB에서 필요한 정보만 반환하면 됨. 그래서 사용함. (게층간의 결합도 분리나 보안)

정리 :

- Controller는 비즈니스 로직이나 외부의 http 요청을 연결해줌
- 그 중간에 dto 존재
- rest와 일반의 차이 -> api 서버로 기능하는가 아닌가.

**Request/Response**

@RequestParam은 URL 뒤에 물음표 ? 를 붙이고 적혀있는 쿼리 스트링 값을 뽑아올 때 사용함.

@RequestHeader

http 헤더 값을 메서드 파라미더로 받기 위해서

@RequestBody

프론트 엔드에서 회원가입 하거나 주문 요청 할 때, 덩치가 큰 데이터를 url에 담아서 보낼 수 없음.

- > 그래서 body에 json 형태로 담아서 보냄.
- > 이때 컨트로러 파라미터 앞에 requestbody를 붙이면 메세지 컨버터가 동작함.
- > json 문자열을 파싱해서 일치하는 클래스의 필드를 찾아서 객체 생성.

정리

- HTTP 메시지의 구조, 그리고 그 구조를 파싱하고 자바 객체로 변환해 주는 것은 프레임 워크의 영역.
- 각 어노테이션에 대한 이해
- PathVariable과 QueryParameter의 차이점과 기준.

**Service**

Controller 배우고 HTTP 요청을 받아서 JSON 객체 (DTO)로 변환되고 다시 DTO로 반환된다.

이 과정 안에서 Service 계층을 배움.

배달앱에서 주문을 생성한다. 비즈니스 동작을 가정.

- > 프론트 엔드 입장에서는 단순하게 /api/orders Post 요청을 보낸 것으로 끝.
- > 나머지는 서비스 계층에서. 어떤게?
1. 사용자가 정상적인지
2. 주문한 식당이 영업중인지

7. 완료되면 알림 메시지

Service 계층이 지휘하고 처리함.

service는 어플리케이션 내부에서 진입점 역할을 함.

주문 로직이 파편화 되지도 않고 동일한 규칙 아래에서 안전하게 실행될 수 있다.

이걸 무시하면 -> 스파게티 코드. 컨트롤러 안에도 결제 로직. 서비스에도 결제 로직.

- > 유지 보수 어려워짐.

사용 이유 :

비즈니스 로직을 웹 계층과 분리해 변경을 국소화 하고, 처리 흐름을 재사용 가능하게 관리하기 위해서.

테스트 코드 작성 용이.

controller안에 잇으면 테스트 할때 가짜 http요청을 만들고 해야하는데 그게 무겁고 느려짐.

service안에 잇으면 테스트 코드에서 임시 서비스 객체 만들어서 메소드의 비즈니스 로직만 검증 가능.

프랜잭션 :

데이터베이스 상태를 갖고 다룰 때 적용하는 논리적인 작업 단위

모두 성공하거나 모두 실패해서 원래대로 돌아가거나 하는 무결성을 지켜준다.

PostService에서 게시글을 작성 할 때,

데이터 정합성 파괴를 막기 위해 트랜잭션을 적용 시켜준다.

- > @Transcational을 붙히면 db 트랜잭션을 열고 정상적으로 끝나면 제출하고, 롤백 대상 예외가 있는데 그걸 만족하면 전부 다 롤백한다.

스프링에서 Runtime이랑 error 계열이 롤백 대상

- > ioexception은 롤백 대상이 아님.
- > 롤백을 처리해주려면 별도로 지정해줘야함

비즈니스 로직의 시작과 끝이 트랙재션의 시작과 끝이 되어야 한다.

비즈니스 -> 서비스 . 그래서 서비스 계층에 트랜잭션이 있어야 하는거임.

정리

- Service 계층은 단순히 비즈니스 로직 담는 공간을 말하기도 하지만. 여러 비즈니스 규칙들을 나누고 호출하고 쪼개서 관리함.
- 서비스 안에는 가능하면 순수 자바코드로 작성이 되어 있어야함.
- 트랜잭션 경계가 왜 서비스가 되어야 하고 readonly = true는 어떤 의미를 갖는가?

**Bean Validation**

사용자가 보낸 데이터가 올바른가? 에 대해서 검사하는데

- > 같은 조건을 처리하려고 하다 보면 if문들이 생긴다.
- > 이걸 어떻게 해결하느냐? 라고 하면 Bean Validation 이라는 제공 도구를 사용한다.

객체의 값이 제약 조건을 만족하는지 자동으로 검증해주는 표준 기반 검증 기능

- > 프론트엔드에서 보내온 json데이터가 dto로 변환
- > 낱개의 변수가 아닌 하나의 객체라는 덩어리로 들어옴
- > bean validation은 ‘객체 자체가 가져갸아 할 올바른 상태를 스스로 정의하고 프레임 워크가 그 객체의 상태를 일관된 기준으로 검증해주는 기술.

예시 ) 회원가입 때 이메일 형식 검사, 회원 정보 수정할때 이메일 형식 검사는 같음.

Bean validaion은 검증 규칙을 메소드에 두지 않음.

- >DTO 객체 자체에 제약조건을 고정 시켜버림.
- > userRequestDTO 클래스의 email필드에 규약을 하는거임.
- > 검증기준이 파편화 되지 않음.

사용 방법

if문 덕지덕지가 아닌 @NotNull이나 @Min, @NotBlank 등..

또는 @Valid 어노테이션 하나가 수십줄의 if문을 대체.

@valid를 통해 클라이언트가 보낸 json 메시지를 메시지컨버터가 자바 객체로 전환

컨트롤러 내부 코드 실행하기 직전에 스프링이 가로채서 방금만든 DTO 객체를 검사를 시킴.

검사 할 때, 위에 잇는 어노테이션을 기반으로 확인을 하고 어긋나면 예외를 던짐.

컨트롤러에서 이미 검증햇는데 또 서비스 레벨에서 하는 이유 :

가끔씩 브라우저를 통해서만 호출되는게 아니기 때문.

AOp같은거라고 생각하면 됨

정리

- BeanValidation 핵심은 검증 로직을 메소드 레벨에 두지 않고 객체의 구조 자체에 어노테이션으로 제약 조건을 나타냄
- 프론트 엔드의 유효성 검사는 사용자 편의를 위한것. 백엔드에서 필수로 관리.
- 별도로 서비스를 호출 할때 유효성 검사를 해야 할 때도 있음.

**Exception Handling**

BeanValidation 배웟고 어노테이션 이용해서 검증 실패하면 예외 던짐.

- > 검증 실패해서 스프링이 요청을 튕겨내먄 프론트엔드 에게는 어떤 형태의 에러가 전송 되는가?

조회하려는 회원이 없을 때, 아니면 잔액이 모자랄 때.

- > 이런 상황들에서 에러가 났다는 사실을 안전하게 통제하고 프론트가 이해할 수 있도록 포맷으로 가공해서 전달을 해야함.
- > 이러한 예외처리를 어떻게 디테일하게 처리하고 깔끔하게 하느냐가 중요함.

에러와 예외의 차이점 :

에러 - 재앙. 시스템 레벨에서 수습 할 수가 없음. Jvm 메모리 터지는 oome나, -> try catch가 안됨 근본적 원인을 제거해야함

예외 - 통제가능. 뭐 아이디 틀렸거나, 첨부 파일 용량제한. 그냥 사소함..

시용 이유 :

비즈니스 로직과 오류 처리 책임의 분리

사용 방법 :

예외를 다루는 방법 크게 두 가지

메소드 내부에서 try - catch 로 처리 / 예외를 throw 해서 상위 계층으로 전파하는 방식

그럼 언제 뭘 쓸까?

메소드 내부에서 try catch로 직접 처리 방법 :

- 기준 : 이 예ㅚ가 발생했을 때 내가 여기서 대안을 마련해서 정상적인 흐름으로 복구 할 수 있는가
- 지금 이 메소드에서 복구가 가능한가? 복구가 가능하면 여기서 해결가능

상위 계층으로 전파하는 방식 :

- 이 예외가 여기에서 로직을 진행하는 것이 무의미 할때,
- 만약에 서비스에서 에러를 던지면 컨트롤러가 예외를 잡고, 컨트롤러는 try-catch 없으니까 자기를 호출했던 상위로 던진다.

정리 :

- 에러는 프로그램이 바로 뻗어버리는 것을 의미하고 예외는 통제 할 수 있는 영역이다.
- 예외는 문제가 아니라 비즈니스 로직이 더 이상 진행 될 수 없음을 알리고 흐름 관리하는 신호이다.
- Throw 통해서 던지는거 판단 할 줄 알아야함.

수업에서 가져가야 할 핵심

- Controller 계층이 웹 요청을 자바에 맞게 번역하고 HTTP로 다시 번역해서 반환하는 관문 역할
- @Controller와 RestController의 차이 ->기술 면접에서 말할 수 있을 정도
- dto를 왜 써야함?
- HTTP 레벨의 Request, Response의 물리적인 구조(상태 줄, 헤더, 바디) 에 대한 이해
- @Pathvariable, @RequestParam, @RequestBody의 차이
- Rest API 설계 할 때, 많이 물어보는 pathvariable과 queryparameter의 차이
- 서비스 계층이 단순히 비즈니스 로직의 집합이 아니라 여러 작업을 쪼개고 나눠서 의미있는 비즈니스 흐름을 만드는 계층.
- Controller 와 service의 격리를 통해서 얻게 되는 이점.
- 트랜잭션의 경계가 왜 service에 계층에서 시작하고 끝나야 하는지.
- 프론트엔드 유효성 검사와 백엔드의 유효성 검사가 둘 다 필요한 이유를 설명
- 프로그램에서 발생하는 예외가 단순히 문제가 아님.
