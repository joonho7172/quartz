**Index**

백엔드에서 성능 튜닝한다고 하면 정말 많이 하는 기본 중의 기본

- > 기본이 쉽고 임팩트가 적어서 그런것이 아닌 인덱스로 설계에서 중요함.

예를 들어 트리 구조도 있음.

B tree : 데이터 베이스와 자료 구조에서 사용하는 좋은 것.

디스크 기반의 DB에 최적화된 균형 트리

이진 탐색 트리는 노드 하나 읽을 때마다 디스크 io가 발생 할 수 있음

그러나 b tree는 노드 하나에 여러개의 값을 담으니 비교 횟수를 줄일 수 있다. -> 트리의 깊이를 낮출 수가 있음.

b+tree 같은 경우는 중간노드에도 데이터의 실제 주소값이 저장이 될 수 있음.

- >더 많은 데이터가 담길 수 있음. 검색 효율이 좋다는 뜻.

그래서 결국 DB에서는 B+Tree를 기본으로 사용을 함. 그 배경에는 디스크 IO를 최소화 하는 것이 중요하고 범위검색이 필요하기 때문에 설계된 구조.

**비클러스터형 인덱스**

PK가 아니라 일반 필드에 개발자가 쿼리를 통해서 설정하는 인덱스. 사용되는 쿼리 패턴에 따라 적절하게 인덱스를 걸어주는게 필요함.

동작방식:

- 별도의 인덱스를 위한 페이지(공간)을 만듦 : 데이터는 테이블에 그대로, 별도의 공간에 인덱스 페이지를 만들음/ - 키값, 포인터(위치) 저장.
- 테이블당 여러개를 생성 : 클러스터형은 테이블 당 하나만 가능 (PK)

조회 과정

1. 인덱스 페이지에서 원하는 키 값을 찾음.
2. 찾은 키 값에 매핑된 포인터(페이지 번호)를 확인을 함.
3. 포인터 따라서 데이터 가져옴

장점 : 상대적으로 입력, 수정, 삭제 작업이 좋다. 참고로 클러스터 형 인덱스 같은 경우는 필수적으로 들어가는 것이다.

단점 : 결국에는 두 단계를 거쳐야 한다. 테이블에 있는 pk를 갖고 찾는것이 아니라 인덱스를 탐색하고 데이터를 탐색한다는 두 단계로 나뉘어져 시간이 걸림. + 저장공간이 좀 들 수 있음.

알아야 하는 이유

인덱스를 사용하면 데이터 빠르게 읽고 출력 가능.

- > 인덱스가 없으면 처음부터 끝까지 모든 데이터를 다 읽어야 하는 경우가 생김
- > 풀스캔

인덱스 단점

1. 저장 공간 차지.
2. CUD 자체의 성능 저하. 테이블을 추가하거나 수정, 삭제 할 때 테이블의 데이터만 바뀌는 것이 아니라 인덱스도 같이 갱신 한다. 조회가 많이 없고 쓰기 작업만 자주 일어나면 인덱스 최소화 하는게 나음

결론 : 인덱스는 쿼리 패턴을 기준으로 설계 해야 한다.

**Explain**

Type : 어떻게 찾앗는지

Possible_keys : 이 쿼리에 사용 할 수 있다고 고려한 인덱스 목록.

Key : 위에잇는 여어 후보중에 실제로 사용하기로 한 인덱스.

Rows : 이 쿼리를 처리하기 위해서 읽어야 할 것이라고 예측한 데이터 row 수 -> 작을 수록 좋음

Extra : 추가적으로 중요한 정보

- Using where : where절로 필터링
- Using index : 커버링 인덱스가 사용됐다는 의미 , 쿼리에 필요한 모든 데이터가 인덱스에 포함. 굳이 실제 테이블 까지 안가도 됨.
- Using filesor : ORDER BY 를 인덱스 순서로 바로 처리하지 못해서 별도의 메모리 공간이나 디스크 사용해서 데이터 정렬.

인덱스가 있어도 못타는 쿼리.

WHERE phone = 01012345678 처럼 숫자로 비교를 하면 Db에서 타입을 맞추려고 형변환이 일어날 수 있음. 즉 어려움이 생길 수 있다..

가능한 컬럼 타입과 조건값 타입을 맞춰서 작성하는 것이 필요함.

LIKE 조건도 사용하능.. index로 범위를 좁혀서 찾는 느낌 인것임.

**카디널리티 / 셀렉티비티**

- 카디널리티 : 컬럼에 저장된 값의 고유성 -> 중복되는 값이 얼마나 적은가?
- 셀렉티비티 : 카디널리티 / 전체 행 개수 로 계산하는 값. 1에 가까울수록 선택도가 좋다.

인덱스는 결국 데이터를 잘 걸러주는 역햘을 해야함.

- 카디널리티가 높은 컬럼 (선택도 좋음 ) : 인덱스 걸면 1명의 유저가 명확하게 나옴. -> 인덱스 효과 높음
- 카디널리티가 낮으면? -> 의미가 없음.. (예시로 뭐 성별)
- 결론 : 카디널리티를 기준으로 인덱스를 설정 할 줄 알아야 함.

**복합 인덱스**

여러 컬럼 묶어서 하나의 인덱스를 만드는 경우가 아주 많다

- > 복합 인덱스
- > 컬럼의 순서가 인덱스의 성능을 결정한다.

예시를 보면 같은 지역 내 같은 이름 내 사용자 아이디. 이렇게. (Location, Name, ID) 순서로 인덱스 만들었을때.

WHERE Location = ‘서울’

WHERE Location = ‘서울’ AND ID = 123 이렇게 여러개 인덱스 가능.

그치만. WHERE NAME = ‘?’ 이렇게 바로 해버리면 순서랑 맞지 않아 인덱스를 처음부터 타지 못함.

- > 복합 인덱스 생성 할 때는 카디널 리티만 보는게 아니라 where절에서 함께 쓰이는 조건, 동등 조건과 범위 조건 순서, ORDER BY LIMIT 패턴을 같이 봐야함.

즉, 복합 인덱스 생성 할 때는 카디널 리티만 보는 것이 아니라 WHERE 절에서 함께 쓰이는 조건, 동등 조건과 범위 조건 순서, ORDER BY LIMIT 패턴을 같이 봐야함.

**커버링 인덱스**

Users 테이블에 (name, age) 순서로 복합 인덱스가 걸려있다고 해보자.

SELECT name, age FROM users WHERE name = "토르”;

- >DB는 굳이 실제 데이터가 있는 곳까지 찾아갈 필요 없음.
- > 커버링 인덱스
- > PK로 조회하는 key lookup 과정을 생략하게 해줌
- > 자주 사용하는 쿼리면 분석해서 커버링 인덱스를 의도적으로 설계하는 경우도 있음.

근데 SELECT * FROM users WHERE name = “토르”; 라고 하면 커버링 인덱스는 타지 못함.

**FULL Text Index**

정의 : 텍스트 검색해서 컴퓨터에 저장된 문서 또는 전문 데이터베이스를 검색하는 기법

역인덱스 : 책 뒤에 단어 기준으로 그 단어가 몇페이지에 나와있는지 알려주는 개념

FTi 과정

1. 파싱이랑 토큰화 : 인덱스로 지정된 텍스트 칼럼의 내용을 단어 단위로 전부 쪼갬
2. 불용어 처리 : 검색에 큰 의미가 없는 단어들을 제거 은, 는 , 이, 가 같은 조사들..
3. 역 인덱스 구축 : 처리된 단어들을 기준으로 어떤 단어가 어떤 문서에 위치하는지 나타낸 정보를 표처럼 만들음.

LIKE 검색을 할 때..

- LIKE ‘검색어%’ : 이건 ㄱㅊ음
- LIKE ‘%검색어’ or, LIKE ‘검색어%’ : 이거는 db가 인덱스 포기하고 하나하나 다 비교해서 처리를 하기 때문에 ..
    - 검색어가 어디에 위치 할지 모름.

한계 : 실무에서는 이것만으로 부족하 겨웅가 많음.

1. 정교한 처리가 안됨 : ngram을 써도 단순한 방식임. 형태소 분석이 더 정확함.
2. 동의어 처리가 약함. 노트북, 랩탑 이런거
3. 랭킹 모델의 한계 : 검색할때 우선순위를 의도적으로 가중치를 매기는데 복잡함
4. 확장성 : 검색 트래픽이 너무 많아지면 결국 데이터 베이스 자체에 부하가 감.

그래서 등장한 검색 엔진

정리 : 텍스트 검색 할 때, like 쿼리 쓰면 안좋고 안티패턴이다 -> 인덱스 못타고 풀스캔 타서.

역 인덱스를 써서 효율적으로 검색 하기도 함.

그치만 한계가 있어서 검색 엔진을 따로 씀.

**Transaction**

주문을 했을때, 주문 버튼 누르고 재고 줄고 결제 실패하고 주문 내역 없고 등등

트랜잭션은 이런 일을 막기 위해 여러 SQL 작업을 하나의 논리적인 단위로 묶는 장치임.

정의

절대로 쪼개져서는 안되는 논리적인 작업의 최소 단위

1. 재고 차감
2. 주문 내역 추가
3. 결제 정보 기록

이런 것들은 비즈니스 논리적으로 하나의 묶음으로 취급을 함.

전부 성공하거나(commit) 전부 실패하도록(rollback) 하는.

트랜잭션 사용 이유는 데이터의 무결성과 일관성을 보장하기 위해서

- > 데이터 깨지거나 논리적으로 맞지 않은 상태가 되는 것을 원천적으로 차단하는 안전 장치

Spring에서는 어노테이션으로 처리를 함. Transactional 어노테이션으로 처리를 하고 spring에게 알려줌.

Actice - 실행 중 상태

실패

- Failed 실패 (오류 발생하면 db마다 처리방식이 다름)
- Aborted : 실패 감지하고 rollback

성공

- Partially committed 부분완료 상태 - 영구적 저장이 아님
- Commit 아예 성공 상태 - 영구적 저장 상태

트랜잭션은 단순히 sql을 묶는것이 아님.

예를 들면 해외 여행 서비스 -> 기차, 항공, 숙소 예매 3가지 하위 트랜잭션이 있어도

그 셋중 하나만 실패하면 전체적인 여행 서비스 트랜잭션이 롤백이 되어야함.
