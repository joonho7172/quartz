트랜잭션의 범위

트랜잭션은 개발자가 비즈니스 논리에 따라서 어디까지 묶고 처리할지를 결정함. -> 트랜잭션의 범위를 설정한다.

- > 트랜잭션은 필요한 최소 범위에서 사용하는 것이 좋다.
- > 성능과 연결이 된다.
- > 트랜잭션을 길게 잡으면 정합성이 좋아지는것이 아니라 불 필요하게 시간이. 오래 걸려서 성능이 떨어질 수 있다.
- > 그래서 트랜잭션은 순수 데이터베이스 작업만 포함하도록 최대한 짧고 간결하게 가져가는게 필요하다.

**ACID**

트랜잭션이 안전하게 수행된다는 것을 보장하기 위해 4가지 특징이 존재함.

이것을 ACID라고 부름.

Atomicity(원자성)

All, or nothing

앞에 커밋, 롤백 예시처럼 연결이 됨.

트랜잭션에 포함된 작업은 전부 성공하거나 아니면 단 하나도 실행되지 않은 것처럼 모두 취소해야함.

Consistency(일관성)

트랜잭션이 실행을 성공으로 완료하면 언제나 일관성 있는 데이터 베이스 상태를 유지해야함.

스키마를 위반하면 안된다는 것임.

예를 들어 계좌 잔고가 - 라던지 그런 일관성이 없으면 조치를 해야한다.

Isolation(격리성)

여러 트랜잭션이 동시에 실행될때, 각 트랜잭션은 다른 트랜잭션의 작업에 영향을 받아서는 안된다.

재고 1개 남았을때, a랑 b주문의 트랜잭션이 들어오면 안된다는 거임..

Durability (지속성)

커밋된 결과는 장애가 나도 사라지지 않아야 한다.

**Isolation Level**

4가지 격리 수준이있다.

개발자가 서비스 특성에 맞게 선택 가능.

격리 수준이 낮을 수록 동시성이 높아짐 - 처리가 빠르게 되면서 성능이 좋아질 수 있고 정합성이 떨어짐.

격리 수준이 높을 수록 동시성이 낮아짐. - 처리가 늦게되고 병목 현상 발생하는 대신 정합성은 좋아짐.

이상 현상

격리 수준을 어떻게 설정하느냐에 따라서 생길 수 있는 문제 현상

- Dirty Read : 두개의 트랜잭션이 있을때, 다른 트랜잭션이 커밋하지 않았을때, 확정되지 않는 데이터를 읽는 현상.
- Non - Repeatable Read (반복 불가능 읽기) : 하나의 트랜잭션 안에서 같은 데이터를 두번 조회했는데 그 사이에 다른 트랜잭션 값을 수정하고 커밋하는 바람에 두 조회 결과가 다르게 나오는 현상.
- Phantom Read(유령 읽기) : 하나의 트랜잭션 안에서 특정 범위의 데이터를 두 번 조회했는데 첫번째 조회에서 없었던 유령 데이터가 두번째 조회에서 나타나는 현상 -> 다른 트랜잭션이 그 범위 안에 새로운 데이터를 추가하고 커밋을 했기 때문.

**NoSQL**

뭐 하나의 커머스 서비스를 한다고 할 때,

티셔츠는 색상, 사이즈, 소재 같은게 중요하고 노트북은 CPU 이런게 중요하고 다른 화장품은 속성이나 유통기한이 중요함.

근데 이런걸 하나의 테이블로 넣으면 .. 많이 이상해짐

이럴때 RDBMS 대신에 NoSQL 이라는 선택지를 가져감.

정의

Not Only SQL . 그냥 다른 개념의 DB임.

- > 어떤 데이터는 키로, 어떤 데이터는 json처럼 문서형태로 관리, 어떤 데이터는 대량 로그처럼 관리..

nosql은 엄격한 규칙에서 벗어나 유연한 데이터 구조를 가질 수 있음.

- > 어떤 user는 이름과 이메일만 가질 수 있고, 어떤 유저는 거기에 뭐 기술, 선호지역 등등 다른 데이터를 가질 수 있음.
- > 그렇다고 설계가 필요하지 않은건 아님.

대규모 데이터 처리에 용이함.수평적 확장성에도 용이함.

**데이터베이스의 확장**

데이터베이스가 확장을 왜 해야하는가?

성능 좋게 하기 위해서 서버 업그레이드만으로는 한계가 있음.

정의 분산 -> 분산은 한 DB가 모든 데이터를 들고 모든 요청을 처리하게 두지 않고 데이터를 나누는 것.

스케일 업 (수직확장) : 서버 한대 성능 업그레이드

스케일 아웃(수평확장) : 여러대의 서버(DB)가 일을 나눠 처리하게 하는 것

- 파티셔닝 : 큰 데이터를 기준에 따라 여러 조각
- 샤딩 : 그 조각을 보통 여러 Db서버나 노드에 나눠 담아 각 서버가 일부 데이터만 맡게 함
- 복제 : 데이터를 나누는게 아니라 같으 ㄴ데이터를 다른 서버가 따라서 복사하는 것.

알아야 하는 이유 : 데이터가 너무 많아지면 단일 서버 데이터베이스로는 처리 한계에 도달하기 쉬움.

DB 장애 상황이 터지면 복구하거나 바로 대응을 하는것이 필요

- 인프라에 들어가는 비용을 효율적으로 다루기 위해서 적절하게 확장
- 시스템의 안정성 : 단일 서버는 그 자체가 단일 장애점. 그 서버가 다운되면 모든 것이 멈춤. -> 데이터를 여러 서버에 복제해두면 메인 서버에 문제가 생겼을 때 예비로 복제해둔 서버를 메인 서버로 승격하고 장애 시간을 줄일 수 있음. -> FailOver -> 단순히 복제 서버가 잇다고만 해서 성능이 확 좋아지는게 아니라 어떤 서버 승격시킬지. 어떻게 처리할지 고민을 해야함.

동작 방식

데이터베이스 확장하는 방법 - 파티셔닝, 샤딩, 복제

- 파티셔닝 : 하나의 거대하고 무거운 데이터를 여러 조각으로 쪼개서 나눠 담는 방식. 각 조각은 전체 데이터의 일부만 가짐. -> 예를 들면 주문 데이터를 기간별, 사용자 구간별, 샤드별로 나눠서 진행
- 복제 : 데이터를 다룰 때 하나의 DB가 있으면 다른 복제된 DB가 그 DB의데이터 상황을 따라가도록 복사하는 방식

둘 다 같이 쓰는 상황이 많음.

실제로 일할땐 복제를 더 많이 쓰는거 같기는 함.,

수직 파티셔닝

칼럼을 기준으로 쪼개는 방식.

- > 단순히 컬럼을 나누는게 아니라 자주 조회되는 컬럼, 아닌 컬럼 등 기준을 가지고 나눔.

사용자 정보 중에 뭐 비밀이어야할 정보, 공개되어도 될 정보 등등

수평 파티셔닝

행 기준으로 쪼개는 방식

수억건의 주문행을 id, order_id, 생성일드읃ㅇ을 기준으로 나누는 것.

말 그대로 행 기준으로 테이터를 나누는 넓은 개념

샤딩은 수평 파티셔닝된 데이터를 여러 DB나 노드에 분산해서 운영하는 방식

왜 하는가?

- > 테이블에 데이터 수억건이 쌓이면 인덱스 써도 시간이 많이 걸림
- > 관리비용도 증가하기 때문에 수평파티셔닝이나 샤딩을 통해서 관리한다.

Range-based Sharding (범위 기반 샤딩)

- 특정 기준 (ID 범위, 날짜 범위) 에 따라 데이터를 분할함.
- 샤딩 키의 값 범위를 기준으로 데이터를 분할
- user_id가 0~999인 사용자는 1번 샤드, 1000~2000은 2번 샤드에 저장하는 방식임.
- 직관적이고 샤딩키 범위와 조회 조건이 맞을 때 효율적.
- 단점 : 순서대로라면 마지막 순서의 샤드는 항상 쓰기가 그곳에 해당되니 부하가 있을 수 있음.

Hash-based Sharding(해시 기반 샤딩)

- 해시 함수를 사용해 일정한 방식으로 샤드에 분배함
- 샤딩 키를 해시 함수에 넣어서 나온 결과값을 기준으로 데이터를 분산
- 해시 함수는 입력값을 고르게 분포 시킬수 있어서 저장 위치가 여러 샤드에 분산될 가능성이 있음.
- 단점 : 범위 기반 조회가 거의 불가능해짐 이어지는 숫자가 붙어있지 않기에.

Composite Sharding(복합 샤딩)

- 범위 기반과 해시 기반 샤딩을 혼합해서 사용함.
- 그래서 혼합해서 쓴다.
- 예를 들면 주문 데이터를 다루는 상황
    - 주문 생성 월 기준을 먼저 나누고 그 안에서 다시 user id 나 order id로 데이터를 해싱 분산 시킴.
    - 이렇게 하면 최근 한 달 주문처럼 기간 기준으로 읽는 작업은 범위를 좁힐 수 있음.

**복제**

샤딩 / 파티셔닝이 데이터를 쪼개는 것이면 복제는 말 그래도 데이터를 복사

그러면 복사를 왜 하는가?

고가용성 : 서버나 네트워크, DB등의 인프라나 시스템이 오랜 기간동안 지속적으로 정상 운영 가능한 성질. -> 시스템 멈추지 않고 24/365 안정적으로 서비스를 제공 할 수 있는 능력

1. 고가용성 : DB에서 장애 발생 했을 때, 중단 시간을 줄이기 위해. 원본 서버가 있고 원본 서버의 변경사항을 따라가는 복제 서버를 여러대 준비함. 그리고 원본 서버에 문제가 생기면 복제본 중 하나 를 새로운 원본으로 승격을 시키고 .. 요청경로를 바꿔서 서비스를 이어나가게 함.
    1. 승격 전에 복제 지연, 데이터 손실
2. 부하분산 : 대부분의 서비스에서 쓰기 작업보다 읽기 작업이 훨씬 많이 일어남

복제 동작 방신

1. Primarysms 데이터의 변경이 발생 할 때마다 그 변경 내역을 바이너리 로그 라는 특별한 로그 파일에 순서대로 기록을 함.
2. repluca가 프라이머리의 바이너리 로그를 지속적으로 감시해서 새로운 내용을 데이터베이스에 반영함.
- > 이 과정을 통해서 replica 는 primary의 변경을 따라가면서 같은 상태로 수렴.

복제의 문제와 주의사항

replica와 primary를 따라 갈때 지연이 발생함
