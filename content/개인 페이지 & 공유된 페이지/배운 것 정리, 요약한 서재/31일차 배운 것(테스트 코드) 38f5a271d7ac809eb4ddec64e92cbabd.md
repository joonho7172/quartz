**테스트 코드**

테스트 코드는 기업들도 우대하는 사항임.

테스트 코드가 갖는 의미에 잘 알아볼 것.

정의 :

- 소프트 웨어의 기능이나 동작이 의도대로 올바르게 작동하는지 검증하기 위한 코드
- > 의도대로 .. 실제 코드와는 다르게

Ex) 두 숫자를 더하는 add 함수에서,, 결과가 예상한대로 나오는지 확인하는 코드가 테스트 코드.

- > 수백 수천개 전체가 판단한 대로 나오는지

사용 이유 :

그냥 해야됨

테스트가 하나도 없는 시스템은 작은 것 하나로 뭐가 어떻게 될지 알 수가 없음.

코드 건드리는게 무서워짐 -> 레거시 코드가 발생

리팩토링이나, 유지보수 비용 절감을 위해서.. +

1. 안전망이 됨

문제가 실제로 생겼을 떄도 도움이 됨.

어느 지점에서 생겼는지 알아야 빠르게 좁힐 수 있음.

1. 리팩토링 마음 편하게 할 수 있다.

기능 그대로 추가 하거나, 바꿀 때, 테스트 코드가 없으면 무서워짐.

- 변경에 대한 두려움을 막아줌.

주문 금액에 할인 쿠폰 등..

1. 문서와 협엽

테스트 코드는 일종의 살아있는 문서임.

- > 잘 작성되면 설명서 같은 역할을 함.
- > 새로 합류한 개발자가 코드 베이스 이해 할 때, 테스트 코드 보는게 효율 적..
1. 테스트 하기 쉬운 코드를 만드려고 하면 알아서 좋은 구조를 가짐..

동작 방식:

특정 기능을 실행하고, 예상 결과와 실제 결과를 비교해서 일치 여부를 자동으로 확인.

준비(Given)

테스트 할 기능을 실행하려면 그에 필요한 환경이랑 입력값을 갖춰야함.

실행(When)

우리가 진짜 검증하고 싶은 기능 호출

검증(Then)

기대 값이랑 같은지 확인, 다르면 실패..

- > 덧셈 기능 가진 클래스. 테스트 대상이 되는 프로덕션 코드.
- (add) 함수라고 생각을 해보자

사용 방법 :

@Test처럼 어노테이션을 붙혀줌.

@Displayname (~~)

assertEquals(expectedResult, actualResult) 등으로 값 비교.

테스트가 실패하면 코드 수정이 필요함.

test가 통과했다고 해서 모든 경우에 만족 하는 가?

- 그건 아니다. 하나의 기능에도 여러 상황을 각각 테스트로 작성을 해야함.
- 즉, 테스트에 경우가 들어가는걸 구분하는 감각이 필요함.
- 

그래서 JUnit 같은 테스트 프레임 워크 갖고 테스트 작업을 맡기는 방법이 있다.

테스트 주도 개발 : 테스트 방법론이나 설계 철학 등등..

테스트 종류 :

단위(함수나 메소드 단위), 통합(여러 개의 단위 들이 서로 결합되었을 때 상호작용), E2E(END To End) 테스트. 3가지가 있음.

정리 :

- 테스트 코드는 소프트웨어가 의도대로 동작하는 지를 사람이 아닌 코드로 검증하는 도구
- 단순히 버그 잡는게 아닌 두려움 없이 코드 고칠 수 있게 해주는 안전망.
- 기능이 어떻게 동작하는지 보여주는 문서 역할
- 동작 방식은 준비-실행-검증으로 3단계가 있음.

**좋은 테스트의 기준**

AI의 작성한 테스트 코드 보면 복잡한 비즈니스 상황에서 모자라거나 하는 경우가 생김.

예를 들면 정산에 관련된 코드 등.. -> 개발자가 보고 판단, 검증, 확인 할 수 있어야함. 그리고 어떤 테스트가 있어야 안전한지 판단 할 줄 알아야 함.

**FIRST(Fast, Independent, Repeatable, self-validating, timely )**

각각 무엇을 뜻하는지 이해 할 것.

단어 뜻 보다 중요한 건 각 원칙이 어떤 신뢰를 주는가?

정의 :

좋은 테스트의 기준?

- 버그 안정적으로 찾고, 코드 변경에 대한 확신, 유지 보수성이 높은 테스트 코드
- 개발자가 원칙과 기준을 기반으로 판단을 할 수 있어야함.
- 널리 쓰이는게 FIRST 원칙.

사용 이유 :

테스트 코드는 전체 테스트 코드 말고 특정 기능을 추가하거나 개발한다고 하면 바로 돌릴 수 있어야 함.

자주 돌려서 개발하고 있는 방향이 틀린지 아니면 의도와 다르게 흘러가는 건 아닌지 확인을 하는게 필요함

- > 테스트는 빠르고 가벼운게 좋음

언제 어떤 환경에서 돌려서 같은 결과가 나올 수 있어야 함

- > 외부의 값에 의존하거나 요일별 설정 등..

테스트는 독립적이고 하나의 시나리오에만 집중 할 수 있어야 함.

즉, 좋은 테스트란 단순히 문제 찾는 도구가 아니라 개발자가 믿고 의존 할 수 있는 자산으로 만들기 위함

- > 어떤게 좋은 테스트인지 안좋은 건지 감각이 있어야 스스로 판단 가능.

**First**

F-Fast

테스트가 빨라야 개발자가 코드 조금 고칠때마다 부담이 없이 실행 할 수 있다.

- > 테스트가 느리면 돌리는 것 부담이고 생산성 저하.
- > 테스트 코드 돌아가는 환경 개선 ,,등등
- > 테스트 코드 시간 줄였다 -> 팀 단위 생산성 증대. 실제 비즈니스 이펙트와의 연결은 모호하지만..

테스트가 빠르다고 하는건 단순한 성능 문제가 아니라 테스트 자주 돌려서 피드백 주기 살아있게 함.

예시) 실제 Repository에 접근해서 작업하려 하면 테스트 결과가 느려짐..

불안정해 질 수도 있음.

해결 - 가짜 객체를 끼워넣음 RealRepository 대신에 fakeRepository를 넣는다던가

어차피 진짜 DB까지 갈 일이 없으니까..

주문을 저장하는 로직의 흐름이면 가짜 객체로 충분함.

만약 DB까지 연동되는게 목적이면 통합 테스트의 영역.

- > 지금은 테스트 목적에 따라서 불필요한 외부 의존성을 떼어낸다.

I - Independent

각 테스트가 서로 독립적이어야 한다.

테스트가 다른 테스트에 영향을 주면 아뇜

testB가 testA에 묶여있는 상황이면.. 실행 순서에 크게 영향을 받을 수가 있음..

testB는 문제가 없는데.. 의존성 때문에 문제를 찾아야 함

이 경우에는 @BeforeEach 등을 설정을 해서 각 테스트 메소드 앞에 설정을 선언 해 줄 수 있음.

즉, 독립적 테스트는 실패한 테스트 하나만 보고도 문제를 명확히 할 줄 알아야 함.

R - Repeatable

테스트는 어떠한 환경에서 돌리던 항상 결과가 같아야 한다.

- > 로컬이던, Ci던.. 오늘이든 내일 이든..

반복 가능성을 깬다,

- localDateTime.now나.. 랜덤 값이나 네트워크 상태 등등
- 같은 코드여도 날짜가 달라지면 검증하는 내용이 바뀜.

해결 - 날짜를 직접 주입을 해버리는 것. LocalDate.of(2025,10,11) 처럼

@ParameterizedTest처럼 여러개 넣어 줄 수 있음.

지금처럼 반복 가능성이 깨진 테스트를 flaky 테스트라고도 말을 함.

어제 통과 했는데 오늘 안될 수도 있는 테스트..

S - self - validating

테스트는 성공인지 실패인지 테스트 코드 자체가 스스로 판단 해야 함.

개발자가 로그 보면서 출력 된 값을 눈으로 확인해야 한다면 좋은 테스트

Println 같은거는 또 개발자가 직접 판단 해야함

그래서 쓰는게 assertEqauls……

T - Timely

좋은 테스트는 코드 다 만들고 작성하는게 아니라 동시에 작성 되어야 한다.

- 적절한 시기에 작성이 되어야 함.
- TDD와 연결.
- 시기나 타이밍이 중요한 이유
- 테스트 먼저 작성하면 개발자가 자연스럽게 어떻게 테스트를 하는지 고민 해 볼 수 잇음. 테스트 코드 작성을 미루지 말자

꼭 절대적인 규칙은 아님.

테스트 커버리지는 어디까지 테스트를 실행했다라는 양적 지표

테스트의 질을 보장하지 않음.

그냥 참고 자료 일 뿐.

**TDD(Test, driven, development)**

테스트 주도 개발.

기능 코드 만들고 테스트 붙히는게 아니라,

아직 존재하지 않은 기능에 대해서 실패하는 태스트를 먼저 작성하고 나중에 보완하며 코드 개선… 세단계의 싸이클 반복

Red - green - refactor라고 함.

(Red)

테스트 먼저 작성 - 기능코드 없으니까 빨간줄. (Red)

“무엇을 먼저 만들지 정의

(Green)

방금 작성한 실패하는 테스트 통과 시킬만의 필요한 코드만 작성, 욕심내지 말것.

(Refactor)

기능이 동작하는 걸 확인 했으니, 코드의 구조를 다듬음

중복 없애고 이름 정리하거나 깔끔한 구조로..

이 과정에서 안전망 역할을함..

기능이 깨지지 않았다는 걸 알 수가 있음.

TDD는 테스트 기법이라기 보다는 설계 방법론임

- 내가 만든 코드의 첫번 째 사용자가 테스트가 되어야 함.

가져가야 할 핵심

- 테스트 코드가 무엇인가?
- 내가 만든 기능이 내 의도대로 동작하는지를 사람의 눈이 아닌 다른 코드로 확인하는 것.
- 왜 사용하는가? - 버그 잡기 위한 도구가 아니라 문제를 덜어주는 안전망.
- 기능이 어떻게 동작하는지 보여주는 문서와 같은 역할
- 모든 테스트는 준비, 실행, 검증하는 세 단계로 흘러감.
- 좋은 테스트와 나쁜 테스트를 가르는 기준이 따로 있다. 그리고 그 원칙 중 하나가 FIRST 원칙임.
