**Blue/Green Deployment**

실행중인 버전 내리고 새 버전 올리는 방식은 중단 배포였다.

새버전 미리 준비해두고 트래픽 옮기면 무중단 배포.

두개의 환경을 두고 트래픽을 전환한다.

설명 할 수 있어야 하는 것

- 블루랑 그린 각각 어떤 역할?
- 문제가 생겼을때의 롤백 방법.

정의

- 두 개의 독립된 환경을 운영하며, 트래픽을 새로운 버전으로 전환해 서비스 중단 없이 배포와 롤백이 가능한 배포 방식
- 하나는 사용자 요청 처리하는 운영 버전의 환경, 하나는 배포 되어잇는데 아직 트래픽 받지 않은 상태.
- 블루 그린은 색깔이 중요한게 아니라 트래픽의 상태가 중요함.

중요한건 한쪽에서 서비스 담당, 다른 쪽에서는 새로운 버전이 전환을 기다림.

트래픽을 전환해주는 nginx 나 ALB와 같은 로드 밸런서가 있어야 함.

트래픽 전환을 검사하는 헬스 체크도 필수임.

배포가 진행되는 순서

블루가 안정적으로 서비스를 사용하고 제공하고 있는 형태

일반적인 상황. 배포 전의 평범한 운영 상태.

1. 기존에 블루는 그대로 서비스를 제공하고 있고, 새로운 배포를 위해서 동일한 별도의 환경인 그린에 v2를 운영 배포
    1. 동일한 환경으로 배포를 하는 이유는 환경이 다르면 그린에서 아무리 확인을 잘해도 결과를 운영에서 받을 수밖에 없음,
2. 그린이 정상임을 확인 (헬스체크) 그 다음 트래픽 전환, 그린이 정상인게 확인이 되면 그때 트래픽을 그린으로 넘김
3. 블루 그린에서 배포가 완료되는 순간은 새로운 코드 올려서 배포 했을 때가 아닌 트래픽의 목적지가 바뀌었을때, 그때 배포가 목표임.
4. 정상적으로 배포된 것 확인했으면 블루 종료, 또는 대기.

반대로 문제 생기면 되돌리기도함,, 이전 환경을 어떻게 처리하느냐에 따름

사용 이유

트래픽 전환만으로 배포.

**Rolling Deployment**

롤링 배포는 블루 그린이랑 접근 방식이 다름.

- 롤링은 환경 따로 만들지 않고 요청 처리하고 있는 대상들을 한번에 바꾸는것이 아닌, 일부만 조금식 새버전으로 순차적으로 변경

설명 할 수 있어야 하는 것

- 롤링 배포가 무엇을 어떤 순서로 교체하는 방식
- 어떤 단계가 있고 어떤 위험이 있는지

정의 :

- 기존 인스턴스를 하나씩 새로운 버전으로 순차 교체하며 전체 서비스를 점진적으로 업데이트 하는 배포 방식

롤링 배포는 인스턴스가 여러개 있다는 걸 전제. 다중 인스턴스 구조를 전제.

- 인스턴스가 하나면 그거 내리는 순간 요청 받아 줄 곳 없으니, 일부만 교체한다는 말이 성립하지 않음.

인스턴스 앞에 동일하게 라우팅 계층이 필요함.. 로드밸런서 같이..

- 롤링 배포에서 로드 밸런서 라우팅 계층이 어떤 역할을 하는가..
- 배포 도중에 어떤 인스턴스를 요청 대상에서 빼고 어떤 인스턴스를 목록에 새로 넣을지.?

배포 전 상태. 아직 아무런 배포도 시작하지 않은 상태.

- 여기서부터 롤링이 하는 일은 전체를 한꺼번에 갈아엎지 않고 순차적으로 배포해나간다.
- 순차적으로 교체 해나가는 과정에서 인스턴스는 계속 요청을 처리함.

장점 :

배포 실패했을 때 멈추기 편하다.

- 새 버전에 문제가 있으면 교체한 인스턴스에서 문제가 먼저 드러남.
- 아직 배포하지 않은 인스턴스들은 이전 버전 그대로 정상 동작
- 다음 인스턴스들 교체하기 전에 그 지점에서 멈추기 가능
- 전체를 한번에 바뀐 뒤에 문제 알게되는거는 상황이 완전히 다름

공통 단계

어쩃든 두가지 패턴 둘 다 인스턴스 바꿀 때 밟는 순서가 비슷함. 공통적인 것들을 먼저 이야기.

라우팅 계층에서 대상 목록을 조정

- 기존 인스턴스를 빼거나 새로운 버전 띄울 자리는 만들어두는 단계
- 그 다음 새 버전 인스턴스
- 헬스체크 과정은 거침 ㅇㅇ. 인스턴스가 요청을 받을 준비가 됐는지 확인하는 헬스 체크
- 구버전의 인스턴스가 있다라고 하면 정리하는 과정을 거침.

근데 정리하는 동안 인스턴스에 남아있는 요청도 같이 정리됨

- AWS에 있음. 로드 밸런서 대상에서 뺀 인스턴스 남은 요청이 끝나기까지 기다렸다가 하는 지연 설정
- 클라이언트가 다시 붙는 재연결 로직을 같이 만들어 둠.

In-place(교체 실행 방식)

기존 인프라 안에서 실행 중인 인스턴스를 하나 내리고 그 자리에 새 버전으로 채우는 방식

- 제자리에서 갈아 끼우는 방식이라고 생각 하면 됨
- 전체 인스턴스 개수는 그대로 두고 진행 하는 방식.

비어있는 자리에 v2인스턴스 실헹. 초록색 박스 하나 생김.

- 인스턴스 실행 했으면 확인하고 통과한 다음에 대상 목록에 들어가서 요청을 받기 시작함.
- V1 인스턴스랑 v2인스턴가 동시에 요청.
- 롤링 배포 끝날 때까지 구버전이랑 신버전이 같이 사용자 요청을 처리하는 구간이 생김.
- 같은 시간인데 어떤 사용자는 v1이 만든 응답 받고 어떤 사용자는 v2가 만든 응답을 받는다.
- 프론트 엔드에서 두 형태가 모두 처리 될 수 있도록 만들어야 함.
- DB도 마찬가지.

로그인 세션 같은 경우에는 서버를 따로 하나 두어서 인스턴에서 로그인을 관리하지 않도록 하는.

Side by side.

위에는 내리고 올렸으면, v1을 하나도 내리지 않은 상태에서 새로운 v2인스턴스를 실행함. 배포전보다 인스턴스가 하나 늘어난 상태.. v2 헬스체크 통과하면 그때 들어감.

새로운 인스턴스가 요청을 정상적으로 받고 있는게 확인이 되면 기존 v1 인스턴스 중 하나를 대상 목록에서 빼고 처리중인 요청 정리하고 내림.

- 처리 용량 면에서 유리한게 잇음
- 새 인스턴스 먼저 올리고 기존 인스턴스를 내리니까 요청을 받은 인스턴스 수가 아래보다 떨어지는 구간이 없음.
- 인플레이스는 하나 내리면 새로운 인스턴스 준비될 때까지 잠깐 낮아지는 구간이 있었음.
- 이런 과정을 반복해서 v2는 늘고 v1은 줄어들음.
- 전체가 v2로 바뀌고 로드 밸런서는 V2로만 요청을 보냄
- Sbs 같은. 경우에는 롤백 할 때
- 배포가 진행 중인 시점에 아직 내리지 않은 v1 인스턴스가 그대로 살아 있는 경우가 됨
- 그래서 문제가 발견되면 남아잇는 v1 인스턴스가 요청 받게하면됨
- 일시적으로 필요한 추가 자원이 있는가..
- 인플레이스는 없음
- sbs는 배포 중에 인스턴스가 늘어나니까 그만큼 여유 자원이 있어야 함.
- 배포 중에 유지되는 처리 최소 용량
- 인플레이스는 교체 중에 원래보다 낮아지는 구간이 잇음.
- sys는 원래 용량보다 낮아지는 구간이 없음.
- 완료까지의 시간은 인플레이스가 더 오래 걸림 .

롤백까지 걸리는 시간

인플레이스는 v1을 다시 끼우는 과정이 있어야 함.

sbs는 남아 있는 v1에 요청을 다시 하면 되면 빠른편.

블루 그린 비교

근본적인 차이는 무엇인가?

- 블루 그린은 새 버전이 돌아갈 환경을 통째로 준비. 검증 끝나면 트래픽 전환
- 롤링은 환경을 통째로 새로 만들지는 않음. 이미 요청 받는 하나의 대상 그룹안에서 순차적으로 배포해나가는 방식.

자원 부담의 차이

- 블루 그린은 트래픽 전환이 되기까지 새 버전이 실사용 요청이랑 섞이지 않게 관리테스트 할 수 있고 관리하는 복잡도가 좀 낮다

롤링은 자원 부담이 가볍지만 v2로 교체가 끝날 때까지 두버전이 함께 요청 처리하는 구간이 존재한다.

정리

- 롤링 배포는 요청를 처리하는 인스턴스가 여러개인 서비스에서 한번에 다 바꾸지 않고 일부 새버전으로 교체 해나가는 무중단 배포 전략
- 라우팅 계층이 있어야 함.
- 교체 순서는 큰 틀에서 인스턴스 대상 목록 조정하고 새버전 실행하고 헬스 체크 확인하고 그 다음에 요청을 받게 함.

카나리에서의 롤백.

카나리 범위에서 오류율이 튀거나 지연이 갑자기 확 늘어남.

- 롤백 할 때 라우팅 계층에서 v2로 향하던 비율을 줄이고 그만큼 v1으로 되돌리면 됨
- v2비율을 0으로 바꾸고 모든 요청 기존 버전으로 보내면 됨
- 전체 인스턴스에서 비율 조정하는 것으로 처리가 가능.
- 롤백하는 대상이라던가 전체적인 난이도가 편리하게 할 수도 있음.
- 라우팅 계층의 설정만 건드리면 됨.

호환성을 염두에 두고 해야함.

정리

- 카나리 배포는 새 버전을 전체에 한꺼번에 열지 않고 실제 운영 트래픽의 일부에만 먼저 노출하고 모니터링 한 다음에 범위를 단계적으로 넓혀가는 전략
- 배포 범위 정하는 방식은 라우팅 계층 통해서 처리 가능.
- 비율이 아니라 사용자 그룹이나 특정 지역으로도 나눌 수 있음.
- 실제로 내부 직원들을 먼저 대상으로 묶어 진행함.
