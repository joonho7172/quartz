**Synchronized**

멀티 스레드로 작업을 하면 여러 작업자가 동시에 일을 하니까 동시에 공유 자원을 건들일 때가 있음.

- > 데이터 충돌을 막기 위해서 기본적으로 해결하는게 synchronized

공유 자원

접근 제한

임계 영역 -> 여러 스레드가 동시에 실행해서는 안되는 프로그램 코드의 일부분 -> 동시에 실행 했을 때 데이터 정합성이 깨지거나 문제가 생기는 구간

— 그래서 사용하는게 lock(자물쇠) 임 자물쇠를 걸면 다른 사람이 들어 갈 수 없고 lock을 반납하면 다른 사람이 사용할 수 있는 것 처럼

Why?? 멀티스레드 환경에서 공유 자원 충돌을 방지하기 위해

무증상 오류 예방, 싱글톤 객체 보호 등

메소드 전체에 적용 가능.

lock같은 경우는 클래스 기준이 아니라 클래스가 가지고 있는 인스턴스 객체 기준으로 적용이 된다.

This 객체를 써서 자물쇠를 잠굴 수 있지만

하나의 클래스 안에서 다른 작업이 일어난다고 하면.

Object lock a = new object()

Object lock b = new object() 등으로 자물쇠를 구분해서 락을 걸 수가 있음.

(동기화 부분을 좀 더 명확하게 분리하기 위함), (데드락 유의 할 것)

결론

- 여러 스래드가 공유 자원 접근 할때 발생하는 충동을 사전에 막기 위해 한번에 하나의 스레드만 접근하도록 임계 영역을 설정 할 것.
- 그리고 임계 영역의 자물쇠를 걸어주는 lock.
- 락의 범위와 성능을위해 블록을 나누거나 위에 언급한 락을 명시적으로 하여 객체를 나누어 줄 수 있음.

**Lock**

멀티 스레드 환경에서 공유 자원 안전하게 보호하기 위해서 synchronized 를 쓴다고 배웠다. 메소드나 블록에 키워드 하나만 붙이면 알아서 해줌

정의 : 멀티스레드 환경에서의 안전한 자원 접근을 보장하기 위해 사용하는 동기화 제어 인터페이스 이다.

Synchronize는 코드 블록 {} 이나 메소드 단위에 락을 걸지만 락은 조금 다르다는 것임.

Synchronized 는 무조건 블록 안에 들어갈때만 락을 획득해야함.

- > 그러나 lock은 개발자가 직접 동기화나 통제권을 온전히 본인에게 달렸다.

비차단 락 : 스레드가 락을 즉시 획득하지 못하면 그냥 다음 로직으로 넘겨버리는거임.

(예시는 티켓 예매) tryLock()을 사용해서 구현.

일정 시간 동안 락을 획득하지 못하는 조건도 추가 할 수 있음)

**ThreadLocal**

스레드 마다 고유 독립 변수를 저장할 수 있게 해주는 클래스

지금까지는 여러 스레드가 공유 자원에 동시 접근 할 때 값이 꼬이는 걸 막았지만

이제는 스레드가 각자의 자원을 갖자는 의미

예시 ) 사용자가 로그인을 하려고 id를 입력해 요청을 보내면 -> 스레드는 여러 계층의 메소드를 거치며 작업을 수행 -> 이때 요청을 보낸 id같은 정보는 메소드의 매개변수로 게속 념거주려고 하면 더러움 -> 이럴때 스레드 로컬을 쓰면 어던 메소드가 가도 파라미터 넘길 필요없이 자기 공책 열어서 꺼내보면됨 -> 동시성 문제 발생 하지 않음

결론

- Lock 인터페이스는 Synchronized의 한계를 극복하고 개발자가 명시적으로 락의 획득과 해제를 제어함
- 비차단락. tryLock()을 사용하면 락을 얻을때까지 무한정 대기하지 않음.
- 스레드 로컬은 락을 걸어서 자원을 공유하는 대신 스레드마다 독립적인 공간을 제공하여 동시성 문제를 해결함 -> 그러나 remove()필수임!!

**Volatile**

Synchronized 랑 락 인터페이스를 통해서 여러 스레드가 동시에 하나의 자원에만 접근 할 때 발생하는 레이스 컨디션에서의 관점을 생각해야할듯

멀티 스레드로 직접 개발을 하다보면 자물쇠까지는 안필요할때.

정의 : 변수의 값을 모든 스레드가 항상 메인 메모리에서 직접 읽고 쓰도록 보장하는 키웓,

자바 프로그램은 성능을 높이기 위해 변수 값은 cpu내부 캐시에 복사해두고 빠르게 읽어옴. -> 그래서 cpu코어 옆에 L2, L1 같은 임시 저장소를 만들어놓았음. ->여기다가 저장했다가 다음에 읽을때 가져오는거임

그치만 이러한 성능이 멀티 스레드 환경에서 독이 될 수도 있다.

따라서 volatile 키워드를 붙여주면 jvm과 cpu에게 이것은 캐시로 저장이 아닌 메인 메모리까지 가서 읽고 쓰라는 거임 -> 모든 스레드가 항상 최신값을 가져올 수가 있다.

WHY?? — 스레드간의 변수 변경 내용을 즉시 공유하고, 값의 최신 상태를 예측 가능하게 유지하기 위해서

synchronized나 lock을 사용해도 해결되는데 왜 굳이 volatile? -> 코드가 더 간결해지고 성능에도 부담이 적은 키워드가 volatile이기 때문임

싱크로 라이즈드는 무거움 . 스레드를 대기 상태로 만들고.. 자물쇠 풀고 잠구고 운영체제에 부담됨 -> volatile은 스레드를 멈추지 않음

volatile을 사용하지 말아야하는 이유:

- 가시성은 보장하지만 원자성은 보장하지 않음.
    - 만약에 여러 스레드가 count++를 동시에 실행한다고 할 때, count에 volatile을 적용하는 것은 적절하지 않음.. 다른것에 비해서 자물쇠를 잠구거나 그런 것은 아니기 때문에 연산에 관해서는 충돌이 발생할 경우가 있음
    - (즉, volatile 은 읽기만 하는 플래그 변수 같은 상황에서만 사용해야함. 연산이 들어가는 것에서는 의도한 동작을 보장 할 수 없다.

**Atomic Type**

volatile만으로는 데이터가 유실되는 것을 막을 수가 없다. 가시성은 보장하지만 원자성은 보장하지 않기 때문. 읽기 전용이라 그럼. 경쟁 상태를 막아주지는 않음

그런 원자성 문제를 해결하기 위해서는 Synchronized나 lock을 사용하는 경우임.

sysnchronized는 성능상 병목이 있긴함.

정의 : 따라서 자바에서는 락을 따로 설정하지 않는. 여러 스레드가 안전하게 값을 수정 할 수 있는 타입을 제공하는 것.

목적 : 경쟁 조건을 막아주는 것

일반적인 변수 연상이 왜 원자적이지 않은 가?

+1 하는 하나의 코드가 컴퓨터 입장에서는 1. 값을 읽고, 2.값을 연산하고 3. 값을 저장하는 단계로 구분이 되기 때문. 그 중에 컨텍스트 스위칭이 발생하게 되면 값들이 꼬일 수가 있기 때문이다.

따라서 이러한 원자성을 lock없이 보장해주는 class라고 생각하면 된다.

어떻게? CAS (compare and swap)연산을 사용하는 것임.

예상값과 현재값이 같아야 연산을 수행함.

WHY?? — 멀티 스레드 환경에서 동기화 없이도 경쟁조건 없이 안전하게 값을 조작하기 위함

그래서 synchronized나 lock을 안쓰고 왜..? -> 데드락도 박을 수 있고 성능 저하도 막기 위함임

Synchronized는 기본적으로 비관적 락 방식이라는 것을 사용한다.

일단 문부터 잠구는 방식인데 운영체제 입장에서는 단순한 연산 하나 하자고 이러기에는 너무 비 효율적이라고 느끼는 것임.

그러나 Atomic Type은 낙관적인 락 방식이다.

일단 연산부터 진행을 하고 읽었던 값과 현재 메모리의 값이 여전히 같은지를 비교한다.

만약 같다면 새로운 값으로 교체, 다르다면 처음부터 최신값을 읽어와서 다시 실행하는 것.

CAS연산은 하드웨어 차원에서 기계어 명령으로 처리가 된다. CPU가 비교하고 교체하는 순간 절대 다른 스레드가 끼어들지 못하도록 보장이 되는 것임.
