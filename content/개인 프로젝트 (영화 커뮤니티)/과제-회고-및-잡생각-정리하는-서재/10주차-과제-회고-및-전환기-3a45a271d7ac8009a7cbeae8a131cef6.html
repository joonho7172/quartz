1.

hooks의 ImagePreview.js 을 검토하는 도중에

selectedImages를 state로 두면서 useRef로 두는 이유가 궁금해져서 찾아보았다.

간단하게 ai에게 한줄 답변을 받고 생각해보려고 했는데

AI는 항상 최신값을 유지하기 위해서 라고 했다.

어쩐지 코드에서 saveSelectedImage 에서도 state값이랑 ref값 둘 다 최신 상태로 유지하고,

나중의 const 에도 nextImages를 state에서가 아닌 ref에서 꺼내는 오는걸 보고 state에서는 최신 값유지가 안되어서 ref를 따로 선언한다고 생각했다. (물론 리렌더링 문제도 있겠지라는 생각)

곰곰히 생각하다가 ai에게 최종 답변을 받았고 결론은 이러 했다.

미리보기 url로 사용하기 위해 URL.createObjectURL(file) 을 생성해서 브라우저 메모리에 저장을 한다. - Line 31

사용이 끝나면 꼭 제거를 해줘야 한다는 것. 그렇지 않으면 계속 메모리 상에 쌓이게 된다.

그래서 뒤에 clearSelectedImages를 호출하게 되는데 여기서의 useEffect의 의존성이 [] 빈배열이기 때문에 처음 렌더링 당시의 selectedImages만을 기억하게 된다는 것.

즉, 처음 렌더링을 하고 이미지를 추가한 후 컴포넌트가 종료가 되면 최신값을 참조하지 못하는 클로저 문제가 발생 할 수 있다는 점을 깨달았다.

validation에서 닉네임 유효성 검사에 react에 최대 10자 이상까지 입력할 수 있다는 검사를 넣었는데,

백엔드에서는 비밀번호가 NotBlank만 Valdiation 검사하고 maxSize는 검사하지 않는다는 것을 우연찮게 알게 되었다. 프론트를 우회한 접근을 차단하기 위해서 백엔드에도 size의 최대를 정해주었고, 뭔가 혼자 프론트와 백엔드를 하려다 보니 까먹고 놓치는 부분이 많은거 같다는 생각이 들었다..

3

수정하시겠습니까? 삭제하시겠습니까? 같은 모달은 전체적인 큰 화면에 작은 팝업 화면을 띄우는거라,

모달을 state로 관리하면서 component 로 관리하고자 하는 생각이 들었는데 구현 피드백을 AI에게서 받았다.

Ai가 제시한 방식은 state - 모달이 열려있는지에 대한 데이터, component - 모달 그 자체

props - state와 이벤트 함수를 모달에 전달.

즉, 부모인 useUserEdit이 모달의 isOpen을 state값으로 가지고 그 props로 component의 모달을 불러와 page와 연결하는 방식을 추천했다.

모달 내부에서 const [isOpen, setIsOpen] = useState(false)로 내부 컴포넌트로 관리하고자 했는데,

부모인 userEditPage가 상태를 알고 ConfirmModal 은 props로 받는 제어 컴포넌트가 좋지 않겠냐고 해서 역할 분리와 맥락상 맞는 말인것 같아 반영 했다.

4

abortController - posts 게시글을 불러올때, 응답 전에 다른 페이지로 이동하면 기존의 컴포넌트를 제거하는 것으로,

post id 1을 조회하자마자 post id 2를 조회했는데 post id 1 게시글 응답이 느려서, 현재 url은 post id 2인데 post id 1 화면이 나오는 문제점, race condition이 일어날 수 있음을 알았다. 다만, abortController는 사용자가 브라우저 응답을 기다리는것을 막는 것이지 이미 시작된 작업까지 반드시 취소하는 것은 아니라는 것을 유의해야 한다고 배웠다.

5

useLike 기능에서 굳이 usePosts에서 like를 state로 관리하는 것 보다, useLike에서 좋아요 요청 할 때마다 setLikeCount 나 setLike를 바꾸게 하여 LikeButton을 재렌더링 하는 방식을 생각해보았다.

결론부터 말하자면 부모의 post, (백엔드 dto인 PostResponse에서 json으로 값을 받고 data를 꺼내온 liked가 setPosts에 저장이 되기 때문에, post.liked가 PostCard로, 다시 likeButton으로, 다시 useLike로 전달 되는 구조가, useLike에서 state로 liked로 다시 관리하게 되면 정합성이 깨질 수 있기 때문이었다. 애초에 useLike에는 state로 liked가 안들어가고 부모가 관리하는게 가장 이상적이라는 걸 알게 되었다. Ai에게서 이걸 단일 진실 공급원, 즉 하나의 데이터를 한 곳에서만 관리하는 구조라고 한다는것도 배우게 되었다.

6

페이지 상세구현에서 댓글 수를 보여주는 과정에,

ai는 comments를 어차피 List로 가져오기 때문에 length 로 댓글 수를 가져왔다.

내 postResponse에는 백엔드에서 구현한 select*을 해서 가져온 commentCount가 있는데 사용하지 않는 이유에 대해서 알아보았다. 이유는 단순하게, 내 백엔드 api에서는 commentCount를 댓글 수정, 삭제가 반영되지 않기 때문이었다. 댓글 api는 새로운 commentResponse를 가져오기 때문에 즉시 반영과 렌더링이 되지 않은 이유 였다. 추가적인 state 없이 length만 가져오면 돼서 간편해 보였다. 만약 내 postResponse에서의 commentCount를 가져와서 굳이 쓰겠다고 하면 updateCommentCount function을 추가해서, 추가, 삭제 될 때마다 값을 바꿔 주는 방법이 있다. 그렇게 되면 hasLoaded state를 사용하지 않을 수 있고, 나중에 페이지네이션 적용에도 전체적 commentCount를 가져오기 때문에 데이터 정합성에도 좋다는 것이다.

length 는 단순하고 편리하지만 댓글 페이지 네이션을 적용하면 당장 보이는 comment의 갯수만 보여주는 치명적 단점이 있기에, 결국 두번째 방법으로 가기로 했다.

사실은 이 모든게 내 api에서 postResponse는 commentCount를 반환하는데 commentResponse는 Count를 반환하지 않기 때문에 생긴 일들 인 것 같다..

사실 프론트에서 삭제하면 -1, 추가하면 +1 해서 계산하는 방법도 나쁘진 않아보이는데

케빈이라면 별도로 List와 commentCount를 돌려주는 dto를 만드시나요?

7

useComments에서 commentText를 state 관리하는데,

사용자가 입력하는 textArea쪽은 useRef로 관리하는게 낫지 않나? 굳이 state로 관리해서 매번 재렌더링은 성능에 안좋지 않나? 라고 생각했다.

사용자가 키보드 입력 → textarea onChange 실행 → changeCommentText(“안녕”) → setCommentText(“안녕”) → commentText state 변경 → PostPage 다시 렌더링 → CommentForm에 value=“안녕” 전달 → textarea에 “안녕” 출력

현재 상태 변화. 순서만 보면 매번 입력할 때마다 성능 저하가 있을 것 같지만 아니었다.

애초에 리액트 vdom기능도 있고 글자 하나가 이미지를 바꾸는 것도, post전체를 리렌더링 하는것도 아니고 입력필드가 여러개 있는 것도 아니므로 별 다른 성능 저하가 없다고 AI는 판단하는 것 같았다.

다만 state로 관리하면 댓글이 비어있을때의 오류나, 버튼의 보이는 상황을 직접 인지 할 수 있기 때문에 textarea를 state로 관리하는 것이 흔한 일이라고도 했다. 그래서 결국에는 state값을 유지하되,

렌더링 범위를 줄이기 위해서 useComments 내부의 state관리를 CommentForm내부로 바꿔서 postPage의 게시글 본문과 댓글 목록은 영향을 덜 받게끔 수정했습니다.

이번 마이그레이션을 통해 Vanilla JavaScript와 React의 차이를 이해할 수 있었습니다. 기존에는 querySelector로 HTML 요소를 찾고 DOM을 직접 변경했지만, React에서는 props와 state를 중심으로 화면을 관리하며 상태가 변경되면 UI가 자동으로 다시 렌더링됩니다. 또한 화면은 컴포넌트로, 공통 기능과 상태 로직은 Custom Hook으로 분리하면서 책임이 명확해졌고 코드의 재사용성과 유지보수성도 향상 되었음을 체감했습니다.

9주차 과제 피드백 수정

writePost 제출은 createPostRequest로 글을 먼저 만들고 saveAttachments로 이미지를 올리는데, 업로드가 중간에 실패하면 catch에서 alert만 하고 폼과 selectedImages를 그대로 둔 채 버튼을 다시 켭니다. 이 상태에서 다시 제출하면 작성 모드에서는 createPostRequest가 또 실행돼 같은 글이 하나 더 생기고, 수정 모드에서는 이미 올라간 이미지가 다시 업로드돼 중복됩니다.

WritePost는 rollback 사용해서 attachment에 오류가 있으면 게시글 작성이 rollback되게 하였습니다.

edit 수정 단계에서는 CurrentAttachment와 selectedImages를 분리하여 완료된 것은 current, 도중에 오류가 생겨 남겨지는 것은 selectedImages에 남겨 다시 재 실행되어도 중복 제출이 안되게 막았습니다. + 제출 중 상태가 바뀌지 않도록 제출 중 이미지 제거 버튼을 비활성화 헸습니다.
