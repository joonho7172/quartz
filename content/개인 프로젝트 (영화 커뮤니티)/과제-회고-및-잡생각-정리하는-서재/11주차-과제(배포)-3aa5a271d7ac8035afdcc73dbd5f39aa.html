11주차 과제(배포)

매번 인스턴스가 종료되고 실행 될 때 주소가 바뀌는 것을 막기 위해 elastic ip를 할당 받아 연결.

거의 매달 3~ 4달러 - 과제가 끝나면 주소 연결해제하고 릴리즈 하기.*

현재 사용중인 내 ip에서만 22번 포트 ssh 접근을 허용해서 안전하게 .pem키로 접속 시도.

EC2에서 nginx 설치와,

EC2에 개발한 java의 버전과 react 파일(vite 8)을 빌드하기 위해 필요한 node를 headless하게 설치한다.

(이래서 docker를 쓰나보다..)

be와 fe를 git에 올리고 EC2에서 pull을 땡기는 방식으로 진행했다.

물리 메모리(RAM)가 부족할 때를 대비해서 SWAP이라고 하드웨어의 내부 공간을 메모리 처럼 사용하는 것을 추가했는데 지금은 lunix 단일 인스턴스 ec2 기반이라 해놨지만, 쿠버네티스에서는 인스턴스의 활용을 100%에 가깝게 하기 위해서 swap 설정을 꺼둔다고 한다.

그 후 백엔드 파일을 jar 파일로 build.

똑같이 react front도 빌드.

실행이 잘 되는 모습.

RDS 연동을 위해 RDS도 mySql 기반으로 만들었다.

인바운드 규칙도 추가해서 EC2에서 MySql에 접근할 수 있게 한다

S3 버킷도 생성, 기존에는 nginx → spring을 통해 EC2의 폴더 내부에서 이미지를 가져왔다면, 인스턴스가 늘어나거나(서버 증가), 인스턴스가 삭제 되면 이미지 값또한 사라질 수 있다.. 이미지 백업과 종속이 EC2에 종속되지 않게 하기 위해서 S3이라는 파일 저장소를 사용한다.

iam 역할을 통해서 EC2와 s3의 권한을 얻어낸 후,

정책 설정에서 GetObject 정도는 열어줍니다. (어차피 민감한 개인정보 게시글 이미지나 프로필 사진은 없을거기에)

기존에 백엔드에서 EC2로 저장하던걸 s3로 바꾸기 위해 yaml 파일에 추가합니다.

그리고 기존에 be의 fileService가 /images/uuid.webp로 처리하던 이미지 경로를 https://s3/images/uuid/webp으로 요청을 바꾸게 코드를 수정합니다. (ai 활용)

그러면 앞으로의 요청은 s3의 images에 들어가게 되는 것을 알 수 있다.

# syntax=docker/dockerfile:1
FROMeclipse-temurin:26-jdk ASbuild //1단계
WORKDIR /app

COPYgradlew .
COPYgradle ./gradle
COPYbuild.gradle settings.gradle ./RUNchmod+x gradlew
RUN./gradlewdependencies --no-daemon

COPYsrc ./src

RUN./gradlewclean bootJar --no-daemon  

FROMeclipse-temurin:26-jre ASruntimeWORKDIR /app //2단계

RUNgroupadd--system spring &&useradd--system --gid spring spring

COPY --from=build--chown=spring:spring /app/build/libs/*.jar app.jar

USERspring:spring

EXPOSE8080ENTRYPOINT["java", "-jar", "app.jar"]

백엔드 도커 파일을 만든다.

dockerfile이란? 어플리케이션 하나를 어떤 이미지로 만들지 라는 정의, 설계도, 이게 있어야 개발환경과 배포환경이 일치해짐.

1단계: JDK 26으로 Gradle 빌드 2단계: JRE 26에서 만들어진 JAR만 실행으로 구성되었다.

마찬가지로 프론트엔드 도커 파일도 생성.

1단계: Node.js로 npm ci, npm run build 2단계: Nginx에 dist 결과물만 복사

최종적으로 backend가 jar파일로 정상 실행되고, 8080포트 / tcp로 compose내부에서 작동,

frontend는 → 80으로 EC2 80번 포트로 잘 이동하고 있다고 나와있다.

Docker 내부의 nginx가 응답하는걸 볼 수 있다 (200 OK)

nginx가 백엔드 컨테이너를 찾아서 요청을 보냈다는 것을 알 수 있음. (401 응답)

환경 변수

기본적으로 RDS 접속 주소와 사용자 이름, 비밀번호는 환경변수로 포함하고, S3 버킷의 경로와 리전도 환경 변수에 포함하였습니다. s3의 액세스 키와 비밀 키는 EC2의 IAM역할을 사용했기 때문에 환경변수에 포함하지 않았습니다. 공개된 배포는 아니기에 aplication.yaml의 JWT 토큰키 또한 환경 변수로 포함하지 않았습니다.

배포 파이프 라인은 어떻게 하셨나요? 에 대한 백지 답변) (CI/CD 제외)

먼저 백엔드는 spring boot로 구성했고 , 프론트는 react와 vite로 구성하여, 각각 별도의 git 저장소에 저장했습니다. 배포 환경은 ubuntu 기반의 EC2 한대와, 데이터베이스는 MySqL기반의 RDS, 이미지, 파일 저장은 S3를 사용했습니다. S3는 엑세스 키나 비밀키를 따로 환경변수로 저장하는게 아닌, EC2의 IAM을 사용해서 접근하도록 했습니다. 처음에는 EC2에 Git pull을 통해 소스 코드를 불러오고, java와 node.js 그리고 nginx를 직접 설치해서 제공했습니다. react의 정적파일은 nginx가 제공하고, api요청은 nginx가 8080포트의 spring boot로 전달하도록 구성했습니다. 이후, 배포환경과 개발환경의 통일성과 배포 편의성을 위해 Docker compose구조로 전환했습니다. 각각을 멀티 스테이지 구조로, 빌드 도구가 이미지에 포함되지 않도록 하여 운영 환경을 단순화 했습니다.

추가 하거나 변경 해야 할 피드백 주시면 좋겠습니다. 다음주 Ci/CD 과제까지 다 하고 백지에서 총 정리 해보려고 합니다!
