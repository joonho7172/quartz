1. API를 리소스 중심으로 설계한다는 것은 어떤 의미인가요?
	1. API를 리소스 중심으로 설계 한다는 것은, 사용자의 행위보다 API의 URI와 HTTP 메소드 post, delete, put, get 등을 자원을 기반으로 작성한다는 것입니다.

2. 주문 취소나 게시글 발행처럼 업무상의 동작을 표현하는 API는 어떻게 설계할 수 있나요?
	1. 업무상의 동작들은 억지로 CRUD로 강제하기보다는, 상태 변경이나, 하위 리소스 생성 등으로 설계 할 수 있습니다. 예를 들면, 주문 취소는 단순 상태 변경으로 patch/ status = canceled, 등을 사용 할 수 있습니다. 

3. 요청 데이터를 path variable, query parameter, request body에 담는 것은 각각 어떤 차이가 있나요? 특정 게시글의 식별자, 목록의 검색 조건, 새 게시글의 내용을 어디에 담을지 이유와 함께 설명해주세요.
	1. path variable은 식별을 위해서, 이 리소스가 없으면 api 요청 자체가 아예 유효하지 않을때 사용하고, query parameter는 특정 리소스들을 어떠한 조건이나 정렬 등 필터링을 위해 사용합니다, request body는 클라이언트가 서버에게 값을 담아서 주는 것으로 구조화된 형식으로, URL에 내용이 노출 되지 않으며 사용됩니다.

4. HTTP 상태 코드 외에 응답 본문으로 오류 정보를 전달하는 이유는 무엇인가요? 클라이언트가 오류 종류를 구분하고 사용자에게 적절히 안내하려면 어떤 정보를 제공해야 하나요?
	1. 상태 코드 만으로는 오류의 내용을 다 표현하고 알아내기가 어렵기 때문이다. 사용자가 어떠한 오류로 잘못되었는지, 사용자 친화적으로 응답코드가 구성이 되어 있기 때문에, 클라이언트는 오류 코드와 함께, 어떤 field가 잘못되었는지, 클라이언트의 잘못인지, 서버의 상태 오류인지, 오류 메시지와 함께, 내용을 담아야 한다.

5. Offset 기반 페이지네이션과 Cursor 기반 페이지네이션은 어떻게 다른가요? 조회 도중 데이터가 추가되거나 삭제되는 상황과 특정 페이지로 바로 이동해야 하는 상황에서 각각 어떤 장단점이 있나요?
	1. Offset 기반 페이지네이션은 전체 목록을 한번 불러온 다음에, page로 나누고, 사용자에게 보여주는 반면, Cursor 기반은 다음에 가져올 값이 있으면 hasNext 값과 다음 값을 가르키는 nextCursor로 구성이 되어 있습니다. 조회 도중에 데이터가 추가 되거나 삭제되면 offset은 이미 잘라놓은 page가 있기 때문에, 데이터가 깨지거나 정합성이 맞지 않을 수 있습니다. cursor 방식은 실시간으로 다음 값을 가져오기 때문에 중간에 데이터가 삭제되거나 추가되어도 데이터가 유지됩니다. 이에 따라 offset은 특정 페이지로 바로 이동 할 수있지만, cursor 방식은 특정 페이지로 바로 이동이 불가합니다. 

6. 클라이언트에서 요청이 타임아웃되면 서버에서도 처리가 실패했다고 볼 수 있나요? 서버는 주문을 저장했지만 응답이 전달되지 않은 상황에서 클라이언트는 어떤 문제를 마주하게 되나요?
	1. 요청이 타임 아웃되는 과정에는 여러 원인이 있기 때문에 서버에서도 처리가 실패했다고 볼 수 없습니다. 만약 서버는 주문을 저장했지만 클라이언트가 응답을 전달하지 않으면, 사용자는 재시도를 할 것이고, 이러할 경우 멱등성을 보장 받지 못하는 시도라면, 요청이 중복적으로 들어가 문제가 될 수 있습니다.

7. 요청이 실패할 때 즉시 반복해서 재시도하면 어떤 문제가 발생할 수 있나요? 재시도 횟수 제한, 지수 백오프, Jitter은 각각 어떤 문제를 줄이기 위한 방법인가요?
	1. 요청이 실패할 때마다 즉시 반복해서 재시도하면, 재시도 폭풍이 올 수 있습니다. 서버의 부하로 요청이 실패되고, 다시 엄청난 양의 재시도가 오면 더 많은 타임 아웃이 생길 수 있습니다. 이를 해결하기 위해, 재시도 횟수를 제한 함으로써, 무한 재시도와 불필요한 서버 부하를 줄일고 있고, 지수 백오프를 통해서 일시적인 서버 장애를 회복할 시간을 벌어줄 수 있습니다, 무작위 대기시간인 jitter를 통해서 한꺼번에 재시도가 몰리지 않도록 할 수 있습니다.

8. 주문 버튼을 비활성화하는 것만으로 중복 주문을 막을 수 있나요? 멱등성 키를 사용한다면 같은 주문의 재시도와 사용자가 새로 시도한 주문을 어떻게 구분해야 하나요?
	1. 주문 버튼을 비활성화 하는것만으로는 중복 주문을 막을 수 없습니다. 하나의 주문 시도에 대해서 멱등성 키를 발급하고, 클라이언트를 주문 요청이 들어오면 발급 받은 멱등성 키를 버리지 않고 저장합니다. 만약 주문이 성공되지 않고 타임아웃이나 재시도가 들어오면 저장한 멱등성 키를 가지고 재사용 합니다. 즉, 일반적인 재시도에는 기존 키를 사용하고 사용자가 명시적으로 새 주문을 시작했을때만 새로운 멱등성 키를 발급 합니다.
