## **1일차 - 캐시**

1. 캐시는 어떤 비용을 줄이기 위해 사용하나요? 같은 데이터를 반복해서 조회하는 상황을 예로 들어 설명해주세요. 캐시를 추가하면 오히려 관리 비용이나 문제가 커질 수 있는 경우는 무엇인가요?
	1. 캐시는 불필요한 DB조회나, api 비용을 줄이기 위해서 사용합니다. 같은 데이터를 찾기 위해, DB의 읽기 작업이나, api요청을 막을 수 있습니다.
	2. 캐시를 무작정 추가하면, 저장소 차거나, 메모리 문제가 있을 수 있습니다.

2. 데이터를 브라우저, CDN, 애플리케이션 서버에 각각 캐시하면 어떤 차이가 있나요? 각 위치에서 어떤 작업과 네트워크 요청을 줄일 수 있으며, 캐시된 데이터를 누가 공유하게 되는지 설명해주세요.
	1. 데이터를 브라우저에 캐시를 하게 된다면 캐시된 파일이나 응답을 기기에서 바로 사용해서 서버로 가는 요청을 생략 할 수 있고 브라우저의 캐시는 브라우저 프로필 안에서 공유됩니다.
	2. CDN에서의 캐시에서도 마찬가지로 CDN 엣지에서 값을 찾아 돌려주기 때문에 원본 서버로의 요청을 생략 할 수 있습니다. 브라우저 캐시와 달리, 같은 캐시 키를 사용하는 사용자 끼리 데이터를 공유합니다.
	3. 애플리케이션 서버에 캐시를 저장하면, 요청은 서버까지 오나, 외부 API나 DB 조회, 반복 계산등을 건너뜁니다. 메모리 캐시는 그 서버에만 데이터를 공유하나, 분산 캐리는 다른 인스턴스 까지 데이터를 공유합니다.

3. 캐시 키는 어떤 역할을 하나요? 같은 상품 목록 API라도 검색어, 정렬 기준, 페이지 번호에 따라 결과가 달라진다면 캐시 키를 어떻게 구성해야 하나요? 결과에 영향을 주는 조건을 키에서 빠뜨리면 어떤 문제가 생기나요?
	1. 캐시 키는 요청의 정보를 어떤 캐시 항목으로 찾을지 정하는 식별자 역할을 합니다. 같은 api라도 특정 조건에 의해 결과가 달라진다면, 그 조건까지도 캐시 키에 넣어야 합니다. 만약에 결과에 영향을 주는 조건을 키에서 빠뜨리면, 같은 캐시 키지만 서로 다른 응답이 내려갈 수 있습니다.

4. 캐시의 TTL은 무엇이며, 짧게 설정할 때와 길게 설정할 때 어떤 장단점이 있나요? 상품 설명, 실시간 재고, 인기 게시글 목록에 같은 TTL을 적용해도 되는지 이유와 함께 설명해주세요.
	1. TTL은 캐시의 생명 주기입니다. TTL을 길게 잡으면 그만큼 캐시 될 가능성이 높아지지만, 그만큼 메모리를 많이 쓰고, 짧게 설정하면, 캐시 될 가능성이 적어지지만 그만큼 메모리를 적게 씁니다. 단시간에 인기가 있는 인기 게시글 목록들은 TTL을 짧게 가져가고, 상품 설명 등 바뀌지 않는 것은 길게, 실시간 재고는 매번 바뀌기 때문에 캐시를 사용하지 않습니다. 

5. HTTP 응답의 Cache-Control에서 max-age, no-cache, no-store는 각각 어떤 의미인가요? 데이터를 저장하는 것과 저장한 데이터를 다시 사용하는 것을 구분해 설명해주세요. -  정리 필요
	1. max_age는 캐시된 데이터의 시간으로, 다른 캐싱 규칙이 적용되면 저장 할 수 있습니다. 시간 내에 유효한 캐시면 재사용하고 그렇지 않으면, 재검증하거나 새 응답을 받아야 합니다.
	2. no-cache 저장 할 수 있는 캐시로, 저장된 응답을 재사용하기 전에 서버로 부터 유효한지 확인 받습니다.
	3. no-store는 저장할 수 없는 캐시로 저장하지도 않고 재사용하지도 않습니다.

6. ETag와 조건부 요청은 어떤 문제를 해결하나요? 서버가 304 Not Modified를 반환하면 클라이언트는 실제 데이터를 어디에서 가져오나요? 서버에 요청하지 않고 캐시를 사용하는 경우와는 어떤 차이가 있나요? 
	1. Etag 와 조건부 요청은 오래된 캐시를 사용하는 불상사를 막을 수 있습니다. 최신 태그와 조건부 요청을 통해, 새 본문을 가져오지 않아도 되면 서버는 304 Not Modified를 반환하고, 클라이언트는 자신이 저장해둔 본문을 재사용합니다. 서버에 요청하지 않고 캐시를 사용하면, Etag를 확인하는 절차가 생략될 수는 있겠지만, 구식 캐시를 사용 할 수도 있습니다.

7. 게시글 수정에 성공했는데 목록이나 상세 화면에는 이전 내용이 계속 표시됩니다. 어떤 위치의 캐시를 확인해야 하며, 데이터를 변경한 뒤 캐시를 삭제하는 방식과 새 값으로 갱신하는 방식은 어떤 차이가 있나요?
	1. 수정 후 목록이나 화면을 가져오는 GET 요청의 응답 본문을 봐야합니다. 데이터를 변경하고 삭제하는 방식에는 DB에 관련 캐시 키를 지우고, 새로 요청하는 값에 캐시를 다시 채우는 방식입니다. 캐시키를 새로 갱신하는 방식에는 수정 후, DB의 캐시키를 갱신 하는 방식입니다. 갱신만 하는 경우 연관된 목록이나, 정렬 등의 캐시 키에는 반영이 안되어 있을 수 있습니다.

8. 캐시가 만료된 직후 같은 데이터를 요청하는 작업이 한꺼번에 몰리면 어떤 문제가 생길 수 있나요? 동일한 데이터 조회를 하나로 합치거나, 이전 데이터를 잠시 제공하면서 갱신하는 방식에는 어떤 장단점이 있나요?
	1. 캐시가 만료된 직후 데이터가 요청하는 작업이 몰리면, 요청마다 api나 DB를 조회하는 비용이 커져 부하가 발생 할 수 있습니다.
	2. 동일한 데이터 조회를 하나로 합치면, 초반 첫 요청에는 API를 수행해 원본을 조회하고, 나머지 요청은 기다렸다가 동일한 캐시 키로 설정된 값을 받습니다. 단점으로는 첫 요청을 기다려야 한다는 것
	3. 이전 데이터를 잠시 제공하면서 갱신하면, 설정한 시간동안 오래된 캐시 데이터를 보여주고, 캐시가 갱신되면 그때 다시 캐시 데이터를 보여 줍니다. 단점으로는 설정한 시간 동안 오래된 캐시 데이터를 보고 있어야 한다는 점.
