1. 테스트 코드를 작성하면 코드 변경과 리팩터링에 어떤 도움이 되나요? 이미 발견해서 수정한 버그에 대해 테스트를 추가하는 이유는 무엇인가요?
	1. 테스트 코드를 작성하면 코드 변경에 있어서 최소한의 가이드 라인이 제공된다. 코드 변경과 리팩터링 후에도 기존 동작이 유지되는지 쉽게 확인 할 수 있다.
	2. 이미 발견해서 수정한 버그에 테스트를 추가하면, 다음 번에 코드가 수정되어 같은 문제가 발생 하더라도 테스트 코드에서 이를 알려줍니다.

2. 단위 테스트, 통합 테스트, E2E 테스트는 검증하는 범위와 실패했을 때 얻는 정보가 어떻게 다른가요? 주문 기능을 예로 들어 각 테스트에서 무엇을 확인할지 설명해주세요.
	1. 단위 테스트에서는 메소드 로직의 동작 방식을 검증해서 계산이나 규칙 같은 특정 로직의 버그 가능성을, 통합 테스트에서는 전체적인 모듈의 구성에 대한 동작을 검증해, 실패시 구성 요소 사이의 연결이나 데이터 변환, 트랜잭션 처리 등을 검증하고, E2E 테스트에는 전체 시나리오의 동작을 검증합니다. 이에 따라 전체적인 흐름 중에 어디가 문제인지는 검증이 가능하나, 추가 조사가 필요 할 수 있습니다.
	2. 주문 기능에서는 주문 총액이나, 수량등의 확인은 단위 테스트, 주문이 성공적으로 처리되었을 때 재고가 차감이 되는지, 장바구니에 담기는지는 통합 테스트, E2E 테스트는 사용자가 장바구니에 물품을 담고, 결제를 하며, 결제 내역과 영수증이 담기는지 등등을 확인합니다.

3. 정상적인 입력에서 성공하는 테스트만으로 충분한가요? “구매 금액이 5만 원 이상이면 배송비가 무료”라는 규칙을 검증한다면 어떤 입력값과 경계 조건을 선택하겠나요?
	1. 실패하는 테스트를 통해서 예외 값도 처리를 해야한다.
	2. 저라면 구매 금액이 음수 일때, 5만원 미만일 때, 5만원 일때, 그리고 5만원 초과일때를 잡겠습니다.

4. 테스트 대상 코드를 실행했을 때 예외가 발생하지 않았다는 사실만으로 기능이 올바르다고 판단할 수 있나요? 게시글 작성 기능을 예로 들어, 테스트에서 어떤 결과나 상태 변화를 검증해야 하는지 설명해주세요.
	1. 그렇지 않습니다. 테스트 대상 코드가 완벽하다는 가정이 없기 때문에 예외가 발생하지 않았다는 사실만으로 올바르다고 할 수 없습니다.
	2. 게시글 작성 기능에서 작성한 게시글이 올바른 게시글 ID를 반환하는지, 올바른 사용자와 연결이 되는지, 또는 유효하지 않은 게시글을 작성해 테스트에서 실패 결과를 주었을때, 그 값이 저장되지 않은 상태인지 검증해야 합니다.

5. 테스트에서 실제 API나 데이터베이스 대신 미리 정한 응답을 반환하는 대역을 사용하는 이유는 무엇인가요? 모든 외부 의존성을 대역으로 바꾸면 어떤 문제를 발견하지 못할 수 있나요?
	1. 테스트에서 미리 정한 응답을 반환하는 대역을 사용하는 이유에는, 네트워크 오류나, 외부 시스템의 상태에 구애받지 않고 테스트 대상 로직을 빠르게 검증 할 수 있기 때문입니다.
	2. 이에 따라 모든 외부 의존성을 대역으로 바꾸면, 실제 연결이 맞는지 검증하지 못하는 문제점이 생깁니다. 대역은 통과해도 실제 Db에 저장이 되거나, api응답이 정상적인지는 검증 할 수 없습니다.

6. 사용자가 볼 수 있는 동작은 그대로인데 내부 함수 이름이나 호출 순서를 바꾸자 테스트가 실패했습니다. 이 테스트는 무엇에 의존하고 있을 가능성이 있나요? 내부 구현과 외부에서 관찰할 수 있는 동작 중 무엇을 기준으로 검증할지 설명해주세요.
	1. 특정 내부 함수가 호출 되었는지, 함수들이 정해진 호출 순서를 지켰는지 확인하는 내부 구현 의존성에 묶여있을 가능성이 있습니다. 보통 테스트 케이스는 외부에서 관찰 할 수 있는 동작으로 검증합니다.

7. 같은 코드를 테스트하는데 어떤 때는 성공하고 어떤 때는 실패하는 이유는 무엇일까요? 현재 시각, 난수, 네트워크 응답, 다른 테스트가 남긴 데이터가 결과에 영향을 준다면 어떻게 개선할 수 있나요?
	1. 외부 의존성에 연결이 되어있을 가능성이 높습니다. 날짜나 시간, 네트워크 상태처럼 테스트 할 때마다의 변수가 생기고 바뀌게 되는 이유로 테스트의 일관성이 없어질 수 있습니다.
	2. 공통 원칙을 명시적으로 강제해서 테스트를 할 때 마다의 환경을 똑같이 만듭니다.

8. 테스트 커버리지가 100%라면 버그가 없다고 볼 수 있나요? 코드가 실행되었다는 사실과 올바른 결과를 검증했다는 사실은 어떻게 다른가요? 테스트를 추가할 시간이 제한되어 있다면 무엇을 우선하겠나요?
	1. 커버리지는 측정 대상인 코드가 테스트 도중 한 번 이상 실행되었다는 뜻일 뿐. 버그가 없는 완전한 코드를 뜻하는건 아닙니다.
	2. 코드가 실행되었다는 것은 경로를 지나갔다는 뜻이고, 올바른 결과를 검증 했다는 사실은 코드의 결과나 상태 변화가 기대값과 일치 했다는 것을 의미합니다.
	3. 테스트를 추가 할 시간이 제한 되어 있다면, 실패 가능성이 크거나 실패 영향이 큰 동작을 우선시 하여 테스트 합니다.
