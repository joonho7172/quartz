## 1일차 - 네트워크 기본 개념

1. HTTP, TCP, IP는 각각 어떤 역할을 하나요?
    1. TCP 기반의 웹 통신을 기준으로 이 프로토콜들이 어떻게 함께 사용되는지 설명해주세요. 네트워크 통신의 역할을 여러 계층으로 나누는 이유는 무엇인가요?

	HTTP는 서버간의 메소드, 행위를 주고받는 프로토콜로 요청과 응답의 형식을 정합니다. TCP 웹 통신은 데이터를 순차적으로, 누락 없이 전달하는 연결을 제공합니다. IP는 출발지와 목적지를 주소로 패킷이 네트워크를 지나가게 합니다. 
	네트워크 통신의 역할을 여러 계층으로 나누어, 서로의 내
	
	부 구현에 대해 의존성을 줄이고, 문제가 발생 할 시에 원인을 명확히 지정하기 쉽게 하기 위해서 입니다.

2. IP 주소와 포트 번호의 역할은 어떻게 다른가요?
    1. 하나의 서버에서 여러 네트워크 프로그램이 실행될 때 요청을 받을 프로그램을 어떻게 구분하나요? `https://example.com`처럼 URL에 포트가 표시되지 않은 경우에는 어떤 포트를 사용하나요?

	IP주소는 어떤 장치로 보낼지에 대한 주소이고, 포트 번호는 장치내에 어떤 통신 서비스로 전달할지를 가르킵니다.
	하나의 서버에서 요청을 받을 프로그램을 포트 번호(목적지, 출발지 포트 번호 등)에 따라서 구분하게 되는데, 예를 들면 웹서버는 TCP 443번, SSH 연결은 TCP 22번 등을 사용해 구분합니다.

	 URL에 포트가 표시되어 있지 않으면 기본 포트 번호, https -> 443, http -> 80 등으로 연결이 됩니다. 

4. DNS는 무엇이고, 웹사이트에 접속할 때 왜 필요한가요?
    1. DNS 조회 결과를 캐시하면 어떤 이점이 있나요? 서버의 IP 주소가 변경되었지만 이전 조회 결과가 캐시에 남아 있다면 어떤 문제가 생길 수 있는지 설명해주세요.

	DNS는 도메인 네임 시스템으로, 웹사이트에 접속 할 때, 도메인의 이름을 가지고, ip주소로 바로 연결되게 해주는 것에서 이점이 있습니다.
	DNS 조회 결과를 캐시하면, 항상 클라이언트가 도메인 이름을 IP로 변환하는 것을 수행하지 않아도 됩니다. 서버의 ip 주소가 변경되었지만 TTL이 반영되지 않아 이전 결과가 캐시에 남아있으면, 사용자는 예전 서비스를 조회할 수 있고, 의도하지 않은 ip로 이동 할 수 있습니다.


6. TCP와 UDP는 어떻게 다른가요?
    1. 연결 설정, 데이터의 전달 여부와 순서 보장 측면에서 비교하고, 각각이 적합한 서비스나 상황을 예로 들어 설명해주세요

	TCP는 데이터를 보내기 전에 서버와 클라이언트의 연결 상태를 확인하고, 응답값을 주고 받은 다음 데이터를 전송합니다. 따라서 데이터의 전달 여부를 확인 할 수 있고, 순서도 보장되며 재처리가 가능합니다. 웹의 http 통신이나, 파일 전송 등 데이터 누락이 치명적인 서비스에서 주로 쓰입니다.
	UDP는 데이터를 보내기 전에 연결 상태나, 응답 값을 확인 받지 않습니다. 그러므로 데이터의 전달 여부나, 순서 측면에서 보장되지 않습니다. 게임 내 실시간 음성, 실시간 채팅 등 빠른 응답을 기반으로 하는 서비스에서 적합합니다.

8. TCP의 3-way handshake는 무엇이며, 연결을 설정할 때 어떤 메시지를 주고받나요?
    1. 이 과정을 통해 무엇을 확인하는지 설명해주세요. TCP 연결이 성립했다는 사실만으로 서버의 애플리케이션이 요청을 정상 처리할 수 있다고 판단해도 되나요?

	연결을 시작 할 때, TCP는 먼저, 클라이언트가 서버에게 연결 할 준비가 되었는지 1번, 서버가 클라이언트에게 준비가 되었다는 메시지 2번, 클라이언트가 서버가 준비되었다는 메시지를 받았다는 응답에 대해 3번.을 보냅니다.
	TCP 연결 가지고 요청을 정상 처리 할 수 있다고 판단 할 수 없는 이유는, 중간에 서버의 장애로 요청을 처리하지 못할 수도 있고, 서버가 많은 요청을 처리하느라 아직 해당 클라이언트의 요청을 처리 할 수 없는 경우의 수도 있기 때문입니다.

10. HTTP와 HTTPS는 어떻게 다른가요?
    1. HTTPS에서 TLS와 서버 인증서는 각각 어떤 역할을 하나요? 통신 내용을 암호화하는 것과 통신 상대가 올바른 서버인지 확인하는 것은 왜 모두 필요한지 설명해주세요.

	통신 내용을 암호화 하느냐, 안하느냐의 차이가 있습니다.
	HTTPS에서 TLS는 HTTP에서 통신 하는 내용을 암호화하는 역할을 합니다.
	서버 인증서는 통신 상대가 올바른 서버인지를 확인합니다. 이러한 이유로는, 중간에 변조를 방지하거나, 위조를 방지하기 위해서 TLS를 사용하고, 통신 서버가 올바른 서버인지 확인을 하지 않으면 가짜 서버가 중간에서 통신을 가로채고, 내용을 복호화해 읽거나, 바꿀 수 있습니다.

14. **[BE]** 서버가 `127.0.0.1`에서 요청을 받도록 설정된 경우와 `0.0.0.0`에서 받도록 설정된 경우는 어떻게 다른가요?
    1. 서버 내부에서는 API 호출이 되지만 다른 컴퓨터에서는 접속되지 않는다면 무엇을 확인하겠어요? 애플리케이션의 수신 주소 설정과 방화벽의 포트 허용 설정을 구분해서 설명해주세요.

	127.0.0.1은 서버 안에서의 접속만 허용하겠다는 뜻이고, 0.0.0.0은 모든 ipv4에서의 접근을 허용하겠다는 뜻입니다.
	서버 내부에서 API 호출이 되지만, 다른 컴퓨터에서 접속되지 않는다면 포트 번호를 먼저 확인 할 것 같습니다.
	127.0.0.1로 설정되어 서버 내부에서의 호출은 가능하지만, 외부 컴퓨터 ip주소로의 접근은 허용되지 않았을 가능성이 있습니다.
	또는, 어플리케이션의 수신 주소 설정을 허용하더라도, 방화벽에서 트래픽을 차단한다면 접근 할 수 없는 것이고, 방화벽에서 트래픽을 허용해 포트 접근을 허용하더라도, 앱이 127.0.0.1 ip를 통해 외부 인터페이스에서 접근 하는 것은 막을 수 있습니다.  

15. **[BE]** 리버스 프록시나 로드밸런서에서 HTTPS 연결을 처리한다는 것은 무슨 의미인가요?
    1. 클라이언트와 프록시 사이의 연결, 프록시와 애플리케이션 서버 사이의 연결을 나누어 설명해주세요. 클라이언트가 HTTPS로 접속했다면 프록시와 애플리케이션 서버 사이의 통신도 자동으로 암호화되나요?

	리버스 프록시나 로드밸런서에서 HTTPS 연결을 처리한다는 것은 클라이언트가 보내는 요청에서 TLS를 풀어 요청을 서버로 전달합니다.
	그리고 프록시에서 서버로 전달하는 데이터는 https 또는 http로 설정해서 전송합니다.
	따라서 클라이언트가 https로 접속 했다 하더라도 서버 사이의 통신이 자동으로 암호화 되는 것은 아닙니다.
	TLS paththrow와 같이 TLS를 해제하지 않고 어플리케이션 서버로 보내는 방법이 있긴 하나, 별도로 설정해야합니다.
