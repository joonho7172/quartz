## 2일차 - 웹 요청의 전달과 처리 흐름

1. 브라우저에 URL을 입력한 뒤 서버의 응답을 받기까지 어떤 과정이 진행되나요? o
    1. TCP 기반 HTTPS 통신을 기준으로 DNS 조회, 연결 설정, TLS 협상, HTTP 요청·응답의 흐름을 설명해주세요. 같은 사이트에 다시 접속할 때는 어떤 과정을 생략하거나 기존 결과를 재사용할 수 있나요?

	브라우저에 URL을 입력하면, 도메인 주소를 ip주소로 바꾸는 작업이 먼저 일어납니다. 이 과정에서 맨처음 local DNS에 먼저 접근 한 후, 저장되어 있는 캐시를 사용하나, 그렇지 않으면 DNS resolver에게 재귀 질문을 통해 ip를 얻습니다. 그렇게 얻은 ip에게 3-way handshake를 통해 TCP 연결을 하고, 서버와 TLS 구조를 협상합니다. (버전, 암호 방식, 키 교환 방식). 이렇게 협상이 끝나면 클라이언트와 서버는 HTTP 요청과 응답을 주고 받습니다. 만약 같은 사이트에 다시 접속 할 때 캐시가 TTL이 지나지 않아 브라우저 캐시로 남아있으면 DNS 단에서 바로 새 ip 조회를 하는 질문 단계가 없을 수 있고, 기존 TLS연결이나 TCP 연결이 살아있으면 별도로 협상이나 3way hand셰이크 없이 연결을 시도 할 수 있습니다. 

2. HTTP 요청마다 새로운 연결을 만드는 것과 기존 연결을 재사용하는 것은 어떤 차이가 있나요?
    1. 연결을 재사용하면 어떤 비용을 줄일 수 있나요? HTTP의 무상태성(Stateless)과 네트워크 연결을 유지하는 것이 서로 모순되는 개념인지 설명해주세요.

	새 연결을 만들 때마다 TCP 연결과정과, TLS 협상 과정이 계속 포함이 되어야 합니다. 이러한 과정에서 네트워크 왕복 비용이나, handshake를 위한 패킷 데이터 등등이 줄어 들 수 있습니다. HTTP의 무상태성은 서버가 클라이언트의 상태를 저장하지 않는것으로, 각 요청이 이전 요청에 기대지 않는다는 뜻입니다. TCP 연결을 재사용 한다고 해서, 독립적인 HTTP 요청을 주고 받을 수 있으므로 모순되지 않습니다. 

3. 프록시는 무엇이며, 포워드 프록시와 리버스 프록시는 어떻게 다른가요?  o
    1. 각각 클라이언트와 서버 중 어느 쪽을 대신하는지 설명하고, 두 종류의 프록시를 사용하는 목적을 각각 하나씩 들어주세요.

	프록시란 클라이언트와 서버 사이를 중개하는 대리객체를 뜻합니다. 포워드 프록시는 말 그대로 앞쪽 클라이언트의 요청을 대신해서 웹 서버에 요청합니다. 보통 외부 웹사이트 접속을 차단하거나, 기록하기 위해서 사용하고 리버스 프록시는, 서버를 대신에 클라이언트의 요청을 받습니다. 부하 분산이나, 적절한 서버로 이동시키기 위해 사용합니다.



4. 로드밸런서는 어떤 역할을 하나요? o
    1. 애플리케이션 서버를 여러 대 운영할 때 로드
    2. 밸런서가 필요한 이유는 무엇인가요? 요청을 여러 서버에 균등하게 나누면 실제 처리 부하도 항상 같아지는지 설명해주세요.

	로드 밸런서는 서버 한 쪽으로 몰리는 트래픽을 분산 시켜주는 역할을 합니다.
	애플리케이션 서버를 여러 대 운영 할 때 한쪽이 장애로 인해 트래픽을 처리하지 못하거나, 응답 지연에 빠지면 다른 서버로 트래픽을 이동하게 하는 정리가 필요하기 때문입니다.
	요청을 서버에 균등하게 나눈다고 부하가 항상 같아지지는 않습니다. 각 서버의 성능도 다를 수 있을 뿐 더러, 요청의 무게도 각각 다르기 때문에, 요청 연결 수를 균등하게 분배한다고 해도 부하를 같게 보장하진 못합니다.


5. CDN은 무엇이며, 어떤 문제를 해결하기 위해 사용하나요? o
    1. 모든 사용자가 원본 서버에서 파일을 내려받는 방식과 비교하면 어떤 이점이 있나요?
    2. 이미지나 JavaScript 파일을 제공하는 경우와 사용자별로 다른 API 응답을 제공하는 경우, CDN 활용 시 고려할 점은 어떻게 다른가요?

	CDN은 content delivery network의 약자로, 여러 콘텐츠를 엣지 서버에 복제해두고, 사용자에게 가까운 곳에서 전달하는 분산 네트워크 입니다. CDN 캐시에 콘텐츠가 있으면 원본 서버로 요청이 가지 않고 엣지 서버가 응답 하므로 서버의 부하를 줄일 수 있습니다.
	모든 사용자가 원본 서버에서 파일을 내려 받으면 I/O 거리가 줄어들기 때문에 응답 시간도 짧아지고, 트래픽이 서버로 가지 않기 때문에 부하도 줄일 수 있습니다.
	CDN 같은 엣지 서버에 이미지나 JavaScript 파일은 캐시를 저장해서 사용자들끼리 공통적으로 제공할 수 있는 반면, 사용자마다 다른 api응답을 제공하는 것은 공유 캐시에 섞이지 않도록 유의해야 합니다.



6. 웹 요청이 실패했을 때 문제가 발생한 구간을 어떻게 구분하겠어요? o
    1. DNS 조회 실패, 연결 실패, HTTP 오류 응답은 각각 어느 단계에서 발생한 문제인가요? 원인을 좁히기 위해 클라이언트와 서버에서 어떤 정보를 확인할지 설명해주세요.

	먼저 DNS 조회 실패는 도메인 주소를 ip로 주소로 변환하지 못한 상태입니다. 서버는 권한 DNS의 로그를 확인하고 클라이언트는 DNS resolver 주소와 조회 결과를 확인합니다. 연결 실패는 서버의 포트까지 TCP 연결이 실패 했다는 것으로, 클라이언트는 서버에서 curl 을 통해 서버가 요청을 받을 수 있는 상황인지를 확인하고, 서버는 loadbalancer 리스너나, 방화벽, 보안 그룹 등을 확인합니다.
	HTTP 오류 응답은 HTTP 처리 단계에서 발생 한 것으로, 클라이언트는 http 상태 코드와, 응답 헤더, 본문 등을 확인하고 서버는 어플리케이션 로그에서 요청 DI를 확인합니다.

9. **[BE]** 웹 서버와 애플리케이션 서버는 각각 어떤 역할을 하나요?
    1. 정적 파일 요청과 비즈니스 로직을 실행해야 하는 API 요청은 어떻게 처리할 수 있나요? 애플리케이션 서버가 직접 HTTP 요청을 받을 수 있는데도 앞에 Nginx 같은 웹 서버를 두는 이유를 설명해주세요.

	웹 서버는 HTTPS, HTTP 연결을 받고, 이미지나 JS 같은 정적 파일을 보내거나 요청을 다른 서버로 전달하는 역할을 합니다. 애플리케이션 서버는 API 요청을 받아, 인증 , 검증, 비즈니스 규칙을 검사하고 동적인 응답을 만듭니다. Nginx 같은 웹 서버를 둠으로써 TLS나 부하 분산을 맡기고 비즈니스 로직에만 집중 할 수 있습니다.


10. **[BE]** 로드밸런서의 헬스 체크는 왜 필요한가요?
    1. 서버 프로세스가 실행 중이라는 사실과 실제 요청을 처리할 수 있다는 것은 어떻게 다른가요?
    2. 특정 서버가 요청을 처리할 수 없게 되거나 다시 정상 상태로 돌아오면, 로드밸런서는 해당 서버로의 요청 전달을 어떻게 조정해야 하나요?


	서버 프로세스가 실행 중이어도, 대기열이 꽉 차있거나, 메모리에 여유 공간이 없으면 실제 요청을 처리 할 수 없는 상태 일 수 있습니다.
	따라서 서버 프로세스가 실제로 요청이 처리가 가능하다는 readiness와 프로세스 생존 여부 liveness를 구분합니다.
	특정 서버가 요청을 처리 할 수 없게 되면 서버로 가는 트래픽을 줄이고 요청 전달을 중단해야 합니다.
	그러다가 다시 정상 상태로 돌아오게 되면, 서버를 정상 풀로 복귀 시키되, 트래픽을 점진적으로 늘리며 워밍업 한 후 복귀 시켜야 합니다.
