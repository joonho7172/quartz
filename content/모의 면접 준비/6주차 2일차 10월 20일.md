1. **[BE]** 관계형 데이터베이스의 기본키, 외래키, `UNIQUE`, `NOT NULL` 제약조건은 각각 어떤 역할을 하나요?
    1. 회원과 주문 테이블을 예로 들어, 각 제약조건으로 방지할 수 있는 잘못된 데이터를 설명해주세요. 애플리케이션에서 값을 검사하더라도 DB에 제약조건을 두는 이유는 무엇인가요?

	기본키는 테이블의 칼럼을 식별할 수 있게 하는 식별자 역할을 하며, 외래키는 다른 테이블에서의 기본키로 , 한 테이블의 값이 다른 테이블의 행을 가르키도록 합니다. UNIQUE는 중복된 데이터를 막는 역할을 하고, NOT NULL을 NULL 값을 허용하지 않습니다.

	회원과 주문 테이블에서 회원 id와 주문 id가 기본키, 회원과 주문의 관계를 맺을 때, order.user_id 로, 존재하지 않는 회원의 주문이 저장되는 것을 막습니다. 한 회원의 동시 주문을 막기 위해 주문 상품 ID를 UNIQUE로 둡니다. 회원의 배송지가 입력되지 않으면 배송이 불가하기에 이러한 값들을 NOT NULL로 둡니다.

	어플리케이션에서 값을 검사하더라도 최종적으로 저장이 되는 곳은 DB이기 때문에, 다른 프로그램 값을 강제로 저장하려 하거나 잘못된 값이 저장되는 것을 막는 역할을 합니다. 



2. **[BE]** 데이터베이스 정규화는 무엇이며, 어떤 문제를 줄이기 위해 사용하나요?
    1. 여러 상품 행에 같은 카테고리의 이름과 설명을 반복 저장하면 어떤 변경 문제가 생길 수 있나요? 상품과 카테고리를 별도 테이블로 나누고 관계를 맺는 방식으로 설명해주세요.
    2. 테이블을 분리하면 조회 시 어떤 비용이 추가될 수 있나요? 정규화가 조회 성능을 항상 높이는지 설명해주세요.

	데이터 베이스의 정규화는 적절한 테이블로 나누고, 중복 저장과 데이터 이상을 줄이는 설계 방식입니다.

	여러 행에 같은 카테고리의 이름과 설명을 반복해서 저장하면, 카테고리 설명을 바꿀 때 해당 상품의 설명을 모두 바꿔야 하는 점이 생깁니다., 따라서 상품과 카테고리를 별도의 테이블로 분리하고, 상품의 카테고리id가 카테고리 테이블을 참조 할 수 있게 합니다.

	테이블을 분리하게 되면, 두 테이블을 함께 검색 할 때 join 비용이 추가되고, 추가 조회 비용이 들 수 잇습니다. 따라서 항상 정규화가 정답은 아니기에, 중복이나 데이터 불일치를 줄이려고 하면 정규화, 조회 속도가 중요하면 비정규화로 성능을 조정 할 수 있습니다.
	



3. **[BE]** `INNER JOIN`과 `LEFT JOIN`은 결과에 포함되는 행이 어떻게 다른가요?
    1. 회원과 주문을 조회할 때 주문이 없는 회원도 결과에 포함하려면 어떤 방식으로 조인해야 하나요? 한 회원에게 주문이 여러 개 있다면 결과 행은 어떻게 달라지나요?
    2. 회원을 기준으로 주문을 `LEFT JOIN`한 뒤 `WHERE`에 `orders.status = 'PAID'` 조건을 추가하면, 주문이 없는 회원도 결과에 남나요? 같은 조건을 `ON`에 넣는 경우와 비교해주세요.

	INNER JOIN은 양쪽 테이블에서 조건에 맞는 행만 결과에 포함하고, LEFT JOIN은 왼쪽 테이블의 모든 행을 포함합니다.

	회원을 LEFT에 두고 LEFT JOIN을 해서, 주문이 NULL인 회원도 조건에 포함되게 합니다.
	만약 한회원ㅇ게 주문이 여러개가 있다면, 주문마다 결과가 하나씩 생겨 회원 정보가 반복 됩니다.

	WHERE에 조건을 추가하면, 주문이 없는 회원은 결과 행에서 빠지게 됩니다, 만약에 ON을 넣으면, 회원은 모두 남지만, 주문은 PAID인 것만 연결이 되어서, 주문이 엇는 회원은 주문 칼럼이 NULL인 행으로 반환됩니다.


4. **[BE]** SQL에서 `GROUP BY`, `WHERE`, `HAVING`은 각각 어떤 역할을 하나요?
    1. 이번 달 주문만 대상으로 회원별 주문 수를 집계하고, 주문이 3건 이상인 회원만 조회하려면 각 조건을 어디에 두어야 하는지 설명해주세요.
    2. `COUNT(*)`와 `COUNT(컬럼)`은 해당 컬럼에 `NULL`이 있을 때 결과가 어떻게 달라지나요? `NULL`을 0이나 빈 문자열과 구분해서 설명해주세요.

	GROUP BY로 행을 그룹으로 묶으며,  WHERE의 조건으로 행을 거르며, HAVING은 집계 한 그룹을 거르는 역할을 합니다.

	이번 달 주문을 대상을 WHERE 절에, 회원별 이므로 회원을 GROUP 절에, 주문이 3건 이상인 조건을 HAVING 절에 넣습니다.

	COUNT(*)는  행수를 세므로 NULL값도 포함해서 count 값을 반환하고 count(컬럼)은 NULL을 제외하고 갯수를 반환합니다.

	NULL은 값이 없거나 알려지지 않았다는 뜻이고, 0은 숫자 값, 빈 문자열은 길이가 0인 존재하는 문자열입니다.



5. **[BE]** 목록을 나누어 조회할 때 OFFSET 기반 페이지네이션과 마지막으로 조회한 값을 기준으로 이어서 조회하는 커서 기반 페이지네이션은 어떻게 다른가요?

    1. 조회 위치가 뒤로 갈수록 OFFSET 방식의 비용이 커질 수 있는 이유를 설명해주세요. 커서 방식으로 바꾸면 임의의 페이지 번호로 바로 이동하는 기능에는 어떤 제약이 생기나요?
    2. 작성 시각이 같은 게시글이 여러 개 있다면 정렬 기준과 커서 값을 어떻게 정해야 하나요?

	OFFSET 기반 페이지네이션은 앞에서 몇행을 건너뛸지 정하고, cursor 방식은 마지막으로 본 행을 기준으로 그 다음 행부터 읽습니다.

	OFFSET은 앞선 행을 버린 후, 뒤에 행을 가져오기 때문에, 조회 위치가 뒤로 갈 수록 읽고 버리는 행의 크기가 커지기 때문에 비용이 커집니다. 이에 커서 방식으로 바꾸면, 특정 페이지가 얼마나 앞에 행인지 모르기 때문에 특정 페이지로 바로 이동하기가 어렵습니다. 

	작성 시간이 같은 게시글이 여러개가 있다면, created_at 만으로는 순서를 보장할 수 없기 때문에, 고유한 id나 다른 고유한 값을 보조 정렬 기준로 잡아 cursor에 담습니다.
	


7. **[BE]** 데이터베이스 인덱스는 조회 비용을 어떻게 줄이며, 인덱스를 추가하면 어떤 비용이 생기나요?
    1. 조회 성능뿐 아니라 데이터 입력·수정·삭제와 저장 공간에 미치는 영향도 설명해주세요. 인덱스가 존재하면 DB가 항상 그 인덱스를 사용하는지 설명해주세요.
    2. MySQL에서 인덱스 추가 전후의 효과를 확인할 때 실행 계획과 실제 실행 결과에서 무엇을 비교하겠어요? `EXPLAIN`과 `EXPLAIN ANALYZE`의 차이도 설명해주세요.

	인덱스를 B+tree 구조에 담아서 이진트리 형식으로 값을 빠르게 가져 올 수 있습니다. 다만, 인덱스를 추가하면 추가적으로 인덱스를 저장하는 저장공간의 비용과 , 데이터 입력 수정, 삭제 할 때 그 값에 대한 추가 인덱스 변경 비용도 발생합니다.
	인덱스가 있다고 항상 그 인덱스를 사용하지는 않습니다. 반환할 행이 많거나 테이블이 작아 full scan이 저렴하다고 판단하면 인덱스를 쓰지 않을 수도 있습니다. 

	EXPLAIN 으로 접근 방식이 전체 스캔에서 인덱스 탐색으로 바뀌었는지, 선택한 인덱스 key값과 rows가 바뀌었는지 확인하고
	EXPLAIN ANALIZE를 통해 실제 단계별 실행 시간, 반환 행 수, loops를 보고 예상 행 수와 비교합니다.

	EXPLAIN은 실행 계획과 예상치, EXPLAIN ANALIZE는 단계별 실제 시간과 행수를 추가로 보여줍니다.
