## 1일차

1. Spring의 IoC와 DI는 무엇이며, 서비스가 의존 객체를 직접 생성하는 방식과 생성자로 주입받는 방식은 어떻게 다른가요?
    1. 의존 객체의 구현체를 교체하거나 테스트용 객체를 전달해야 하는 상황을 예로 들어 설명해주세요.

	Spring 의 IoC는 제어역전으로, 개발자가 직접 객체를 생성하고 관리하는 것이 아닌, Spring container에게 객체의 생명주기를 관리하도록 맡기는 것입니다. Di는 의존성 주입으로, 개발자가 생성자를 선언하면, Spring이 bean을 찾아 생성자를 호출 합니다.

	예시로는 주문 서비스가 결제 기능을 넣는다고 할 때, 결제 수단에는 여러 가지가 있다. ㅋ카오페이, 토스 페이 등등, 필요한 결제 수단을 골라서, 주문 서비스에 전달만 해주면 됨.
	주문 서비스 자체가 결제에 의존하면 나중에 코드 수정이 번거러움


3. Spring의 기본 빈 스코프인 싱글톤은 어떤 범위에서 하나의 인스턴스를 공유한다는 의미인가요?
    1. 싱글톤 서비스의 필드에 현재 요청의 사용자 정보를 저장하면 어떤 문제가 생길 수 있나요? 요청마다 필요한 값은 어떻게 전달하거나 보관해야 하는지 설명해주세요.
    2. 싱글톤 빈에서 의존성 주입 후 초기화가 필요하거나 컨테이너 종료 시 자원을 정리해야 한다면 `@PostConstruct`와 `@PreDestroy`를 어떻게 활용할 수 있나요?


	컨테이너 안에서 하나의 인스턴스로 관리하고 공유한다는 의미 입니다.
	1. 싱글톤 서비스의 필드에 저장하면, 여러 요청이 겹칠 때 값이 덮어씌어질 수 있습니다. (여러 사용자가 요청해도 하나의 싱글톤을 공유하기 때문) 그래서 요청마다 필요한 값은 메서드 인자 (매개변수)로 전달하고 메서드 안에서만 사용하게 관리합니다.
	2. 초기화가 필요할 때는 @PostConstruct, @PreDestory는 spring container가 종료될 때 자원을 정리할 때 사용합니다. 
	3. 순서는 객체 생성 -> 의존성 주입 -> @PostConstruct -> 사용 -> @PreDestory로 나누어 집니다.



2. Spring Boot의 자동 설정은 무엇이며, 개발자가 모든 빈을 직접 등록하지 않아도 필요한 구성이 만들어지는 이유는 무엇인가요?
    1. 클래스패스의 라이브러리, 설정값, 이미 등록된 빈이 자동 설정의 적용 여부에 어떤 영향을 줄 수 있나요? 컴포넌트 스캔과 자동 설정의 역할도 구분해서 설명해주세요.


	Spring Boot의 자동 설정은 클래스 패스와 설정을 보고 자주 필요한 component를 bean으로 등록해주는 기능입니다.
	클래스 패스의 라이브러리는 관련 라이브러리가 있으면 그 기능을 설정 할 수 있게 해주고, 설정값으로 빈의 동작을 정하거나 특정 설정을 끄고 켤 수 있습니다. , 이미 등록된 빈이 있으면 자동 설정에서 빈을 새로 만들지 않으므로 개발자가 미리 빈을 만들어놓으면 자동 설정의 기본값을 대체 할 수 있습니다.
	컴포넌트 스캔은 어플리케이션 코드에서 @Service, @Componen 등 어노테이션이 붙은 클래스를 찾아서 빈으로 등록하는것이고
	자동 설정은 spring boot의 조건에 맞게 웹, DB 같은 기본 빈을 등록하는 것이다.



4. Spring MVC에서 HTTP 요청이 들어와 컨트롤러 메서드가 실행되기까지 어떤 과정이 진행되나요?
    1. `DispatcherServlet`, `HandlerMapping`, `HandlerAdapter`의 역할을 연결해서 설명해주세요.
    2. `@RestController`가 반환한 Java 객체는 어떤 과정을 거쳐 JSON 응답으로 전달되나요? `HttpMessageConverter`의 역할을 설명해주세요.

	먼저, 요청이 request를 통해서 들어오면, DispatcherServlet이 요청을 받고, 처리할 곳을 찾아서 넘깁니다. HandlerMapping이 적절한 controller를 찾아서 요청을 넘기고, HandlerAdapter가 요청을 받아서 메서드를 실행 시킵니다.

	RestController가 반환한 응답 본문 Java 객체는 HttpMessageConverter가 그에 맞는 반환 타입과 응답 형식에 맞게 변환기를 찾고, Jackson 기반 변환기가 HTTP 응답 형식에 실릴 수 있는 JSON 형태로 반환 합니다.



6. Servlet 필터와 Spring MVC 인터셉터는 요청 처리 과정의 어느 위치에서 동작하며, 어떤 차이가 있나요?
    1. 요청·응답을 감싸서 공통 처리를 하는 경우와 실행할 컨트롤러 메서드의 정보를 확인해야 하는 경우에 각각 무엇을 선택할지 설명해주세요.

	필터는 서블릿 컨테이너에서 동작해 dispacther servlet보다 먼저 동작합니다, MVC 인터셉터는 Handler 매핑이 요청을 처리할 컨트롤러 메서드를 찾은 이후에 동작합니다. 
	필터는 어떤 controller가 받았는지 모르고, 인터셉터는 어떤 controller가 받을지 아는 차이가 있습니다.

	따라서 요청을 감싸서 MVC 밖의 요청까지 감싸서 처리하는 경우에는 servlet 필터, 실행할 컨트롤러 메소드의 정보를 확인 한 후 보내야 하는 요청에는 intercetor를 사용합니다.






7. Spring MVC에서 요청 DTO에 선언한 검증 조건을 적용하고, 검증 실패를 일관된 오류 응답으로 전달하려면 어떻게 구성해야 하나요?
    1. `@Valid`와 Bean Validation 제약조건의 역할, `@RestControllerAdvice`와 `@ExceptionHandler`의 역할을 구분해서 설명해주세요.
    2. 필수값 누락이나 형식 오류와, 현재 재고 부족처럼 비즈니스 데이터에 따라 판단해야 하는 오류는 각각 어디에서 검증할지 설명해주세요.


	먼저 DTO에 제약조건을 넣어 Bean Validation 제약조건을 설정합니다. @Valid를 통해 controller에서 들어오는 요청의 검증을 시도합니다. @RestcontrollerAdvice는 여러 컨트롤러에서 발생 하는 오류의 예외를 공통으로 처리할 클래스에 붙히는 어노테이션이고, ExceptionHandler는 어떤 예외를 처리 할지 지정하고 그에 맞는 응답을 만드는데 사용합니다.

필수값 누락이나 형식 오류 등 값만 가지고 판단해야 하는 오류는 DTO에서 먼저 검증하되, 재고가 충분한지 등, DB의 최신 상태와 비즈니스 규칙을 알아야 하는 요청에 대해서는 서비스 메소드에서 검증합니다.
