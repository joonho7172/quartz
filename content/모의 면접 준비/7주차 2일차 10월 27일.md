## 2일차 - JPA와 Spring 트랜잭션 / 서버 데이터와 화면 상태 관리

1. JPA의 영속성 컨텍스트는 무엇이며, 엔티티가 영속 상태라는 것은 어떤 의미인가요?
	영속성 컨텍스트는 EntityManager가 엔티티를 관리하는 작업 공간이며, 엔티티와 기본키의 대응 관계를 관리하고, 변경 사항을 추적해 DB와 동기화 해줍니다. 엔티티가 영속 상태 라는 것은. 영속성 컨텍스트에 의해서 관리되고 있음을 나타냅니다.
    1. 같은 영속성 컨텍스트에서 `EntityManager.find()`로 동일한 기본키의 엔티티를 반복 조회할 때, 이미 관리 중인 객체와 DB 조회는 어떻게 처리되는지 설명해주세요.
	같은 영속성 컨텍스트에서 관리 중인 엔티티를 find해서 돌려줍니다. 이때 새로 DB에서 SELECT해서 주지 않고, 기존에 관리 되던 객체를 돌려줍니다.
    2. `detach()`나 `clear()`로 관리 대상에서 제외된 엔티티의 필드를 변경하면, 영속 상태의 엔티티를 변경할 때와 어떤 차이가 있나요?

	detach()는 한 엔티티가 관리대상에서 빠지게 되고, clear()는 컨텍스트에서 관리하던 모든 엔티티를 비워냅니다. 따라서 detach 와 clear 한 엔티티의 변경 감지가 적용되지 않아 DB에 commit되지 않다는 점에서 영속 상태의 엔티티를 변경 할 때와 차이가 있습니다.
	
2. 쓰기 가능한 트랜잭션 안에서 조회한 영속 상태의 엔티티를 수정했습니다. 별도의 수정 쿼리를 호출하지 않아도 변경 내용이 DB에 반영될 수 있는 이유는 무엇인가요?
    1. 변경 감지와 `flush()`의 관계를 설명해주세요. `flush()`로 SQL이 실행되었다는 사실과 트랜잭션이 커밋되었다는 사실은 어떻게 다른가요?

	영속 상태인 엔티티가 수정되면 drity check로 인해 JPA가 자동으로 flush()를 하고, 이를 통해 처음 값과 다르다면, 변경된 내용을 UPDATE SQL로 바꿔서 적용합니다. flush 는 현재 트랜잭션 내부에서 DB에 동기화 할 뿐 실제 commit은 아니기 때문에, 롤백되면 flush()도 취소 됩니다. 


3. JPA 연관관계의 지연 로딩과 즉시 로딩은 무엇이며, 연관 데이터를 사용하는 시점에 어떤 차이가 생기나요?
	지연 로딩은 필요 시점에 연관된 엔티티를 불러 오는 값이고, 즉시 로딩은 필요와 상관없이 조회 할 때 연관 데이터를 한꺼번에 조회하는 방식입니다
    1. 즉시 로딩을 설정하면 연관 데이터가 항상 하나의 JOIN 쿼리로 조회된다고 볼 수 있나요? 데이터를 불러오는 시점과 실제 SQL 형태를 구분해서 설명해주세요.
    
	즉시 로딩으로 설정했다고 연관 데이터가 항상 하나의 JOIN쿼리로 조회하지는 않습니다. 부모 엔티티를 반환 할 때 , 연관된 데이터가 로드 되어 있어야 합니다. 그때 데이터를 불러오고, 실제 SQL 형태는 JOIN으로 한번에 가져올 수도 있지만, 부모를 먼저 조회한 후 select로 가져올 수도 있다.
    1. Hibernate에서 영속성 컨텍스트가 닫힌 뒤 아직 초기화하지 않은 지연 로딩 데이터를 사용하면 왜 문제가 생길 수 있나요? 필요한 데이터를 어느 시점에 조회할지 설명해주세요.

	지연 로딩은 처음 조회 할 때 프록시를 넣어 두기 때문에, 영속성 컨텍스트가 닫히면 원분의 SQL을 실행 할 수가 없어 오류가 발생 할 수 있습니다. 즉, 필요한 데이터를 컨텍스트가 닫히기 전, 트랜잭션 내부에서 조회해야 합니다. 

2. 주문 목록을 조회한 뒤 각 주문의 회원 이름을 읽었더니 회원 조회 SQL이 반복 실행되었습니다. N+1 문제가 발생하는 이유와 확인 방법을 설명해주세요.

	먼저 주문목록을 가져오는 SQL 한번과 각 주문마다의 회원 이름을 반환하는 회원 조회 SQL이 N 번 반복되는 형상이 반복 되면 그것이 N+1 문제이다. 이를 확인하기 위해서는 mysql workbench나, hibernate intercept 를 통해 확인 할 수 있다. 
    1. 연관관계를 `LAZY`로 설정하는 것만으로 이 문제가 해결되나요?
	조회를 미룰 뿐 n+1 문제를 해결할 수는 없다.
    2. 조회에 필요한 연관 데이터를 fetch join으로 함께 가져오는 방법과, Hibernate의 배치 조회로 여러 식별자를 묶어 가져오는 방법은 어떻게 다른가요?
	fetch join으로 필요한 연관 데이터를 가져오는 방법은 필요한 데이터만 JPQL 쿼리로 JOIN해서 가져 올 수 있지만, hibernate는 지연 로딩을 유지하다가 IN 쿼리 배치 조회로 여러 식별자를 묶어 가져오는 방법입니다.  batch size를 지정해야 합니다.

2. 하나의 업무에서 여러 Repository 메서드를 호출할 때, 각 메서드가 별도 트랜잭션으로 실행되는 경우와 서비스 메서드 전체를 하나의 트랜잭션으로 묶는 경우는 어떻게 다른가요?

만약에 서비스 메서드 전체를 하나의 트랜잭션으로 묶으면, Repository 메서드들은 그곳의 transaction에 참여를 합니다. 다만, 각 메서드를 별도 트랜잭션으로 묶어버리면, 각 메서드가 끝날때마다 별도로 커밋이 되게 됩니다. 
    1. 롤백 규칙을 별도로 변경하지 않은 Spring의 기본 설정에서, `RuntimeException`과 체크 예외가 메서드 밖으로 전달되면 롤백 여부는 어떻게 달라지나요? 체크 예외에도 롤백이 필요하다면 어떻게 설정할지 설명해주세요.
Spring의 롤백 기본 규칙은 RuntimeException이나, Error가 메서드 밖으로 전달되면 롤백하는 것이기 때문에, 체크 예외는 롤백하지 않고 커밋을 이어나갑니다. 체크 예외에더 롤백이 필요하다고 하면, 
트랜잭션을 시작하는 서비스 메서드에 롤백 대상을 지정합니다.


2. Spring의 기본 프록시 방식에서, 트랜잭션이 없는 서비스 메서드가 같은 객체의 `@Transactional` 메서드를 직접 호출했습니다. 해당 애너테이션으로 트랜잭션이 시작되지 않을 수 있는 이유는 무엇인가요?

	Spring의 기본 프록시 방식에서는 @Transactional 이 프록시를 거쳐서 트랜잭션 처리를 합니다. 
	같은 객체 내부에서 호출하게 되면, 외부에서 호출해 프록시를 부르는 것이 아니므로 트랜잭션 인터셉터가 처리되지 않고 해당 어노테이션 만으로 시작되지 않을 수 있습니다. 
    1. 외부에서 Spring이 제공한 프록시를 통해 호출하는 경우와 객체 내부에서 직접 호출하는 경우를 비교해주세요. 트랜잭션이 필요한 작업을 별도 빈으로 분리하면 호출 구조가 어떻게 달라지나요?

	만약 별도 빈으로 분리하면 호출이 프록시를 통과하기 때문에, 트랜잭션이 적용됩니다.
