**1. Kafka 도입 이유 — “왜 썼나요?”부터 시작**

1. ★ **왜 Kafka를 사용하셨나요? 이 프로젝트의 어떤 문제를 해결하려고 도입했나요?**
	1. Kafka를 사용한 가장 큰 이유는 이벤트 로그 보존의 fan-out 설계 였습니다. 하나의 조회 이벤트를 가지고 조회수 연산, 인기순 상품 정렬, 조회 기반 관심도 알림, 함께 본 물품 추천 등 여러 기능이 독립적으로 소비 진행 상태를 관리하고, 보관된 이벤트를 다시 읽어 재구축 하는데 필요했기 때문입니다.
2. 비동기 처리만 필요했다면 `@Async`로도 가능한데, Kafka가 추가로 제공해야 했던 가치는 무엇인가요?
	1. @Async 같은 어플리케이션 레벨의 비동기 처리는 서버가 다운되거나 장애가 발생 시 데이터가 유실되거나 discard 정책으로 인해서 풀이 포화가 되면 기존의 이벤트를 버리는 문제가 있었습니다. 이에 kafka가 제공하는 offset 기반으로 장애시 이벤트를 재처리하고, 재처리 과정에서의 멱등키를 두어 중복 재처리를 방지 하는 방법으로 진행했습니다. 
3. 실제로 Kafka가 없는 환경에서는 `@Async` 구현을 사용하는데, 두 방식의 차이를 어떻게 설명하시겠어요?
	1. @Async 는 어플리케이션에서 executor 를 통해서 별도의 스레드 요청을 분기해 서로 다른 스레드로 실행 시키는 것이고, Kafka는 이벤트 발생 시 producer가 broker 에게 이벤트를 전달하고, consumer가 이를 소비하는 형태이기 때문에, 어플리케이션 단계에서의 장애가 미들웨어인 kafka 에게 까지 전파되지 않습니다. 반면, @Async 는 메모리를 직접 사용하기 때문에, 프로세스 종료 후에 복구가 어렵습니다.
4. RabbitMQ, Redis Streams, DB 작업 큐와 비교했을 때 Kafka를 선택한 기준은 무엇인가요?
	1. 첫번째로 고려 한 것은 동일한 행동의 이벤트에 여러 consumer group이 독립적인 기능 수행을 해야한다는 점이었습니다. 물론 rabbit mq 도 prefetch 를 통해 백프레셔 대응이나, fan-out이 가능하기 때문에 고려하지 않은 것은 아니었고, redis streams나 rabbitmq streams도 이벤트 보존이 가능 했습니다. 그러나 조회나 검색 행동 로그를 가지고 여러 기능이 소비하며, consumer group 마다의 offset 관리를 통한, 필요할 때 다시 읽을 수 있다는 점에 중심을 뒀습니다.

**2. Consumer group — 사용자가 말한 질문을 깊게 파는 구간**

11. ★ **왜 consumer group을 기능별로 따로 두셨나요?**
	1. 하나의 이벤트를 다른 consumer group 이 독립적으로 소비 하기 위해서 입니다. offset은 각 group, topic, partition 마다 가지므로, 하나의 group이 장애가 나거나, 문제가 생겼을 때, 다른 group은 그 그룹과 독립적으로 자기 offset부터 재개할 수 있습니다.
12. 조회수·추천·알림 리스너를 같은 그룹으로 묶으면, 각 리스너가 모든 조회 이벤트를 처리할 수 있나요?
	1. 아니요 만약에 서로 같은 consumer group 으로 묶으면, 각 리스너 중 하나의 그룹만 파티션에 할당되기 때문에, 이벤트가 litenser들 사이에 나뉘어서 전달됩니다. 각 리스너가 모든 이벤트를 받지 못하기 때문에 , 별도 그룹으로 두어야 각 가능이 모든 이벤트를 독립적으로 소비 합니다.
13. 같은 그룹 안에서 consumer를 늘리는 것과, 새로운 그룹을 추가하는 것은 어떤 차이가 있나요?
	1. 같은 그룹 안에서 consumer 를 늘리는 것은,   하나의 partition의 이벤트를 하나의 consumer 만 소비 할 수 있지만, 새로운 그룹을 추가하게 되면 각자만의 독립된 Offset으로 하나의 partition을 소비 할 수 있어 독립된 기능을 추가하기 편리합니다.

15. 서로 다른 토픽을 처리하는 리스너들이 같은 그룹을 사용해도 괜찮나요? 어떤 결합이 생기나요?
