**1. Kafka 도입 이유 — “왜 썼나요?”부터 시작**

1. ★ **왜 Kafka를 사용하셨나요? 이 프로젝트의 어떤 문제를 해결하려고 도입했나요?**
	1. Kafka를 사용한 가장 큰 이유는 이벤트 로그 보존의 fan-out 설계 였습니다. 하나의 조회 이벤트를 가지고 조회수 연산, 조회수 집계, 조회 기반 관심도 알림, 다른 사용자가 본 물품 추천 등 여러 기능이 독립적으로 소비 되어야 했기에 kafka를 사용했습니다.
2. 비동기 처리만 필요했다면 `@Async`로도 가능한데, Kafka가 추가로 제공해야 했던 가치는 무엇인가요?
	1. @Async 같은 어플리케이션 레벨의 비동기 처리는 서버가 다운되거나 장애가 발생 시 데이터가 유실되거나 정합성이 맞지 않을 가능성이 있었습니다. kafka가 제공하는 offset 기반으로 장애시 이벤트 재처리를 통한 고가용성이 필요했습니다.
3. 실제로 Kafka가 없는 환경에서는 `@Async` 구현을 사용하는데, 두 방식의 차이를 어떻게 설명하시겠어요?
	1. @Async 는 어플리케이션에서 별도의 스레드 요청을 분기해 서로 다른 스레드로 실행 시키는 것이고, Kafka는 이벤트 발생 시 producer가 브로커에게 이벤트를 물어다 주기 때문에 서버의 장애가 곧 이벤트 유실로 이어지지 않습니다.
4. RabbitMQ, Redis Streams, DB 작업 큐와 비교했을 때 Kafka를 선택한 기준은 무엇인가요?
	1. 첫번째로 RabbitMQ 같은 경우는 이벤트가 소비 되면 기록이 없어지기 때문에 독립적인 처리가 필요한 
5. ★ **트래픽이 많지 않아도 Kafka 도입을 정당화할 수 있나요? 운영 복잡도보다 얻는 이점이 컸나요?**
6. 조회수 기록, 검색 이력 저장, AI 가격 산정은 서로 다른 작업인데, 모두 Kafka로 처리한 공통 기준은 무엇인가요?
7. 같은 조회 이벤트를 추천과 알림에 재사용하는 구조가 Kafka 선택에 어떤 영향을 줬나요?
8. 채팅과 실시간 알림 전달에는 Redis Pub/Sub을 쓰면서, 조회·검색 이벤트에는 Kafka를 사용한 이유는 무엇인가요?
9. Kafka가 요청 응답 시간, 장애 격리, 재처리 중 어떤 부분을 개선했나요? 측정한 수치가 있나요?
10. 지금 Kafka를 제거한다면 어떤 기능과 운영 능력을 잃게 되나요?


첫 질문은 코드상 다음 흐름으로 답변을 준비할 수 있습니다. 실제 도입 당시의 판단과 성능 수치는 본인 경험으로 채워야 합니다.

> 조회와 검색 요청에서 부가 처리를 분리하고, 하나의 행동 이벤트를 여러 기능이 독립적으로 소비하도록 구성했습니다. 조회 이벤트를 조회수 기록뿐 아니라 인기 추천, 함께 본 상품 추천, 관심 알림에도 사용합니다. 가격 산정은 외부 AI 호출이므로 요청 처리에서 분리하고, Outbox와 재시도 상태를 이용해 처리 과정을 관리했습니다.

11번은 다음처럼 **기능 간 분리와 동일 기능의 확장**을 구분해서 설명하면 좋습니다.

> 조회수·추천·알림은 같은 조회 이벤트를 각각 처리해야 하므로 서로 다른 그룹으로 두었습니다. 같은 기능을 수행하는 서버 인스턴스들은 같은 그룹으로 묶어 파티션을 나눠 처리합니다. 다만 현재 조회수·검색 이력·가격 산정 리스너는 기본 그룹을 공유하므로, 모든 리스너가 별도 그룹인 구조는 아닙니다.
