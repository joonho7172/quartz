# 스프링 핵심 원리 기본편 15~19강 복습

## 강의 정보
- 강사: 김영한
- 사용자 수강 범위: 15~19강
- 복습 시작: 2026-09-16 / 완료: 2026-09-17 (한국 시간)
- 공개 커리큘럼 및 관련 개념을 바탕으로 진행했다. 유료 영상·자막은 직접 확인하지 않았다. 공개 페이지에서 17~19번의 개별 제목은 확인하지 못했으므로 정확한 차시별 내용으로 단정하지 않는다.
- 이번 질문 주제: DIP 재확인, AppConfig를 통한 책임 분리, 할인 정책 교체. 세 문제로 수강 범위 전체의 이해도를 평가한 것은 아니다.

## 핵심 요약
- DIP는 추상화에 의존하라는 설계 원칙이다. Spring의 자동 주입이나 빈 선택 우선순위를 의미하지 않는다.
- 인터페이스 타입을 사용해도 서비스 내부에서 구체 구현체를 직접 생성하면 해당 구현체에도 의존한다. 수정할 코드가 한 줄이어도 마찬가지다.
- AppConfig는 객체 생성과 연결을 담당하고, 주문 서비스는 주문 처리에 집중한다.
- 주문 서비스가 AppConfig에 의존하는 것이 아니다. AppConfig가 주문 서비스를 구성하고, 주문 서비스는 DiscountPolicy 인터페이스에 의존한다.
- 수동 구성에서는 AppConfig가 생성해 전달하는 객체를 FixDiscountPolicy에서 RateDiscountPolicy로 바꾼다. 생성자 주입 자체에는 구현체 선택 우선순위라는 개념이 없다.
- 두 구현체가 같은 DiscountPolicy 계약을 충족하고 주문 서비스가 구현 세부사항에 의존하지 않으면, 할인 정책 교체 시 주문 서비스 코드는 그대로 유지할 수 있다.
- DI는 외부에서 의존 객체를 전달하는 방법이며 Spring 없이도 가능하다.

## 문제·답변·피드백

### 1. 한 줄의 변경도 DIP 위반일까?
**문제:** 주문 서비스가 DiscountPolicy 인터페이스를 사용하지만 내부에서 FixDiscountPolicy를 직접 생성한다. 이를 RateDiscountPolicy 생성으로 바꾸는 한 줄의 수정만 필요해도 DIP 위반인가? 이유는?

**사용자 답변:**
> 네, DIP 라면 Spring에서 discountpolicy와의 의존성만 해결해두면 알아서 우선순위에 의해 내부 구현체가 주입이 됩니다. FixDiscount를 RateDiscount로 바꾸었다고 추상 클래스가 아닌 구체에 의존하는 것은 바뀌지 않습니다

**피드백:** 구현체를 교체해도 구체 클래스 의존이 남는다는 판단은 정확하다. 지난 복습에서 보완했던 ‘수정량이 아닌 의존 대상’이라는 기준을 이해했다. 다만 DIP는 Spring의 주입 우선순위가 아닌 설계 원칙이며, 여기서 추상화는 DiscountPolicy 인터페이스다.

### 2. AppConfig에도 구체 클래스가 있는데 왜 나아질까?
**문제:** AppConfig가 할인 정책 객체를 만들어 주문 서비스 생성자로 전달한다. AppConfig에는 구체 클래스 이름이 남아 있는데도 개선된 이유는?

**사용자 답변:**
> AppConfig와의 의존성 하나로 상위 클래스는 구체클래스를 몰라도 되기 떄문입니다

**피드백:** 주문 서비스가 구체 클래스를 몰라도 된다는 핵심은 맞다. 다만 서비스가 AppConfig에 의존하는 것은 아니다. AppConfig가 객체 생성·연결을 담당하고, 주문 서비스는 DiscountPolicy에 의존한다. ‘상위 클래스’보다는 ‘주문 서비스’라고 표현하면 상속 관계와 혼동하지 않는다.

### 3. 정액 할인을 정률 할인으로 교체하기
**문제:** 책임을 분리한 뒤 정액 할인을 정률 할인으로 바꾸려면 어디를 수정해야 하며, 주문 서비스 코드는 왜 유지할 수 있는가?

**사용자 답변:**
> 구현체인 정률 할인을 생성자 주입의 우선순위로 두면 됩니다. 주문 서비스 코드는 구현체들이 계약하는 할인 인터페이스만 가르키면 돼요

**피드백:** 주문 서비스가 할인 인터페이스에만 의존하므로 유지할 수 있다는 설명은 맞다. 이번 수동 구성에서는 우선순위를 설정하는 것이 아니라 AppConfig가 RateDiscountPolicy 객체를 생성해 전달하도록 변경한다. 어떤 객체를 전달할지 선택하는 일과 생성자를 통해 전달하는 방식은 구분해야 한다.

## 이해한 부분
- 구현체 직접 생성이 구체 클래스 의존을 만든다는 점.
- 인터페이스에 의존하면 구현 교체의 영향을 줄일 수 있다는 점.
- 서비스가 구체 구현체를 몰라도 동작하도록 구성해야 한다는 방향.
