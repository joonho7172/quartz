kafka.. 메시지 처리 속도를 높이고 싶다면?
parallel consumer로 처리 가능. consumer는 절대 partition의 갯수를 넘을 수 없으므로 하나의 스레드에서 OOM등의 오류가 났을 때, 데이터 중복, 유실등이 다른 스레드 컨슈머에게 영향을 끼칠 수 있음
-> rebalance, 순서 보장 장애 처리 고려 

##### 어떻게?
1. consumer thread를 하나 띄우고 이를 실행하는 worker thread를 여러개 실행
or
2. consumer instance 에서 폴링을 하는 thread를 여러개 띄워서 컨슈머 멀티 스레드 전략 


### 1. consumer thread 띄우고 worker thread를 여러개 실행 

브로커로부터 전달받은 데이터 record를 병렬로 처리 -> 향상된 속도로 처리 가능
for문으로 처리할 경우 이전 데이터 처리를 기다려야 할 수 있음. 이러한 문제를 해결하기 위함. 

java 라이브러리에서 executor 사용해서 스레드 풀에서 재사용, runnable 인터페이스 impl 받아서 스레드에서 실행 시킴. -> 앞서 언급했던 리밸런싱과 데이터 중복 유실. 장애 처리 고려 할 것.

##### 주의 할 점 :
스레드를 사용하기 때문에 데이터 처리가 끝나지 않았어도 커밋을 하기 때문에 생기는 일들이 많음. 
스레드의 처리가 끝나서 데이터를 return 받기 전에 그 다음 poll()을 실행 시에 commit 할 수 있기 때문

record처리의 역전 현상 발생 가능
for 구문으로 worker 스레드에게 일을 할당하는데, 끝나는 시간은 제각각 이기 때문.

###### 그래서 어디에 적합하나?
레코드 처리에 있어 중복이 발생하거나 역전현상이 일어나도 괜찮을 만큼 매우 빠른 처리 속도가 필요한 데이터 처리에 적합함.

### 2. consumer multi thread 전략

하나의 partition은 최대 하나의 consumer에게 할당 될 수 있다는 배경에서 나온 전략
말 그대로 topic에서 그냥 하나의 partition에 하나의 consumer를 두자

### 3. Confluent Parallel Consumer 라이브러리 사용

파티션 증설 없이 데이터 처리 증가? ( 파티션을 증설 하면서 생기는 trade off를 고려하지 않아도 됨, 복제 비용, 응답시간.. index 저장 비용 snapshot 비용 등등..)

![[Pasted image 20261012234929.png]]

보통은 consumer가 이벤트를 소비하고, offset을 commit까지 하는게 순서였다면, parallel consumer에서는 offset commit 조차 비동기로 batch 처리해서 넘겨버림.

전체적인 흐름은 consumer가 메시지를 읽고, worker pool이 하나의 작업(메시지) 줄을 모아 shard 단위로 나누어서 처리, 처리 완료를 추적하고 offset을 commit 하는 방식

##### shard의 순서는 어떻게 보장하느냐?
1. Partition
	1. 처리 순서를 파티션 전체 순서를 따라감 - 병렬 처리는 서로 다른 파티션 끼리 가능

2. key
	1. 같은 key안에서의 순서만 따라감 - 병렬 처리는 서로 다른 key끼리 가능

3. unordered
	1. 순서 보장 없음 - 병렬 처리는 그냥 잡히는대로

key가 핵심인데, partition의 수가 적어도 key의 분배만 잘 되어있다면 여러 병렬 처리가 가능하다는 뜻.

##### 음 그러면 key 분배를 잘하더라도 순서 보장이 안될 수 있지 않나요

offset이라는게 다음에 읽을 순서를 저장하기 때문에 (페이지네이션에서 cursor 생각하면 편할듯)
처리 중인 커밋 위치를 뒤로 넘길 수가 없다...

##### 어떻게 해결하나

아직 처리가 끝나지 않은 가장 앞쪽 메시지까지만 오프셋을 커밋한다.
그 뒤에서 이미 완료된 `102`, `103` 같은 메시지는 별도 오프셋 메타데이터에 기록해, 다시 읽더라도 이미 처리한 메시지는 건너뛴다.

##### 또 고려해야 할 것은 멱등성..
하나만 처리된다는 원자성을 완전하게 수행하는 것이 아니기에, DB나 외부 api 응답 같은 side effect들을 안전하게 처리하려면 멱등성 키를 통해서 중복을 방지한다거나 해야함


정리
1. Parelle Consumer에서의 병렬성은 offset을 땡겨온 메시지별로 추적을 하고, 순서 제약에 맞춰서 (partition, key, unordered) 작업을 나누는 (shard) 것에서 온다. 
2. 어디에 유용하냐면,, DB 작업이나 Http 프로토콜 처럼 대기 시간이 긴 작업, 파티션을 이미 너무 많이 증설 했을 때, 동시성과 처리량은 비례 관계일 수 있으나 downstream 서비스가 감당 가능한 선에서 타협할 것
