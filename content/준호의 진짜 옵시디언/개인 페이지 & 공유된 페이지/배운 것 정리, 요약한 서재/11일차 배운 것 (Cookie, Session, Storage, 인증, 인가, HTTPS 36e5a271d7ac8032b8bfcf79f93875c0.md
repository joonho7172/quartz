**Cookie**

단점 :

1. 보안 : 클라이언트에 담아둬서 민감 정보는 탈취 될 수 있음. 민감정보는 서버측에..
2. 브라우저 간 공유 불가 : 특정 브라우저에 종속 하므로 집, 회사 들 브라우저가 다르면 공유가 안됨
3. 네트워크 부하 증가 : 매 요청마다 자동으로 전송…

보안 문제

아래에 있는 속성은 쿠키의 보안문제를 막기 위해 설정할 수 있는 속성

HttpOnly - 자바 스크립트를 통한 쿠키 접근 차단. document.cookie라는 문법으로 접근 불가

Secure - 쿠키가 HTTPS를 통해서만 전송 되도록 함. MITM 방지용. HTTP연결에서는 쿠키를 전송하지 않음

SameSite - CSRF 공격을 방지하기 위해 퍼스트파티에서만 전송되도록 제한 하는 용도. 다른 도메인에서 사이트로 요청을 보낼때 쿠키를 보낼지 말지를 결정하는 정책.

SameSite 옵션 설명

1. Strict
    1. 퍼스트파티 쿠키 전송만 허용하는 것. (가장 엄격한 옵션)
    2. 우리 사이트 안에서만 이동할때 쿠키 전송.
2. Lax
    1. Strict 보다는 완화되어있는 정책 -> 다른 사이트에서 링크를 클릭하거나 주소창에 직접 주소를 입력하는 등.. 안전하다는 판단에 쿠키 전송.
3. None
    1. 그냥 다 허용
    2. 대부분 잘 사용되지 않음 (보안이 너무 약함)

**Storage**

웹 브라우저에서 클라이언트 측 데이터 저장을 위한 단순 저장소

쿠키랑은 다르게 그냥 클라이언트 측 데이터를 저장하기 위한 목적.

쿠키는 쿠키에 있으면 네트워크를 통해서 데이터가 오고 감. -> 불필요하게 서버에 보낼 네트워크를 타는 데이터. (예를 들면 다크 모드 이런거..)

이러한 문제를 해결하기 위해서 storage가 나옴 . 스토리지에 저장된 데이터는 서버에 자동으로 전송되지 않음. 브라우저에만 머뭄.

로컬 스토리지

영구적으로 저장됨. 데이터 저장하면 사용자가 브라우저 닫거나 컴퓨터를 꺼도 데이터가 사라지지 않음. 사용자가 직접 지우거나 js코드로 삭제하기 전까지는 계속 남아있음.

Ex) 다크 테마, 언어 설정

세션 스토리지

임시 저장소. 데이터가 세션 동안만 유자됨. ->여기서 말하는 세션은 브라우저의 탭이나 창 하나를 의미함. 탭 닫으면 모두 사라짐. -> 같은 사이트면 다른 탭 에서 열거나 다른 창에서 열면 서로 다른 스토리지로 감.

Ex) 입력 폼 작성할때 새로고침해도 남기기 위해서.

결론 : 서버가 모든 요청 알아야 한다 -> 쿠키

서버는 몰라도 되고 브라우저에만 저장해둔다 -> 스토리지

**Session**

컴퓨터 프로세스 사이에서 서로를 인식한 후 데이터 송수신을 마칠 때까지의 상태 정보

세션은 서버쪽에 저장됨..

세션이랑 쿠키가 경쟁관계가 아니라 협력관계임

식당 가서 옷을 맡긴다고 가정

1. 직원에게 옷을 맡김
2. 직원이 옷을 보관 사물함에 보관
3. 옷을 찾을 수 있는 번호표(세션 id)를 줌
4. 번호표만 주머니(브라우저 쿠키)에 넣어서 갖고 다니면 됨.

쿠키에 민감정보를 가지지 않고 세션에서 관리한다는 의미 -> 중요한 정보는 세션에 있지만 서버 입장에서는 사용자를 식별하기 위해 브라우저마다 세션 id를 발급 -> 브라우저는 발급받은 id를 쿠키에서 관리하고 저장함.

세션을 저장하는 서버 속도가 중요함(redis 사용이유)

사용 이유 : 쿠키의 단점을 뒤집으면 세션의 장점이 됨

1. 민감 정보의 안전한 저장
2. 중앙 관리의 용이성 -> 서버에서 모든 사용자의 세션을 관리하니까 특정 사용자를 강제로 로그아웃 시키거나 접속을 제어함.

사용 흐름

로그인 하는 시나리오

1. 로그인 요청 : 사용자가 아이디, 비밀번호 입력해서 서버에 로그인 요청
2. 세션 생성 : 서버는 유효한지 확인하고 해당 사용자를 위한 고유 세션 id를 만들음. 그리고 세션 id와 사용자 정보를 서버측 세션 저장소에 저장함.
3. 세션 id를 반환 : 서버는 http응답에 set-cookie헤더에 생성된 id를 클라이언트에 보냄
4. 쿠키 저장
5. 이후 요청 : 사용자가 행위를 할때 브라우저는 매번 요청 헤더의 쿠키 필드에 저장해둔 세션 id를 서버로 전송
6. 세션 조회 : 세션 저장소에 해당 id를 찾아 사용자 조회
7. 인증 및 응답 : 사용자 정보가 확인되면 요청에 맞는 응답

**인증, 인가**

인증 : 누구인지 식별하는 행위

인가 : 권한을 받고 접근하는 행위

RBAC - Role Based Access Control 역할 기반 접근 제어

인가는 사용자에게 꼭 필요한 최소한의 권한만 부여를 함 -> 사용자가 자신의 역할에 맞는 작업만 수행하도록 제한해서 실수나 악의적인 행동으로 시스템 전체가 위험에 빠지는 것을 방지.

1. HTTP 통해서 이용
2. 세션 통해서 이용
3. JWT 통해서 이용

JWT를 이용하는 방식

JWT - Json Web Token

서버에서 사용자의 상태를 저장하지 않고(state less) 토큰 자체에 정보를 담아서 클라이언트랑 통신하자

1. 로그인 요청 : 사용자가 아이디 비번 서버에 보냄
2. 토큰 생성 : 유효하면 사용자 정보(권한, id)와 만료 시간을 담은 토큰 생성. (서버의 비밀키로 암호화 서명)
3. 토큰 전달 : 서버는 생성된 JWT를 클라이언트에게 응답으로 전달
4. 토큰 저장 및 전송 : 클라이언트는 토큰을 쿠키에 저장하고 서버에 요청 보낼때마다 Authorization….. 뭐시기를 보냄
5. 서버 검증 : 서버는 요청 헤더에 담긴 jwt받아서 서명이 유효한지 확인.

**HTTPS**

HTTP + secure

웹 기반에서 통신을 하는 주체

- 클라이언트 -> 브라우저
- 서버 -> 접속하려는 컴퓨터
- CA -> 인증 기관

기존 HTTP 통신은 클라이언트와 서버가 데이터를 주고 받을 때 아무런 보호장치 없이 평문으로 전송. (중간에 가로챌 수 있음..)

HTTPS -> 이러한 문제를 해결하기 위해 암호화 . -> 통신을 시작하기 전에 서로를 먼저 확인 -> 암호화에서 사용할 키를 교환하는 과정 -> TLS 핸드셰이크 -> 3가지 단계

1. 서버의 신원 확인(https 통신을 하기 위해서 인증서를 발급 받는 과정)
    1. 클라이언트가 서버에 접속하려고 할 때 접속 하려는 서버가 진짜 네이버 서버인지 아닌지 알 수가 없음. -> 서버의 신원을 증명하는 과정이 필요함. -> ca에서 인증된 인증서를 발급
    2. 신원 확인 키 생성 : 서버 관리자는 먼저 한쌍의 열쇠를 스스로 만들음. 하나는 모두에게 공개하는 공개키. 다른 하나는 비밀키. -> 공개키로 암호화된 데이터는 비밀킬로만 복호화 가능.
    3. CSR 생성 : 서버 관리자는 CA에 제출할 신청서 작성. 여기에는 신원 정보랑 서버의 공개키가 들어감 -> 신청서가 위조되지 않았다는 것을 증명하기 위해 서버의 비밀키로 서명.
    4. CA가 CSR을 제출 : 신청서를 CA 에 보냄 Ca가 이 신청자가 정말 맞는지 신원 확인을 함.
    5. 인증서 발급 : 신원 확인이 끝나면 CA는 이 공개키는 어떤 서버의 것이 맞다. 라고 ca보증이 담긴 디지털 인증서를 발급. -> 진위 여부를 보장하기 위해 CA자신의 비밀키로 서명을 해서 건네줌
    6. 인증서 설치 : 서버 관리자는 발급받은 인증서를 웹서버에 설치하고 서버는 클라이언트에게 접속 받을 준비가 끝남.
    7. 클라이언트의 인증서 검증 : 브라우저가 서버에 접속 -> 서버가 먼저 인증서를 브라우저에게 보여줌 브라우저는 이게 신뢰 할 수 있는 CA가 발급한게 맞는지 확인을 함. -> 브라우저는 ca목록이랑 공개키를 미리 갖고 있음. 신뢰 할 수 있는 루트 인증 기관 저장소들이 있음. 브라우저는 CA의 공개키를 갖고 있다가 서버가 준 인증서의 서명을 확인을 함. CA의 공개키로 서명이 성공적으로 검증되면 신뢰 할 수 있는 CA가 발급한 신분증.

클라이언트가 서버에 요청하는 절차

이제 서버가 진짜라는 것을 확인 후 본격적으로 (HTTPS)를 만드는 단계

1. 클라이언트의 요청 : 브라우저가 서버에게 통신을 요청하면 서버는 본인의 인증서라며 응답
2. 서버의 인증서를 클라이언트가 확인 : 브라우저가 이 인증서가 신뢰할 수 있는 CA에서 발급된 것인지 , 유효기간은 남았는지, 접속하려는 주소랑 인증서에 적힌 주소가 일치하는지 검증을 함.
3. 대칭키를 생성하고 전달함 : 이 단계가 실제 데이터를 암호화 하는 단계가 아닌. 둘만의 비밀 암호임
    1. 브라우저가 앞으로 서버와 빠르고 안전하게 통신하기 위해 사용할 임시 비밀번호. -> 대칭키를 그냥 보내면 중간에 탈취 가능하니.. 서버의 공개키로 대칭키를 암호화. (서버의 비밀키로만 열 수 있는 상태로 말하는 것)
    2. 제일 기초적인 원리를 말하는 것. 수학적 퍼즐 교환하거나 각자 대칭키 만들음
4. 전송 : 브라우저는 서버 공개키로 암호화 해서 만든 대칭키
5. 데이터 복호화, 검증 : 서버는 암호화된 대칭키를 받아서 자신만이 갖고 있는 서버의 비밀키로 복호화 함. -> 클라이언트랑 서버, 둘만 알고 있는 비밀 암호가 공유
6. 공유 완료 : 왜 이렇게 복잡한 과정을 거치는가? 이 전 공개키 비밀키 등등은 속도가 느림 계산 복잡.. -> 대칭키 암호화는 속도가 빠름

HTTPS는 두 방식의 장점만 갖고 처리를 한 것

- > 느리지만 안전하 비대칭키 방식으로 처음에 딱 한번만 안전하게 대칭키 교환
- > 그 이후의 모든 데이터는 빠르게 대칭키 사용

대칭키 교환

1. 대칭키 생성: 브라우저가 이번 통신 세션에서만 사용할 임시 대칭키 생성
2. 대칭키의 안전한 암호화 : 서버의 공개키로 암호화 -> 비밀키로만 복호화 가능
3. 대칭키 전송 : 암호화된 대칭키를 서버에 전달
4. 대칭키를 사용한 통신 : 서버는 자신의 비밀키로 복호화 해 대칭키를 얻고 이후에 모든 통신 처리

**공개키/ 비밀키(or 비공개키 or private key)**

항상 쌍으로 존재하고 비대칭키 암호화 방식에서 사용

- 공개키 : 이름처럼 누구에게나 공개해도 되는 열쇠. 주로 데이터 암호화하거나 상대방의 서명을 검증하는데에 쓴다.
- 비공개키 (비밀 키) : 나만 갖고 있어야 하는 열쇠. 공개키로 암호화 된 데이터를 복호화 하거나 내가 보낸 데이터라는걸 증명함.
- 공개키가 자물쇠, 비공개키가 자물쇠를 여는 열쇠

**HTTP 자격 증명 헤더**

정의 : 웹 브라우저(클라이언트)를 통해 어떤 웹사이트 (서버)에 접속한다고 가정

- > 마이페이지에 접근하려고 하는 상황
- > 서버는 “당신이 누구인지 증명해야 접근 가능하다”
- > 이 과정이 인증하는 절차.
- > 이때 클라이언트와 서버가 서로 신분증을 주고 받으면서 대화를 하는데 이것이 HTTP 프로토콜에서 이루어짐
- > 신분증 정보가 담기는 곳이 HTTP 메시지의 헤더 부분 <- 이게 HTTP 자격 증명 헤더

WW-Authenticate (서버가 클라이언트에게 인증이 필요함을 알림)

Authorization (클라이언트가 서버에 자신을 인증하기 위해서 제공)

식당에 가정

1. 문을 열고 들어가려고 함 (클라이언트가 보호된 리소스에 첫 요청)
2. 서버 응답 : 입구에 직원이 .”예약된 사람만 입장 가능. 이름 확인” (401, WW-Authenticate)
3. 다시 시도 (인증 정보 포함) : 예약 확인증을 꺼내서 보여줌 (Authorization에 필요한 값 담아서 요청)
4. 맞으면 200ok
- 기본 인증 : 가장 원시적이고 간단함 id랑 비밀번호 -> ㅇㅇ 안씀
- 다이제스트 인증 : 기본 인증의 보안적인 문제를 개선하기 위해서 비밀번호 직접 보내지 않고 챌린지 리스폰스라고 하는 방식을 씀. -> ㅇㅇ 안씀 (알필요도 없다)
- Bearer 토큰 (Bearer Token) JWT포함 : 아이디 비번 대신 로그인시 발급받은 토큰이라는 열쇠를 요청할때 마다 제시.
- OAuth : 인증 뿐만 아니라 인가까지 다루는 프로토콜. 소셜 로그인. -> 직접 비밀번호를 알려주진 않고, 내 정보 중 일부(이메일, 프로필 사진)에 접근하는 것을 허락한다 와 비슷한 개념..

**JWT**

나중에 한번 더 설명..

JSON - 데이터 포맷 {“이름” : “토르” , “나이” : 11 } 등등

Token - 비유를 하면 놀이동산 갔을 때, 자유 이용권 팔찌 느낌. -> 사용자가 한번 로그인 성공하면 서버가 인증되었다는 토큰 발행. 그 후 매 요청마다 자신의 신원 증명

JWT -> 애플리케이션 간의 정보 교환, 정보를 JSON형식으로 포함하는 자체 포함형

자체 포함형이란?

JWT의 컨셉이자 철학. 이 토큰 하나에 인증에 필요한 모든 정보가 담겨져 있음

- > 서버 입장에서 엄청 편해짐 -> 전통적인 세션 방식에서 클라이언트에서 새션 id를 가지고 오면 db나 메모리 뒤지면서 찾아옴

그러나? JWT는 토큰 자체에 필요한 정보가 다 있어서 서버는 토큰의 위조 여부만 파악하면 됨

- > 서버의 부담이 줄고 서버 확장에도 많이 용이함.

사용 이유:

1. 무상태 인증과 확장성
    1. 전통적인 세션 방식은 서버가 모든 사용자의 로그인 상태를 기억하고 있어야 함….
    2. 사용자가 늘어나면 상당히 서버에 부화가 오기도 함.
    3. 사용자 늘어날수록 세션 정보 관리하는 부담이 생김
    4. JWT는 이런 문제를 해결.. 서버가 사용자를 기억하는게 아니라 사용자가 본인 스스로를 기억해 jwt를 들고 옴.
    5. MSA 마이크로 서비스 아키텍쳐 환경에서도 많이 씀.
2. 보안과 데이터 무결성.
    1. JWT는 마지막 부분에 서명을 포함함 (토큰의 내용이랑 서버만 아는 비밀키를 조합)
    2. 내용과 비밀키를 조합했기 때문에 .. 내용이 바꾸면 서명도 달라짐
    3. 서버는 토큰을 받을 때마다 다시 계산.. 전달 받은 서명이랑 다르면 요청 거부
    4. 데이터 무결성 보장

사용방법

JWT 토큰 생명주기

1. 토큰 발급 : 사용자가 아이디, 비밀번호 로그인 성공하면 서버가 토큰을 생성해서 클라이언트에게 전달
2. 토큰 전송 : 클라이언트는 토큰을 쿠키에 저장. 서버에서 api요청 할 때마다 토큰을 http 요청 헤더에 담아서 전달.
3. 토큰 검증 : 서버가 요청을 받을 때마다 토큰을 검증하고 서명이 올바른지 유효기간 확인.
4. 권한에 따른 처리 : 토큰의 정보를 바탕으로 요청에 대한 처리를 수행

토큰은 헤더, 페이로드(실질적 내용), 서명 (지정된 알고리즘으로 비밀키를 사용해서 서명)

**액세스 토큰**

JWT 토큰이라고 하는 규격을 가지고 엑세스 토큰, 리프레시 토큰으로 나누어짐

정의 : 이름 그대로 서버의 데이터나 기능에 접근 할 수 있는 권한.

호텔 객실 출입 카드 느낌. -> 카드만 유효하면 사용자 안따짐

사용자가 브라우저에서 아이디 비밀번호를 입력해서 로그인 요청 -> 서버는 데이터베이스 확인해서 해당 사용자가 맞는지 인증함. -> 서버가 사용자 식별 정보랑 유효기간 담아서 jwt생성, 이때 서버만 알고있는 비밀키로 서명

- > 이런 토큰을 클라이언트에 전달하면 토큰을 내부적으로 저장해뒀다가 필요한 API 호출 할 대마다 HTTP 요청 헤더에 담아서 서버로 보냄.

액세스 토큰은 유효기간이 짧음.. 보안을 위해서.. 근데 그러다 보면 사용자 경험이 좋지 않음 -> 반대로 사용자 편의를 위해서 유효기간을 길게 하면 또 보안성이 안좋음

**리프레시 토큰**

위의 문제점을 해결하기 위해 리프레시 토큰을 사용.

액세스 토큰을 재발급(refresh)하기 위한 용도로만 사용하는 토큰

결국 리프레시 토큰이랑 액세스 토큰을 혼합해서 사용함.

JWT + 세션 혼합 구현 방식

JWT의 통제 불가능이라는 단점을 보완하기 위함.. jwt와 세션을 혼합.

단기 jwt + 장기 세션

1. 사용자가 로그인하면 유효기간 짧은 jwt를 발급
2. 클라이언트는 api요청시 짧은 jwt사용
3. 유효기간 지나면 세션 쿠키 이용해서 새로운 jwt 요청함
4. 관리자가 특정 사용자를 강제 로그아웃 하고 싶으면 서버에서 해당 사용자 세션 삭제.

RTR - refresh token rotation

리프레시 토큰을 사용해서 새로운 엑세스 토큰을 활성화 -> 새로운 리프레시 토큰도 함께 발급.

- > 이전에 사용했던 리프레시 토큰은 폐기
- > 만약 공격자가 탈취한 리프레시 토큰을 사용하려고 시도하면 서버는 이미 폐기된 토큰임을 감지하기 위함.
