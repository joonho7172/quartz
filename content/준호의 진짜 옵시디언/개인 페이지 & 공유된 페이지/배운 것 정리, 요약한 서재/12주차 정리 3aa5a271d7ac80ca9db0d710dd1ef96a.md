# 12주차 정리

## Registry

컨테이너 이미지는 빌드한 컴퓨터의 로컬에만 존재한다. Dockerfile이 있으면 다른 곳에서 같은 이미지를 다시 만들 수는 있지만, 이미 만들어진 이미지 자체가 실행 서버로 전달되는 것은 아니다.

Registry는 이 문제를 해결하기 위해 컨테이너 이미지를 중앙에서 저장하고 배포하는 이미지 전용 저장소이다.

### 이미지 전달 흐름

```
개발 환경
→ 이미지 빌드
→ Registry에 Push
→ 배포 서버가 Pull
→ 컨테이너 실행
```

배포 서버는 직접 이미지를 빌드하지 않고, Registry에 저장된 검증된 이미지를 내려받아 실행한다.

이미지는 여러 개의 레이어로 구성되기 때문에 이미 Registry에 존재하는 레이어는 다시 전송하지 않고, 변경된 레이어만 Push하거나 Pull한다.

### Registry를 사용하는 이유

1. **배포 일관성**
    - 모든 서버가 동일한 이미지를 내려받아 실행한다.
    - 개발자마다 다른 환경에서 이미지를 빌드하면서 발생할 수 있는 차이를 줄인다.
2. **배포 자동화**
    - CI/CD가 코드를 빌드하여 이미지를 만들고 Registry에 올린다.
    - 배포 서버는 해당 이미지를 내려받아 자동으로 실행할 수 있다.
3. **롤백**
    - 이미지 태그를 이용하여 버전을 구분한다.
    - 새로운 버전에 문제가 생기면 이전 이미지로 쉽게 되돌릴 수 있다.

대표적인 Registry 서비스에는 Docker Hub, AWS ECR, Google Artifact Registry 등이 있다.

## ECR

ECR은 AWS에서 제공하는 완전 관리형 컨테이너 이미지 Registry이다.

일반 Registry와 마찬가지로 이미지를 저장하고 Push·Pull하는 역할을 하지만, AWS 환경에서는 IAM, 리전, AWS 컨테이너 서비스와 통합된다는 차이가 있다.

### ECR의 이미지 식별 구조

```
AWS 계정
→ 리전
→ Repository
→ 이미지 태그
```

ECR은 리전 단위 서비스이며, 계정과 리전 안에서 Repository를 통해 애플리케이션을 구분하고 태그를 통해 이미지 버전을 구분한다.

### 접근 권한

ECR은 기본적으로 Private Registry이므로 인증된 사용자나 AWS 리소스만 이미지에 접근할 수 있다.

```
IAM 자격 증명
→ ECR 인증 토큰 요청
→ Registry 로그인
→ 이미지 Push 또는 Pull
```

이미지를 올리는 주체와 내려받는 주체는 필요한 권한이 다르므로 최소 권한 원칙에 따라 IAM 권한을 분리해야 한다.

자격 증명이나 토큰을 이미지 또는 소스코드 안에 직접 저장하면 이미지와 함께 외부로 노출될 수 있으므로 사용하면 안 된다.

### ECR을 사용하는 이유

- IAM을 통한 이미지 접근 제어
- 이미지 취약점 검사
- ECS, EKS, EC2, Fargate와의 연동
- Registry 서버를 직접 관리하지 않아도 되는 관리 편의성
- 여러 가용 영역을 활용한 저장소 자체의 안정성

## Volume

이미지는 한 번 만들어지면 내용이 변경되지 않는 읽기 전용 결과물이다.

컨테이너가 실행되면 이미지 위에 쓰기 가능한 레이어가 추가되고, 실행 중 생성되는 파일과 변경사항은 해당 쓰기 레이어에 저장된다.

```
읽기 전용 이미지 레이어
+
컨테이너 쓰기 레이어
```

컨테이너가 삭제되면 쓰기 레이어도 함께 삭제되기 때문에 컨테이너 내부에 저장한 데이터도 사라진다.

즉, 기본 상태에서는 컨테이너의 수명과 데이터의 수명이 묶여 있다.

### Volume의 역할

Volume은 데이터를 컨테이너 외부인 호스트 파일 시스템에 저장하여 컨테이너와 데이터의 수명을 분리한다.

컨테이너와 Volume을 연결하는 작업을 **마운트**라고 한다.

```
호스트의 Volume
↕ Mount
컨테이너 내부 경로
```

컨테이너를 삭제한 뒤 다시 생성하더라도 같은 Volume을 마운트하면 기존 데이터를 그대로 사용할 수 있다.

또한 하나의 Volume을 여러 컨테이너에 연결하면 컨테이너 간 데이터를 공유할 수 있다.

### Docker가 관리하는 Volume

Docker Volume을 사용하면 개발자가 호스트의 실제 저장 경로를 직접 지정하지 않아도 된다.

Docker가 전용 저장 영역에 데이터를 보관하고, 사용자는 Volume 이름으로 해당 저장소를 참조한다.

이 방식은 실행 구성이 특정 호스트의 디렉터리 구조에 강하게 의존하는 문제를 줄여준다. 다만 데이터 자체는 Volume이 생성된 호스트에 남아 있다.

### Volume에 저장할 수 있는 데이터

- 사용자가 업로드한 파일
- 데이터베이스 데이터
- 애플리케이션 로그
- 여러 컨테이너가 공유하는 설정 파일
- 실행 중 유지해야 하는 캐시 데이터

## Bridge Network

Bridge Network는 동일한 Docker Host 안에 있는 여러 컨테이너를 하나의 가상 내부망으로 연결하는 Docker 네트워크 방식이다.

예를 들어 하나의 EC2 안에 다음 컨테이너가 실행될 수 있다.

```
Nginx 컨테이너
Spring Boot 컨테이너
Database 컨테이너
```

이 컨테이너들은 서로 격리되어 있지만 Bridge Network에 연결되면 사설 IP를 이용해 통신할 수 있다.

VPC가 EC2와 같은 AWS 리소스를 연결하는 클라우드 네트워크라면, Bridge Network는 하나의 EC2 내부에서 컨테이너들을 연결하는 네트워크이다.

### 구성 요소

#### docker0

Docker Host에 생성되는 가상 Bridge이다.

가상의 네트워크 스위치처럼 컨테이너 간 트래픽을 중계하고, 컨테이너가 외부 인터넷으로 요청할 때 호스트 네트워크로 전달한다.

#### 컨테이너의 eth0

각 컨테이너 내부에 존재하는 가상 네트워크 인터페이스이다.

컨테이너에서 발생한 네트워크 요청은 eth0을 통해 나간다.

#### veth pair

컨테이너의 eth0과 docker0 Bridge를 연결하는 가상 케이블 역할을 한다.

#### Host의 eth0

Docker Host가 실제 외부 네트워크와 통신할 때 사용하는 네트워크 인터페이스이다.

### 컨테이너 간 통신 흐름

```
Spring Boot 컨테이너 eth0
→ veth
→ docker0
→ DB 컨테이너의 veth
→ DB 컨테이너 eth0
```

같은 Bridge Network에 연결된 컨테이너 간 요청은 호스트 내부의 가상 네트워크에서 처리된다.

### 컨테이너 이름 기반 통신

사용자가 직접 만든 Bridge Network에서는 Docker의 내부 DNS를 사용할 수 있다.

따라서 변경될 수 있는 컨테이너 IP 대신 컨테이너 이름 또는 서비스 이름으로 상대 컨테이너에 접근할 수 있다.

```
spring-app → database:3306
```

### 다른 네트워크 방식

- **Host Network**
    - 별도의 가상 네트워크 없이 컨테이너가 호스트 네트워크를 직접 사용한다.
- **Overlay Network**
    - 서로 다른 호스트에 있는 컨테이너를 같은 가상 네트워크에 있는 것처럼 연결한다.
- **MacVLAN Network**
    - 컨테이너에 별도의 MAC 주소와 IP를 부여하여 물리 네트워크의 독립된 장비처럼 동작하게 한다.

## Docker Compose

Docker Compose는 여러 컨테이너로 구성된 애플리케이션의 실행 구성을 YAML 파일에 선언하고, 하나의 단위로 실행하고 관리하는 Docker 도구이다.

```
docker-compose.yml
→ Docker Compose가 파일 해석
→ Docker Engine에 작업 요청
→ 컨테이너, 네트워크, Volume 생성
```

Compose 파일이 직접 컨테이너를 만드는 것은 아니다. Compose는 YAML 파일을 읽고 Docker Engine이 필요한 상태를 만들도록 지시한다.

### Compose 파일에 작성하는 내용

- 사용할 이미지 또는 빌드 방법
- 컨테이너가 사용할 포트
- 환경 변수
- Volume 연결
- Network 연결
- 서비스 간 의존 관계
- 컨테이너 실행 명령어

`services` 아래에 작성되는 각각의 항목을 서비스라고 하며, 기본적으로 하나의 서비스 정의는 하나의 컨테이너 실행으로 이어진다.

### Docker Compose를 사용하는 이유

Compose가 없다면 각 컨테이너를 실행할 때마다 이미지, 포트, Volume, Network 등을 명령어로 직접 지정해야 한다.

이 경우 설정 누락이나 오타가 발생하기 쉽고, 다른 개발자가 동일한 실행 환경을 재현하기 어렵다.

Compose는 필요한 시스템 구성을 파일로 선언하여 다음 장점을 제공한다.

- 여러 컨테이너를 한 번에 실행하고 종료
- 실행 환경의 일관성 유지
- 다른 개발자의 로컬 환경에서도 동일한 구성 재현
- 컨테이너 간 네트워크와 Volume 관계를 명확하게 관리
- 실행 구성을 코드로 관리

컨테이너, Network, Volume 등의 인프라 구성을 코드로 선언한다는 점에서 Docker Compose도 넓은 의미의 IaC로 볼 수 있다.

## 빅뱅 배포

빅뱅 배포는 여러 기능과 변경사항을 큰 단위로 모아 특정 시점에 운영 환경에 한꺼번에 반영하는 배포 방식이다.

기존 버전과 새로운 버전이 동시에 트래픽을 처리하는 구간 없이 기존 버전을 내리고 새로운 버전으로 전체 교체한다.

```
기존 Version 1 종료
→ Version 2 전체 배포
→ Version 2만 운영
```

빅뱅 배포는 특정 서버나 도구를 의미하는 것이 아니다.

EC2나 Docker를 사용하더라도 변경사항 전체를 한 번에 교체한다면 빅뱅 배포에 해당한다.

### 장점

- 배포 절차가 비교적 단순하다.
- 변경사항을 정해진 시점에 한 번에 반영할 수 있다.
- 운영해야 하는 버전이 하나이므로 구조를 이해하기 쉽다.

### 단점

- 한 번에 많은 기능이 변경되어 문제가 발생했을 때 원인을 찾기 어렵다.
- 문제가 있는 기능만 되돌리기 어렵고 정상 기능까지 함께 롤백될 수 있다.
- 기존 버전을 내리고 새 버전을 실행하는 사이에 서비스 중단이 발생할 수 있다.
- 변경 범위가 크기 때문에 운영 리스크가 높다.

최근에는 클라우드와 컨테이너를 통해 서버를 유연하게 확장하고 배포를 자동화할 수 있게 되면서, 큰 변경을 한 번에 배포하기보다는 작은 변경을 CI/CD로 자주 배포하는 방식을 주로 사용한다.

변경 범위가 작으면 문제가 발생했을 때 원인을 좁히기 쉽고 롤백해야 하는 범위도 작아진다.

## 전체 흐름

```
Dockerfile
→ 동일한 이미지 빌드

Registry / ECR
→ 이미지를 중앙에 저장하고 배포 서버에 전달

Volume
→ 컨테이너가 삭제되어도 데이터를 유지

Bridge Network
→ 같은 호스트의 컨테이너끼리 통신

Docker Compose
→ 여러 컨테이너의 구성을 파일 하나로 관리

배포 방식
→ 만들어진 컨테이너 애플리케이션을 운영 환경에 반영
```

이번 내용의 핵심은 컨테이너 하나를 실행하는 방법이 아니라, **이미지를 저장하고 전달하고, 데이터를 유지하고, 컨테이너를 연결하고, 여러 컨테이너를 하나의 시스템으로 관리하는 전체 구조**를 이해하는 것이다.
