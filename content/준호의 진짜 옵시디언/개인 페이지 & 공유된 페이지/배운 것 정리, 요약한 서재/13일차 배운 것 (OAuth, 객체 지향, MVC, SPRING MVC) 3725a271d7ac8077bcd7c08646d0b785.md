**HTTP 자격 증명 헤더 - OAuth**

OAuth는 기본적으로 소셜 로그인 구현하면서 인증의 역할을 수행 -> 근본적인 목적은 A라는 서비스가 사용자를 대신해서 B라는 서비스의 특정 자원에 접근 할 수 있도록 하는 권한 위임

핵심 (사용자 비밀번호를 노출하지 않고 애플리케이션이 사용자의 데이터에 안전하게 접근 할 수 있도록 도와줌)

**사용 이유**

1. 보안 리스크 분산
    1. 예시로 -> 사용자의 은행 계좌 내역을 분석해서 소비패턴을 알려준다.. -> OAuth없으면 사용자가 인터넷 뱅킹 아이디나 비밀번호를 직접 입력해서 서버에 저장해야 함 -> 리스크가 너무 크다.
    2. OAuth가 잇으면. 입출금 내역 정도만 접근하게 허용 동의를 구하고 데이터 조회.
2. UX 향상
    1. 카카오로 1초만에 로그인하기..
3. 선택적 권한 부여
    1. OAuth 쓰면 필요한 정보나 권한만을 줄 수 있음

**동작 방식**

1. OAuth 로그인 시작 -> 대충 버튼 클릭
2. 클라이언트가 인증 서버로 요청.

예시

1~2단계 : 오늘의 집에서 구글 계정으로 사진 가져오기를 누른 상황.

- > 브라우저는 구글 로그인 페이지로 이동
- > 이때 주소창 보면, client_id, scope, redirect_url 등등이 있을거임
- > 구글에게 “안녕하세요 ~~인데 권한 좀 넘겨주세요”

3~4단계 : 신원 확인.

- > 사용자는 구글 페이지에 로그인. (즉, 구글만 비밀번호를 안다)

5~6단계 : 임시 출입증 발급

로그인과 권한 동의가 성공하면 구글에서 브라우저를 보내줌.

- > 이때 주소 뒤에 code = 임시코드를 붙혀서 보내줌
- > 임시코드는 Authorization code임
- > 이코드를 가지고 오시면 권한을 드릴게요와 같음

7~8단계 : 백엔드에서 방금 받은 임시 인증 코드랑 client_id, client_secret을 함께 구글 인증 서버로 보냄

- > 아까 사용자의 임시코드이다. 권한을 주세요
- > 요청이 유효한지 확인을 하고 액세스 토큰을 발급해줌

Why? -> 보안 때문임 임시코드는 사용자 브라우저를 통해서 전달되어서. 탈취될 위험이 있음. -> 액세스 토큰은 쓰려는 서버와 로그인 시켜주는 서버를 통신해서 전달하기 때문에 훨씬 안전함. (서버 to 서버)

- > 리프레시 토큰도 함께 발급 될 수 있음.

9~13단계 : 액세스 토큰을 가지고 로그인 한 서버에 ~~ 달라고 요청.

- >그럼 로그인 한 서버는 액세스 토큰 유효 확인 후 권한 줌.

**정의**

현실 세계의 객체 개념을 기반으로 데이터를 속성과 기능으로 묶어 프로그램을 설계 하는 패러다임

- > 현실 세계의 사물을 컴퓨터 세계로 옮겨온 것이다.
- > 객체는 단순한 데이터 묶음이 아니라 자신이 맡은 역할과 책임을 수행하는 단위임.

객체는 혼자 존재하지 않고 시스템은 여러 객체가 상호간의 메시지를 주고 받으면서 동작한다.

- > 객체간의 상호작용. 외부 클래스에서는 객체의 내부 구현을 직접 다루지 않고 객체가 제공하는 역할과 인터페이스를 통해서 상호작용 -> 캡슐화

시스템 잘게 나누는 것을 모듈화

- > 모듈화는 역할과 책임이 분명한 작은 단위로 나눠서 구성하는 설계 방식
- > 쇼핑몰 만들 때 하나의 거대한 코드로 짜는게 아니라 결제 모듈, 배송 모듈, 재고 모듈로 나누는 등..
- > 결제 시에 문제가 생겨서 코드를 수정해야 할 때, 다른 코드는 건드릴 필요가 없는 상태가 객체 지향임.

이러한 객체지향의 개념은 프론트엔드에도 존재함.

- > 각 컴포넌트는 자신이 맡은 화면 렌더링이나 상태관리만 책임.

질문 : 객체지향의 특징은?

- > “객체지향은 시스템이랑 역할을 가진 객체들의 협력관계로 나타내는 패러다임이다. 실무적으로는 변경이 발생했을 때, 다른 코드에 미치는 영향을 최소화하고, 구현체만 바꿔 확장을 쉽게 만드는 구조를 만들기 위해서 사용”

알아야 하는 이유

결제 정책이 포인트 결제에서 카드 결제로 바뀌더라도 책임이 나뉘어져 있으면 결제 로직이 담당하는 객체만 교체하면 끝남 -> 컨트롤러가 흔들릴 이유 없음. Repository 계층이 흔들리지도 않음.

- > 테스트 코드 작성이 쉬움.

DI

주문 서비스 객체가 결제 객체의 기능을 가지고 주문 처리를 해야하면.

원래는 개발자가 직접 코드 안에서 new 결제객체() 등을 선언해서 만들어야함.

- > DI는 필요한 객체(결제 객체)를 직접 만들지 않음. 프레임 워크가 대신 만들어서 넣어 줌.
- > 내가 직접 new 카카오페이결제()를 해서 하면 다른 결제로 바꿔야 할 때 코드를 뜯어 고쳐야함. -> 그냥 결제 기능이 있는 객체 아무거나 들어오면 난 주문처리만 알아서 하겠다 라고 해야함. -> 결합도는 낮고, 확장성은 쉽게.
- > 대충 조력자 느낌임

객체지향 vs 절차지향

패러다임의 차이 -> 가장 큰 차이는 시스템을 바라보는 설계 기준의 차이

절차 지향은 “어떤 순서로 함수를 실행하고 로직이 흘러가야 하는가에 집중함.

규모가 작을 때는 사람의 사고방식인 시간 순서랑 비슷해서 직관적이고 코딩이 편함.

- > 하지만 은행의 금융 시스템이나 카톡 같은 대규모 서버등 규모가 커지고 기능이 복잡해지면 절차 지향 방식은 한계가 있음.

oop(객체지향)은 누가 책임지고 처리하는가에 집중함 -> 데이터랑 데이터를 처리하는 함수를 객체라는 캡슐 안에 묶음 -> 시스템은 중앙 통제가 아닌 독립적인 객체들의 협력이다.

정리

- 클래스를 데이터를 저장하는 보관소에서 벗어나 객체를 협력하는 존재 라는 관점을 가져야함.
- 이렇게 책임 분리 이유도 코드 수정 할 때, 편리하게 확장성 좋게 하기 위함.

**Dependency(의존성)**

방금 배운 OOP는 객체가 역할과 책임을 갖고 동작함 -> 객체들 끼리 메시지를 주고 받으며 협력하면서 동작함.

- > 객체들이 서로 협력을 한다는 것은 . 다른 누군가를 필요로 한다는 것.

Spring Boot 프레임워크 존재의 이유 중 하나가 의존성을 개발자가 대신 똑똑하게 관리하기 위함.

정의 -> OrderService가 단순히 PaymentService의 pay()메소드를 사용한다고 하지 않음 -> 의존한다고 표현.

- > 의존성이 있다는 건 한 객체의 변경이 다른 객체의 동작이나 수정으로 이어질 가능성이 존재한다.
- > 의존성이 있다는 것 자체가 한 객체가 다른 객체의 동작을 전제로 설계 되었다는 것을 의미함. (객체 지향 프로그래밍은 필수로 의존성이 있어야함)

생성과 조립 책임의 외부 위임

- > 외부의 객체 팩토리 클래스가 해주거나 컨테이너 같은 개념이 있어야 함.
- > 이것을 해주는 것이 Spring 프레임 워크이다.
- > IoC나 DI 철학.

개발자가 개발을 할 때, 비즈니스 로직에만 집중 할 수 있다. 객체를 생성하고 조립하는 일을 Spring이라는 외부 환경에 위임한다.

- > 개발자가 new 계속 선언하거나 팩토리 클래스 만들어서 의존성 관리함.

결론

- 의존성은 객체지향에서 피할 수 없는 협력의 결과물. 의존성 자체가 나쁜 것이 아니라 어떻게 관리하느냐가 핵심 -> 의존성을 적절하게 관리하기 위해서 객체지향을 기반으로 개발자가 책임을 나눠서 설계를 해야함.
- 클래스 내부에서 new 키워드로 다른 객체 직접 생성하는 것은 결합도를 높임.
- 이걸 해결하기 위해서 객체는 자신이 필요한 의존성을 선언만하고 생성과 조립은 Spring 같은 도구를 이용해서 위임 할 수 있다.

**MVC(model, view, controller)**

Model은 데이터와 비즈니스 로직.

View는 화면 표현

Controller는 요청 처리와 흐름 제어 (사용자 입력이나 HTTP 요청)

MVC 패턴 목적이 기능을 나열하듯이 분리하는 것이 아닌. 각 구성 요소를 변경 이유에 따라서 분리함.

- > 화면 표현이 바뀐다고 해서 비즈니스 규칙이 바뀔 필요가 없음./ 흐름이 바뀐다고 해서 데이터가 변할 필요가 없음. -> 구조적 차워에서 아예 격리를 함

동작 방식

Spring Boot에서는 MVC가 동작한다고 가정함.

1. Controller로 클라이언트의 요청이 들어옴
2. Model 영역에서 비즈니스 처리 수행
3. Controller는 처리결과를 view로 전달
4. view가 최종 응답 생성

Spring Boot에서 Service가 모델이라는 의미인가요?

MVC 패턴은 나온지 엄청 오래 됐다. 옛날에 데스크톱 어플리케이션 시절에 나온 개념.

스프링 푸트는 비교적 최근에 나온 개념

MVC 패턴에서 말하는 model이라는 단어는 특정 클래스 하나를 지칭 하는 것이 아니라. 비즈니스 로직과 데이터를 처리하는 모든 영역(Service, Domain, Repository) 을 통틀어 부르는 개념적인 영역이다.

Service 클래스는 model 영역 전반을 지휘하는 역할.. 편의상 Service가 모델을 대표한다.

결론

- 관심사의 분리.
- 컨트롤러, 모델, 뷰 분리를 통해서 영역을 나누어야 변경 영향을 덜 받을 수 있다.

**Spring MVC**

사용자들은 스마트폰이나 브라우저에서 접속을 해서 서비스를 사용함. -> 주문하기

정의 : 웹 요청을 controller로 받아 처리 흐름을 제어하고, model, view를 연결해 응답을 생성하도록 설계된 spring 기반 웹 mvc 프레임 워크

프레임 워크:

프레임워크와 라이브러리 차이가 무엇인가? -> 기초적인 질문

프레임워크의 가장 큰 특징은 제어의 역전. -> 내가 코드를 부르는게 아니라 프레임워크가 특정한 타이밍에 내가 작성한 코드를 알아서 불러준다.

구성 요소

1. 디스패처 서블릿
    1. 전체 흐름을 지배하는 총괄 지배인. Spring Mvc의 진입점
    2. 클라가 요청을 보내면 가장 먼저 디스패처 서블릿을 거치게 됨
    3. 모든 손님이 하나의 정문을 통해서만 들어오게 한 것임. -> 프론트 컨트롤러 패턴
    4. 왜 모든 요청을 한곳으로 모으는가? 공통적인 보안검사, 인코딩 처리, 요청 정보 로깅 등을 한번에 한곳에 끝내기 위해서.
    5. 교통 정리 역할이라고 생각하면 됨 gateway느낌
2. 핸들러 매핑 HandlerMapping
    1. 디스패처 서블릿이 요청을 받으면 누가 처리할지 정해줌.
    2. @GetMapping(“/users”) 같은 정보들이 스프링 어플리케이션이 켜질 때 핸들러 매핑에 싹 다 기록이 됨.
    3. 위는 getUser메소드가 담당 이렇듯.
3. 컨트롤러 Controller
    1. 실제로 처리를 담당하는 영역. 우리가 작성한 영역.
    2. 컨트롤러는 핸들러 매핑에 의해서 FE에서 받아온 파라미터, JSON 데이터 갖고 service 계층까지 처리를 해서 반환을 한다.
4. 뷰 리졸버 view Resolver
    1. 전통적인 웹개발. 스프링 서버가 HTML 까지 다 그려서 브라우저로 보내는 경우에 활동하는 구성 요소
    2. 컨트롤러가 “home”이라는 문자를 반환하면 디스패처 서블릿(지배인)은 뷰 리졸버 에게 “home”이라는 실제 문자열의 html 파일 경로를 믿음.
    3. View resolver는 서버내부의 html 경로를 찾아서 반환해줌.
5. View
    1. HTMl 탬플릿이랑 service가 처리한 데이터를 섞어서 최종적으로 브라우저가 읽을 수 있게 HTML 코드로 렌더링함.
6. Response
    1. 완성된 결과물을 HTTP Response객체 담아서 클라이언트에게 반환

알아야 하는 이유

실제로 일할 때는 스프링 부트 안에서 제공하는 인터셉트나 필터를 사용해서 요청을 추가적으로 처리를 함.

- > 모든 api 요청에 대해서 사용자가 로그인 한 사람인지 토큰을 검사하자 라는 요구사항
1. Dispatcher Servlet이 요청 수신
    1. 브라우저에서 상품 조회 클릭하면 HTTP 메시지 백엔드로 보냄
    2. 제일 먼저 도착하는게 디스패처 서블릿.
    3. 디스패처 서블릿은 http 메시지 덩어리를 HTTP 요청 객체로 감싼다.
    4. 이후의 작업을 편하게 진행 될 수 있도록 세팅을 함
2. HandlerMapping이 처리할 Controller를 찾음
    1. 디스패처 서블릿이 핸들러 매핑을 꺼내서 지금 들어온 요청이 우리가 갖고 있는 컨트롤러 중 어떤건지 찾음
    2. Annotation 스캔해서 매핑 테이블 만들음.
    3. 여기서 일치하는게 없으면 404임.
3. HandlerAdapter가 Controller 실행 준비.
    1. 중간에 핸들러 어댑터라는 관리자가 등장함.
    2. 왜 어댑터가 필요한가? 스프링은 좀 나이가 먹은 프레임 워크..
    3. 컨트롤러 형태가 다양함. restController도 잇고 옛날 방식의 레거시 컨트롤러도 있고..
    4. 그래서 어댑터 계층을 두고 책임을 위임하기 위해서 사용한다.
    5. 어떤 형태의 컨트롤러든 동일한 규격으로 실행할 수 있게 중간에 인터페이스를 맞춰주는 역할.
4. Argument Resolver가 메소드 파라미터 구성
    1. 핸들러 어댑터가 컨트롤러를 실행 시키기 전에 파라미터 객체가 있다면 자바 객체로 생성하고 반환하는 역할.
    2. EX) @PathVariable Long id -> 클라이언트는 자바의 Long 타입을 모름.

**IOC**

스프링을 쓰면 계층의 분리가 됨

- > 계층의 분리가 된다는 것은 클래스가 서로 떨어져 있다는 것.
- >우리가 직접 new로 만들지 않아도 연결해주는것.
- > 그것이 스프링 프레임워크의 IoC이다.

IoC원리를 아는 것과 모르는 것은 차이가 크고. 대규모 서비스에서 스프링을 쓰는가에 대해서 답변 할 수 있다.

정의 :

객체의 생성과 의존성 관리를 개발자가 아닌 외부 컨테이너가 제어 하도록 하는 설계 원칙

- > 개발자가 직접 코드를 치면서 통제 했던 의존성 관계를.
- > 프로그램의 흐름, 객체의 생명 주기. 그리고 객체간의 짝을 짓는 것을 모두 개발자의 코드로 직접 제어하고 있었다.
- > 역전은 무엇인가? : 개발자의 제어권을 넘겨주는 것. Sping contaioner에게.

알아서 선언만 하면 객체를 밀어넣어줌.

사용 이유 :

코드의 결합도를 낮추고 구조의 유연성과 테스트 용이성을 높이기 위해서이다.

1. 결합도
    1. OrderService 라는 주문 로직을 만들었고 데이터베이스에 저장하기 위해서, MySQLOrderRepo 라는 구체적인 클래스를 직접 new로 생성했다고 가정. -> 이 순간 그 둘은 강한 결합이다. 구체적인 클래스로 묶였기 때문.
    2. 만약에 MySQL이 아닌 다른 PG로 교체하자고 하면,,,
    3. PostgresSQLOrderRepo 라는 새로운 클래스를 만들음.
    4. 그럼 전혀 상관없는 OrderService 클래스 파일을 열어서 수정을 해야됨.
    5. IoC를 적용하면 그냥 OrderService와 OrderRepository에만 의존하게 만들고 구현체만 주입.
2. 테스트 용이성
    1. 제어권이 밖에 있어서 테스트 코드 작성 할 때 가짜 객체를 밀어 넣어서 테스트 가능.

IoC와 SOLID 원칙의 관계.

IoC의 내용을 보다 보니까 SOLID원칙과 겹치는 내용이것 같다.

DIP 고수준 모듈은 (비즈니스 로직인 CarService) 저수준 모듈에 (구체적인 기술이 들어간 GasolineEngine)에 의존해서는 안된다.

정리

- 예전에는 개발자가 new로 직접 객체를 만들고 다뤄서 강한 결합 때문에 객체지향도 아니고 유지보수성도 떨어졌는데.
- 객체의 생성과 조립 권한을 스프링 컨테이너 라는 외부 관리자에게 넘겨주니..

수업에서 가져가야 할 핵심

- 역할과 책임을 기준으로 객체를 바라보는 시각이 어떤 느낌이고 개념인지
- 절차적인 순서가 아니라 객체간 메시지와 협력으로 프로그램의 흐름이 만들어진다는 개념
- 변경에 유연하고 유지보수 하기 쉬운 구조를 만들기 위한 객체지향
- 의존성 자체는 나쁜게 아님.
- 객체 내부에서 new 키워드를 사용해 다른 객체를 직접 생성하는 것이. 왜 유지보수와 테스트를 어렵게 만드는가?
- 객체의 생성 책임과 사용 책임을 분리하고 외부에서 의존성 주입을 받는구조의 이점
- 어플리케이션을 model, view, controller 세가지 역할로 나누는 근본적인 이유를 이해
- 변경의 이유가 다른 코드들이 섞여있을 때 발생하는 유지 보수의 문제를 인식하고 MVC가 어떻게 해결하는 가?
- Spring Boot에서 말하는 Model 영역이 단순히 하나의 클래스가 아니라 service랑 repository를 포함하는 비즈니스 영역이다.
- 현대의 rest api개발 환경에서 전통적인 view가 어떻게 json 응답 데이터로 대체 되는지
- DispatcherServlet 의 역할과 중요성에 대한 이해
- 클라이언트의 HTTP 요청이 들어와서 컨트롤러를 거쳐서 응답이 나갈때 까지의 흐름을 머릿속에서 그릴 수 있어야 한다.
- REST API 환경의 스프링 부트에서 view resolver대신 message converter가 어떻게 동작하는지 이해
- 면접에서 IoC가 뭔지 물어보면 대답 할 줄 알아야함.
- 제어의 주체가 누구고 그것이 어떻게 역전이 되는가 라는 의미를 이해
- New 키워드 직접 사용 할 때 생기는 강한 결합의 문제점
- 객체의 생성과 연결을 개발자가 아닌 스프링 컨테이너가 대신 수행 함으로써 얻게 되는 테스트의 용이성과 확장성에 대한 이해
- IoC 가 객체 지향 설계 원칙, 그 중에서 의존 역전 원칙을 어떻게 실현하는지 구조적으로 파악
