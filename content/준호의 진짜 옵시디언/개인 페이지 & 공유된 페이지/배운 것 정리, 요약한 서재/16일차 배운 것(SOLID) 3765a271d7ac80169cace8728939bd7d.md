SRP(Single Responsibility Principle):

하나의 클래스가 하나의 역할과 하나의 변경 이유만을 가지도록 설계 해야 한다는 객체 지향 설계 원칙.

예시 ) 하나의 클래스가 여러 이유로 변경될 가능성이 있다면 이미 여러 책임을 동시에 지고 있는 상황 Employee(calculatePay(), saveToDatabase(), reportHours()) 등등이 있으면 각자 수정 할때 클래스 계속 열어야 함.

정리 :

- SRP는 하나의 클래스가 오직 하나의 변경 이유를 가져야 한다는 원칙
- 책임 제대로 분리하지 않으면 하나의 요구사항 수정 할 때, 다른 기능까지 문제 생기는 상황이 생길 수 있다.
- 원칙을 맹목적으로 따지기 보다는 상황에 맞게 유연하게 대처 할 줄 알아야 함.

**OCP(Open Closed Principle)**

개방 폐쇄 원칙.

실제로 일할 때, 기획자나 PM이 “간단하게 추가해주세요”

- > 개발자 입장에서는 간단하지 않은 경우들이 생긴다.
- > 요구 사항은 간단한 추가인데 실제 코드 열어보면 기존에 잘 돌아가던 if - else 많이 쌓여있는 것 고쳐야 하는 상황도 생기고 그러다 보면 기존 로직에서 문제가 생길 까봐 걱정이 됨.

OCP는 새로운 요구 사항이 들어왔을때, 기존 코드를 건드리지 않고 어떻게 기능을 확장 할 것인가?

즉, 비즈니스 요구사항이 변경되거나 새로운 기능 추가 필요할 때, 그것이 쉽게 수용 할 수 있는 구조를 갖춰야함.

기준 -> 변하는 것과 변하지 않는 것을 분리해야함

정리 :

- OCP는 기능의 확장은 열어두되 기존 코드 변경은 닫아라
- If else 계속 증식하는 코드는 새로운 요구 사항 추가할 때, 기존 내용 문제 생길 수 있으니 인터페이스나 별도의 구현 클래스 분리해서 다형성 활용
- 코드를 계속 수정하는것이 아닌 추가하는 것으로

**DIP(Dependency Inversion Principle)**

의존 역전 원칙.

OrderService -> MySQLRespository 의 의존성을

OrdeService -> OrderRespository <- MySQLRepository 방향으로 의존성을 역전 시키는 것임.

사용 이유 :

개발하다 보면 비즈니스 로직의 수명이랑 세부 구현 기술의 수명은 완전히 다름.  DIP를 적용하지 않으면 수명이 긴 비즈니스 코드가 짧아질 수 있음.

DI는 DIP라는 원칙을 실천하기 좋은 수단이다.

사용 방법

주문처리 서비스와 데이터베이스 저장소 관계에서

실제 데이터베이스 저장하는 구현 로직을 주문처리 서비스가 알 필요가 없는거임.

상위 모듈은 추상화에만 의존하고 구체 구현은 외부에서 주입을 받으면 됨.

같은 비슷한 코드 예시, 사례 더라도 관점을 중심으로 설명 할 수 있어야 한다.

정리 :

- DIP는 상위 모듈의 의존 원칙을 역전하는 것.

가져가야 할 핵심

- SRP에서 말하는 책임은 단순히 기능의 개수가 아닌 “코드가 변경 되어야하는 이유”를 의미한다.
- 하나의 클래스에 여러 책임이 몰려 있을 때, 연쇄적으로 발생하는 문제나 유지보수 어려움 구조적으로 파악.
- 확장에 열려있고 변경에 닫혀 있다는 OCP의 문장이 코드 수준에서 어떻게 구현되는지 이해
- If-else 분기문이 지속적으로 늘어나는 코드가 왜 유지보수에 좋지 않고 이것을 어떻게 인터페이스로 구현하는지
- DIP를 적용하지 않으면 상위 모듈이 하위 모듈에 의존하지만 DIP를 적용하면 의존성의 방향이 역전된다.
