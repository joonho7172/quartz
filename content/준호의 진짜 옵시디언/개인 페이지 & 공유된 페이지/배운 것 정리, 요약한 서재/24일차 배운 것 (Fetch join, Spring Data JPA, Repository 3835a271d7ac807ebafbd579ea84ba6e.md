**Fetch join**

ORM -> JPA 뭔지 배우고 영속성 컨텍스트부터 연관관계 매핑 배우고 지연로딩이랑 그와 연결되는 프록시 까지 배웠음.

JPA사용하게 되면 쉽게 마주치는 문제가 N+1문제

데이터가 많지 않을때는 크게 티가 안나는데.. 심각할땐 심각할 수 잇음.

Fetch join이 이 문제를 해결하기 위해 국룰처럼 씀.

정의 : 지연 로딩된 연관 엔티티를 한번의 쿼리로 함께 조회하기 위해 사용하는 조인 방식

JPQL 사용 할 때 넣는 일종의 문법.

지연 로딩 무시하고 연관 관계 매핑 데이터까지 가져오는게 fetch join,

user.getPost()해도 이미 데이터가 메모리에 잇어서 추가 쿼리가 없다.

즉, 기본 로딩 전략을 lazy로 두고 개발자가 필요할 때만 fetch join 써서 선택적으로 사용할 수 잇는거임.

사용 이유

지연 로딩된 연관 엔티티를 한번의 쿼리로 함께 조회해서 N+1 문제를 해결하고 성능 최적화하기 위해서

Select u from user u join fetch u.posts where —  로 정해진 경우.

DB에서 조인 걸어서 한방의 쿼리로 다 가져옴.

- > 결과 객체에 이미 게시글 데이터 다 들어가 있어서 따로 찾을 필요없음.

그리고 DTO 변환하고 json 직렬화 하는 과정에서 트랜잭션 끝나고도 접근하다가 lazyexception 발생도 막을 수 있음.

일반 inner join이랑 다른점?

JPA에서는 데이터를 필터링 하거나 검색 조건으로 쓰는 inner join과 데이터를 객체를 조립하기 위해서 가져오는 것과는 차이가 있음.

Fetch 라는 단어가 -> 조인만 걸고 필터링 하지 말고 데이터도 다 가져와서 객체 그래프를 채워달라는 것.

일반 조인은 그냥 연관된 엔티티를 검색 조건으로만 쓰고 싶을 때,

패치 조인은 연관된 엔티티 자체를 화면에 그리거나 DTO에 담아서 응답해야 할 때 사용하는 것.

단점 : 부작용과 한계

User와 Post 관계 처럼 연관 관계에서 컬렉션을 fetch join하는 상황 ->

DB에서 1:N 조인을 하면 데이터의 행 수는 무조건 n 쪽에 맞춰지게 됨.

문제가 되는 상황은 컬렉션 패치 조인을 두개 이상 걸었을 때 문제가 됨.

(사용자-게시글-댓글을 다 가져오려고 할때)

게시글 수 x 댓글 수 만큼의 코드가 됨 -> 카테시안 곱으로 늘어남.

그래서 2개 이상의 컬렉션은 패치 조인 하지 않는다.

하이버 네이트 사용 할 때 순서가 보장되지 않는 기본 List 타입으로 두개 이상의 목록을 페치 조인함.

결론 : manyToOne, OneToOne 일때는 패치조인 페이징 가능.

OneToMant, ManyToMany 일때는 패치 조인 불가.

Batch Size 를 사용하면 한번에 묶어서 가져오고 싶을 때 사용함.

Hibernate가 IN 쿼리를 가져오는듯.

toOne 일 상황에는 fetch join을 적극적.

toMany일때는 좀 소극적으로 사용

응답 화면, 목록 화면은 DTO를 사용한다.

컬렉션 조회는 batch size를 같이 고려하는 방식으로 n+1 문제를 해결한다.

**Spring Data JPA**

지금까지 배웠던 JPA는 순수 JPA

- > EntityManager 이용해서 데이터 조작하고 했음.

정의 : JPA 기반의 데이터 처리를 자동화해 인터페이스만으로 리포지토리를 쉽게 구현 할 수 있도록 도와주는 Spring 모듈

사용 이유 : 반복적인 CRUD코드 없이 인터페이스만으로 레포지토리를 구현해 개발 생산성과 유지보수 효율을 높임.

매번 em.persist() 등등을 사용하지 않을 수 잇음.

이 친구가 제공해주는 JpaRepository가 EntityManager를 어떻게 대체 하는지??

예를 들면 순수 jpa에서는 persist쓰고, 수정을 더티체킹을 쓴다고 함.

Spring data jpa의 save는 내부적으로 이 엔티티의 중복 여부를 체크하고

중복이 됏으면 merge함.

- > 이런 객체가 save()에 들어오면 Spring Data JPA는 이 객체는 완전히 새 엔티티가 아니라 기존 엔티티일 가능성이 있겠구나 판단.
- > 그럼 내부적ㅇ로 persist()가 아니라 merge() 호출 할 수 있다.

즉, 신규 저장 - save()

- 기존 엔티티 수정 - 트랜잭션 안에서 조회하고 값 더티체킹
- save() 내부원리 - 새로운거면 persist, 아니면 merge

그럼 무조건 spring data jpa 쓰면 되지 않나?

- > 기본적인 CRUD나 단순한 조회는 맞다..
- > 그러나 통계쿼리나 복잡한 다중조인, 동적 쿼리(사용자가 어떤 검색을 할지)를 작성할 때는 한계가 잇다.
- > 메소드 이름이 한도끝도 없이 길어지거나 원하는 최적화를 못함.
- > 이때 쓰는게 JPQL
- > 쿼리 어노테이션.

정리 : Spring Data JPa를 기본으로 하고 복잡한 곳에서만 순수 JPA이용해서 커스텀 쿼리 쓰거나 QueryDSL 작성해서 이용한다.

Spring data jpa에서는 단건 조회할떄 없으면 예외를 하는게 아니라 null을 반환하는데

그래서 사용하는게 Optional을 반환하는 법이 있다.

정리 :

save()메소드는 객체 상태에 따라서 merge()나 persist()를 구분해서 사용함.

**Repository**

반복적으로 작성되는 코드 , persist, find, remove 등

- > 반복적으로 하니까 힘들어서 spring data spa 라는 것 쓰고,

그 안에서 사용하는것이 repository.

정의 :

Spring Data JPA에서 엔티티를 저장하고 조회하는 역할을 맡는 데이터 접근 계층

- >레포지토리 계층은 반복적이고 기계적인 작업들을 추상화해서 없애줌.
- > 스프링이 알아서 런타임에 인터페이스의 구현체(프록시 객체)를 만들어서 스프링 컨테이너에 bean으로 등록해줌.
- > 그러면 우리는 만들어진 빈을 주입받아, save, findById 같은 메소드를 호출하기만 하면 됨.

사용 이유

서비스 계층 코드에 em.createQuery(“selec— 같은 코드가 들어있다고 가정.

- > 서비스 계층은 원래 비즈니스 핵심 로직을 담당하는 계층인데..
- > 여기에 테이블 이름이랑 쿼리를 어떻게 짜고 트랜잭션을 언제 커밋할지 같은 요소가 잇으면 안됨
- > 관심사의 분리.

레포지토리 계층을 이용하면 서비스 계층은 아예 상관이 없어짐. Jpa인지 mysql인지..

정리

- repository는 인터페이스 선언하고 상속만으로 반복되는 코드

- 인터페이스만 갖고 메소드 쓸 수 잇는건 프록시 기반.

**Query Method**

Spring Data JPA에서 JpaRepository 인터페이스 상속 하나 받으면 기본적인 CRUD 해결 되는걸 알아봣음.

- > 실무 하다 보면 기본 제공되는 findById나 findAll만으로는 부족함.
- > 이메일로 유저 찾기 아니면 특정 닉네임이 포함된 게시글 찾기 조건 조회가 필요함.
- > 낮은 복잡도를 가진 조회를 하게 하는게 쿼리 메소드

FindByTitleAndCommentContains(—)등 메소드가 잇으면

스프링이 이름만 보고 대충 sql 짜준다.

잘못된 구문은 애플리케이션 기동 시 즉시 오류로 드러나 안정성이 높다.

만약 길이가 너무 길어지면 JPQL을 쓰던가 쿼리 어노테이션을 만들기도 한다.

정리

- 쿼리 메소드르 통해서 메소드 이름만으로 쿼리를 자동 생성 할 수 있다.
- 접두사랑 필드명 조건 연산자 조합해서 직관적으로 데이터 조회 할 수 있다.
- 객체 그래프 탐색 할 때는 _ 사용해서 명확하게 할 수 있음.
- 이름 너무 길어지면 가독성 떨어져 상황에 맞게 사용해야함.

**@Query**

쿼리메소드 너무 길어지면 한도끝도 없음.

가독성이 떨어질수도잇음.

그걸 해결하기 위함.

가져가야 할 핵심

- EntityManager 직접 다루는 순수 JPA랑 Spring Data JPA의 차이와 도입 이유
- JPARepository 가 제공하는 기본 메소드들이 내부적으로 EntityManager의 어떤 동작을 호출하는지
- Repository 라는 것의 의미랑 데이터 접근 로직의 도메인 단위 분리 목적
- Spring Data JPA가 내부적으로 생성하는 프록시 객체가 어떻게 생성되는지 원리
- 메소드 이름만으로 JPQL 쿼리가 자동 생성 되는 원리에 대한 이해
- 쿼리 메소드 사용했을때 생길 수 있는 단점 (쿼리 메소드 만으로 모든 문제를 풀려고 하면 생기는 단점)
- @Query 쓰는 이유 와 시점
- 파라미터 바인딩 할 때 반드시 이름 기반으로 해야하는 이유

정의

레포지토리 메소드에 JPQL이나 SQL 쿼리를 직접 작성해 실행 할 수 있도록 하는 어노테이션.

- > 쿼리 메소드는 메소드 이름을 분석해서 JPA가 쿼리를 만들어줬음.

@Query는 우리가 쿼리 문자열 직접 적어두면 스프링 데이터 JPA가 어플리케이션이 켜질 때 이 쿼리를 읽고 분석.

실제로 조건이 2개 3개가 넘어가면 그냥 쿼리 어노테이션을 쓰면 됨

JPQL에서 외부에서 들어온 값 세팅하는 파라미터 바인딩에는 2가지 방식.

하나는 위치기반 바인딩, 또 다른 하나는 이름 기반 바인딩임.

//위치 기반 바인딩

- 엔티티전체 필요 없을 때는 DTO로 받아 올 수 있다.
