# 38일차 배운 것 2 (Concurrent Rendering, Route, Form)

**Concurrent Rendering**

- 서스펜스 같은 기능들이 부드럽게 동작하도록 밑에서 받쳐주는 렌더링 방식

화면 그리는 작업을 나눠서 동시에 쳐리한다는 내용. (우선 순위 스케줄링)

정의

사용자가 기간을 7에서 90으로 바꾸면 다시 계산해서 표랑 차트를 새로 그려내야함.화면 그리는 중인데도 화면이 붙잡혀 오류가 걸리면 사용자는 문제로 여김.

이런 문제를 다루기 위해서 리액트가 사용하는 렌더링 방식이 Concurrent Rendering임.

- 리액트가 내부적으로 렌터링 작업을 끊어서 쪼개고 우선순위를 조정해서 사용자 인터렉션을 우선 처리하도록 한 렌더링 방식
- 우선순위 조정한다는 이야기는 사용자가 방금 누른 필터나 메뉴 조작을 먼저 끼워넣는다는 것.
- 그 결과 사용자 인터랙션이 먼저 처리됨.

리액트에서는 왜 이런 멈춤이 기존에 있나?

리액트 17이하는 동기 렌더링 이엇음. (다른 일을 못함)

지금은 작은 조각으로 나눠서 문제 해결. (Concurrent rendering ) 따로 설치하거나 설정할 필요는 없음.

사용 이유 :

- 사용자 경험
- ui가 멈추지 않은 것처럼 보이게 해서 사용자 경험 부드럽게 만드는게 목적.
- 목록개수 많은 수록 글자 입력 할 때마다 필터링 렌더링 끝날 때까지 입력창이 반응을 못할 수가 있다.
- 리액트가 렌더링을 작은 조각을 나누고 타이핑 같은 이벤트가 들어오면 잠깐 멈추고 다른걸 먼저 선택해서 렌더링 할수가 있다.

리액트는 어떻게 렌더링을 작은 조각으로 나누는가?

- 내부에서 Fiber 구조. 렌더링을 여러 작업 단위로 쪼갠 뒤 각 조각 사이에 브라우저에게 잠깐 제어권을 넘겨준다.
- 렌더링 도중에도 입력 이벤트 받아서 처리 가능.
- 중간에 양보 가능..

우리가 평소에 하는 일반적인 상태 변경. setState로 값을 바꾸는 경우는 여전히 한번에 처리되는 동기 렌더링

- > 그 렌더링이 무거우면 그동안 화면은 그대로 멈춤 리액트가 스스로 알아서 쪼개고 양보하자는 판단은 하지 않음.

그러면 렌더링을 실제로 쪼개고 양보하는 Concurrent 동작은?

- 개발자가 직접 표시해줄 때 켜짐
- 무거운 렌더링을 일으키는 상태 변경을 transition으로 명시해주면 그때 리액트가 그 작업을 낮은 우선순위로 미루고 급한 입력을 먼저 처리함.
- 엔진은 이미 켜져 있고 그 엔진을 쓰겠다는 스위치를 우리가 눌러야 함.
- 그 스위치가 useTransition.

API와 응답자체는 그대로, 그 응답을 화면에 반영하는 무거운 렌더링을 뒤로 미뤄서 전환 같은 즉각적인 반응이 가능하게 하는 것.

isPending은 transition으로 표시한 업데이트가 진행중인지 알려주는 값. 로딩 표시에 그대로 쓸 수 있음.

startTransition은 함수. 함수 안에 넣은 상태 변경만 급하지 않은 것으로 취급.

입력은 즉시, 무거운 계산은 transition

처리속도는 동일한데 더 부드럽게 처리하기 위해서 사용 하는 것임.

API연동

무거운 렌더링이라고 하는건 서버에서 데이터 받아와서 한번에 목록으로 그릴 때도 렌더링이 무거워질 수 있음.

startTransition은 fetch 를 감싸고 있는게 아니라 응답이 도착한 다음에 그 결과를 화면에 반영하는 setList만 감싸고 있음.

- 요청이 서버를 오가는 속도는 transition이 다루는 건 응답을 반영하느라 발생 하는 무거운 렌더링
- 응답을 큰 리스트로 그리는 동안에도 사용자 입력이나 탭 전환은 즉시 반영하는게 가능하다.
- 즉시 반영할 값(setQuery)을 따로 두지 않고 탭을 바꾸는 setTab 자체를 startTransition으로 감쌌다..

새 탭을 그리는 렌더링 전체가 무겁기 때문

- 사용자가 게시글 탭을 누르면 브라우저가 그 렌더링에 붙잡혀서 멈추는 대신 버튼은 계속 눌리는 상태를 유지하고 ispending이 true가 됨
- 그 동안 화면에는 이전 탭이 그대로 남아있다가 새 탭이 준비되면 부드럽게 교체됨.

정리 :

- 렌더링 빠르게 해주는 기술 아니고 여러 작업 병렬도 돌리는 것도 아니고 하나의 스레드 안에서 렌더링 잘게 쪼개고 그 다음에 급한일 먼저, 그리고 안급한일 다음으로 하는 우선순위 스케줄링 개념임
- Q. 동시성 렌더링을 통해서 성능 개선 가능한가?
- Q. 동시성 렌더링 통해서 얻는 이점?
- 일반적인 상태 변경은 여전히 동기 렌더링이라서 무거우면 화면이 멈춤. 어떤게 더 무거운지 개발자가 알려줘야됨,
- 그게 useTransition..무거운 렌더링만 start transition안에 넣으면 됨.
- isPending으로 진행상태 표시까지 처리 가능.

**Route**

실제로 웹 어플리케이션 다루면 화면이 여러개임.

react에서 여러 화면을 가진 앱을 어떻게 다루는지.

배우는게 라우팅

정의 :

- state로 화면을 전환하는 방식에는 지금 이 화면이 어디라고 가르킬 주소가 없음.
- 화면은 여러개인데 주소는 계속 하나에 머물러 있음.
- 기능들은 화면마다 붙는 고유한 주소가 있어야 돌아감
- 화면마다 주소를 부여하고 그 주소에 맞는 화면을 보여주는 체계가 Route
- URL을 통해서 화면 기능 데이터의 위치를 익숙해지는 배경

소프트웨어 전반

Route는 서버나 프로그램이 들어온 요청을 어디로 보낼지 정하는 규칙.

API 서버에서도 요청이 들어왔을 때의 지도를 관리하는것이 라우팅.

요청을 받아서 알맞는 처리 지점으로 안내

웹 환경

Route는 URL 경로와 화면 또는 처리 로직을 연결하는 규칙

하나는 서버 라우팅, 클라이언트 라우팅

우리가 다루는건 클라이언트 라우팅.

리액트에서의 라우팅이란?

URL과 컴포넌트를 연결해주는 규칙.

- > 상세에 /product 123 같은 주소를 붙여서 주소가 그 화면을 가르키게 만드는 것.
- 핵심은 페이지 전체를 새로 고침 하지 않고도 주소를 바꾸면서 다른 화면을 보여준다는 것임.

이 역할을 해주는게 react roter/ nextjs의 app router 같은 것도 같은 일.

사용 이유

리액트로 만든 앱. SPA (single page application)는 처음에 HTML이랑 JS를 한번 불러오고 화면만 바꿔가면서 보여줌

- 화면만 바뀌면서 주소는 그대로면 문제가 생길 수 있음.
- Route는 이 문제를 해결하기 위해 화면과 주소를 짝지어 둠.

코드 스플리팅과 같은 성능 최적화도 가능. 페이지, 컴포넌트 단위 권한 관리와 미들웨어.. 동적 파라미터, 쿼리 상태를 url에 직렬화..

**URL을 화면의 상태로 읽는 다는 것.**

라우팅을 단순 페이지 옮겨다니는 기능이 아닌,

상태를 담는다 라는 관점

/products/123?tab=review - 123번 상품이다, 그 중에서도 리뷰 탭이 열려있다.

**Form**

화면에서 사용자는 무언가를 입력함. 그 값을 어떻게 받아서 확인하고 제출할 것인가? - form

여러 칸에서 사용자의 입력을 모으고 그 값이 올바른지 확인하고 틀린 곳이 있으면 그 자리에서 알려줌.

입력칸 하나가 아니라 입력, 검증, 제출이 하나의 목적으로 묶인 단위

- form이라고 하면 데이터를 입력받아 제출하는 구조적 UI, HTML의 form 태그가 기본 형태. 그 안에 input, select.. 등 입력 필드가 같이 들어감
- > 리액트에서 관점으로 보면 단순한 태그만이 아니라 상태랑 유효성 검증, 제출, 등 포괄적 개념

왜 이렇게 까지 설명하는가?

- 리액트가 SPA라서.. Single Page application. 하나의 HTML 페이지 위에서 동작하는 방식.
- 서버로 페이지 통쨰로 넘기지 않고 브라우저 안에서 입력값을 실시간으로 검증하고 화면 일부만 다시 그려줘야함.
- form이 이 부분을 책임 짐.

사용 이유

값을 state로 소유하고 value로 화면에 되돌려주는 입력 방식을 제어 컴포넌트, controlled component. 화면에 보이는 값의 원천이 DOM이 아니라 리액트 state에 있다는 뜻.

값을 state로 관리한다는 것은 입력 도중에도 그 값을 근거로 화면을 실시간으로 바꿀 수 있다는 의미

- 제어 컴포넌트가 필요한 이유

로그인 폼에서 필드가 2, 3개일 때는 작동 잘하고 문제 없음. 문제는 폼이 커질 때

- > 필드가 이름, 이메일 주소, 전화번호, 약관 동의까지 해서 나중에 10, 20개 된다고 가정.
- > 방금 방식대로 하면 필드마다 useState가 하나씩 필요함. 20개 정도
- > 한필드에 글자 하나만 쳐도 state가 바뀌고 컴포넌트 전체가 다시 렌더링 됨. 필드 20개짜리 폼에서 타이핑 할 때마다 화면 전체를 다시 계산하면 비용이..

폼이 작으면 ㄱㅊ은데 커지면 성능이 떨어짐.

Form을 감싸면 생기는 이점

브라우저가 알아서 입력값을 묶어줌

HTML의 form 태그로 입력들을 감싸면 그 안의 input들이 자동으로 하나의 그룹으로 묶임.

각 input에 name만 붙여두면 제출하는 순간 new FormData 한줄로 이름과 값이 연결된 데이터를 통째로 얻을 수 있다.

필드가 몇개든 이부분의 코드는 그대로

아까 이야기 했던것 처럼 state 20개 조립 할 일 없음.

접근성이랑 기본 동작 그대로 가져다 쓸 수 있음.

렌더링 비용을 줄일 수 있음.

Form 태그로 감싼다고 해서 저절로 리렌더링이 줄어드는 건 아니고 값을 어디에 담느냐가 렌더링을 좌우함.

어떻게?

- React - hook -from 라이브러리는 입력값을 state로 관리하지 않고 ref로 관리함 ref 기반이라고 하는 건 값을 react state가 아니라 dom요소에 직접 연결된 ref 로 읽고 쓴다는 것,
- input에 ref를 걸어두면 타이핑 할 때마다 리렌더링 하지 않고 필요할 때 그 ref로 값을 꺼낸다.
- 그래서 필드가 많은 폼에서도 입력하는 동안 리렌더링 없고 매끄럽게 돌아감.

입력을 다루는 방식이 2가지

1. input을 state로 관리하는 제어 방식
2. 값을 ref에 담아두는 비제어. Uncontrolled 방식. 리렌더링 거의 없어서 빠르지만 실시간으로 제어하는건 덜 세밀하다.

폼의 성격에 따라서 선택을 하는게 필요하다.

리액트에서 Form이 중요한 이유

리액트에서 폼을 하나의 개념으로 묶는게 왜 중요한가..

리액트 자체는 상태를 화면으로 바꾸는 일에 집중하는 도구. 입력값을 어떻게 모으고 검증하고 제출 할 지는 리액트가 대신 정해주지 않음..

입력 필드랑 제출 로직을 논리적으로 묶을 수 있음.

- 하나의 폼 컴포넌트가 있으면 입력들이 제출 이벤트로 간다는걸 한눈에 보여줌. 어떤 input이 어떤 제출로 이어지는지 흩어지지 않고 묶어서 볼 수 있음.

성능이랑 제어성을 같이 챙길 수 있습니다.

단순히 제출만 하면 되지 않음.

설명 할 수 있어야 하는 것.

- Custom Hook이 무엇인지, 왜 사용하는지 어떻게 만드는지.
- Custom Hook이 로직을 재사용하는 도구고 상태를 공유하는 도구가 아닌점.
- 컨텍스트가 무엇인지, 왜 필요한지
- createContext, Provider, useContext 어떻게 쓰는지
- Provider의 값이 바뀌면 어떤 컴포넌트가 다시 그려지는지
- 컨텍스트를 어디까지 써야하고 어디서부터 다른 도구를 써야하는지
- Error 바운더리가 무엇이고 왜 필요한지..
- 실제로 어떻게 감싸고 대체 화면을 보여주는지
- 이 경계가 모든 에러를 잡아주지는 못하고 그 한계를 어떻게 다루는지
- Suspense 무엇인지, 왜 필요한지, 어떻게 감싸서 쓰는지
- 단순한 로딩 스피너가 아니라 화면의 일부를 잠시 대기시키는 경계
- Concurrent rendering이 렌더링을 더 빠르게 만들어주는 기술이 아니고 여러 작업을 병렬로 돌리는 것도 아니다. 렌더링 작업을 잘게 나눠서 급한 일을 먼저 처리하고 덜 급한 일은 잠깐 미루거나 중단할 수 있게 해주는 기반.
- Concurrent
- Route가 무엇인지
- 리액트 같은 단일 페이지 구조에서 왜 필요한지, 그리고 url과 화면을 어떻게 연결 하는 지.
- 라우팅을 그냥 버튼 누르면 다른 페이지로 이동하는 기능으로 이해하지 않고, url이 지금 화면의 상태를 담고 있다는 관점으로..
- 리액트에서 폼은 단순한 태그가 아니라 왜 상태량 검증, 제출을 묶은 개념인지
- 입력값을 state로 관리하는 방식과 ref로 관리하는 방식이 각각 언제 유리한지
- 사용자가 키 하나를 누르는 순간부터 화면이 다시 그려지기까지 어떤 일이 일어나는 지
