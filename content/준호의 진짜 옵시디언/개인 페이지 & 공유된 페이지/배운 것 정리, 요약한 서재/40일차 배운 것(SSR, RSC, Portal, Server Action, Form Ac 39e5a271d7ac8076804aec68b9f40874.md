# 40일차 배운 것(SSR, RSC, Portal, Server Action, Form Action)

**40일차 7/15 수요일**

SSR은 서버가 데이터가 담긴 HTML을 먼저 준비하고 나중에 살려내는 하이드레이션으로 데이터 채움.

CSR로든은 큰 스크립트 받아서 화면을 채움

이후에는 CSR이랑 SSR이랑 동일하게 동작함.

Streaming SSR

- 서버가 완성된 HTML을 한꺼번에 보내지않고 순차적으로 보내는 방식.
- 앞에서 설명했던 서버가 HTML 만들어서 브라우저가 그리고 구간이 더 빨라짐.

Selective Hydration

- 컴포넌트를 하이드레이션 하는 과정에서 모든 컴포넌트를 한번에 살리는게 아닌 사용자가 실제로 보는 영역부터 점진적으로 이벤트 붙이는 방식.

SSR 그대로 두고 안을 빠르게 만드는 이야기

- 그 HTML을 언제 만드는가

CSR은 초기 HTML 아예 만들지 않고 브라우저가 그림.

SSR은 요청이 올 때마다 서버가 그 자리에서 만들음.

여기에서 렌더링 방식 선택지가 생김.

SSG (next.js 환경)

빌드 시점. 배포용 파일 만들어 두는 시점에 HTML을 미리 다 만들어 놓고 요청이 오면 꺼내주기만 하면 되는 방식.

매번 렌더링 하지 않아서 빠르기는 함. 내용이 바뀌면 다시 배포해야함.

그래서 이용약관이나 회사 소개글이나 서비스 마다 진짜 안바뀌는 페이지가 있다면 거기에서 렌더링 방식으로 사용합니다.

ISR

미리 만들어둔 HTML 사용 정해진 주기가 지나면 다음 요청을 기점으로 해서 다신 만들어서 새버전으로 갈아 끼웁니다.

매번 만들지 않으면서도 내용이 너무 오랫동안 낡지 않게 하는 절충안.

SSG랑 ISR은 리액트 자체 기능이 아니라 nextjs 같은 프레임 워크가 제공하는 방식.

미리 만들어진 HTML은 브라우저에 하이드레이션 거쳐야 함.

**Portal**

컴포넌트가 리액트 트리에서 차지하는 위치는 그대로 두고 실제 화면 DOM에서 그려지는 위치만 다른 곳으로 옮기는 기능

정의 :

상품 목록 페이지 개발한다고 가정.

- 상품 카드가 가로로 있고 미리보기 버튼이 있다고 가정. 버튼 누르면 페이지 이동 안하고 상품의 상세 정보를 화면 한 가운데 모달로 확인..
- 이걸 구현하기 위한 자연스러운 방법은 상품 카드 컴포넌트 안에서 버튼 누르면 열리는 모달 그대로 렌더링
- 이유는 부모쪽 CSS에 있음. 상품 목록이 가로로 넘치지 않게 잘라둔 설정이 들어가거나 확대 효과 스타일이 자식 모달까지 가두면 문제 발생 가능.
- 문제의 정체는 모달이 두가지 위치를 동시에 원해서 그럼
- 하나는 논리적인 위치,
- 다른 하나는 물리적인 위치 실제 화면 등에서 어디에 그려지는가, 카드 안이 아니라 화면 최상위에 떠야 한다는 위치

두 위치를 뗴어 놓는 도구가 portal

컴포넌트 트리는 그대로 두고 돔만 다른 곳으로 옮겨서 렌더링 할 수 있게 해주는 통로

정리하면 포탈은 리액트 안에서 상태랑 이벤트 흐름은 원래 부모를 따라가게 두고 실제로 그려지는 돔 위치만 원하는 곳으로 이동해 가는 매커니즘

UI를 유연하고 안정적으로 만들어주는 도구이다..

사용 이유

- 상태 이벤트 컨텍스트를 유지하면서 DOM만 분리
- 포탈로 dom위치를 옮겨도 리액트 트리는 그대로 유지
- 모달 안에서도 부모 컴포넌트의 상태를 그대로 참조 가능, 예전에 배운 컨텍스트로 공유한 값도 참조 가능
- 이벤트 버블링
    - 물속에서 거품 올라오는 그림이랑 비슷
    - 화면에서 어떤 버튼 클릭하면 그 클릭 이벤트가 쭉 부모요소 를 타고 전달이 되는 것
- 웹 브라우저는 실제 돔 구조에 따라서 이벤트를 위로 올려 보냄
    - 리액트의 포탈은 포탈을 통해서 실제 돔 위치는 최상위에 있는 <body> 에 올려보내도 이벤트 버블링 만큼 실제 돔이 아닌 직접 작성한 코드의 리액트 트리를 타고 부모로 올라 온다.

**RSC(React Server Component)**

CSR, SSR의 다음 단계

rsc는 브라우저로 js 보내지 않고 서버에서만 도는 컴포넌트 만들 수 잇음

정의 :

클릭에 반응하지 않고 스펙 표가 움직이지도 않고…

실제로 사용자가 반응하는거는 화면 전체에서는 일부임.

보여주기만 하면 되는 요소들까지 유저의 브라우저에 대해 다운받고 다 함..

상품 페이지는 검색 엔진이 페이지 내용 바로 읽을 수 있어야 함.

어차피 보여주기만 하면 되는 부분이라면 굳이 그 보여주기만 하면 되는 부분을 그림.

그러면 그냥 js 사용자 에게 주지 말고 서버에서 그려서 주자 -> RSC

컴포넌트를 서버에서 렌더해서 클라이언트로 JS 번들을 거의 보내지 않고 특수한 스트림 포맷으로 전달, 결합하는 기술

서버에서 렌더 -> 컴포넌트가 서버에서 실행해서 화면 결과를 만든다.

Js 번들을 거의 보내지 않음- 번들은 여러개의 자바 스크립트 파일을 하나로 묶은 결과물. 리액트 앱처럼 모듈이 많은 프로젝트는 js로 묶어서 내려 보냄. 번들을 거의 내려보내지 않는 다는 건 컴포넌트를 그리기 위한 js 코드가 브라우저로 다운되지 않는다.

SSR과 RSC의 관계

서버에서 화면 그려서 보내니까 SSR이랑 같은거 아닌가?

sSR 생각 하면 서버가 컴포넌트 트리 전체를 HTML로 미리 그려서 보냄. 브라우저는 그 HTML을 화면에 끼운 다음 하이드레이션 함.

근데 RSC는 이미 완성된 결과물로 넘어가기 때문에 SSR보다 하이드레이션이 적다.

그래서.. 버튼 클릭이나 입력처럼 동작해야하는 부분만 SSR 그게 아니면 RSC로 처리.. (즉, 함께 처리한다)

RSC는 어떤 코드를 클라이언트로 보낼지 나누는 층.

SSR은 그 결과를 첫 화면 HTML로 만들어주는 층.

일반적인 방식은 js 번들이 다 내려와서 데이터를 그려줌 초기 뼈대만 ssr로 받고 그치만 서버에서 다 초기를 글서 내리는게 RSC.

사용 이유

자바 스크립트 번들 크기 감소

데이터 근접성

- 서버 컴포넌트는 서버 환경에 가까운 곳에서 직접 데이터를 읽을 수 있음.음
- 브라우저가 API에 요청 보내고 기다리는 과정 없이 server to server 로 결과만 내려보내면 됨
- 그게 뭔 차이?
- 서버 컴포넌트가 데이터랑 개념적으로 가깐 곳에서 실행된다는 의미가 있음.
- 반대로 브라우저가 직접 데이터 가져오는 경우에도 API 왕복 비용이 있다.

보안성 강화

서버에서만 실행 된다는 성질은 보안성에서 큰 장점,

민감한 비즈니스 로직이나 비공개 API등을 브라우저로 내려보내지 않고 서버에서만 다를 수 있음.

브라우저로 내려간 코드는 누구나 열어볼 수 있으므로 서버에서 처리한다는건 보안성의 장점이 있음.

Server Component 의 기본 개념 이해하기

서버 컴포넌트는 서버에서 실행 되고 브라우저에는 HTML과 필요한 데이터만 전달함. JS 번들 내려가는 크기가 적고 초기 로딩이 빠름.

그러면 어떤게 서버 컴포넌트고 어떤게 클라이언트 컴포넌트인지 어떻게 정하는가?

- 파일 맨위에 use Client 라는 지시어 적지 않으면 자동으로 서버 컴포넌트로 취급이 됨 (기본값이 서버 컴포넌트라는 뜻)
- next에서 기본값이 서버 컴포넌트고 브라우저에서 동작 필요하면 use Client 붙여서 클라이언트 컴포넌트로 바꿔줌

useClient 없이 봤던 예제는 다 서버 컴포넌트 였나..?

- 그건 아님 useCLieent 잇는건 RSC 지원하는 환경 한정.

클라이언트 컴포넌트와 섞어 씀. (버튼과 같은 이벤트 클리커 들이 있기 떄문에 …)

서버 컴포넌트가 위에서 데이터 준비하고 클라 컴포넌트가 자식으로 들어가는 구조.

- 서버 컴포넌트는 서버에서 한번 실행되고 끝나기 때문에 useState나 useEffect 처럼 상태를 기억하고 리렌더링 일으키는 훅을 쓸 수 없음.
- 서버 컴포넌트 onClick, 같이 이벤트나, window, document 같은 브라우저 객체는 사용 불가..
- 서버 컴포넌트에 useState 넣으면 터짐.
- 그래서 화면에 상호작용이 필요하거나 리렌더 훅에서 돌아가는게 있다면 그 부분만 useClient 붙여서 클라 컴포넌트로 떼어내야 함.

서버 컴포넌트랑 클라 컴포넌트 섞어쓴다는 말은 결국 이 경계를 컴포넌트 단위로 나눔.

지금 시점에서 서버가 클라 컴포넌트 부르는건 가능해서 클라이언트가 서버 컴포넌트를 부르는 것은 되지 않는다.

Props 를 통해 클라이언트를 서버와 연결하기

서버에서 데이터 가져온 다음에 데이터를 props로 넘겨주는 것.

데이터 준비, 뿌리는 역할을 나눠서 분담 하는 것.

서버 컴포넌트에서 클라로 props 넘길 때는 일반 객체처럼 전송 가능한 객체들만 데이터만 넘길 수 있음.

그래서 필요한 값만 문자열 배열로 정리해서 넘기는게 필요함.

정리 :

- RSC는 서버에서만 실행되고 JS를 브라우저로 보내는 양을 줄이는 컴포넌트이다. 덕분에 번들 작아지고 초기 로딩 빨라지고 서버 가까이에서 데이터 응답성 좋음.
- 보안 측면에서도 서버에서 관리하기 떄문에 용이성이 있다.
- SSR은 첫 화면만 서버가 그려주고 모든 컴포넌트의 JS가 브라우저로 가서 하이드레이션 됨.
- 그러나 RSC의 서버 컴포넌트는 코드 자체가 브라우저로 가지 않아서 하이드레이션 대상이 아님.
- 상호작용이 필요한 부분만 클라이언트 서버로 값을 처리함. 결국은 함께 사용을 한다는 것.

**Server Action 면접에서는 잘 안물어보더라..**

정의 :

RSC는 화면을 서버에서 그리는 일.

- 그러면 이벤트 리스너 같은 것들은? db에 저장하거나.. 무언가를 요청하는 일은?

서버에서만 실행되는 함수를 미리 만들어 두고 사용자가 클릭이나 폼 제출과 연결해서 그 함수가 서버에서 실행 되도록 해주는 기능.

- 서버에서 수행되는, 실행되는 동작
- 어떤 사용자가 버튼을 클릭함
- db에 저장등..
- 문제는 사용자 등록 버튼 클릭은 서버가 아니라 브라우저에서 일어난다..
- 필요한 건 브라우저에서 일어난 클릭을 서버에서만 실행되는 안전한 처리로 이어주는 방법
- 이게 서버 액션

리액트가 제공하는 서버 전용 함수 호출 기술

- 핵심은 서버에서만 실행되는 함수를 하나 만들어 둔다.
1. 사용자가 동작을 하면 리액트가 요청을 서버에 전달
2. 서버에서 요청 살향
3. 결과를 가지고 브라우저로 돌아감.

RSC는 화면에서 서버 내려서 보내는 것.

서버 액션을 클라이언트 이벤트를 서버의 안전한 함수

클릭이나 제출이라는 클라쪽 이벤트랑 서버에서의 함수를 이어주는 역할.

사용 이유

API 라우트랑 핸들러에서 반복해서 써야 했던 코드를 줄여주고 초기 번들 크기 줄여줌,

예전 방식(REST/route handler)

백엔드가 완전 별도 서버라면 요청 보내도됨

- 리액트 프로젝트 안에서 데이터나 db에 직접 접근해야하는 상황이라면 기존 통신 방식에는 클라가 신경 써야 할 것이 많아짐

서버쪽에서 요청을 받아줄 라우트 파일을 하나 만들어야 함.

같은 기능을 server action으로 만들면 과정이 간소화가 됨

폼 컴포넌트는 서버 함수 가져다 쓰긴하지만 useFormStatus나 useFormState 같은 훅을 사용함,.

- 훅을 쓰는 컴포넌트는 기본적으로 브라에서 동작하는 클라 컴포.
- 서버 액션 함수 자체는 서버에서, 그 결과를 뿌리는 폼 컴포는 클라쪽.

예전에는 라우트 파일 따로 만들고 클라엣서 fetch로 요청 보내고.. 응답처리, 상태 관리, 캐시 갱신을 모두 손으로 나누어서 했었음.

서버액션은 이 과정을 하나의 서버 함수로 모음,

보안성 증가

결제 요청 처리하는 상황. 결제 서비스랑 통신하러면 비밀키가 필요한데 이 키는 브라우저에 노출되면 안된다.
