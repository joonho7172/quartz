자바의 인터페이스는 런타임이 구현해야 할 메소드 계약이라는 점에서 객체지향적.

인터페이스는 구현 세부 사항 없이 클래스가 구현해야 할 메소드의 집합만을 정의 한 설계 명세서 이다.

Why -> 실제 프로젝트에서 모든 기능이 완벽하게 정해지지 않은 상태에서 개발을 할 수도 있다(특히 신규)

**캡슐화**

클래스안에 필드와 메소드를 넣어서 객체를 구성하기도 하지만 그렇다고 클래스 모두를 필드 밖으로 내보내도 되는 것은 아니다.

- > 객체 지향에서 데이터를 숨긴다는 것 보다는 객체가 스스로 자기 상태를 책임지게 만드는 설계 방법임

중요한 건 상태가 언제 어디서 어떤 규칙으로 바뀌는지 추적 할 수 있어야 한다.

즉, 차단이 아니라 통제이다.

public class Car {

// 필드를 private으로 감춤

private int speed;

// 외부에서 읽을 수 있도록 getter 제공

public int getSpeed() {

return speed;

}

// 외부에서 값을 설정할 수 있도록 setter 제공

public void setSpeed(int speed) {

if (speed >= 0) {

this.speed = speed;

}

}

}

Why -> 그냥 막 speed를 선언해버린다면 큰 프로젝트에 대해서는 어디에서 speed를 선언했는지, 어디에서 값이 오류가 났는지 알수가 없다 .

그리고 어떤 api호출 뒤에 상태가 깨졌는지 추적할 수가 있다.

캡슐화를 시키면 상태 변경 지점이 setSpeed()로 지정이 되기때문에 규약이나 제한을 넣기가 좋다.

따라서, 중요한 상태 일수도 필드를 숨기고 getter와 setter로 받는 것이 낫다.

그치만 **위에 **관한 **예시에서는 **그저 *set*메소드만 **두는 **것 **보다는 *setFuel*보다는 *reFuel, consumeFuel* 등 **세분화하서 **해야 **기능적으로도*,* 좋다*.*

캡슐화는 객체의 내부 상태를 외부에서 접근하게 하지 못하고 메소드를 통해 간접적으로 접근하도록 하는 개념.

이유는 -> 객체의 내부 사태 보호, 데이터의 무분별한 변경 막기.

방법은 -> 클래스 내 필드를 private로 바꾸고 public 메소드를 통해 get과 set을 제공하는 것. (의미를 고려)

찐 결론 : 자기 상태를 스스로 보호

**Generic**

List<String>과 같은 꺽쇠 괄호를 의미함.

제네릭은 잘못된 타입 사용을 컴파일 시점에 막아주는 장치이다.

public class Garage<T> {

private T car;

public Garage(T car) {

this.car = car;

}

public T getCar() {

return this.car;

}

}

public class Main {

public static void main(String[] args) {

Garage<String> garage1 = new Garage<>("전기차");

Garage<Integer> garage2 = new Garage<>(2025); // 생산연도

System.out.println(garage1.getCar()); // "전기차"

System.out.println(garage2.getCar()); // 2025

}

}

이런 부류임

오류가 생겨도 런타임 보다 컴파일 단계에서 들어감

당연히 기본 타입으로는 못받고 래퍼 타입으로만 받을 수 있다.

Why-> 하나의 코드를 다양한 타입에 재사용. ++ 컴파일 시점에 타입 오류를 잡기 위해서 ++ 불필요한 캐스팅 (타입 변환) 제거

결론 )

- 제네릭은 타입 안정성과 코드 재사용성 동시에 확보
- object를 쓰는 다른 방안도 있지만 캐스팅 필요. 런타임 오류로 발생 가능.

**와일드카드 Wildcard**

제네릭은 타입을 안전하게 고정해주는 문법이었음. 실제로 일할 때는 여러 래퍼 타입을 읽고. 나중에 정하기 위함

그러나 와일드 카드는 제네릭 타입을 사용 할 때 구체적인 타입을 명시하지 않고 어떤 타입이든 가능한 것을 표현하거나 특정 범위 안에서만 허용되도록 제한 할 수 있는 문법 요소 임

결론 : 와일드카드는 제너릭을 사용할 때 받을 수 있는 타입의 범위를 지정할 수 있도록 도와주는 문법이다.

사용방법

? - 불특정한 어떤 타입이든 허용하는 표현

? Super T - T또는 그 상위 타입만 허용

? Extends T -> T또는 그 하위 타입만 허용

- 제네릭의 불공변성 a가 b의 하위타입이어도 제네릭 <a>가 제네릭 <b>의 하위 타입은 아니다.

사용 예시 ) List<car>를 받으면 List<Electriccar>나 List <Gasoline> 같은 거는 못받으니까 List<? Extends car>라고 해서 car의 하위 타입을 모두 받고 모두 넘기는 방안으로 쓰는거임

**Set**

list는 순서도 있고 중복도 허용하는 구조임. 어떻게 보면 set은 중복을 허용하지 않는 컬렉션임

사용 이유 : 순서보다는 유일 성 만약 순서가 중요하다면 List가 자연스럽고 키로 값을 찾는다면 Map이 자연스러움 그리고 중복 제거에 있어서 list보다 훨씬 나음

그리고 가장 중요한 것이 의도표현임 중복제거하는 코드를 삽입하는거보다 set을 사용하므로써 그냥 초반부터 중복되면 안된다는 것을 보여주는 거임

- > 변수 타입이 요구사항을 설명해줄 수 있음.

만약에 입력 순서를 기억을 하고 싶다면 LinkedHashSet을 사용하는 것이 낫다.

내부에서 이중 리스트로 연결함

- set은 단순히 중복을 없애주는 편의 기능이 아니라 데이터의 유일성을 코드 구조로 표현하는 도구이다.

- 동등성에 영향을 주는 값을 바꾸지 않는 것이 안전하다

- 실무에서 캡슐화의 개념은 데이터 검증, 유지보수, 장애 원인 추적, 테스트 가능성, api변경 비용 감소등.
