**서블릿, 서블릿 컨테이너, 서블릿 필터**

Ex) 디스패처 서블릿

서블릿 이란?

- 자바에서 웹 요청 하나를 받아서 응답을 만들어 내는 표준 규격 ‘객체’.
- 브라우저가 HTTP 요청이 서버에 도착하면 결국 어딘가에서는 자바 코드가 그 요청을 받아서 처리를 해줘야 함
- 그 처리를 담당하는게 서블릿.
- 들어온 요청을 controller 에 할당하는 디스패처 서블릿이 예시.

서블릿 컨테이너(tomCat, WAS)가 서블릿들을 관리함.

서블릿 컨테이너는 네트워크로 HTTP 요청을 자바가 다루기 좋은 객체 형태로 바꿔주고 서블릿 생성, 정리 하는 일을 함.

- > 이게 없으면 저수준 통신 코드를 직접 작성해야함. 있기 때문에 응답객체랑 요청으로 일 할 수 있음.

서블릿 필터란?

- 서블릿 보다 먼저 가로채는 장치 (어떤 서블릿 보다 먼저 실행됨
- 또한 서블릿 컨테이너가 관리
- 여러 필터가 한 줄로 이어져서 요청을 처리함 (필터체인)
- 이 필터 자리가 spring security가 들어가는 지점.

웹 요청의 흐름: Filter -> Controller까지.

1. 요청 보냄 -> 톰캣 같은 WAS를 거침. 그 후 필터를 지나고 디스패처 서블릿(인터셉터), 그 다음에 컨트롤러에 도착.
2. ss(spring security)는 어느 시점에 동작하는가? - 서블릿 필터 단계에서 동작을 함.
3. 비즈니스 로직이 들어있는 컨트롤러 닿기 전에 보안 검사 가능.

왜 보안검사를 할 때 필터를 쓰는가?

- 동작하는 시점의 차이
- 필터는 디스패러 서블릿(인터셉터) 보다 먼저 (컨테이너 레벨에서 동작)
- ss는 전체 보안을 책임져야 하기 때문에 MVC에 종속되지 않고 모든 요청을 검사 할 수 있는 필터 기반으로 설계.

Q. 필터와 인터셉트의 차이

사용 이유

- 반복적으로 구현하는 인증, 인가, 방어 로직을 안전하고 편리하게 처리하기 위해서

동작 원리

- 필터, 그 다음으로 delegation 프록시 그리고 아래가 서블릿.
- 요청은 서블릿, 우리 코드에 닿기 전에 여러 필터를 통과함.
- Ss 보안 검사가 이 단계에서 일어나는 것.

**DelegationFilterProxy**

서블릿 필터는 톰캣 같은 서블릿 컨테이너가 관리하는 영역

bean이나 설정 클래스는 스프링 컨테이너가 관리

둘은 서로 다른 세계

Delegation-  은 바깥 쪽 서블릿 필터 체인에서 들어온 요청을 안쪽 스프링이 관리하도록 해주는 관리 프로그램

(서블릿과 스프링을 묶어 주고 보안 관리를 위임함)

**SecurityFilterChain**

보안 필터 목록

(CSRF 공격이나 폼 로그인 요청.. URL 따라서 권한 검사하는 필터 등..)

모든 필터를 통과해야만 controller에 도달이 가능하다.

- > SpringSecurity는 controller에서 동작 하는게 아니구나.

정리

- Ss 인증과 인가를 포함한 보안 처리해주는 프레임 워크
- 인증과 인가의 차이. 항상 인증이 먼저임
- 스프링 시큐리티를 통한 보안 처리가 컨트롤러가 아닌 그 앞단의 서블릿 필터 체인에서 보안 처리 됨
- 요청은 여러 필터 순서대로 통과 되어야함.

**Spring Security 아키텍쳐**

- > 요청이 들어와서 응답이 나갈 때까지 보안처리가 어떤 순서로 처리 되는지.
- 요청이 controller 닿기 전에 어떤 단계를 지나는지, DelegatingFilterProxyfkd FilterChainProxy와 시큐리티 필터 체인이 각각 무슨 일을 하는지.
- 인증된 정보는 어디에?, 필터 인터셉터 AOP가 실행시점과 책임이 어떻게 다른지

정의 :

아키텍쳐 - 설계도

- > ss에서 설계의 중심은 서블릿 필터 기반의 연쇄적인 보안 처리 구조
- > 사용자 HTTP 요청이 서블릿 도달하기 전에 여러 보안 필터로 구성된 체인.

필터 체인 : 서블릿 컨테이너 수준에서 동작하는 필터들의 연결된 목록. 시큐리티 보안 로직이 이 안에서 처리됨.

Security context : 인증 정보와 권한 담아두는 객체.

설계도를 알아야 하는 이유 :

필터에서 처리 하기 위해서는 기술이 언제 동작하는지 알아야함.

(디버깅의 실마리 잡기), (ai시대에서 히네스 잡기)

동작 원리

1. 서블릿 필터 체인, 서블릿 컨테이너 tomcat 같은 웹서버가 관리하는 필터 체인을 지남. 스프링의 영역이 아닌 것 유의
    1. 인코딩 변환이나 로깅 같은 일반 필터
    2. 여기에 본인 필터 (delegating filter proxy)를 넣음
2. DelegatingFilterProxy
    1. 위임하는 프록시
    2. 본인이 직접 보안 검사하는게 아닌 스프링 컨테이너 안에 등록된 빈에게 실제 보안 처리를 넘김.
    3. 왜 굳이? - 컨테이너의 차이에 있음
        1. 서블릿 필터트 서블릿 컨테이너가 관리해서 Spring의 di나 bean 기능 사용 못함. - 그치만 보안에서는 다 사용함. 그 간극 해결.
3. FilterChainProxy
    1. DelegatingfilterProxy가 일을 넘기는 상대가 필터 체인 프록시
    2. 필터 체인 프록시가 스프링 시큐리티의 실질적 시작점
    3. 역할은 관리자이자 라우터.
    4. ss는 여러개의 필터 체인 가질 수 있음.
    5. Url 보고 그거에 맞는 보안 요청을 골라서 할당해줌
4. Security.FilterChain
    1. 필터 체인 프록시 통해서 선택된 시큐리티 필터 체인의 실제 보안 로직의 집합
    2. CSRF 방어, 헤더 처리, 로그인 처리 등등 체인 안의 개별 필터로 수행
    3. 체인 안에 책임이 서로 다른 필터들이 정해진 순서대로 줄지어 있다..
5. SecurityContextHolder 와 SecurityContext
    1. 인증에 성공한 다음부터
    2. 인증 필터가 사용자 확인하면 그 사용자의 신원, 증명 권한을 담은 Authentication 객체를 만들고 Security context에 담김. 그것들을 모아 놓은게 SecurityContextHolder.
    3. SecurityContextHolder는 스레드 로컬 방식..
    4. 같은 요청(스레드)을 처리 하는 동안이라면 어디서든 접근 가능.
    5. JWT 사용 하는 경우에도 사용됨. 세션에 저장만 안하고 요청 처리하는 동안에 인증 정보를 holder에 올려서 사용함.
    6. 요청 끝나도 다음 요청에는 토큰으로 인증.

**Filter, Interceptor, AOP의 비교**

공통점 : 중간에 가로챔.

- > 그런 기능이 필요할 때 어디서 무엇을 사용

Filter

- 셋중에서 가장 먼저 서블릿 컨테이너 수준에서 실행됨.
- HTTP의 원시정보에 접근 할 수 있음.
- 이 시점에는 어떤 컨트롤러가 요청을 받는지도 모름.
- 스프링 빈을 직접 주입 받는 것도 번거로움
- 인증, 인가 처럼 모든 요청에 공통으로 적용해야하는 보안 규칙이 있으면 가장 적합함.

HandlerInterceptor

- 디스패처 서블릿과 컨트롤러 사이에서 실행.
- 이미 Spring MVC 안에서의 영역. 어떤 controller가 호출될지 알아서 Spring Bean에도 접근 가능.
- 로그인한 사용자에 대한 다루는 건 적합함
- 디스패처 서블릿 거치지 않은 요청은 처리 불가

AOP

- 메소드 실행 전후나 주변에서 동작함.
- 메소드 이름이나 파라미터, 어노테이션 등,.. 특정 메소드 단위 제어에 적합함.
- 트랜잭션 관리에 쓰이기도 함 - 같은 맥락
- 대신 설정 복잡, 전체 흐름 파악 어려움

선택 기준은 무엇을, 언제 처리하고 싶은가? 에서 선텍.

- > 전역적인 보안 = filter
- > 핸들러 정보 = interceptor
- > 메소드 단위 = AOP

정리

- 요청은 서블릿 필터 체인 먼저 지나고 그 안에서 DelegatingFilterProxy가 바깥 서블릿 세계랑 안쪽 스프링 세계를 잇는 다리 역할을 함.
- 필터 체인 프록시가 요청에 맞는 시큐리티 필터 체인을 골라주는 관리자 역할을 함.
- 그 안에서 cSPR, 인증, 인가 같은 보안검사
- 모두 통과해야함
- 필터, 인터셉터, AOP의 차이도 알아두자

**Spring Security - 인증 흐름**

Security filter chain 안에서 사용자가 로그인 할 때 안에서 일어나는 것.

- > 그 중에서 가장 기본이 폼 기반 로그인 방식

정의 :

Authentication

- 누가 인증을 시도하고, 인증의 성공 여부를 담음 (인증과 관련된 정보를 담는 상자
- 인증 전과 인증 후 두가지 상태를 가짐. 인증 하고 나서 생기는 객체가 아님.
- 검증 통과하고 나면 DB에서 가져온 사용자 정보와 권한이 채워진 인증 완료 상태의 객체로 바뀜

UserDetails

- 서비스의 사용자 정보는 보통 DB에 저장, 보통 User table,
- Spring Security가 어떤 칼럼 이름과 테이블 구조인지 모름
- 알아 들을 수 있게 각색한 사용자 정보 형식이 UserDetail.
- 우리 DB의 사용자 정보를 스프링 시큐리티가 이해하는 형태로 바꿔주는 중간 계층의 클래스

Form Login

- HTML 폼에 아이디랑 비밀번호 입력해서 제출하는 전통적인 로그인 방식
- 폼 로그인 설정 켜면 정해진 URL로 들어오는 로그인 요청을 가로채서 자동으로 처리해줌

동작 방식 :

1. UsernamePasswordAuthenticationFilter
    1. 유저 네임과 패스워드 인증 처리하는 필터
    2. 폼 로그인 켜면 활성화 된ㄴ 필터
    3. GET요청은 지나가고, Post 요청은 붙잡고 처리
    4. 앞에서 CSRF 같은 필터는 먼저 동작,
    5. 로그인이 안될 때 이 필터까지 왔는지를 확인 해야함.
2. Authentication 객체 생성 (미인증)
    1. 필터는 붙잡은 요청에서 아이디와 비밀번호를 꺼냄.
    2. 그리고 UsernamePasswordAuthenticaitonTOken객체(구현체)에 담음.
    3. 인증 정보 상자라고 보면 됨. (아직은 미인증.)
3. 매니저에 넘기기
    1. 필터가 직접 검증하지 않음
    2. AuthenticationManager에게 넘김
    3. 근데 얘도 직접 처리하는게 아니라 적절한 애 찾아서 넘김
    4. > 그게 바로 Authentication Provider 임.
    5. 왜 매니저랑 따로 둘이서 ..? -> 책임을 일부러 나눠 놓은 것.
    6. Authentication Provider는 실제로 처리하는 실무자. Db에 접근하고 비밀번호 비교하는 작업
    7. 나중에 새로운 인증 방식 추가하고 싶을 때 매니저 그대로 두고 provider만 새로 만들면됨 (확장 깔끔)
4. 진짜 인증 작업
    1. 가장 일반적인 폼 로그인은 Dao AuthenticationProvider…
    2. DAO - data access object
    3. 이 프로바이더는 실제 인증 시작하는데 안에서 3가지 작은 작업을 함.
        1. 사용자 찾아옴. 아이디 주면서 사용자 정보 찾아옴.
        2. userDetailService가 사용자 조회해서 객체로 만들어 반환.
        3. 반환 된 내용을 비교. Provider 는 방금 입력한 비번과 db에서의 비번을 비교.. passwordEncoder (암호화) 해서 비교 합니다.
5. 인증 완료된 객체로 바뀜
    1. 새로운 객체를 만들음. 사용자 정보와 권한 목록까지 다 담긴 인증 완료 상태, Authentication 객체임.
    2. 미인증객체가 검증 통과하면서 권한이 채워진 인증 완료 객체로 바뀌는 것.
6. Security Context에 저장
    1. 인증 완료된 객체는 다시 필터로 돌아옴
    2. 필터는 이 객체를 저장.
    3. 한번 인증되고 나면 컨트롤러 서비스 등 어디서든 사용자가 누구인지 꺼내 쓸 수 있음.
7. 세션 저장하고 리다이렉트
    1. 지금까지의 시큐리티 컨텍스트는 이 요청 끝나면 사라짐.
    2. 세션 쓰면 다시 로그인 할 필요 없음. 인증된 시큐리티 콘텍스트가 HttpSession 같은 곳에서 저장이 됨
    3. 그래서 이후 요청에서도 로그인 상태 유지됨
    4. 설정해둔 로그인 성공 페이지로 리다이렉트

정리 :

- 로그인 요청이 필터에 붙잡히고, 미인증 객체 만들어지고, 매니저 -> 프로바이더에게 넘기고 -> 유저디테일서비스로 사용자 조회 -> 패스워드 인코더로 변환해서 비밀번호 확인 -> 확인되면 인증 완료 -> 그 객체의 정보가 시큐리티 컨텍스트로 저장

**Spring security - 인가 흐름**

인증 흐름 - 사용자가 아이디랑 비번 로그인 -> AuthenticationFIlter 거쳐서 Authentication 객체가 시큐리티 컨텍스트에 저장되는 과정

- > 다음 단계가 인가.

정의 :

인증을 통과한 사용자가 특정 리소스에 접근할 권한을 확인하는 단계

Security Context에 Authentication 객체가 있다는 사실이 인가의 전제 조건임.

동작 원리:

1. 사용자가 GET /admin/dashboard 같은 요청을 보냄
    1. 인증 필터 끝나서 Authentication이 되어있는 상태.
2. AuthorzationFilter가 요청을 가로챔
    1. 인증이 끝난 요청이 이 필터에 도달
    2. 필터는 인가 판단을 직접 하지 않음. 대신 현재 요청 정보와 인증된 사용자 정보로 AuthorzationManager에게 넘김 -> 요청 허용되냐고 결정을 위임함.
    3. 똑같이 흐름을 제어하는 쪽과 실제 판단을 하는 쪽을 분리.
    4. 인가 규칙이 바뀌어도 필터는 그대로 두고 판단 로직만 유연하게 바꿀 수 있음.
3. AuthorzationManager는 설정 파일을 읽음.
    1. 현재 요청이 URL이 어떤 규칙과 일치하는지 확인, 규칙이 요구하는 권한을 객체가 실제로 갖고 있는지 비교.
    2. 경로에 맞게 사용자가 권한을 가지고 있는지 확인함.
4. 결과에 따라 허용 or 거부 (isGranted() - true or false )
    1. 허용되면 다음 필터로 요청.. 최종적으로 controller
    2. 거부 되면 - Authorzation이 AccesDeniedException이라는 예외 발생. - ExceptionTranslationFilter가 받아서 처리
    3. 인증은 됐는데 권한이 부족한 경우.. 403

401, 403 구분 잘 해야함.

정리 :

필터는 흐름만 제어하고 매니저가 Authentication 객체와 설정 규칙을 비교해서 내림.

**익명 사용자**

AnonymousAuthenticationToken 이라는 토큰을 부여해서 관리를 함.

이러한 개념으로 규칙들이 명확해진다. permitAll, isAnonymous, isAuthentication 등..

정리 :

- 인가는 인증이 끝난 다음 사용자에 대해 권한이 있는가 판단하는 단계
- 인가 흐름에서 핵심은 AuthorizationFilter와 Manager임. 필터가 요청 가로채고, manager가 위임. authorizedHttpRequest에 적힌 규칙과 Authentication 객체가 가진 권한 비교 해서 허용과 거부 결정.
- 설정은 URL 기반 or 메소드 기반.

가져가야 할 핵심

- 스프링 시큐리티가 무엇, 어떤걸 해결해주는 도구 인지, 인증/인가 개념 안에서 보안을 책임지는 프레임워크
- 인증/ 인가 차이 - 순서 이해
- 웹에서 요청이 오면 controller 전에 어디를 지나는지, 앞단의 필터 체인 유의
- 요청은 바로 컨트롤러로 가지 않음. 서블릿 필터 체인 통과하고 보안 검사함
- 필터 구조는 크게 3가지 부품, delegating Filter proxy(스프링과 서블릿 컨테이너를 잇는 다리) FilterChainproxy (요청에 맞는 보안 체인 골라주는 라우터), securityFilterChain(보안 필터들의 집합)
- 인증한 사용자 정보는 시큐리티 컨텍스트 홀더에서 다룸
- 로그인 인증은 컨트롤러가 아니라 security filter 단계에서 끝난다.
- 로그인 한 번은 한 객체가 다 처리하지 않고 여러 부품이 책임을 나눠서 맡음. 요청을 가로채는 필터, 일을 배분하는 매니저, ,등등
- 이 과정의 결과물은 Authentication 이라는 인증 정보 담는 곳이 있음. 인증되면 Security context에 담김
- 인가는 인증이 끝난 뒤에 시작함
- 시큐리티 컨텍스트에 들어있는 Authentication을 전제로 권한을 따지는 단계
- Authorization Filter - 흐름만 제어
- AuthorizationManager - 요청정보와 Authentication 설정 규칙 비교해서 판단 내림
    - 허용되면 controller, 실패하면 AccessDeniedException,
