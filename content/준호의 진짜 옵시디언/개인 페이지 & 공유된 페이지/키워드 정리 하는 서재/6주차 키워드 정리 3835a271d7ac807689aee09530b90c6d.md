    ## 키워드
    
    **ORM**

    - 객체-관계 패러다임 불일치
    - 영속성(Persistence)
    
    **JPA** 
    
    - JPA (자바 진영의 표준 ORM 인터페이스)
    - JPA · Hibernate · JDBC 계층 구조
        - JDBC (Java Database Connectivity)

    **Entity**

    - 무분별한 @Setter 지양

    - 자연키(Natural Key) vs 대체키(Surrogate Key)
    - (선택) 복합 키 (@IdClass, @EmbeddedId)
    
    **기본 키 생성 전략** 
    
    - @GeneratedValue
    - IDENTITY 전략
        - AUTO_INCREMENT

    ORM / JPA
    
    1. ORM이 무엇인지 설명하고, 객체 지향 언어와 관계형 데이터베이스 사이의 ‘패러다임 불일치’가 구체적으로 어떤 부분에서 발생하는지 설명해주세요.
        1. 객체를 테이블로 이동하는데에서는 패러다임 불일치가 난다. 자바에서는 데이터를 객체로, DB에서는 테이블과 행, 열로 다루기 때문에 호환성에 문제가 있어. ORM과 같이 연관 관계 매핑 기술을 사용한다.- 객체의 참조와 DB의 외래키 차이도 있음
    2. JPA와 Hibernate의 관계를 설명해주세요.
        1. JPA를 구현하는 대표적인 구현체가 Hibernate이다.
    3. JPA를 사용하면 JDBC를 직접 다루던 방식과 비교해 어떤 점이 좋아지는지 설명해주세요.
        1. 일단은 반복적인 SQL 커리 작업이 사라져 개발자가 객체지향 비즈니스적 설계에 집중 할 수 있다. 더티체킹 등..
    4. JPA가 제공하는 1차 캐시가 무엇이고, 같은 트랜잭션 안에서 동일한 데이터를 두 번 조회할 때 어떻게 동작하는지 설명해주세요.
        1. JPA안에 영속성 컨텍스트가 1차 캐시 메모리 공간을 만들고 같은 트랜잭션 내에 한번 조회한 데이터는 1차 캐시에 보관해 뒀다가 동일한 데이터를 조회하게 되면 1차 캐시 내부에서 꺼내서 반환한다.
    
    **Entity · @Id (엔티티 매핑 기초)**
    
    1. @Entity 클래스가 지켜야 하는 규칙(기본 생성자, final 제약 등)을 설명해주세요.
        1. 기본 생성자는 필수로 작성해야하고, final등을 사용하지 말아야 한다. 프록시가 부모 객체를 상속받지 못하기에.
    2. JPA(Hibernate)가 DB에서 읽어온 데이터를 엔티티 객체로 만들 때 사용하는 자바 기술은 무엇이며, 그 때문에 엔티티에 매개변수 없는 기본 생성자가 반드시 필요한 이유를 설명해주세요. 또 기본 생성자를 public이 아닌 protected로 두는 것을 권장하는 이유는 무엇인가요?
        1. DB에서 읽어온 데이터를 동적으로 객체로 만들때 사용하는 기술은 Reflection 이고 기본 생성자가 있어야 빈껍데기 호출 가능, 기본 생성자는 아무곳에서나 생성되지 않도록 protected를 권장한다. private는 프록시 생성이 안돼서 아예 예외
    3. 엔티티 클래스에 무분별하게 @Setter를 열어두면 어떤 문제가 생기는지 설명하고, 상태를 변경할 때 대신 사용해야 하는 방식을 설명해주세요.
        1. 객체의 일관성이 깨짐, 도메인 규칙을 우회 할 수도 있고, 변경 의도를 알기 어려움.. 양방향 연관관게의 객체 상태가 깨질 수 있음. 그리고 무엇보다 JPA의 더티체킹으로 예상치 못한 UPDATE가 나갈 수 있다.
    4. @Id가 무엇이고, JPA가 엔티티를 영속성 컨텍스트에서 관리하기 위해 식별자가 반드시 필요한 이유를 설명해주세요.
        1. 결국 엔티티 객체를 관리하는 주요 키가 있어야한다 DB로 따지면 기본 키. 빠르게 식별하기 위해서
    5. 실무에서 이메일·전화번호 같은 자연키 대신 의미 없는 대체키를 @Id로 사용해야 하는 가장 큰 이유를 설명하고, 기본 키 타입으로 int·Integer가 아닌 Long을 사용하는 것이 안전한 이유도 함께 설명해주세요.
        1. 결국 정책이 바뀌면 자연키들은 언제든지 바뀔 수 있기 때문. 이러한 일이 일어나면 비용적인 측면에서도 많이 손해다. 그래서 아에 불변하는 의미없는 대체키를 사용함.
        2. Long도 결국 사용자가 늘어나면 int로 감당이 안될 수 있기 때문.
    
    **기본 키 생성 전략**
    
    1. @GeneratedValue의 키 생성 전략 4가지(IDENTITY, SEQUENCE, TABLE, AUTO)의 동작 방식과 차이를 설명해주세요.
        1. IDENTITY는 기본키 생성을 아예 DB에 맡기는 방법이다. mysql의 auto_increment가 여기에 해당됨. squence는 db 시쿼스를 이용해서 기본 키 값을 먼저 얻고, 그 값을 엔티티에 넣은 뒤 반환하는 전략.
    2. IDENTITY 전략을 사용할 때 em.persist()를 호출하면 INSERT 쿼리가 언제 실행되며, 그 이유는 무엇인지 설명해주세요.
        1. IDENTITY 전략은 DB에서 기본키를 ㄱ가져오는 것이기 떄문에 Insert쿼리가 바로 실행된다.
    3. SEQUENCE 전략의 allocationSize 옵션이 DB와의 네트워크 통신을 줄여 성능을 최적화하는 원리를 설명해주세요.
        1. 매번 sqeunce 값을 가져오지 않고 일정개수만큼 미리 땡겨와 받아와 할당하는 방식이다.
    
    **영속성 컨텍스트**
    
    1. 영속성 컨텍스트가 무엇인지 설명해주세요.
        1. 영속성 컨텍스트는 JPA가 관리하는 저장소이다.
    2. 엔티티 생명주기 4가지 상태(비영속·영속·준영속·삭제)를 설명하고, 각 상태로 전이되는 시점을 설명해주세요.
        1. 영속 상태는 컨텍스트 안에서 관리되는 상태, 비영속은 아닌 상태, 준영속은 영속 상태엿다가 벗어난 상태이다.
    3. em.find()로 같은 ID의 엔티티를 두 번 조회하면 SELECT 쿼리가 몇 번 나가고, 두 결과를 ==로 비교하면 어떻게 되는지, 그 이유와 함께 설명해주세요.
        1. 1차 캐시 때문에 select 쿼리는 한번만 나간다 그리고 동등하게 비교해도 true, 동등성을 보장하기 때문에 같다. 
    4. 쓰기 지연(Write-Behind)이 무엇이고, persist() 호출 시점과 실제 INSERT가 실행되는 시점(플러시/커밋)이 어떻게 다른지, 그리고 굳이 쿼리를 모아서 보내는 이유를 설명해주세요.
        1. 말 그대로 Db에 바로 쿼리를 보내지 않고 모아두앗다가 하는거임, 커밋과 플러시 하면 바로 보내지는것은 맞지만 롤백의 차이에서 다름. 굳이 모아서 보내는건 통신 줄여서 성능 확보 
    5. update 메서드를 호출하지 않아도 엔티티 값만 변경하면 DB에 반영되는 메커니즘의 이름은 무엇이며, 스냅샷을 이용해 어떻게 동작하는지 설명해주세요.
    
    **Transaction**
    
    1. JPA에서 트랜잭션이 무엇이고, 영속성 컨텍스트에 모인 변경 내용이 커밋과 롤백 시점에 각각 어떻게 처리되는지 설명해주세요.
    2. @Transactional을 메서드에 선언할 때와 클래스에 선언할 때의 차이를 설명해주세요.
    3. 스프링 부트 테스트에서 @Transactional을 붙이면 DB에 데이터가 남지 않는 이유와, 데이터를 실제로 남기려면 무엇을 추가해야 하는지 설명해주세요.
    4. @Transactional(readOnly = true)가 무엇이고, 조회 작업에서 어떤 이점을 주는지 설명해주세요.
    
    ### 심화
    
    1. IDENTITY 전략이 쓰기 지연(Batch Insert)을 사용할 수 없는 이유를, 1차 캐시가 PK를 Key로 사용해 엔티티를 저장한다는 점과 연결지어 설명하고, MySQL에서 대량 데이터를 삽입해야 할 때 어떻게 대처할 수 있는지 설명해주세요.
    2. 분산 환경(MSA·샤딩)에서 AUTO_INCREMENT 기반 키가 충돌할 수 있는 이유를 설명하고, UUID가 이를 어떻게 해결하는지, 그리고 랜덤 UUID(v4)를 PK로 쓸 때 인덱스 성능에 어떤 단점이 생기는지 설명해주세요.
    3. 변경 감지가 기본적으로 변경되지 않은 컬럼까지 포함해 모든 필드를 UPDATE하는 이유를 설명하고, @DynamicUpdate를 적용하면 동작이 어떻게 달라지는지와 그 트레이드오프를 설명해주세요.
    4. 1차 캐시가 ‘전역 캐시’가 아니라는 말의 의미를 트랜잭션 생명주기 관점에서 설명하고, 애플리케이션 전체에서 캐시를 공유하려면 무엇(2차 캐시·외부 캐시)을 사용해야 하는지 설명해주세요.
    5. 엔티티 클래스나 필드에 final을 사용하면 안 되는 이유를, JPA의 프록시(지연 로딩) 생성 방식 및 리플렉션을 이용한 필드 주입 과정과 연결지어 설명해주세요.
    6. OSIV(Open Session In View)를 켰을 때와 껐을 때 영속성 컨텍스트·DB 커넥션의 생명주기가 어떻게 달라지는지 설명하고, 트래픽이 많은 환경에서 OSIV의 단점과 LazyInitializationException에 대한 대처 방법을 설명해주세요.

    ## 키워드
    
    - 연관관계 매핑
        - 객체 참조 vs 외래 키(FK) 패러다임 차이
        - 객체 그래프 탐색
    - @ManyToOne
        - 연관관계의 주인(Owner)
        - 단방향 매핑 (N → 1 참조만 존재)
        - 양방향 매핑 (N ↔ 1 상호 참조)
    - Fetch 전략
        - 지연 로딩(LAZY)
        - 즉시 로딩(EAGER)
        - Fetch 전략 기본값
    - N+1 문제
        - EAGER로 인해 강제로 터지는 N+1
        - LAZY 상태에서 프록시 초기화로 발생하는 N+1
        - (이후 학습) fetch join, @EntityGraph로 해결
    - @OneToMany
        - 컬렉션(List/Set)으로 1:N 표현
        - mappedBy (다대일 양방향에서 1쪽에 선언)
        - 1:N 단방향 매핑의 한계
    - Cascade (영속성 전이)
        - CascadeType.PERSIST / REMOVE / ALL
    - Orphan Removal
        - CascadeType.ALL + orphanRemoval=true 세트 (강한 종속)
    - @OneToOne
        - 외래 키 위치에 따른 3가지 구조
            - 주 테이블에 FK (단방향)
            - 주 테이블에 FK (양방향, 권장)
            - 대상 테이블에 FK (양방향)
        - 대상 테이블 FK의 지연 로딩(LAZY) 제약
            - 주 테이블만으로는 연관 존재 여부(null) 판단 불가 → 프록시 대신 강제 조회
            - LAZY 설정이 무시되고 EAGER처럼 동작 → N+1
    - Proxy
        - 내부에 식별자(ID)만 보유
        - 프록시 초기화(Initialize)
            - 실제 데이터(getNickname 등) 접근 시 영속성 컨텍스트 통해 DB 조회
            - getId()는 쿼리 미발생 (이미 식별자를 들고 있음)
        - 타입 비교 주의사항
            - 프록시 클래스명 (User$HibernateProxy$xxxx)
            - == / getClass() 비교 금지 → instanceof 사용
        - LazyInitializationException
            - 준영속 상태(영속성 컨텍스트 종료 / detach / clear)에서 프록시 초기화 시도 시 발생
    - JPQL
        - DB에 맞춰 SQL로 번역 → DB 독립성
        - 벌크 연산 (UPDATE / DELETE)
        - 다른 기술과의 비교
            - Criteria API
            - QueryDSL
            - Native SQ
