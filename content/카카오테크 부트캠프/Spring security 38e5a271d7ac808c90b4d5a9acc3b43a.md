# Spring security

정의 : 인증 인가를 포함한 보안 기능 처리하는 프레임 워크

HTTP의 stateless 한 특성으로 인해 서버가 클라이언트를 기억하지 못하기 때문에 인증과 인가의 절차가 필요함

HTTP 요청 오면 서블릿 컨테이너가 먼저 가로챔 (tom cat )—> 컨테이너에서 서블릿 필터 체인을 거침 → DI나 bean 기능 사용이 안됨 → delegating filter proxy 사용해서 스프링과 연동 → 필터 체인 프록시에서 → Spring Security filter 에서 매니저가 provider에게 정보 요청 → 시큐리티 필터 체인에서 요청에 맞는 필터 적용, → 다 통과하면 시큐리티 컨텍스트로 Authentication 객체로 정보 저장

이렇게 인증이 끝나면 인가로.. 

똑같이 흘러가는데 

인가 필터가 요처을 가로채고, 인가 매니저가 요청 URL에 따라서 규칙에 맞는 권한을 가지고 잇는지 확인 요청 →

확인되면 isGranted() 같은 boolean 메소드 true나 false로 바뀜.

인가의 방법에는 URL, 메소드 기반이 있음.

필터와 인터셉트와 aop는 발생시점? 인증 적용 시점이 달라서 용도가 다를 수 있다.

전역적인 보안 관리는 필터, 핸들러의 정보가 필요하면 인터셉트, 메소드 단위의 검증은 aop.

모두 각각의 장단점이 있음.

# Cors

sop(표준 원칙)를 만족하면서 서로 다른 출처의 리소스를 접근하는 걸 허용하게 해주는 방법이다.

서로 다른 출처란?

- 프로토콜, 호스트, 포트 중 하나라도 다른 것.

과제 할 때 vscode로 만든 liveserver와 백엔드 api의 호출이 달라서 생기는 문제와도 연결

127.0.0.5000과 [localhost:8080](http://localhost:8080) 이런것 과의 연결을 위함.

서로 다른 출처의 리소슷 접근하기 위해서는 서버에서 다른 출처를 허용 시키고 그것을 사용할지 말지는 브라우저가 판단을 함.

사용 이유 :

브라우저의 동일 출처 정책을 완화해서 웹 어플리케이션 구조를 가능하게끔 함. (Ex. SPA, React)

동작 방식 :

### 1. 단순 요청

조건을 만족 할 때 단순 요청.

1. 첫번 째로 get, post, head와 같은 메소드 일 것. (위험도가 낮다는 뜻.)
2. Contenttype이 multipar/form-data, text/plain, www-form-urlencoded 중 하나 일 것.
3. 기본 헤더만 포함.

말 그대로 단순 요청. 브라우저에서 바로 서버로 요청 하는 것임. 브라우저에서 서버에 요청, 서버가 응답을 하고, 서버에 cors 허용 코드가 있는지 확인, 있으면 브라우저에서 리소스 사용.

### 2. 예비 요청

조건을 만족하지 않으면 모두 예비 요청

1. contentType이 application.json 파일로 받는다거나..
2. put, delete 같이 위험한 메소드 일때,

말 그대로 예비 요청. 브라우저가 서버에 OPTIONS 요청을 보내고 서버가 cors를 확인해 허락 하는 응답을 하면, 브라우저가 진짜 요청을 보냄 , 그리고 서버가 진짜 응답을 함.

- 허락하는 메소드는 Access - controll - allow - origin(header, method 등등 바뀔 수 있음)

# CSRF (cross site request forgery)

사이트 허위 탈취 공격 기법..

만약 어떤 사이트에 내가 로그인 되어 있고 쿠키 기반 인증이라고 하면 그 사이트에 요청을 보낼때마다 내가 맞다는 쿠키를 함께 실어 보냄. → 이걸 악용한 방법

다른 사이트에서 그 사이트에 http 요청을 보내는 url을 만들면 당할 수 밖에 없음..

해결 법 : CSRF 토큰 발행.

즉, 요청을 할때 브라우저와 서버가 각각 토큰을 가지고 있고 요청을 할 때 그 토큰을 비교해서 요청을 처리한다.

SOP로 인해 각각의 사이트 끼리는 토큰을 복제 할 수 없음.

기본 default는 CSRF가 켜져있고 만약 쿠키가 아닌 다른 방법, JWT를 쿠키가 아닌 athurization헤더 등을 통한다면 꺼도 됨, 즉 토큰의 종류가 아닌 토큰을 어디에다가 저장하느냐가 관건.

한줄 요약 : spring security에는 인증과 인가의 방식이 있는데 인증, 그 후에 인가의 방식 순서이다. 먼저 인증은 서블릿에서부터 시작해 spring의 security 필터까지 오고 인증에 성공하면 authentication 이라는 객체로 security context에 담기게 됨. 그 후에 인가의 절차를 시작하는데 인가의 절차는 거시적인 방법인 URL 방식과 미시적 방법인 메소드 기반의 방식이 있음.

CORS는 sop를 만족하면서 다른 출처의 리소스 접근을 허용 해주는 것, 허용 여부를 서버에서 관리하고 요청 판단은 브라우저에서 함. 단순 요청과 예비 요청이있음, CSRF는 쿠키를 사용할 때 나타나는 공격 방식인데, 기본으로 켜져 있고 쿠키를 사용하지 않으면 꺼도 된다. 유의점은 토큰의 종류가 아닌 전송 방식에 따라 CSRF 토큰을 활성화하거나 비활성화 할 것.
