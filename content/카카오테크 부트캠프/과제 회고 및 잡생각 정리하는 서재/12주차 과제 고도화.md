## 2. 영화 상세 조회.

먼저 movieResponse 는 처음부터 가져올 movie 엔티티의 내용을 모두 포함 할 수 있게 만들었다.

11주차의 피드백을 포함해서 class가 아닌 record로, 

사실 영화 데이터 가져오면서 가장 걱정했던건 Actors 배열이었다.

영화 하나에 배우들이 여러 명 있으며, 이것을 어떻게 저장해야 할지. 따로 entity를 만들어 movie와 일대다 관계를 만들지, 고민 하다가 elementCollection내용이 적절해 보여서 선택했다.

moive엔티티 안에 리스트와 같은 형태를 넣을때 적절한 것으로, JPA가 별도의 테이블을 사용해서 값을 보여준다.

@CollentionTable과 같이 사용하며, 컬렉션 테이블은 매핑할 테이블을 지정할 때 사용한다.

elementCollection을 사용한 정확한 이유는, 일단 actor를 별도의 id로 저장할 필요가 없다는 것.(독립된 데이터로 보지 않겠다는 의미), 그리고 생명주기 관리의 편의성 (movie id에 종속되어 있으므로 영속성 전이와 고아 객체를 제거 기능을 가진다는 편의성), 기존적으로 elementCollection은 지연 로딩으로, 데이터를 바로 불러오지 않는 다는 점에서 지금의 actor 정의와 어울리는거 같아 선택했다.

만약에 내가 배우 프로필를 따로 제공하거나, 배우 관련 기능들을 제공한다고 하면 일대다의 독립된 엔티티를 만드는 것이 맞는것 같다.

- 주의점으로는 elementCollection으로 정의된 리스트는 일부 수정이 되는 것이 아닌, 전체를 지우고 다시 값을 집어넣어야 사이드 이펙트가 발생하지 않는다는 주의점이 있다.

그리고, actor같은 경우는 movie resposne에서 movie 엔티티를 가져오고, 그 리스트를 List.copyOf()로 두었는데,

다른 postResponse의attach나 postlike 같은 경우는 왜 List.copyOf()로 두지 않았냐면, 그것들은 값들이 변하기 때문.. 수정 등..

## 5. 리뷰 목록 검색 엔진 구현

먼저 Elastic Search 를 적용하기 위해서는 기존의 title이나 content 같은 내용들을 별도의 json 문서로 정리해 elastic document로 정리해줘야 했다. 

elastic document는 Nori 분석기 활용을 위해 별도의 index설정이 필요하므로 spring에서 자동으로 생성해주는 인덱스가 필요 없다. → create Index = false로,

그 외 title이나 content를 제외한 like나 countComment 등 같은 내용은 id로 RDS로 가져오면 되므로, Post에서 필요한 정보만 elastic Search 문서로 가져오는 단계이다.

다음. PostSearchRepository를 만들어 ElasticSearch를 사용해 만든 PostSearchDocument를 삭제하고, 저장하는 역할의 Repository를 만든다. (기존에 만들어 놓은 글들 마이그레이션 용도)

그 후 ElasticSearch에서 검색한 후 게시글 ID를 반환하게 하고.

RDS에서 해당 ID를 찾아 실제 게시글의 상세 정보를 보여주는 findAllByIdsWithDetails 쿼리를 PostRepository에 작성한다. 그 후 postLike와 commentCount를 결합 해 PostListResponse 페이지로 반환하는 PostSearchService를 작성한다.

그 후 Postcontroller에서 front에서 request로 넘긴 keyword와 함께 service로 전달하는 작업 후, 기존의 RDS에 있던 내용을 search 후 , List로 넘겨주면 된다.

Elastic Search는 검색용 문서를 따로 보관해야하기 때문에 일단 Post의 crud작업과 동기화를 해줘야겠다.

spring event발행을 통해서, repository.save()이후에 바로 elastic Searcg 문서 동기화 작업이 아닌,

transaction commit이후에 이벤트를 발행하도록 하였다.

검색어 같은 경우에는 NotBlank같은 경우도 고려했지만, 사용자의 실수에 하나하나 오류를 띄우기 보다는,  front에서 이미 keyword가 없을 경우에는 기존의 /posts를 띄워주게 되어 있고 프론트에 의지 하지 않고 누군가가 /posts/search?keyword= 에는 Service 단계에서 validateKeyword가 null일때의 오류를 띄우도록 하여 ux도 고려했다.

## 6. DTO projection을 통한 검색 쿼리 향상.

기존의 postListResponse를 보면, findAll을 통해서 Attach 를 가져왔다, 그 중에서 첫번째 first를 가져와서 썸네일 url로 저장하던 원리 였는데, 그러다 보니 post마다 모든 attach 목록을 가져오는 불편함이 있었다. attach가 lazy로 batch size를 설정해놨기 때문에 어느정도 감수는 되었지만, 성능 향상을 위해서 post 에 첨부된 attach 중에서 id가 가장 적은 (가장 먼저 등록 된 attach)를 검색 하도록 하는 응답 DTO projection을 추가했다.

이 생각을 가장 먼저 떠올린건 ES document에 RDS와 같은 문서를 올릴 때다. ES 검색 문서에는 사실 attach url이나 이미지가 필요가 없는데 굳이 post 전체를 갖다 붙히는게 손실인 것 같았다.

먼저 , PostListProjection을 만들고, attachThumbnailProjection을 만들어서 첨부 파일용과 그 외 나머지의 projection을 조합해 PostListResponse 를 만들면 되지 않을 까 싶었다. 

## 7.  영화 목록 검색 기능

영화 목록은 게시글에서의 검색과는 다르게 제목에만 Mysql like를 도입했다. 영화 목록의 검색 목적은 영화 정보를 찾기 위해서 이기 때문에, 고유 명사의 단어 검색을 의식해서 ES를 굳이 도입하지 않았다.

영화 제목은 정확성이 중요하므로, 정확한 키워드에 정확하고 빠른 결과가 나와야 한다는 근거가 있었다.

- 일단 %검색어% 검색 보다는 검색어% 로 B-tree 인덱스를 적용했다.

## 전체적으로 느낀 점

페이지 네이션과 여러 조회 정책을 도입하면서 관심사 분리 SoC 가 필요한 이유를 다시 한번 알게 되었다.

지금이야 page를 post는 10건, movie는 9건, comment는 20건 이렇게 세군데에서만 다루지만 나중가서 api가 더 많아지고 dto가 더 늘어 나면 이러한 정책을 한곳에서 정리하고, 수정 할 수 있다는 편리성을 깨달았다.

ES를 배우면서 느낀 점은 사실 외부 api 형태로 진행되는 줄 몰랐다. es를 구현하는 오픈소스나 이런게 있는 줄 알았으나, EC2에 Es docker container를 설치하고, 검색용 문서를 따로 만들어 뱉어내는 과정이었다.

그리고 기존 RDS에서 검색어를 찾는게 아닌 ES만의 인덱스에 문서 형태로 저장한 후, Lucene가 필드를 분석해 역색인을 만들어 저장하는 것을 알게 되었다.

즉, 그래서 RDS와의 데이터 동기화가 필수였고, RDS에 데이터가 올라가는 Repository.save()와 동시에 ES를 호출하는 것보다는 commit이후의 이벤트 형식이 맞다는 생각을 하게 되었다. 규모가 커지고 사용자가 많아지면 이렇게 DB 트랜잭션과 Elastic search 갱신을 하나의 흐름으로 잡기 어렵기 때문에, 메시지 큐나 kafka 같은 기술을 사용한다는 것도 알게 되었다.
