# 4주차 과제 회고

중간에 값들을 다른 클래스에서 얻기 위해 getId 등등을 직접 선언했는데 @Getter의 기능을 알게 되고 유용하게 사용한 것 같다. (사용 방법을 알아보다가 OOP에서는 getter와 setter의 값을 지양해야 한다는 글을 봤다. 캡슐화의 의미가 약간 무색해지는 것 같다는 생각이 들었다. 어떻게 좋고, 어떻게 나쁜지는 알았는데 어떤 상황에서 좋고 나쁜지는 아직 판단이 안서는 것 같다)

게시글 수정을 Patch로 설정해서 원하는 값(title, content, imageUrl)만 Body로 넣어서 수정이 가능하게 하고 싶었는데 잘 되지 않았다. 정형화된 PostRequest 파일 대신에 UpdatePostRequest 파일을 만들기도 해봤는데 어떤 값이 바뀔지 알고 타입을 넣는게 말이 안되는 것 같아 중단했다. (PUT같은 경우는 그냥 PostRequest 사용하면 될 것 같은데 Patch 같은 경우에는 어떻게 하나요?)

처음에는 Controller에서 Request를 Service 계층으로 넘기고 돌아오는 Response만을 찍었는데 성공 여부를 알기 위해서 공통되는 부분인 CommonResponse를 추가했다. 이 과정에서 <T> 제너릭이 생각이 나서 적용해봤는데 잘 작동해서 매우 뿌듯했다. (사실 이 부분이 AOP 개념이랑 비슷한 것 같은데 AOP는 @aspect 어노테이션을 붙여서 사용하는 것으로 알고 있습니다. 이렇게 따로 Common DTO를 만드는 것이 AOP 개념으로 봐도 되는 것일까요? 아무리 봐도 프록시가 가짜 객체를 생성하는 AOP와는 달라 보이는데 제가 한 방법도 편리해 보이기는 합니다. 단점이 있다면 말해주세요!)

지난 주차 피드백에서 오류 상태 코드에 대한 피드백을 받았는데 어떤 오류 상태 코드가 어떤 상황에 나타나는지 모르고, 앞자리만 확인 했던거 같아 이번 기회에 잘 알아보고 적용해보려 했습니다. Get이 성공했을때는 200, Post면 201 등 여러 상태 코드의 구분 방법은 알았으나 적용까지의 시간이 없어 어떤 식으로 코드가 짜여지는지 확인하기 위해 Ai에게 예시 코드를 물어봤습니다. 그 결과로 Spring내부의 httpstatus 클래스를 import하여 사용하라고 하던데 이거 혹시 실무에서도 만능인지 궁금합니다.

로그아웃 구현도 안되어있고 조회수, 그리고 이미 구현된 부분에도 부족한 부분이 스스로 느끼기에도 많은 것 같습니다. 그리고 이번 과제는 특히나 끝이 없는 과제 같습니다. 이제 5주차 수업이 나가고 앞으로 5주차 과제를 해야하는데 이번 4주차 과제는 여기서 마무리 하는게 맞는지 궁금합니다. 이번 주 부터 개인 프로젝트의 시작점으로 알고 있는데 그럼 나중에 더 수정, 추가 할 기회가 있는지, 과제 피드백 내용만 잘 생각해보고 숙지하면 되는 것인지 궁금합니다.
