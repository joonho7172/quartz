# 과제 기능 구현 검색 엔진

먼저 각각의 성능을 비교하기 전에 기준이 되는 검색어를 정하였다.

검색어 1. 공포 영화 (공포 + 영화의 합성어)

검색어 2. 배우 연기가 좋은 영화 (조사와 띄어쓰기가 포함되어 있는 자연어)

검색어 3. 영화 (하나의 단어로 많은 데이터를 얼마나 효율적으로 검색해내는지 확인하기 위함)

# 기존 LIKE에 인덱싱 적용

![image.png](content/카카오테크%20부트캠프/과제%20회고%20및%20잡생각%20정리하는%20서재/과제%20기능%20구현%20검색%20엔진/image%2011.png)

제목과 내용은 5000자 제한이기 때문에 1000자에만 인덱싱을 적용해본다. (사진에는 191이지만 실제를 1000자로 진행함)

50만 건의 진행에서는,

| 검색 방식 | 실행 경로 | 검사한 행 | 실행 시간 |
| --- | --- | --- | --- |
| `LIKE 'NSMC review #1%'` | **Covering index range scan** | 56,809 | **32.4ms** |
| `LIKE '%NSMC review #1%'` | **Covering index full scan** | 500,000 | **169ms** |

B-tree 기반 접두어 검색 성능으로 index를 적용하여 “영화” 키워드를 검색 한 결과, 범위 검색으로 성능이 향상 되긴 했지만, 중간 문자열 검색에서는 여전히 50만개의 행을 다 검사하며 실행시간도 유의미하게 변하지 않았다.

# 또 다른 대안. MongoDB (NoSQL)

https://liltdevs.tistory.com/213

`MongoDB`는 데이터를 데이터를 `JSON-like documents`로 저장하는 NoSQL 데이터베이스이다.

MongoDB 같은 NoSQL은 JSON(BSON) 형태의 유연한 문서 구조를 사용하며, 데이터마다 필드가 달라도 한 문서 안에 계층적으로 담아 한 번에 검색할 수 있다는 이점이 있다. 즉, 비정형된 문서 데이터 검색에 강하다는 결론 하나로 실험을 해볼 가치는 충분 했다.

기존의 MySQL에 있던 데이터를 MongoDB로 복사 한 뒤, 검색 성능을 확인하기 위한 함수를 생성하고,

```java
workapi_benchmark> function measure(collectionName, keyword) {
|   var collection = db.getCollection(collectionName);
| 
|   var filter = {
|     $or: [
|       { title: { $regex: keyword } },
|       { content: { $regex: keyword } }
|     ]
|   };
| 
|   // 워밍업
|   collection.countDocuments(filter);
| 
|   collection
|     .find(filter)
|     .sort({ createTime: -1, _id: -1 })
|     .limit(10)
|     .toArray();
| 
|   // COUNT 측정
|   var startedAt = Date.now();
|   var resultCount = collection.countDocuments(filter);
|   var countElapsedMs = Date.now() - startedAt;
| 
|   // 목록 측정
|   var plan = collection
|     .find(filter)
|     .sort({ createTime: -1, _id: -1 })
|     .limit(10)
|     .explain("executionStats");
| 
|   printjson({
|     collection: collectionName,
|     keyword: keyword,
|     resultCount: resultCount,
|     countElapsedMs: countElapsedMs,
|     listExecutionTimeMs: plan.executionStats.executionTimeMillis,
|     totalDocsExamined: plan.executionStats.totalDocsExamined,
|     totalKeysExamined: plan.executionStats.totalKeysExamined
|   });
| }
```

MySQL의 LIKE %%와 같이 MongoDB의 $regex를 사용해서 측정을 했다. 첫 실행에서만 발생하는 준비 비용을 제외하기 위한, 각자의 워밍업 후에 키워들의 값들을 측정했다.

# 마지막 대안 : Elastic search

https://trends.builtwith.com/operations/Elasticsearch

결국 또 다른 대안이 없을까 찾아보던 중, BuiltWith 기준으로 현재 가장 많이 사용되고 있는 검색엔진은,

Elastic Search 와, OpenSearch , MeiliSearch 가 있었다. 

MeiliSearch는 간단하고 구현이 쉬워 스타트업에서 많이 사용하는 검색 엔진이다. 다만, 한국어 형태소 분석 기능이 없어 한국어의 자연어 기반의 검색에는 약하다는 단점이 있다.

Elastic Search는 Nori라는 한국어 형태소 분석기를 공식적으로 지원한다.

커뮤니티에서 검색 기능은 사실 속도 보다 품질이 더 중요도가 높다고 생각하기에, 이 점은 상당히 매력적이었다.

예를 들면, “마동석이 출연한 액션 영화”라는 문장이 있으면 단순 공백 기준, “마동석이” “출연한” “액션” “영화”가 되겠지만, Nori를 사용하면, “마동석” “출연” “액션” “영화” 와 같이 의미 있는 단어를 추출해 검색해 준다.

OpenSearch는 AWS가 포크해서 만든 검색 엔진으로 AWS가 자동으로 관리해주는 Elastic Search서비스라고 볼 수 있다. 그러나 이번에는 학습을 위해서 OpenSearch 대신 Elastic Search를 사용했다.

두 방식 모두 앞에 와일드 카드가 있으므로 전체 데이터를 검사했다.

- MySQL 같은 경우는 LIKE %검색어%로 Table Scan을 하고
- MongoDB 같은 경우는 $regex: 검색어로 COLL Scan을 했다.
- 문서가 JSON 형태라는 이유만으로 NoSQL이 MySQL보다 빠르진 않았다.

## B-tree 인덱스 실험

| DB | 검색어 | 목록 인덱스 전 | 목록 인덱스 후 | 변화 | COUNT 전 | COUNT 후 | 결과 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| MySQL | 영화 | 207ms | 324ms | 1.57배 느림 | 199ms | 202ms | 개선 없음 |
| MongoDB | 영화 | 444ms | 815ms | 1.84배 느림 | 348ms | 381ms | 더 느려짐 |
| MongoDB | 공포 영화 | 407ms | 630ms | 1.55배 느림 | 340ms | 349ms | 더 느려짐 |
| MongoDB | 배우 연기가 좋은 영화 | 441ms | 657ms | 1.49배 느림 | 378ms | 378ms | 목록만 느려짐 |

인덱스가 문제 였는지 MySQL과 MongoDB에도 각자 인덱스를 적용해서 실험해 봤다.

MySQL은 여전히 Table Scan을 하고, MongoDB도 역시 모든 인덱스에서 key검사를 하여,

 %검색어%에는 도움이 되지 않았고 오히려 조회가 느려졌다.

검색 패턴에 따른 차이도 함께 보았다.

| 검색 조건 | 결과 수 | COUNT 시간 | 실행 방식 |
| --- | --- | --- | --- |
| `title LIKE 'NSMC review #1%'` | 56,809 | 32.4ms | `Index Range Scan` |
| `title LIKE '%NSMC review #1%'` | 56,809 | 155ms | `Full Index Scan` |

예상과 같이 B-tree 인덱스는 검색어% 와 같은 index Range Scan은 약 5배 빨랐지만,

%검색어% 같은 경우에는 전체 테이블과 인덱스를 탐색 해야 하므로, 인덱스 적용 효과가 없었다.
