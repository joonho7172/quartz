**Rest Api**

정의 : 상태를 표현해서 전송하는데 JSON이나 XML 같은 표현적인 데이터 형식으로 만들어서 전송함 -> 자원의 상태를 특정 형식으로 표현

REST는 소프트웨어 아키텍쳐 스타일 중 하나이다.

REST와 REST API는 어떤 차이가 있나?

- > REST는 일종의 설계 철학, 가이드 라인. 특정 기술이나 언어, 프레임 워크 아님.

**Rest의 아키텍쳐 스타일**

- Uniform Interface
    - 모든 자원에 접근하는 방식을 통일 하자.
    - /users 는 사용자 목록 /posts 게시글 목록 -> 개발자의 생각 시간을 줄임
- Client - Server (클라이언트 - 서버 구조)
    - 화면을 담당하는 클라이언트랑 데이터 저장이나 비즈니스 로직 처리하는 서버의 역할을 명확하게 분리하자.
- Stateless(무상태성)
    - 서버가 클라이언트 이전 요청 상태를 기억해서는 안된다.
    - 서버가 상태를 관리할 필요가 없어 서버를 수평적 확장에 유리함.
- Cacheable(캐시 가능)
    - 서버가 보내는 응답에는 클라이언트가 캐시를 저장해도 되는지 여부를 명시해야함.
    - 캐시가 저장되면 굳이 서버까지 안가도 되어서 응답속도가 빨라지고 서버 부하 줄어들음.
- Layered System
    - 클라이언트는 로드밸런서, 프록시 서버, 캐시 서버등 여러 층의 서버를 거쳐야함.
    - 클라이언트는 알 필요가 없으니 api주소로 보내먄 됨.
- Self-Descriptiveness
    - API응답 메시지 그 자체만으로 의미를 충분히 이해 할 수 있어야 함.
    - {“age” : 24} -> 데이터의 명확하게 설명하는 키랑 함께 오면 응답만 보고 데이터가 무엇인지 유추 할 수 있음. 여기다가 + 상태 코드

사용 이유 : 개발자 간의 일관된 통신 규칙을 마련해 업무 효율을 높임.

1. URL은 정보의 자원을 표현해야 한다.( 동사대신 명사, 행위를 넣지말자 (getUsers))
2. 행위나 동사는 http 메소드를 이용하자 get, post… 등
3. 슬래시는 계층 관계를 나타날 때 사용함.
4. 소문자로 통일
5. 밑줄 말고 하이픈 사용
6. 확장자(.png, .txt) 사용 하지 않음
7. url의 마지막에 슬래시를 포함하지 말자.(선택)

결론 :

1. 개발자들이 표준 소통하는 방식이 Rest Api
2. Rest가 단순한 기술이 아니라 시스템을 유연하고 확장 가능하게 만들음.

**TCP**

두 개의 호스트를 연결하고 데이터 스트림을 교환하게 해주는 중요한 네트워크 프로토콜

연결 지향형 프로토콜인건 알지?

데이터 스트림 -> 파일을 쪼개서 세그먼트라는 작은 단위로 만들고 각 조각에 번호표를 붙혀 차례대로 전송함 -> 받는 쪽에서 이 번호표를 보고 조각들을 원래 순서대로 재조립해서 복원함.

전송 계층, 4계층에 해당됨. -> 브라우저에 주소 입력하고 엔터 치는 순간 컴퓨터랑 서버 사이에 TCP연결이 맺어짐.

**동작 방식**

1. 연결 설정 (3-way handshake)
    1. 통신의 시작. 서버랑 클라이언트가 세번의 통신을 통해서 서로의 상태를 확인
    2. Syn - 클라이언트가 서버에 보내는 첫번째 메시지. Syn 패킷. 초기 번호 순서가 담겨져있음.
    3. SYn - Ack : 서버가 전송을 받고 다시 클라이언트에게 응답함. SYN - ACK 패킷. “초기번호 잘 받았고 거기서 +1 해서 보내줘. 나는 다른 초기번호로 시작할게”
    4. ACK : 서버에 응답을 보고 다시 응답함. 서버에게 잘 받았고 “다른 초기번호에 +1 해서 다시 보내줘”
2. 데이터 전송
    1. 데이터 스트림 방식으로 주고 받고 큰 데이터 세그먼트로 쪼개고 시퀀스 번호를 붙혀서 보냄
    2. 받는 쪽에서 데이터 재조립 후 완성.
3. 신뢰성 있는 전송
    1. ACK 매커니즘으로 부터 오는 신뢰성
    2. 송신측에서 데이터 보내면 수신측에서는 잘 받았다는 의미의 ack 패킷을 보냄. 일정시간 동안 ack을 받지 못하면 다시 보냄.
4. 흐름 제어, 혼잡 제어
    1. 흐름 제어 : 수신 측이 처리할 수 있는 데이터의 양이 한계가 있음. 버리는 데이터를 막기 위해서 수신측이 본인의 현재 상태를 슬라이딩 윈도우 라는 값에 담아 송신 측에 알려줌
    2. 혼잡 제어 : 흐름제어 1:1 통신에서의 속도 조절. 혼잡 제어는 네트워크 전체 상황을 고려. -> 인터넷 망이 막히기 시작하면 tcp는 속도를 조절함.
5. 연결 종료
    1. 연결 종료 할 때는 4 way handshake 라고 해서 보낼 데이터가 없으니 연결을 끊겠다는 패킷을 주고 받으며 연결을 주고 받는다.

**UDP**

빠르고 간단한 통신을 위해 연결 설정 없이 데이터를 전송하는 네트워크 프로토콜

비연결성 프로토콜인건 알지?

tcp는 세그먼트라면 udp는 데이터 그램이라는 단위로 보냄. 순서 보장 x 그냥 보냄.

장점 : 오버헤드가 적다

**동작 방식**

1. 데이터 그램 전송
    1. 그냥 목적지 찾아감
2. 비신뢰성 및 비연결성
    1. 도착을 보장하지 않고 순서 또한 보장하지 않음.
    2. 재연결도 안함(필요시)
3. 빠른 전송
    1. 접근 방식은 프로토콜 오버헤드를 줄여 네트워크 지연을 최소화함.

**3-way-handshake**

정의 : 네트워크 연결 절차, tcp/ip 네트워크 프로토콜에서 연결을 초기화 하는 과정

신뢰성 : 데이터 보냈을때 중간에 데이터 사라지거나 순서가 뒤바뀌지 않고 목적지에 정확하게 전달 되는 것.

연결 지향성 : 데이터를 보내기 전에 보내는 쪽과 받는 쪽이 서로 준비가 되었는지 확인함.

알아야 하는 이유 :

SYN Flooding -> 공격하는 사람이 첫번째 단계에서 요청하는 sun 요청만 대량으로 보내고 서버가 보내는 sun - ack응답에 대해 마지막 ack를 보내지 않고 잠수를 탐. -> 서버는 요청을 기다리면서 연결을 끊지도 못함.

동작 방식

1. SYN 단계
    1. 클라이언트 -> 서버 : SYN 패킷 (seq = 1000)
    2. 클라이언트가 서버에 접속 시도하는 첫번 째 단계
    3. Syn 패킷을 보낸다.
    4. Syn 플래그 : tcp 헤더에는 여러개의 플래그 (제어 비트) 가 있음.-> 이 패킷은 연결을 요청하는 용도입니다. 고 표시하기 위해서 syn 플래그의 비트를 1로 설정해서 보냄.
    5. 시퀀스 넘버 (seq) : tcp는 데이터 순서 보장한다고 함 -> 세그먼트에 고유한 번호를 붙임 -> 연결 시작 할 때 몇번부터 보낼건지 초기 넘버를 임의의 숫자로 생성해서 보냄.
    6. 여기서 클라이언트 연결 상태가 syn_sent로 바뀜 -> syn 보냈으니 응답 기다리는 중.
2. SYN - ACK 단계
    1. 서버 -> 클라이언트 : syn - ack (seq=2000, ack 1001)
    2. 서버가 syn 패킷을 받으면 접속 허용 가능 상태인지 확인. 문제 없으면 응답 패킷을 클라이언트에게 보냄
    3. Syn 플래그 + ack 플래그 : 연결 준비 됨. 초기 시퀀스 번호를 보내고 동시에 syn 받았다는 의미의 ack플래그도 1로 설정

**HTTP Cache**

웹 리소스들을 사용자의 브라우저나 서버에 임시로 저장해두는 기술임..

상품 카테고리 조회하는 api가 있다고 가정 -> 요청 값에 따라서 달라지는 경우가 거의 없음

첫 페이지의 전체 카테고리 보여주는 건 사용자에 따라서 달라지는 게 없음.

동일한 값이니 서버 입장에서는 캐싱을 함 -> 분산 환경이 아니면 로컬 캐싱을 하고 분산 환경이면 redis 같은 인메모리 db를 두고 캐싱함.

**Private cache**

각자의 크롬, 같은 웹 브라우저에 저장되는 캐시.

**Shared cache**

공유 캐시. 여러 사람들이 함께 사용하는 캐시. 서버에 저장이 됨 -> 회사나 학교 네트워크에는 프록시 서버라는 것이 있을 수 있음.

**CDN**

Shared Cache 개념을 세계 규모로 확장함. -> 전 세계 주요 거점에 캐시 서버를 두고 사용자랑 가장 가까운 서버에서 컨텐츠 전송해주는 기술..

- > 물리적인 거리가 줄어들어서 속도가 향상됨

**Managed Cache**

개발자가 직접 코드 레벨에서 관리하는 캐시.. redis 같은 저장소를 씀

- >복잡한 데이터베이스 조회를 통한 결과가 있다면 그걸 redis에 캐싱해두고 꺼내주는 형식.

캐시는 클라이언트에 가까울 수록 개인에게 최적화.. 서버에 가까울 수록 다수의 사용자를 위해 동작 함.

이유 :

성능 최적화, 비용 절감, 사용자 경험 향상, 개발 및 유지보수 효율성

동작 방식

브라우저가 logo.png라는 이미지 파일을 서버에 요청하는 과정…이라고 가정

1. 요청 캐시 검사 : 브라우저가 서버에 요청 보내기 전에 먼저 자기 컴퓨터 캐시 저장소 확인함
2. 만료 검사 : 캐시에 파일이 있음. 그럼 그 다음으로 이 파일이 신선한지를 확인. 서버가 처음 파일을 보내줄 때 http헤더에 정보를 기록.. (캐시 유통기한이라고 생각하면될듯.)
3. 조건부 요청 : 유통기한이 지났다라고 하면 파일이 변경 됐을 수도 있다는 의미.
4. 서버의 응답 및 저장 : 서버는 브라우저의 질문을 받고 파일 변경을 확인.
    1. 변경 되지 않았다면. “변경 되지 않았다”는 의미의 304 Not Modified 응답을 반환
    2. 변경 됐다면. 200OK로 새로운 파일 보냅
5. 캐시 제어 : 캐시 헤더를 통해서 동작 제어.

**SWR 전략**

Stale - While - Revaldiate 전략으로, 캐시가 만료된 후에도 즉시 그 데이터를 사용자에게 제공하면서 동시에 서버에게 해당 데이터의 최신 버전을 요청하는 방식.

즉, -> 오래된 데이터를 보여주면서 백그라운드에서 재검증을 한다.

기존에는 캐시가 만료되면 사용자는 서버로부터 새로운 데이터를 받아 올 때 까지 기다려야 했음. -> 그치만 SWR은 이 대기시간을 없앰.

결론 : swr전략 사용하면 사용자에게 항상 빠른 응답 제공하면서 데이터의 최신성도

쿠키의 정의

인터넷 사용자가 웹 사이트를 방문할 경우 사이트가 사용하고 있는 서버를 통해 인터넷 사용자의 컴퓨터에 설치되는 작은 기록 파일

쿠키를 이해하려면 HTTP의 stateless 속성을 알아야 함. -> stateless 상태가 없음. -> 서버는 클라이언트가 보낸 각각의 요청을 완전히 독립적인 것으로 취급함. ->로그인 하고 나서 마이페이지 들어가도 stateless 그 자체의 특징을 가지면 로그인이 안된 상태로 마이페이지.

- > 이런 불편함을 해결하기 위한 것이 쿠키이다. -> 서버가 사용자를 기억 할 수 있도록 만들어 주는 기술 -> 응답을 보낼 때 클라이언트에게 작은 정보 조각(쿠키)를 보냄 -> 브라우저는 이 쿠키를 자신의 저장 공간에 잘 보관해둠.

**퍼스트파티 쿠키**

직관적임. 사이트방문 하면 직접 발행한 쿠키 . 현재 보고 있는 사이트의 도메인과 쿠키에 설정된 도메인이 동일한 경우

**서드파티 쿠키**

여러분이 [news.com](http://news.com/)이라는 뉴스 사이트 방문했는데 ads. 광고가 붙을 수 있는데 ads서버가 브라우저에 쿠키를 심을 수가 있다. -> 즉 현재 방문한 사이트 도메인([news.com](http://news.com/))과 다른 도메인(ads.)에서 발행된 쿠카.

최근에는 개인정보 보호 때문에 서드파티 쿠키 기본적으로 차단함.

**쿠키의 단점**

쿠키는 어디에 저장되는가? -> 클라이언트에 저장이 됨. 중요한 정보를 담아두면 위험하기 때문에 여러 보안 속성을 설정하고 민감 정보는 서버측( 세션)에 저장함.

브라우저 간 공유 불가 (디바이스 x) -> 쿠키의 본질적인 한계. 어떤 브라우저든 동일한 사용자 경험을 제공 할 수 있음.

네트워크 부하 증가 -> 쿠키는 매요청마다 자동으로 전송.

수업에서 가야 가야 할 핵심

- Rest api는 자원을 url로 표현함.
- 행위를 http method로 표현함
- 개발자들끼리 이해하기 쉽게 만든 api 설계의 규칙
- rest를 구성하는 6가지 원칙.. -> 이론이 실제 api 설계 할 때랑 간접적으로만 연결되어 있음.
- 자원 나타날때 슬래시로 표현함
- 쿠키와 세션의 차이점. *
