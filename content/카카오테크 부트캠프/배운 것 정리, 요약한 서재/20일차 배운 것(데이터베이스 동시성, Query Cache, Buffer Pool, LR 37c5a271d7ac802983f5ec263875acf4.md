**비관적 락**

말 그대로 상황을 비관적으로 바라보는 방식

방어적인 접근이라고 보면 됨

화장실갈때 물리적인 열쇠를 아예 들고 가는 것이라고 생각하면 됨.

비관적을 걸면 다른 트랜잭션은 그 락이 풀릴 때까지 대기상태에 빠지게 됨.

데이터 정합성이 중요하고 데이터 충돌이 자주 일어날 것으로 예상 되는 비즈니스 로직에 반드시 필요

Shared- Lock -> 여러 트랜잭션이 동시에 읽을 수는 있지만 쓰기는 차단함.

X (Exclusive)- Lock -> 읽기와 쓰기를 모두 차단하여 단독 접근을 보장함.

- > MySQL의 InnoDB 같은 MVCC 기반 DB에서는 일반 SELECT는 막히지 않고 대신 데이터 원본을 읽는게 아닌, 이전에 커밋된 스냅샷을 읽을 수는 있다.

Intent Lock - 하위 지원에 락을 걸 의도가 있음을 상위 레벨에 알림.

- > 트랜잭션이 특정 행에 락을 걸기전에 속한 테이블 전체에 락을 걸 의도가 있다고 알리는 것.
- > 왜 알리나? 테이블 구조 변경하려고 락 전부다 확인은 불가능. 효율적인 락 관리 가능하다/

**데드락**

비관적 락 사용할 때 생기는 현상이 데드락임.

두개 이상의 트랜잭션이 서로가 가진 락을 해제 하기만 하면 무한정 기다리면서 시스템이 멈추는 상태.

A가 1번 행에 x lock을 걸고 다른 테이블의 1번 행에 락을 걸려고 함

딱 그 순간에 B가 그 다른 테이블 1번 행에 x lock을 걸고 a가 락 걸엇던 테이블에 다시 락을 걸려고 함.

결국 둘다 무한정 기다리는 눈치 싸움…

**동시성 제어 방식**

2PL

- > 트랜잭션이 락을 관리하는 표준
- > 트랜잭션을 두개의 단계로 나누어서 처리함.
1. 확장 단계 : 트랜잭션이 필요한 락을 계속해서 획득하기만 하는 단계. 락을 절대 해제하지 않음
2. 수축 단계 : 트랜잭션이 락을 하나라도 해제하기 시작하면 수축 단계라고 함. 이 단계에서는 락을 절대 획득할 수 없고 락을 반납하기만 함.
- > 트랜잭션의 획득과 반납의 과정을 직렬로 처리되는게 보장 됨

**낙관적 락**

비관적 락은 어쨋든 성능에서 아쉬운 부분이 있고 데드락 위험도 있음.

그래서 고안한 대안이 낙관적 락

- > 상황을 낙관적으로 바라봄

낙관적 락은 물리적인 락을 걸지 않음 -> 소프트웨어락, 어플리케이션 락

데이터 충돌이 자주 발생하지 않을 것으로 예상되거나 읽기 작업이 압도적으로 많을 때 사용

낙관적 락은 테이블에 version이라는 컬럼 하나 두고 구현가능.

조건 문을 두는거임. 내가 사용할때 version이 1일때 commit하고 version을 1로 늘린다. 근데 누군가가 만약 version을 하나 늘려서 바꿔버리면 업데이트가 안되는 거암

대신 낙관적 락은 충돌이 자주 일어나는 환경, 데이터애ㅔ서 서버에 부하를 많이 줌. -> 충돌 빈도를 예측 해야한다.

비관적 락과 낙관적 락의 차이점

1. 락을 거는 시점. 비관적 락은 데이터 읽는 시점부터 걸고, 낙관적 락은 업데이트를 시도하는 시점에서 충돌을 검사한다.
2. 비관적 락은 x lock 같은 물리적인 락 쓰는데 낙관적 락은 컬럼 이용해서 어플리케이션 레벨에서 처리
3. 선택 기준 : 충돌 자주 일어나고 정합성 중요하면 비관적 락. 충돌 적고 읽기 성능 중요하면 낙관적 락임.

**Query Cache와 Buffer Pool**

쿼리 캐시

- > MySQL에서 우리가 날린 SQL 쿼리 문장 자체와 그 결과 데이터를 통째로 메모리에 저장
- > 똑같은 쿼리 들어오면 디스크나 옵티마이저 거치지 않고 바로 반환
- > 빠름
- > 근데 만약 한 테이블을 조회한 결과를 캐시했을때, update 등 수정이 들어가면 캐시를 다 버려야함.
- > 대부분의 서비스는 근데 자주 추가 되고 수정이 됨.
- > 결국 캐시 지우고 관리하는 비용이 오버헤드가 되어 성능을 갉아먹음
- > 사라진 것..

그 대안으로 나온 것이

- > Buffer Pool
- > 쿼리 문자열 자체를 캐싱하는게 아닌 디스크에 저장된 데이터 페이지랑 인덱스 페이지 자체를 메모리에 올려둠.

즉, 데이터 수정 할때,

- > 디스크에 기록하면 느리니까
- > 디스크에 원본 데이터 놔두고 메모리(버퍼풀)에 올라와 잇는 데이터만 먼저 수정
- > 메모리에서는 수정됏지만 디스크에는 반영이 안됨
- > 백그라운드 스레드가 주기적으로 반영되지 않는 상태의 데이터를 모아 디스크로 밀어냄 (플러시)
- > 이렇게 성능을 향상.

버퍼풀은 크기 조절 가능.

정리

- 동시성 제어 필수, 데이터 정합성과 무결성을 지키기 위해 존재
- 데이터 충돌 잦고 정합성이 절대적이면 비관적 락, 그게 아니라 성능 우선이면 낙관적 락.
- 비관적 락 -> 데드락 발생 가능.

**SOLID - LRP(Liskov Substitution Principle)**

OCP 지키기 위해서 인터페이스 만들고 상속 받거나 구현하는 자식 클래스들 신나게 생성하면 문제가 생김.

- > 한도 끝도 없이 계속 추가하게 되는 상황이 생길 수 있음.
- > 상속과 다형성이 안전하게 작동하도록 지키는 원칙 LSP 리스코프 치환 원칙임.

정의 :

자식 클래스는 언제나 부모 클래스를 대체 할 수 있어야 한다는 객체지향 설게 원칙임.

즉, 특정 자식 객체에서만 예외가 있으면 안된다는거암.

Bird 클래스가 fly()를 가지면 penguin은 오버라이딩을 해야하듯이 예외가 있음. 그래서 어떻게? bird클래스에는 fly()를 가지지 않고 따로 flyable 인터페이스를 만들던지 해서 참조하라는것.

오버라이딩을 해도. 행위의 규칙을 훼손해서는 안된다는 것임.

지켜야 하는 이유 :

OCP 배운 것 생각

- > OCP 달성하기 위해서 Service 클래스가 인터페이스나 추상 클래스에 의존할 수 있도록 만들음.
- > DI로 외부에서 구현체 주입 받음.
- > 만약에 주입받은 구현체가 (자식 클래스)가 LSP 위반해서 엉뚱한짓을 한다면,,,,,
- > OCP 주는 이점이 사라짐.

Composition / LSP 무조건 적용하는게 좋은가?

LSP를 지킬 수 없는 상속이면 그 상속 자체가 잘못된 설계

- > 상속 유지기보다 조합이나 인터페이스로 구조를 바꾸는 것이 좋다

결론 :

LSP는 부모타입만 알고 호출하더라도 실제 주입된 자식 객체가 부모의 행위적 계약을 깨지 않고 예측 가능하게 동작해야한다는 원칙.

- 자식 객체가 부모 객체의 의도와 계약을 그대로 준수하면서 호출하는 곳에서 아무런 의심 없이 부모타입으로 자식을 다룰 수 있게 해야한다는 원칙

**SOLID - ISP(Interface Segraga Principle)**

Srp - 단일 책임 원칙, 클래스의 책임을 하나로 좁힘.

Ocp - 변경에는 닫혀있고 확장에는 열려있게 하는 원칙

Lsp - 다형성 안전하게 보장하기 위해 부모의 계약을 지켜야 하는 원칙

ISP - 인터페이스 분리 원칙.

하나의 거대한 인터페이스에 수십개의 메소드를 때려넣는 실수를 하지 않기 위해서..

- > 호출하는 입장에서 사용하지 않는 기능까지 떠안아야 할 수 있음.

ISP 는 인터페이스 거대하게 만들지 말고 인터페이스를 사용하는 곳의 목적에 맞게 잘 쪼개라는 것.

정의 :

클라이언트는 자신이 사용하지 않는 메서드에 의존하지 않아야 한다는 객체 지향 원칙.

UserServicelmpl이라는 클래스를 만들고 여기에 로그인, 회원가입, 비밀번호 변경 기능이 다 들어가서 UserService라는 인터페이스를 생성

만약 일반 사용자가 쓰는 UserController 가 있고 관리자용 AdminController가 잇다고 하자.. 두 컨트롤러가 UserService를 주입받고 있다면?

- > 클라이언트는 실제로 불필요한 결합도 받는거임

Machine이라는 인터페이스에 fax, print, scan 등등이 잇다고 하자. Printer 가 machine을 상속받으면 프린트 기능 뿐 아닌 다른 것 까지 받음.. 이건 좋지 않다.

사용 이유 :

불필요한 결합과 변경 전파를 구조적으로 차단하기 위해서

커머스 개발하는데 OrderService 라는 인터페이스를 하나 만들음/

- > 인터페이스가 갖고 있는 계약들이 너무 많으면 테스트의 의도가 흐려짐.
- > 고객은 주문 생성만 하는걸 확인하면 되는데 뭐 배송 정산 환불 인터페이스에 다 연결되어 잇는 것 처럼 보이기 때문에 코드 읽는 입장에서는 수많은 기능 중에서 어떤걸 어떻게 쓰지? 라고 혼란에 빠질 수 있다.
- > 목적에 맞게 분리를 해야한다는 거임.
- > 구현체 클래스는 3개 다 구현 할 수도 있다.
- > 중요한 클라이언트가 바라보는 시선에서 하나의 거대한 OrderService 가 아니라 명확한 인터페이스만 가져다 쓸 수 있다.

Srp는 구현하는 클래스의 관점이고 isp는 사용하는 클라이언트의 관점에서 다름.

정리 :

- isp는 클라이언트가 자신이 사용하지 않는 메소드에 의존하도록 강제되어서는 안됨
- 인터페이스가 너무 비대해지면 이를 구현하는 클래스는 불필요한 메소드를 빈깡통으로 취급해 isp 규칙을 위반 할 수 있다.

**Custom Exception**

예외가 버그나 문제가 아니라 비정상적인 상태 알리고 흐름 제어하라는 신호면 -> 서비스 계층에서 할 수 있는 상태가 아니면 throw를 통해 예외를 상위로 던져야 함.

프론트엔드에 좀 정확한 에러코드를 알리기 위해서,

CustomException(개발자가 정의한 사용자 정의 예외)를 쓰고 Global Exception Handler를 통해 처리를 해줘야함.

결국 명확한 의미를 알리기 위해서 씀.

(NullPointerException, IllegalArugumentException 이런거는 이해하기도 어렵고 비즈니스 관점에서 보기 어려움)

일관되게 오류 관리를 하기 위해서.

- > FE BE 협업 측면

사용 방법

1. 예외 클래스 정의
2. 오류 상황에서 throw로 예외 발생.
3. 전역 예외처리기에서 응답으로 매핑

서비스에서 예외를 던지고 -> RestControllerAdvice 붙은 클래스에서 받아서 처리를 함.

예외처리가 횡단관심사의 대표적인 예시. @RestControllerAdvice는 예외를 묶어서 처리해주는 스프링의 장치.

이 어노테이션이 붙은 클래스는 스프링에 있는 모든 컨트롤러 클래스에 대해서 예외가 터져서 나오면 처리해주는 장치를 한다.

가져가야 할 핵심

- 데이터 일관성과 무결성을 지키기 위한 동시성 제어의 필요성
- 비관적 락과 낙관적 락에 대한 이해
- 데드락의 발생 원인과 이해
- 상속이나 구현을 했다고 다형성이 완성되는 건 아님. 자식이 부모의 계약을 준수 해야한다.
- Instance of로 타입을 검사하거나 특정 자식 클래스 전용 if 분기문이 등장한다면
- ISP의 중심은 클래스가 아니라 그 인터페이스를 사용하는 클라이언트
- 사용하지 않는 메소드에 의존할 때 발생하는 불필요한 결합과 변경의 연쇄 반응을 구조적으로 파악하는 것이 필요.
