**ORM(Object Relational Mapping)**

Orm 은 개념. 기술이지만 실제적인 구현체 이전에 개념임.

- > 이 개념이 왜 탄생했고 왜 쓰이는지 그 배경에 대해서 이야기.

ORM이라는 개념의 표준 -> JPA가 무엇인지 배울 것이고

- > DB테이블과 자바 객체를 연결해주는 엔티티 매핑에 대해서도 배울 것이다.

영속성 컨텍스트와 트랜잭션에 대한 이야기.. 영속성 컨텍스트는 많이 중요함.

자바는 객체로 다루는 값이나 데이터를 저장함..

자바는 행과 열로 데이터를 다룸.

우리가 java나 spring으로 db의 데이터를 다루면 충돌이 일어남.

그래서 우리가 SQL 쿼리 직접 짜고 DB에서 가져온 데이터 매핑 시키면서 반복적인 일을 함.

- > 이걸 편하게 해주는 것이 ORM

정의 : 자바의 객체와 데이터베이스 테이블을 자동으로 연결하고 변환해, 객체 지향 코드로 데이터를 조작 할 수 있게 해주는 기술.

- > 중간 계층에서 객체와 테이블간 구조적 차이를 해소해준다.

자바에서 뭐 user 객체의 클래스 이름이랑 필드를 분석해서 매핑되어 있는 데이터베이스의 Users 테이블 구조에 맞춰 INSERT SQL 자기가 생성하고 실행까지 해줌.

사용 이유 :

객체 지향과 관계형 데이터베이스 간의 간극을 줄여, 설계의 일관성과 코드의 생산성을 높이기 위해서.

**JPA(Java Persistence Application)**

ORM 이라는 개념. 객체지향이랑 RDB 사이의 패러다임 불일치 해결해주는 중간 계층 도구

- > ORM이라는 개념이 자바에서 어떻게 구현되어 있는지 시작하는 큰 그림

정의 : 자바 객체와 관계형 데이터베이스를 매핑하고, 객체 단위로 데이터를 저장 조회 할 수 있게 해주는 표준 ORM 인터페이스

- > 자바에서 ORM 만들려면 이런 이름의 메소드를 만들고 이런 규칙을 지켜라 라고 정해둔 자바 진영의 공식 명세서
- > 구현체가 필요한데 대표적인 구현체가 하이버네이트.

JDBC를 직접 사용하지 않고도 객체를 데이터베이스에 저장하고 불러올 수 있도록 돕는 중간 계층 역할.

- > JDBC가 무엇인가?
- > 자바 어플리케이션이랑 데이터베이스랑 연결해주는 가장 밑바닥의 표준 API
- > 어떻게 DB와 커넥션을 맺고 처리하는가? 에서 쓰는 도구가 JDBC
- > MySQL을 쓰든 오라클을 쓰든 JDBC를 거쳐서 데이터베이스와 통신
- > 과거에는 JDBC를 직접 다뤘는데 .. 이제는 JPA가 알아서 다 해줌.

JPA 인터페이스 -> 하이버네이트 구현체 -> JDBC -> DB

1차 캐시?

jpa가 갖고있는 요소. JPA만의 임시 메모리 공간이라고 보면 됨.

한번 DB에서 데이터를 가져오면 객체로 만든 후 메모리 공간에 할당을 하는것.

정리 :

JPA는 ORM 표준 인터페이스이고 실제로 동작하게 만드는 구현체는 따로 있다. 그 중에서 가장 대표적인 것이 하이버네이트.

**Entity**

ORM 무슨 기술인지 배웠고 왜 써야하는지를 패러다임 불일치랑 엮어서 설명

JPA가 자바 진영의 ORM의 표준 인터페이스

그럼 이 JPA의 작동 원리 중 하나가 엔티티.

정의

데이터베이스 테이블과 1:1로 매핑되어 데이터를 객체 형태로 표현하는 자바 클래스

예전에는 회원목록 조회한다고 치면

SELECT * FROM users 라는 쿼리로 조회.

자바는 객체지향인데 Db는 문서 형태로 반환하니 일일히 매핑해야했음.

그러나, JPA를 사용하면 자바 클래스 하나 만들어 두고 @Entity 어노테이션을 하나 붙여주면 됨.

- > 붙여주는 것의 의미는 “ 이 클래스는 데이터베이스의 users 테이블이랑 똑같이 생긴 클래스다” 라고 지정하는 것.
- > JPA의 관리 대상이 되는 클래스가 생기는것.
- > 이거를 영속성 컨텍스트 라는 곳에서 관리.

데이터를 하나의 객체로 묶어 구조와 규칙을 함께 관리하여 코드의 오류를 줄이고 설계를 일관되게 유지할 수 있기 때문에

데이터베이스는 좋은 데이터 저장소,

- > 그러나 비즈니스 규칙을 담을 수가 없음.
- > DB에 제약조건을 걸거나 트리거를 걸어서 처리를 할 순 있지만..

엔티티가 없다면 비즈니스 로직을 Service 계층에 넣게됨.

- 일종의 파편화..
- 따라서 엔티티 안에 작성하는 게 좋음/
- 데이터 담고 있는 User Entity 클래스 내부에 change password 같은 메소드를 만든다거나.
- 비밀번호에 관한 규칙이나 제약을 걸수도 있음.
- 비밀번호를 변경하려는 모든 서비스의 로직은 user 엔티티의 changepassword 메소드를 호출해야만함.
- 응집도가 높아짐.
- 사실.. 서비스 계층에 있어도 되는데
- 클래스가 갖고 있는 데이터가 있으면, 그 데이터 자체를 조작하거나 다루는 메소드는 해당 클래스에 있으면 좋다는거임.
- 객체가 스스로의 상태를 책임지고 관리하는 객체가 됨.

사용 방법은 @Entity 를 붙히면됨.

규칙 1. 기본 생성자가 반드시 존재

Protected 클래스명 () {} 이렇게 파라미터 없는 생성자 필수로 있어야함.

- 하이버네이트가 먼저 객체를 동적으로 new 하려고 할때..
- 빈 객체를 만들고 리플렉션을 통해서 필드에 값을 꽂아넣는 방식으로 동작함.

규칙 2. 클래스나 필드에 final을 쓰면 안됨.

나중에 지연 로딩이나 프록시의 개념을 배울 것임.

- > JPA는 성능 최적화 하기 위해서 진짜 객체 대신 껍데기만 있는 가짜 객체(프록시)를 만들어서 사용함.
- > 지연 로딩에 쓰이는 프록시(가짜 객체)가 원본 엔티티를 상속해서 만들어짐.
- > final 클래스는 상속이 안됨.
- > 상속이 안되면 프록시도 못만들고 지연로딩도 못함.
- > 필드에도 final 쓰면 안됨.
- > 하이버네이트가 기본 생성자로 빈 객체를 만들고 값을 넣는데..
- > final은 생성자 이후에 값을 바꿀수가 없음.

알아 두면 좋은 정보

무분별한 @Setter 사용은 재앙이다. (안티패턴임..)

클래스 레벨에 세터를 열어두면 어플리케이션 어느곳에서는 serPassword 같은 메소드로 값을 마음대로 바꿀수 있음 -> 추적이 어렵도 가독성도 떨어짐.

무분별한 setter 사용은 객체의 일관성을 해치고 변경 추적도 어렵게 만든다.

정리

- Entity는 데이터베이스 테이블과 1:1로 매핑, 데이터뿐만 아니라 비즈니스 로직까지 응집해서 처리 가능.
- JPA가 리플렉션 통해서 객체 생성하고 필드 다룰 수 있도록 기본 생성자가 반드시 필요. 프록시 생성을 위해 final 키워드 못씀.
- 객체의 안전성, 유지보수성을 위해서 무분별한 setter 사용 지양.

**@Id**

DB테이블 설계할 때, 필수로 들어가야 하는 요소가 PK

- > 데이터 행이 많이 쌓여있으면 “이 데이터가 바로 그 데이터다”라고 식별 할 수 있는 기준. 중복이 안됨.

DB에서는 PK라고 DDL에 붙여주는데 자바에서는 어떻게 다루지??

- > 객체는 메모리 주소로 식별, 데이터베이스는 기본키 값으로 식별을 함.
- > 그 식별 방식을 연결 시켜 주는게
- > @Id
1. 직접 할당

자바에서 객체 생성해서 관리하려면 PK설정을 해줘야함.

개발자가 자바 코드에서 user.setId(’12’)등으로 직접 세팅하는 방식.

1. 자동 생성

데이터베이스에서 PK만들때 auto increment 기능이나 시퀀스 기능을 활용해서 db에서 순차적으로 번호를 매겨주는 방식

자연키 : 이메일, 뭐 중복 안되는 전화번호. 등 비즈니스 적인 의미를 갖고 있으면서 유일성을 만족하는 키.

대리키 : 비즈니스 의미는 없어도 식별만을 위한 키. 1,2 , 3, 4,등 순차적으로 증가하는 값이나 난수 문자열 같은 것들.

그냥 거의 무조건 대리키를 써야함.

만약에 이메일을 기본키로 잡는다면…

변경 하려고 할때 엄청난 비용이 들어감..

즉, 비즈니스 환경이 어떻게 변하던 절대 변하지 않는 값

- > 대리키를 써야 한다.

이메일이나 비밀번호는 유니크 제약조건 정도만 걸어서 중복 맡기고 진짜 식별자는 대리키에 맡겨서 처리를 해야함.

사용 이유

@Id로 지정한 기본키는 영속성 컨텍스트에서 엔티티를 찾고 관리하는 열쇠

이걸 식별하고 관리를 할 수 있어야 JPA의 1차 캐시나 더티 체킹 같은 기능들이 돌아감.

1차 캐시 - JPA가 한번 꺼내온 엔티티를 잠깐 메모리에 들고 있는 임시 보관함 -> @Id에 있어야 식별, 조회 가능

정리 : JPA가 엔티티를 관리할때, @Id를 중심으로 하기 때문에 편리하구나..

JPA가 객체를 식별하는 유일한 기준임.

DB의 PK와 매핑이 되고, 영속성 컨텍스트에서 객체를 식별하는 역할을 함.

**기본 키 생성 전략**

DB 테이블에 기본키가 있는데 JPA 엔티티에도 기본키와 매핑되는 식별자가 필요하다 라고 얘기 했을때 쓰는게 @Id

- > 우리가 Id에 대한 값을 직접 지정하지 않고 @GeneratedValue를 붙혀서 씀 AUTO_INCREMENT 처럼

단순히 기본키를 어떻게 만들 것인가에 따라서 성능의 차이가 생김.

- > DB 테이블 설계 할 때 PK 어떻게 만들지 지정을 함.
- > MySQL 같은 경우는 AUTO_INCREMENT로 하고 오라클은 sequence를 사용하기도 함

**TABLE 전략**

별도의 키 전용 테이블을 두고 시퀀스 동작을 흉내 내는 방식.

MySQL 같은 경우 시퀀스 객체 같은건 없고 기본적으로 AUTO_INCREMENT 기능을 씀.

아예 데이터 베이스 안에 키를 생성하기 위한 전용 테이블을 하나 만들음.

id_generator 라는 테이블을 하나 만들고 저장해서 꺼내 쓰는 방식이 있긴한데… -> 안씀, 동시성 문제나, 성능 면에서 너무 떨어짐.

**SEQUENCE 전략**

오라클, postgreSql 같은 DB에서 시퀀스 오브젝트를 지원할 때 사용 할 수 있음.

시퀀스는 DB 내부에서 순차적으로 증가하는 숫자를 빠르고 안전하게 만들어주는 객체

동작 방식

우리가 em.persists(post) 이런 메소드를 써서 엔티티를 저장하려고 할 것임.

그러면 JPA 입장에서 영속성 컨텍스트에 엔티티를 보관하려면 필수로 PK값이 필요함. - 식별하기 위함.

- > 아직 엔티티로만 존재하고 DB에 저장하기 전이라면 아직 ID값이 없음.
- > 그러면 JPA가 DB에서 다음 PK값 알려달라함.
- > DB가 알려주면 그 세팅을 영속성 컨텍스트에 저장. 여기에 차곡차곡 쌓임.
- > 나중에 트랜잭션이 커밋 될때 쌓여있던 INSERT 쿼리들이 한번에 DB로 날아감.

질문 ) 시퀀스 전략을 쓰면 엔티티 저장 할 때마다 시퀀스 값을 가져오기 위해 DB랑 네트워크 통신 해야하는데 성능 떨어지지 않을까요?

- > 맞는 말임. 이런 네트워크 비용 줄이기 위해 제공하는 옵션이 allocationSize를 제공함 한번에 좀 크게 가져간다는 뜻.

**INDENTITY 전략**

MySQL이나 MariaDB에서 사용하는 AUTO_INCREMENT 기능을 활용하는 방식

데이터베이스에서 INSERT 할 때, PK 컬럼 비워두고 넣으면 DB가 알아서 1, 2, 3… 증가시키면서 값을 채워주는 기능.

Identity 전략과 쓰기 지연은 충돌..

원래는 영속성 컨텍스트에 저장 할 때 PK가 잇어야하는데

여기서의 PK는 DB가 저장해주는 것이기 때문에.

아이덴티티 전략은 persist() 호출하면 즉시 INSERT 쿼리를 날림.

- >쿼리를 날리면 DB가 방금 생성한 PK를 저장을 함.
- > 쓰기 지연을 이용한 최적화가 안됨
- > 회원 1만명을 엑셀로 업로드 해서 한번에 저장하는 기능이 있다고 쳐도 부하가 걸릴 수 있음.

정리 :

- 기본키 생성 전략 엔티티 식별자 자동으로 생성하는 방법.
- DB 환경에 따라서 4가지 전략 중 하나를 선택해야한다.
- 성능 문제로 TABLE은 안쓰고 DB에 맞춰서 IDENTITY나 SEQUENCE를 명시적으로 지정해서 쓴다.
- 시퀀스 전략은 allocationSize이용해서 쓰기지연도 쓸수 잇음.
- 아이덴티티 전략은 쓰기지연 쓰기 어렵다.

**영속성 컨텍스트**

중요한 내부 동작에 대한 개념

모르면 -> persist로 저장했는데 왜 안되는지, update 쿼리 날린적 없는데 수정되는 이유 등 이슈들을 겪을 수가 있다.

정의 :

JPA가 엔티티 객체를 관리하며, 동일 트랜잭션 내에서 변경 사항을 추적하고 자동으로 데이터베이스와 동기화 하는 메모리 상의 저장소.

- > 메모리 상의 저장소

눈으로 보고 다루는 객체가 아닌 논리적인 개념임 . EntityManager 라는 객체를 통해서 접근함.

- > persists() 이런거 쓴다라고 앞서서 이야기 함. 이런 메소드를 호출해서 영속성 컨테스트에게 명령을 내림.

플러시 단계 : 영속성 컨텍스트에 쌓여있던 변경 내용을 실제 DB에 한번에 밀어넣는 동기화 작업

비영속 : User user = new User(); 이렇게 방금 객체를 생성한 상태

JPA는 이 객체가 존재하는지도 모름 , 영속성 컨텍스트와 상관이 없는 상태

영속 : 방금 만든 객체가 있고 이걸 em.persist(user)해서 entity Manager에게 넘겨준 상태.

준영속 : 영속성 컨텍스트안에 있던 객체를 끄집어낸 상태.

삭제 : em.remove(user) 호출해서 “이거 DB에서 지워줘” 라고 삭제를 예약한 상태.

사용 이유 : 그냥 객체에서 바로 DB에 SQL 날리면 되지 않나..

ORM이나 JPA 수업때 했던 것과 연결이 됨

- > 객체지향과 관계형 디비 사이의 패러다임 불일치가 있고 이 불일치를 해결하기 위해 영속성 컨텍스트가 중간 계층으로서 존재함.
- > 객체는 메모리 주소로 동일성 비교하고 DB는 PK로 동일성을 비교한다 그리고 DB에 네트워크 타고 쿼리 날리는 것도 비용이 듬.

영곡성 컨텍스트를 쓰면 중간에 캐싱을 통해서 네트워크 비용도 줄이고.. 쿼리 모아서 보낼수도 있고.. 객체를 다룰수 있게해서 동일성을 보장하기도 함.

원래는 동일성 보장이 안되는 객체인데 영속성 컨텍스트로 인해서 동일성 보장이 되듯, 장점이 있음. - 1차 캐시의 장점

영속성컨텍스트는 단순히 메모리 상에서 엔티티 저장하는 데서 안끝나고 엔티티 상태변화 지켜보고 있다가 트랜잭션 커밋 시점에 DB랑 동기화 됨.

쓰기 지연 이용하면 로직 다 수행하고 트랜잭션이 커밋되기 전에 쿼리 날려서 DB의 락 시간을 줄일 수 있다.

변경 감지 이용하면 1차캐시던 기존에 있던 원본을 저장해서 바뀐게 있으면 알아서 update 해줌.

- 개발자가 SQL에 신경 쓰지 않고 순수하게 자바 객체로 상태를 변경하는 비즈니스 로직에만 집중하게 하기 위해서임.

정리 :

- 영속성 컨텍스트는 어플리케이션과 DB사이에서 entity를 관리하는 논리적인 메모리 저장소임.
- 덕분에 1차 캐시, 쓰기지연, 변경감지와 같은 기능이 가능하도록 만들어줌
- 기능의 대상인지 아닌지는 영속 상태에 따라서 달라짐. 엔티티의 생명 주기에 대해서 알아야 함.

**Transaction**

트랜잭션은 데이터베이스의 상태를 변화시키기 위해 수행하는 작업의 단위이다.

JPA에서 트랜잭션은?

- > 영속성 컨텍스트의 생명주기와 결합이 됨
- > JPA는 엔티티 객체의 상태변화를 감지 하더라도 그것을 즉시 DB에 반영하지 않음 , 일단 기록만 해둠
- > 커밋될떄 플러시 하는 것임.

사용 이유 : 일관되게 처리하기 위해서 . 정확하게 반영하기 위해서.

@Transactional(readOnly= true) 같은것은.

스냅샷, 더티체킹 생략해서 읽기 전용으로 선언해서 함.

**OSIV (Open Session In View)**

뷰 영역까지 session을 open 해둔다는 뜻.

단점도 많음 - OSIV로 인한 커넥션 풀 고갈이 발생 할 수 있음.

원래 서비스 계층에서 반납하고 끝인데 OSIV 켜져있으면 범위가 넓어져 시간이 길어짐.

아무튼 끄고 사니까 이걸 실제로 꺼줘야댐( 요즘은 켜져잇는게 디폴트)

지연로딩 끝내고 엔티티가 아닌 DTO로 넘겨주면 되는거임.. 굳

**Persist**

자바 코드에서 new 키워드로 생성한 순수 자바 객체와 비교되는

영속성 컨텍스트에서 공간으로 밀어넣는것이 persist임.

단순 저장 + 영속 상태로의 전환

Identity - MYSQL의 뭐 auto increasment 같은거는 즉시 db에 insert가 되지만 (그래서 jpa의 쓰기 지연을 제대로 활용하기 어렵다)

Sequence - oracle 같은 곳에서 쓰는 방식인데 db에 insert 즉시 할 필요는 없음. commit이나 flush까지 미룰 수 있음. 그래서 쓰기지연도 가능하다는 거임.

가져가야 할 핵심

- ORM의 정확한 의미 그리고 중간 계층으로서의 역할 이해
- 객체 지향 모델과 관계형 데이터베이스 모델간의 패러다임 불일치
- SQL 중심 개발하면 만나는 한계와 ORM의 이점
- JPA의 개념이랑 JDBC, 하이버네이트와의 관계 이해
- 단순한 객체, DTO와 JPA가 관리하는 엔티티의 차이점
- 엔티티 만들때 지켜야하는 룰 - 기본 생성자의 필요성, final 키워드가 못 쓰는 등의 규칙
- 무분별한 setter 사용하면 안되는 이유
- JPA가 엔티티를 식별하는 유일한 기준. @Id의 역할과 중요성.
- 자연키와 대리키의 차이점. 실무에서는 대리키를 쓰는 이유.
- @Id가 영속성 컨텍스트에서 엔티티를 식별하는 열쇠 역할
- 기본 키 생성 전략 4가지(TABLE, sequence, identity, AUTO)의 동작원리와 차이점
- Identity 전략이 영속성 컨텍스트의 쓰기 지연에 미치는 영향
- Sequence 전략은 allocationSize라는 값이 성능에 미치는 영향
- 영속성 컨텍스트의 개념이랑 엔티티의 생명주기 - JPA가 객체를 관리하는 방법
- 1차 캐시와 동일성 보장
- 트랜잭션이 JPA 영속성 컨텍스트와 어떻게 결합해서 DB 동기화 시점을 결정하는지
- @Transactional이 가져다 주는 성능 최적화
