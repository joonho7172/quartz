**Persist**

정의 :

새로 생성한 엔티티를 영속성 컨텍스트에 등록해서 DB에 저장하도록 만드는 메서드.

장바구니 추가 버튼 느낌이라고 보면됨. 장바구니 (영속성 컨텍스트)

New 로 만든 객체를 persist 해줘서 컨텍스트에 담음.

물론 identity 전략 중 auto increment는 바로 db에 저장시킴.

그게 아니라면 쓰기 지연 저장소에 보관되었다가 commit 시점에 실행.

사용 이유

엔티티를 JPA가 관리하도록 위임해서 중복 코드 없이 안정적으로 저장 로직을 처리,

객체를 persist로 넘기면 JPA는 현재 사용하는 DB에 맞춰서 SQL을 동적으로 생성해줌.

- > 쓰기 지연으로 여러 엔티티 저장해도 깔끔히 롤백 가능.
- > 한번 영속 상태가 되면 트랜잭션 동안 1차 캐시안에 있어 데이터 로딩 수월. 그리고 값 바뀌면 더티 체킹으로 자동 UPDATE

정리 :

- persist가 단순한 INSERT 명령어가 아니라 객체를 JPA 영속성 컨텍스트로 넣어서 영속 상태로 등록하는 메소드
- Persist 호출한다고 해서 즉시 쿼리 나가는게 아니라 쓰기 지연 발생함. 하지만 아이덴티티 전략일 때는 즉시 DB에 반영됨

**FLUSH**

Persist 메소드랑 쓰기 지연에 대해서 배웠음.

- > 엔티티 저장해도 즉시 DB에 쿼리 날아가지 않고 트랜잭션 커밋되는 시점에 날아감.
- > 근데 커밋 안기다리고 바로 DB에 쿼리 보내서 상태 동기화를 원할 때 사용하는 것.

영속성 컨텍스트 안의 쓰기 지연 SQL 저장소를 모두 실행 시키는 것.

- 쿼리가 DB로 갓다고 해서 트랜잭션이 끝난 것이 아님. 커밋이 안됐고, 롤백이 될 수도 있음. 그냥 DB에 전송만 한 상태임.
- 1차 캐시도 유지가 됨. 그냥 쓰기 지연 저장소의 쿼리들만 DB로 비워내는것

사용 이유

1. 검증이랑 예외를 지금 당장 당겨서 받기 위해서.
    1. 미리 에러를 잡고 예외 처리를 하기 위함임.
2. 네이티브 쿼리 실행전에 동기화
    1. 실제로 일할 때 레거시 쿼리 때문에 따로 네이티브 쿼리를 작성해야함.
    2. 네이티브 쿼리는 1차 캐시가 어떻게 반영되어있는지 모름. 수정 되기전의 옛날 데이터를 읽어옴.
    3. 데이터 불일치 발생
    4. 따라서,, 네이티브 쿼리를 쓰고 다룬다 하면 flush()를 명시적으로 호출해서 변경된 닉네임을 DB에 밀어넣고 그 다음에 조회를 해야한다.
3. 대용량 데이터 배치 처리 할 때 OOM 방지
    1. 너무 많은 데이터를 persist로 자주 업로드 하면 OOM 뜰 수 있음.
    2. 이럴때 좀 끊어서 flush()를 호출함

Flush 와 커밋의 차이는?

- Flush는 쿼리를 DB에 전송해서 동기화 하는것이고 확정 짓는 것이 아님. 롤백 가능하고 1차 캐시에도 유지됨.
- 커밋은 트랜잭션 끝나고 데이터를 영구적으로 반영하는 작업임.

정리 :

- Flush 는 JPA가 알아서 해주는 쓰기 전송 타이밍을 개발자가 수동으로 조작하는 것.
- 예외를 조기에 발견하거나 네이티브 쿼리 전에 동기화 하기 위해서 사용함.

**Remove**

데이터 생명주기에서 삭제 하는 단계

JPA에서 remove 쓰면 어떻게 호출하고 처리 되는지

영속 상태의 엔티티를 삭제 예정으로 표시하여, 플러시/트랜잭션 커밋 시 데이터베이스에 DELETE가 반영되도록 예약하는 메서드.

- > 삭제 예정과 예약
- > 1차 캐시에 해당 객체에 삭제 예정이라고 하는걸 마킹을 하고 쓰기 지연 저장소에 DELETE 쿼리를 만들어둠.

대상 엔티티가 반드시 영속 상태여야 삭제 가능.

DB에 있다면 find()해서 영속 상태로 만들거나 해야함.

사용 이유 - 1차 캐시랑 정합성 때문임.

- > remove 호출한뒤 같은 트랜잭션에서 find하려 하면 JPA는 DB가 아닌 1차 캐시를 확인함.
- > remove가 호출이 된 후 이므로 null을 반환

만약 JPA 무시하고 네이티브 쿼리로 DELETE 날리면 DB에서는 지워졌지만 1차 캐시에서는 살아있는 모순이 됨.

소프트 딜리트 - 논리 삭제

삭제 된 것 처럼 보이게 하는 것임.(회원 탈퇴ㅡ 주문 취소, 게시글 삭제 처럼 나중에 문제가 생겼을때 기록이 필요할때.)

**연관 관계 매핑**

데이터 베이스에서는 외래키 가지고 양방향으로 각 테이블을 넘나들 수 있다.

자바 객체의 세계는 어떤가?

- > 참조가 있는 쪽에서만 넘어갈 수 있음.

연관 관계 매핑을 이용하면 데이터베이스는 여전히 외래키 사용하지만 자바 코드에서는 User user 등 객체 참조 자체를 필드로 가질 수 있게 해줌.

@ManyToOne

@JoinColumn(name = "member_id")

private Member member;

이엏게 외래키 매핑하는 것임

이렇게 해두면 자바 코드상에서 점(.)만 찍어서 자연스럽게 가져올 수가 있음.

사용 이유

객체 간의 관계를 관계형 데이터베이스의 외래 키와 정확히 연결하여, 데이터 정합성과 설계 일관성을 유지하기 위해서

- > 데이터 정합성.
- > 코드를 작성 할 때, “이 게시글의 작성자는 이 회원이다” 라는 도메인의 규칙이 자바 코드에 명확히 드러나야 함.
- > post.setUser(user)라는 코드는 단순히 user_id 컬럼에 숫자를 넣으라는 말이 아님.
- > JPA가 트랜잭션이 끝나는 즉시 플러시 시점에 참조 상태를 읽어오고 참조가 바뀌었다면 알아서 UPDATE SQL을 날려줌.

정리 :

- 연관관계 매핑이 무엇이고 왜 필요한지를 배웠고 이제 어노테이션들 실제로 어떻게 사용하는지도 배우고 , 단방향과 양방향 차이, 연관관계의 주인이라는 이어서 사용.
- 데이터베이스는 외래키로 관계 맺고 자바는 참조로 관계를 맺는다 -> 패러다임의 불일치.
- 이걸 해결하기 위해서 연관관계 매핑이라는 것을 사용함.

단방향 매핑

- > 잘 알아야 설계하거나 관계 만들때 유리함.

단방향 사용 이유

필요한 방향으로만 관계를 맺어 설계를 단순화하고 불필요한 의존성을 줄이기 위해서.

1:N 관계에서 외래키는 무조건 N 쪽에 잇음. 한명의 유저가 여러 게시글을 쓰면 외래키는 게시글 테이블에 있음.

규칙 1. 외래키를 가지는 쪽(N)이 무조건 연관관계의 주인이 되도록 연관관계를 세팅해야한다.

연관관계의 주인이 무엇이고 왜 N쪽이 주인이 되어야 하는가?

- 연관관계의 주인은 데이터베이스의 외래키를 관리하는 주체를 의미, 관계형 DB에서는 1:N 관계에서 항상 N쪽에 외래키가 존재한다. 객체 모델에서도 N쪽 엔티티를 연관 관계의 주인으로 설정해야 객체의 변경이 자신의 테이블에 대한 insert, update가 자연스럽게 이어진다.

정리 :

- 단방향은 객체간의 관계 안에서 한쪽으로 조회 할 수 있도록 참조를 열어둔 관계
- 불필요하게 양방향 하면 복잡도가 높아질 수 있다.
- 외래키를 가진 쪽이 연관관계의 주인이 되어야 한다.
- One to many 단방향인데 1이 주인이 되는 방향으로 만들면 성능 저하나 불필요한 쿼리가 생긴다.

양방향 연관관계

정의 : 두 엔티티가 서로를 참조해 양쪽 모두 관계를 탐색할 수 있도록 매핑한 방식.

Post 안에 User 참조가 있으면 User  안에도 List<Post>가 잇어야 한다는 것.

JPA의 딜레마가 생김.

- > DB의 외래키는 1개. 객체에서 이 외래키와 연결된 참조는 2개가 된 것 .
- > 즉 양방향의 핵심은 연관관계의 주인

데이터베이스 테이블에 외래키가 있는 곳에 매핑된 엔티티 필드가 무조건 연관관계의 주인

즉, 당연하게 Post의 User user필드의 주인. 그럼 User의 List<post>는?

자연 스럽게 읽기 전용이 되는것임

이렇게, 주인이 아닌쪽으르 JPA에게 알려주는것이 MappedBy 어노테이션임

웬만해서는 양방향을 쓰지는 않음.

정리 :

- 데이터베이스는 외래키 하나로 양쪽 조인이 가능하지만 객체는 참조가 있는 방향으로만 이동할 수 있다.
- 객체의 양방향 관계는 사실 단방향 2개이다.
- DB의 외래키는 하나인데 객체 참조는 두개인데 JPA는 둘 중 하나를 관계의 주인으로 정한다.
- 외래키가 있는 쪽이 주인이고 아닌 쪽은 mappedBy 사용해서 읽기 전용.

가져가야 할 핵심

- 플러시는 커밋이 아님. 영속성 컨텍스트와 DB를 동기화 하는 작업
- 플러시를 사용하는 시나리오 3가지에 대해서 이해.
- 삭제는 예약이다. - remove 쓴다고 해서 즉시 DELETE쿼리가 실행되지는 않음.
- 영속 상태가 필수 - 아무 객체나 지울 수 없고 영속 상태로 만든 후에 삭제
- 소프트 딜리트
- 관계형 데이터베이스의 외래키 방식와 객체지향의 참조 방식의 패러다임 불일치
- 객체 그래프 탐색이라는게 왜 객체지향적으로 코드를 만들어주는가에 대해 인식하기
- 객체와 데이터베이스의 차이를 이해 - 양방향 통행 가능한 DB 단방향만 가능한 객체
- 연관 관계의 주인 - 외래키를 갖고 있는 진짜 주인이 누구인지 판별
- 1:N 단방향의 위험성 - 실무에서 @OneToMany 단방향 매핑 왜 피해야하는지
