**ManyToOne (N:1)**

정의 :

여러 엔티티가 하나의 엔티티와 관계를 맺도록 하는 매핑 구조

- > 제일 많이 쓰는게 게시판
- > 하나의 사용자에 여러개의 게시글
- > 반대로 생각하면 여러개의 게시글 입장에서는 작성자가 단 한명의사용자
- > 게시글과 사용자의 관계가 ManyToOne

RDB에서 FK는 항상 어디에 위치?-> N 쪽에 위치함.

JPA도 똑같이 따라감.

- > 외래키를 실제로 갖고 있고 이 외래키를 관리해야하는 쪽이 N쪽 엔티티
- > N쪽 엔티티의 참조 필드가 연관관계의 주인이 됨. (ManyToOne, JoinColumn)

다대일 단방향

N쪽 엔티티에서만 1쪽 엔티티를 참조하는 구조

어차피 자바 입장에서 단방향이든 양방향이든 DB 테이블은 똑같고 단방향 매핑이라는 것은 자바 세계에서의 방향성을 이야기함.

mappedBy-> 읽기 전용이고 연관 관계 주인 어디에 두는지 JPA에 알려주는 것.

- > 양쪽 객체 서로 참조 가능하긴 함.

사용 이유 :

게시글 클래스가 userId 숫자 들고 잇는거보다 user 클래스 객체를 가지고 있는게 훨씬 깔끔함.

- > 개발자는 그냥 객체지향 기반으로 개발해나가면 됨.

만약 (fetch = FetchType.LAZY)로 되어 있으면.. 그 외래키가 사용이 되는게 아닌 이상. DB에서 가져오지 않음.

즉시 로딩(EAGER)는 …

N+1 문제에 대한 이해

**OneToMany**

방금 다대일 관계와 비슷하게 일대다 관계인것임.

정의 : 한엔티티가 여러 개의 다른 엔티티와 관계를 맺는 매핑 구조

회원 1이 게시글N개 가능.

1:N 단방향 매핑을 해버리면 post에 user_id를 넣을 수가 없음.

User 객체에 post 컬렉션에 Post 들어잇는 것을 확인하고 JPA가 하고 INSERT 해준 post테이블 레코드를 찾아가서 user_id값을 채워넣는 update 쿼리를 발행.

- > 그냥 비효율 적임.

**Cascade**

영속성 전이, 부모 엔티티에 지시한 명령을 자식 엔티티에게도 똑같이 전파 시키겠다.

편리한 도구

- > 이걸 반드시 따져보고 사용을 해야함
- > 이 자식 엔티티가 부모 엔티티에 완전히 종송적인가? 따져보고 사용을 해야한다.
- > 예를 들면 게시글 엔티티와 이미지 엔티티 -> 게시글이 사라지면 이미지도 사라짐

그게 아닌 다른 자식 엔티티가 다른 곳과도 연관이 있으면 case

Orphan Removal (고아 객체 제거)

부모와의 연관 관계가 끊어진 자식 엔티티를 JPA가 고아로 판단하고 자동으로 DELETE 시키는것임.

만약 게시글 수정 로직에서 이미지가 지워졌다. 하면 그 데이터는 지워지는 방법 등으로 씀. 선택적으로 사용합니다.

**OneToOne**

하나에는 하나

정의 : 하나의 엔티티가 다른 하나의 엔티티와 매핑이되는 구조

- > DB관점에서 생각하면

1:1 단방향 매핑 (주 테이블에 외래키)

외래키를 내가 주로 다루는 테이블쪽에 두고 주 엔티티가 대상 엔티티를 직접 참조 (주 테이블에 외래키를 두어야함)

예를 들면 사용자 테이블과 사용자 테이블 등등

1:1 양방향 매핑

- > 외래키를 가진 쪽이 연관관계의 주인

양방향으로 묶어두면 그래프 탐색 편하고 잘됨.

만약 주 테이블이 아닌 곳에 외래키가 잇으면.. fetch=LAzY가 이어도 JPA가 무시하고 즉시로딩처럼 처리한다.

근데 잘 없음 웬만해서는 1대n으로 열어놓음

테이블 구조가 바뀔 수 있기에

1. 지연로딩 제역.. 외래키 없는 쪽에서 조회하면 즉시 로딩 걸리니까.
2. 쿼리 최적화 난이도

정리 :

- OneToOne 매핑은 두 엔티티 1:1로 결합한다
- DB에서는 외래키에 Unique 제약 걸어서 보장한다.
- 실제로 일할 때는 확장성 때문에 기피하긴함.
- 외래키 대상 테이블에 두고 양방향으로 묶으면 JPA가 프록시 생성 못해서 지연 로딩 못하고 N+1문제가 발생 할 수 잇음

**Proxy**

엔티티 연관관계 계속 배워오고 있음

- > 매핑 해두면 객체 그래프 따라서 가져오기 쉽다.

잘못 설정하면 안티패턴 발생

- >post하나 조회 했는데 거기에 엮여잇는 모든 정보를 가져오지 않기 위해 lazy를 쓰고
- >그걸 가능하게 해주는게 proxy

정의 : 대리인

약간 치킨 시켯는데 진동벨 주는데 그게 프록시 라고 생각해도 됨.

예를 들어 getReference를 호출해서 프록시에게 ID=1 등 조건을 던져주면

그걸 실제로 조회할때 프록시가 자신이 갖고 있던 내부 참조를 진짜 엔티티랑 연결을 하는 것임.

사용 이유 :

연관된 엔티티를 실제로 사용할 때까지 조회를 미뤄, 초기 쿼리 수를 줄이고 성능을 최적화하기 위해서

왜 그럼 내부에서 프록시를 써야하는가?

프록시 사용 방법

이미 지연 로딩 안에 프록시의 개념이있다.

타입 비교 시의 주의 사항

우리가 자바 코드 짜다 보면 두 객체의 타입이 같은지 비교해야할 떄가 있다.

if(user1.getClass() == user2.getClass()) 이건 자ㅣ바에서 상관없음 문제 없음 ㅇㅇ

근데 JPA 환경, 프록시가 돌아다니는 환경에서는 문제를 일으킴. 방금 코드 예시처럼 진짜 엔티티 클래스는 user지만 객체의 클래스는 hiber xxx로 나올 수 잇음

비즈니스 로직상으로는 같은데 getclass 하면 false가 나오는 상황

그래서 instanceof로 연산자는 비교해야한다.

프록시 객체는 원본 엔티티 클래스를 상속 받아서 만들어짐.

자바에서 자식 클래스는 부모 클래스의 instanceof 비교를 통과함. 그래서 진짜 엔티티든 가짜 프록시 엔티티든 true를 탄환함.

Lazy exception : 프록시가 지연로딩 때문에 데이터를 영속성 컨텍스트에서 가져오려고 하는데 영속성 컨텐이너가 닫힌 상황.

해결 -> DTO를 반환하면 됨 서비스에서 컨트롤러로 반환하지 말고.

정리 :

- 프록시는 지연 로딩을 위해 실제 DB조회를 미루고 반환되는 가짜 껍데기 객체이다.
- 프록시는 내부에 ID만 갖고 있다가 살제 데이터가 필요한 순간 영속성 컨텍스트를 통해서 DB조회해서 초기화한다.
- ==대신 instance of 써야한다.
- 영속성 컨텍스트가 닫혀잇으면 LazyinitException 발생

**JPQL의 정의**

엔티티 어떻게 설계하고 객체간의 연관 관계 어떻게 맺고 지연로딩, 프록시가 뭔지 배웟는데

,,

좀 더 실무적인 방법임.

- > MySQL 쓰다가 Oracle로 바뀌면 DB에 종속적인 쿼리들을 고치거나 수정을 해야할 때가 있음.
- > JPQL이라는 추상화된 객체지향 설계를 유지하는것임.

사용 방법

JPQL에서 쿼리의 대상은 테이블이 아니라 엔티티 이름이다.

그리고 반드시 별칭을 부여해야한다.

만약 JPQL의 update나 delete를 해두면 영속성컨텍스트를 무시하기 때문에, 1차 캐시에 남아잇던 예전 데이터가 남아잇어 불일치가 일어날수잇다.

이를 해결하기 위해서 flush나 clear를 해줘야함.

JPQL은 치명적인 단점이 있다.

- > 문자열 이라는 점
- > 빌드할 때는 오류가 안남. 문자열이기 때문에

그 안에 들어있는 내용이 문법에 맞는지 아닌지는 모름.

- > 따라서 이것은 런타임에 터짐. (오타 같은 것으로)

이걸 해결하기 위해서 Criteria Api, QueryDSL 같은 것을 쓴다.

코드로 짜니까 오타가 나면 무조건 컴파일 에러로 잡을 수 있을까?

- > 그것도 아니긴함.

JPQL과 순수 SQL의 차이점이 무엇이냐?

A. SQL은 DB의 테이블과 컬럼을 대상으로 하고 JPQL은 엔티티 객체와 필드를 대상으로 한다. 이렇게 하기 때문에 DB에 독립적인 쿼리 쓸 수 있다.

JPA 에서 벌크연산 수행 할 때 주의점이 무엇인가?

A. 벌크 연산은 영속성 컨텍스트 무시하고 DB에 바로 꽂아버리기 때문에 연산 직후에 영속성 컨텍스트랑 DB 불일치 발생 할 수 있음.

가져가야 할 핵심

- 다대일 관계에서 외래키의 위치와 연관 관계 주인 누구인지
- 객체 그래프 탐색 위해서 단방향 매핑과 양방향 매핑 차이점
- 즉시 로딩과 지연 로딩의 차이. 지연 로딩을 기본으로 사용하는 이유 -> 이 둘의 개념은 프론트엔드에서도 성능을 위해 이런 개념이 나타남.
- 1:N 단방향 매핑의 단점과 대다일 매핑이 표준이어야 하는 이유.
- 영속성 전이에 대한 이해
- OneToOne 매핑의 기본 구조랑 OneToOne에서 외래키 위치를 어디에 두는가에 따라서 연관관계 주인 차이
- 지연 로딩 제약이랑 프록시 문제
- OneToOne을 사용하지 않아야 하는 경우
- 프록시 객체의 초기화 과정
- 프록스 객체의 개념이랑 db조회 지연 시키는 내부 동작에 대한 이해
- JPQL은 테이블이 아닌 엔티티 객체를 대상으로 작성하는 쿼리 언어
- 영속성 컨텍스트와 DB간의 상태 불일치.
