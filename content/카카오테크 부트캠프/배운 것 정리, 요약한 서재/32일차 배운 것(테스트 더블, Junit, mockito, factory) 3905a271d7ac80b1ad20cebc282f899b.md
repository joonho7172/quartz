**테스트 더블**

- > 테스트 코드는 결국 서비스, 컨트롤러 등 실제 로직의 동작을 가져와서 수행 시켜야함.
- > 주문은 DB 호출해서 저장하거나 해야하고 회원가입 로직 안에서 이메일 서버 부르는 등 .. 의존성이 다 있음.
- > 이런 외부 의존성을 가져오는 순간 테스트가 느려짐.
- > 이런 문제를 해결하기 위한 도구

정의 : 테스트 하려는 코드가 의존하는 실제 객체를 대신하는 가짜 객체.

SUT - System Under Test : 테스트의 대상이 되는 코드( 주문, 회원 가입, 글쓰기 등)

SUT가 일을 하기 위해서 빌려 쓰는 다른 객체

왜 이걸 써야 하는가?

- 코드 대부분이 Java만으로 해결되지 않음. Db에 접근 할 때도 있음 (실제 의존성)
- 이걸 그대로 쓰면 테스트 느려지고, 외부 환경 바뀌면 결과가 달라짐
- 네트워크 오류 같은 상황도 재현해서 그 상황에 우리가 의도한 예외 처리?
- 테스트 더블을 사용하면 실제 의존 객체를 흉내내서 테스트가 외부 환경과 분리된 채로 빠르고 안정적으로 돌아가도록 도와줌.

종류 : dummy, fake, stub, spy, mock 등이 있음.

- > stub이랑 mock 중심.

**사용 방법**

1. STUB

상태를 검증하기 위해서 사용하는 가짜 객체

Stub은 호출 되었을 때, 미리 준비된 고정 답변을 돌려주는 객체임

- > 메소드가 호출되면 이 값을 반환하라는 것이 stub의 역할.

언제 사용?

- 테스트 대상이 의존 객체로부터 어떤 값을 받아와서 그 값을 가지고 로직을 수행하는 경우
- 우리 관심사가 의존 객체가 호출되었는지가 아니라 값을 받은 테스트 대상이 올바른 결과를 내는지 궁금 할 때,
    - 테스트 의존이 DB에 있을때..

결과 상태를 검증하는 방식을 상태 검증이라고 부름 이때 저장소가 stub 역할을 했다고 볼 수 있음.

- > 실패한다면.. DB나 의존성 객체를 볼 것이 아니라 비즈니스 수행 로직을 살펴 봐야함.
1. Mock

행위 검증을 하기 위해 사용하는 가짜 객체.

Mock도 답변을 설정 할 수 있지만 목적은 다름.

특정 메소드가 올바른 인자와 함께 정확한 횟수만큼 호출 되었는지를 검증하는 객체.

- > 이 메소드가 특정 조건으로 호출 되었는지 확인..

언제 쓰는가?

- 테스트 대상이 의존 객체의 메소드를 올바르게 호출 했는지 자체가 중요할 때..
- 반환 값에는 관심이 없을 수 있음. (뭐 알림 메소드나 sendEmail 메소드 등)
- 이러한 것이 행위 검증임. 함수를 반환하거나 결과를 돌려주는게 아니라 의존 객체와 어떻게 상호작용을 했는가?
- 호출 여부를 감시하는데 쓰인 이메일 클라이언트가 Mock 역할을 한다.

stub과 mock은 검증의 시선이 다르다.

stub은 단순히 정해진 답변만 하는 역할.

mock은 테스트 대상이 특정 메소드를 제대로 호출 했는지 감시함

- > 답변의 내용 자체보다 외부 메소드를 제대로 호출 했는지

stub과 mock의 차이

stub은 테스트 올바르게 굴러가도록 상황을 만들어주는 역할

- > 검증의 대상은 테스트 대상의 최종 상태(반환 값)

stub이 돌려준 값을 받아서 테스트 대상이 올바른 결과를 냈는가를 봄

- Stub 쓴 테스트는 보통 assertEquals 나 assertTrue같은 ㄴ결과 검증으로 끝남.

Mock - 의존 객체와의 상호작용

- > verify

너무 많이 테스트 더블을 쓰면 생기는 일

- 과도하게 많이 쓰면 테스트가 내부 구현 방식에 강하게 묶임
- 내부적으로 상호작용한다고 가정
- 각각의 호출을 verify검증하면..
- 리팩토링 할 때 기능의 최종 결과는 같은데 호출 방식이 달라져서 테스트가 깨짐.
- 리팩토링 할 때마다 테스트 재설정

정리 :

- 테스트 더블은 테스트 대상이 의존하는 실제 객체를 대신하는 가짜 객체.
- 외부 의존성이 테스트를 느리게 만들거나 할 수 있어서.
- 테스트 더블로 의존성 격리하면 FRI 지킬 수 있다. 오늘은 stub이랑 mock의 구분이 중요함.
- stub은 상태 검증.
- mock은 행위 검증.

**Junit**

@Test나 assert~ 같은 코드가 어떤 도구에서 올라가는지

핵심은 어노테이션 이름을 외우는 게 아님

- > Junit 이 테스트가 성공했는지 실패했는지 사람 대신 자동으로 판단해주는 도구

정의 :

JVM에서 실행되는 테스트 프레임 워크

그 규칙 맞춰서 테스트 메소드 작성하면 Junit이 알아서 결과를 알려줌

사용 방법

@Test 어노테이션을 붙히면 Junit에게 테스트 메소드라고 선언

그럼 Junit이 알아서 테스트 어노테이션 실행함. 메소드 이름은 자유

assertNotNull도 있고, assertEquals.. assertThrows -> 의도한 예외가 던져졌는지 확인

@BeforeEach -> test실행 되기 전에 매번 실행되는 역할.

@AfterEach -> 테스트 끝난 후에 매번 실행, (리소스 반환 할 때..)

‘’ All 도 있다. -> 각 테스트가 아니라 클래스 전에서 딱 한번만 실행됨, 무거운 작업을 하고 싶을 때

assertThrows는 발생한 예외 객체를 돌려줌, 그걸 바다서 assertEquals까지 사용 가능

단순히 예외를 넘어서 의도한 메시지와 함께 발생했는지 확인 가능.

정리:

- Junit 테스트 프레임 워크, 테스트의 성공과 실패를 사람이 아니라 도구가 판단 해준다.
- 어노테이션 외우는게 목적이 아니라 도구가 준비 실행 검증이라는 흐름 안에서 녹아 들어가 있다.
- assertThrows를 통해서 예외를 던지고 그에 대해서 테스트 하는 상황 -> 테스트 코드 처음 작업하면 성공 케이스만 작성하는 경우가 잇는데, 좋은 테스트 코드는 예외에 대해서 얼마나 꼼꼼하게 작성했는가가 중요 함.

**Mockito**

테스트 더블 할 때 가짜 클래스 만들었는데,

Mockito 는 가짜 클래스를 좀 편하게 만들어주는 도구임.

(테스트 더블 편리하게 만들어주는 도구)

- > mock만 아니라 stub의 역할도 함

Mock 메소드로 만든 객체여도 when theReturn 이면 stub이고 verify로 행위 검증하면 stub

정의 :

테스트 더블 자동으로 만들어주고 가짜 객체가 어떻게 답할지를 정하고 테스트 대상이 그 객체랑 제대로 상호작용 하는지 검증하는 도구

테스트 더블 만드는 귀찮은 작업을 자동화해서 비즈니스 로직에만 집중.

사용 방법

1. 의존성 추가 (Gradle)
2. Mock 객체 생성
    1. 의존 객체 위에 mock 어노테이션을 붙일 수 있음.
    2. EX)
    3. @Mock
    4. Private CarRepository carRepository 같이
    5. 그러면 mockito가 자동으로 이 필드를 가짜 객체로 만들어줌
    6. 테스트 메소드 안에 Mockito.mock 직접 호출해서 처리하는 것도 가능.
    7. 보통은 어노테이션 붙혀서 사용함
3. Stubbing
    1. 스터빙은 의존 객체의 답을 우리가 통제해서 테스트 대상을 안정적으로 검증이 가능하게 함.
4. Verification(행위검증)
    1. 스터빙으로 상황 만들고 테스트 대상 실행 후 마지막으로 검증 하는 단계
    2. 아까 봤던 mock이랑 사용방법 같은. 호출 행위를 검증 하는 것.
    3. injectMocks - 전에 만든 mock을 넣어주는 어노테이션.

**Factory**

디자인 패턴이란? -

개발자가 실제로 개발하면서 반복적으로 부딪힌 설계 문제를 푸는 검증된 해결 구조.

일종의 패턴으로 정의 해두면 개발자들끼리 소통하는데도 공통된 워딩이고 언어가 됨.

어떤 문제를 해결할까?

- 코드에 대한 문제가 첫번째, 두번째는 아키텍쳐 레벨의 문제
- 디자인 패턴은 코드 레벨의 문제를 다루지만 확장하면 아키텍쳐 레벨의 문제를 다룰 때도 비슷하게 적용되는 개념이 있다.
- 시간이 지날 수록 복잡성이 높아지고 시간과 비용이 들음.
- 이런 문제를 줄이기 위한 방법이 디자인 패턴.
- 디자인 패턴은 일종의 약속.
- 책임 분리를 하고, 변경 지점을 한 곳으로 모으고 SOLID 원칙과도 연결이 됨.
- 자연스럽게 스프링에서 배웠던 IoC, DI 같은 개념과 연결이 됨.

팩토리가 다루는 문제는 객체를 만드는 일

- > 객체 생성. 우리가 평소에 아무 생각 없이 쓰는 new가 흩어지면 안좋은 점

정의:

객체 생성 책임을 호출부로부터 분리해, 생성 방식과 의존 관계를 한곳에서 관리하는 클래스

public class PaymentService {

public void pay(String type) {

Payment payment;

if ("CARD".equals(type)) {

payment = new CardPayment(cardClient, feePolicy);

} else if ("BANK".equals(type)) {

payment = new BankPayment(bankClient, feePolicy);

} else {

throw new IllegalArgumentException();

}

payment.pay();

}

}

구현체를 만들려면 어떤 재료가 필요한지 알고 다 알아야 함.

를 paymentFactory와 paymentService로 나누어서 관리 가능함.

서비스가 더 간결해지는거임.

더이상 카드와 뱅크의 페이먼트와 같은 구체 클래스를 몰라도 됨.

즉, paymentService가 클라이언트,

만들어지는 대상인 Payment가 product.

실제 구현체인 페이먼트가 concrete product.

생성 책임을 가져간 paymentFactory가 Factory

이렇게 책임을 나누어 갖고 쪼개진다.

- > 누가 무엇을 알고 있어야 하는가
- > 생성에 관한 지식은 팩토리만 알고 있으면 된다.

왜?

- 객체 생성 방식을 호출부에서 분리해 생성 규칙 변경이 코드 전반으로 확산되는 것을 막고, 의존 관계와 테스트를 예측 가능하게 바꾸기 위해서

팩토리가 있으면 어떤 구현체로 만들지 넘길지 하는 로직이 팩토리 한곳에 모여 있다.

- > 변경 지정이 흩어지지 않고 한 곳으로 수렴.

팩토리는 의존 관계 정리하는 역할도 함.

- 객체 하나 만드는데 필요한 부품이 많아지면 호출부에서 가져다가 조립해, 순서나 로직이 섞임.

테스트 관점에서도 이점이 있음.

사용 방법:

객체를 직접 new로 생성하지 않고, 생성 책임을 전담 하는 클래스나 메서드를 통해 생성함. - 스프링 컨테이너에서는 객체를 만들고 알아서 의존 관계 조립해서 넣어줌

그러나, 생성 규칙이 복잡한 경우에는 팩토리를 사용함.

spring이 대부분 해주지만, 모든 생성 규칙을 설정 만으로 깔끔하게 표현하기 어려운 경우가 잇음

- > 조건에 따라 구현체 골라야 할지 판단이 복잡하거나 객체를 만드는 과정에 도메인 규칙이 끼어들거나 하는 경우.
- > 그래도 객체 생성은 스프링, 그 중에서 선택은 팩토리가.

팩토리 클래스부터 먼저 만드는 것보다 생성 규칙이 단순하면 스프링 설정이랑 의존성으로 처리..

생성 과정에서 조건 분기가 얽히고 객체를 조립해야한다면 -> 도메인 판단

- 그때 팩토리 도입해도 좋음
- Order order = new Order();

정리:

- 팩토리가 해결하는 문제는 객체를 만드는 규칙이 코드 곳곳에 흩어지는 상황을 해결한다.
- new가 흩어지면 모든 호출부를 다 고쳐야함
- 팩토리가 분리하는 책임은 생성 책임이다.
- 어떤 구현체를 만들지 의존 객체를 넘길지
- 변겅지점 한곳으로 모으고 팩토리만 고치면 됨

디자인 패턴이 기존에 배운 프레임 워크와 어떻게 연결되어 있는가?

가져가야 할 핵심

- 테스트 더블이 무엇이 왜 쓰는지? (외부 의존성 격리가 필요한 이유)
    - 테스트 대상이 의존하는 실제 객체를 대신하는 가짜 객체
- 가짜 객체의 종류가 여러 개.. 이 중에서 stub이랑 mock의 차이점
    - > 상태 검증과 행위 검증의 차이
- Junit의 본질은 자동으로 테스트 결과 판정.
- Junit은 결국 어노테이션이랑 Assertions 두 축으로 돌아감
    - 어노테이션은 결국 테스트의 구조와 흐름을 정의
    - Assertion은 기댓값과 실제 값이 같은가 처럼 결과를 검증함.
- 모든 도구는 준비 - 실행 - 검증의 어딘가에 들어감.
- mockito는 새로운 개념이 아니고 가짜 객체 코드 몇줄로 만들어주는 도구. 새로운 이론이 아닌, 이미 아는 개념이 어떻게 코드가 되는지.
- 테스트 대상이 내놓은 결과값 검증과 제대로 호출됐는지 확인하는 검증이 있음.
    - 테스트 코드 볼 때, 문법 보다는 테스트 하는 대상이 무엇인지, 격리하는 의존성이 무엇인지, 무엇을 검증하려 하는지 이해를 하는 것이 우선임.
- 팩토리는 객체를 만드는 책임을 그 객체를 쓰는 코드에서 떼어내는 패턴
- 객체 new로 만드는 코드 많이 있으면 생성 방식이 바뀔 때 그 자리를 다 고쳐야 하는데 팩토리는 이걸 다 해결한다.
- 책임 - 팩토리는 결제를 처리한다와 같은 원래 일과 결제 객체를 어떻게 만든다는 생성 책임을 갈라놓음
