**Strategy Pattern**

팩토리는 생성 책임 분리에 초점.

전략 패턴은 객체가 어떻게 동작 할 것인가에 대한 문제. (처리 방식)

- 행위, 동작 방식을 분리하는데 초점을 맞춘다.
- 전략 패턴은 자꾸 늘어나는 처리 방식을 어떻게 구조적으로 정리할 것?

정의 :

변경 가능한 행위를 인터페이스로 분리하고, 실행 시점에 구현체를 교체 할 수 있도록 설계하는 객체.

변경 가능한 행위를 인터페이스로 분리함.

- > 행위는 메소드 같은 작은 단위가 아님. 특정 상황에서 적용되는 처리 규칙이나 절차.
- 결제 처리, (카드 결제, 계좌 이체)
- 서로 다른 처리 흐름을 독립된 객체로 떼어 내는 것

실행 시점에 구현체 교체.

- 전략 패턴과 클래스를 나누는 것을 구분 짓는 지점
- 컴파일 하는 순간에 무엇을 쓸지 .. 어떤 전략을 쓸지 결정 가능.

역할

1. 전략을 사용하는 객체(컨텍스트)
2. 실제 처리 규칙을 담고 있는 전략 객체. 처리 방식을 안에 감추고 똑같은 형태의 계약만 내보냄
3. 계약이 인터페이스

각 객체가 무엇을 알고 몰라도 되는지 정의하는게 중요함.

- 어떤 기능을 해야한다는 것만 알면 됨
- 처리 방식에 대한 판단과 구현은 전략 객체 쪽에 있음.
- 실행 시점애 어떤 전략이냐에 따라 동작이 달라짐.

사용 이유

변경되는 처리 규칙을 한곳으로 수렴시켜 조건 분기 폭증을 막고, 변경 시 영향 범위를 예측 가능하게 통제하기 위해서

---

- > if 문 사용의 불편함 해소 가능.

디자인 패턴 적용할 때 어떤게 변경 빈도가 높고, 변경 가능성이 있을 것인지 인지 하는게 중요함.

- > processPayment의 책임이자 바뀌지 않는 것은 결제를 처리 한다는 목적
- 바뀔 여지가 있는건 결제를 처리하는 구체 방식.
- 처리 규칙을 하나의 메소드에 쌓는 것 보다 각 규칙을 별도의 전략 객체로 분리해두면 , 전략을 하나 더 만드는 형태로 정리

그렇다고 너무 막.. 다 바꿔버리진 말것.

개발자가 맥락이랑 상황을 파악해야하고, 기획에 대해서도 알고 있어야 함.

- > 결제 예시로 들면 새로운 페이를 추가 할 수 있어야 함.
- > 판단이 필요할때 기획자에게 물어보고 확인하는게 필요하다.

사용 방법

(순차적으로)

1. 변하는 부분을 찾고 그 부분이 따라야 할 약속을 정하고 구현 컨텍스트를만들고 어떤 구현을 쓸지 실행 시점에 고르는 것.
2. 전략 분리 대상 식별(무엇이 변하고 무엇이 불변하는 지)
3. 전략 인터페이스 정의
    1. 분리 대상을 정했으면 여러 처리 방식이 공통으로 따라야 할 계약을 인터페이스로 정의
4. 전략 구현체 분리
    1. 조건 분기 하나가 여기서는 구현체 하나로 대응.
    2. 각각을 interface를 상속하는 class로 묶던지
5. 컨텍스트 구성.
    1. 인터페이스 하나에만 의존하고 주어진 전략을 호출 하는 책임
6. 실행 시점 전략 선택
    1. 결제 서비스 코드를 고치는게 아니라 주입하는 전략 객체만 바꾸면 됨
    2. new가 아닌 스프링에게 맡김.

DI랑의 차이점?

- 해결하려는 문제의 층이 다름.
- 전략 패턴은 변경 행위 자체를 어떤 객체 구조로 떼어내는지, 이 기능의 처리 규칙이 언제 바뀌는지.
- DI는 그 선택을 어떻게 연결 할 것인가, 그냥 책임을 외부로 빼내는 것.

전략 패턴으로 갈아 끼울 수 있는 구조를 먼저 설계, 전략 객체를 실제로 끼워넣을 때 DI를 쓰는 것.

(전략 패턴으로 구조를 먼저 잡고 Di로 전략을 주입 한다.)

정리 :

- 전략 패턴이 푸는 문제는 같은 목적을 두고 처리하는 방식이 자꾸 늘어날 때 if문이 폭증하면서 변경이 어디로 될지 모르는 것을 막는다.
- 분리 하는 책임은 , 고정된 목적 -> 컨텍스트 , 유동적인 방법 - 전략 객체로 끼워넣음
- 전략 패턴은 행위를 분리, Di는 선택을 연결하는 방식.

**Proxy Pattern**

객체를 어떻게 다루느냐가 아닌 객체에 어떻게 접근하느냐를 설계 하는 것

정의 : 대리인

실제 객체에 대한 접근을 대리 객체가 제어하며 호출 전후에 공통 처리나 접근 통제를 삽입하도록 설계

클라이언트 (호출 하는 쪽)은 실제 객체를 쓴다고 착각.. 실제로는 프록시?!

어차피 클라이언트는 모름

프록시는 단순히 호출만 전달이 아님

- > 실제 객체에 요청을 넘기기 전이나 필요한 처리를 끼우기 가능.

상황에 따라서는 요청 자체를 막거나 미루는 것도 가능.

프록시 패턴은 실제 객체에 일을 더 시켜서 문제를 푸는 것이 아닌 실제 객체 앞에서 제어 지점을 하나 더 두는 방식.

- 실제 객체는 자기 일에만. 부가적인 관심사는 프록시가.

사용 이유 :

객체 접근 시점에 공통 제어 로직을 끼워 넣어 실제 객체를 수정하지 않고도 접근 통제와 부가 처리를 일관되게 적용하기 위해서

해당 메소드의 책임에 따라서 가변성과 불변성을 알아야 함.

- > 프록시는 둘을 떼어놓음.

실체 객체 앞에서 호출이 반드시 프록시를 거치도록 함.

프록시는 언제 실제 객체를 부를지까지 제어 할 수 있음.

사용 방법

실제 객체와 동일한 인터페이스를 구현한 대리 객체를 두고, 클라이언트는 대리 객체를 통해 실제 객체를 호출하는 형태로 구성.

우선, 프록시와 실제 객체가 같은 계약을 공유해야함.

1. 프록시도 같은 interface를 구현함.
2. 그래서 클라이언트가 프록시를 호출해도 type 관점에서는 같은거임
3. 실제로 구현한 실제 객체, 를 안에서 target으로 구현함 (선언 해줌)
4. 그리고 안에서 override로 안에서 실행 로직이나 관심사를 넣는 것.
5. 프록시는 접근 정책을 적용하는 위치.

클라이언트 호출 경로 고정.

프록시가 효과를 가지려면 호출 경로가 프록시로 고정이 되어야함.

실제 객체를 만들고, 프록시가 감싸고, 넘겨줌.

- 프록시패턴에서는 호출이 반드시 프록시를 통과해야 한다, (경로 고정)*

**프록시와 혼동하기 쉬운 구조**

MVC에서의 컨트롤러.. (비즈니스 로직 대신 호출해주니까 프록시인가?)

당연히 아님. 구분 기준은 같은 인터페이스를 구현해서 대신 행세 하냐는 것.

필터/ 인터셉터는 ?

프록시는 객체를 대신 제어하고, 필터와 인터셉트는 객체 대리가 아니라 http 요청과 응답, 흐름 전체를 가로 챔.

AOP는 ?

사람이 손으로 프록시 클래스는 짜는 일은 없음.

스프링이 대신 만들어줌..

@Transacntional 이 대표적인 예.

직접 로깅을 끼워넣는것과 비슷하게 .. 작동함.

같은 클래스 안에서 메소드가 다른 메소드를 this로 호출하면 프록시 거치지 않음.

- Transactional 있어도 걸리지 않는 경우가 생김.
- 외부에서의 호출은 프록시 지만, 내부에서 부르는 호출은 실제 객체 부르기 때문에 걸리지 않음.

self_invocation 문제 / 자가 호출 문제

같은 클래스 내부에서 호출 했을 때, 프록시로 전환이 안됨.

외부에서 접근 할 때만 가능함.

**Adapter Pattern**

프록시와 비슷하게 객체와 객체 사이에 중간을 둔다는 점은 비슷함.

- > 목적이 다름
- > 프록시는 인터페이스를 둔 채로 접근만 통제, 어댑터는 인터페이스가 맞지 않을때 차이를 변환해서 연결

코드를 처음부터 원하는 모양으로 작성할 수 없음.

- > 이미 만들어진 레거시 코드가 있고 결제 외부 APi처럼 외부 라이브러리를 써야 할 때가 있음.

정의 :

호환되지 않는 인터페이스를 가진 객체들이. 함께 동작하도록, 중간 객체가 변환해주는 객체지향 구조 패턴.

호환되지 않은 인터페이스

- > 클라이언트, 기능 사용하는 쪽은 어떤 메소드 이름이나 어떤 파라미터, 어떤 반환 형태를 기대하고 있음.
- > 실제 외부 라이브러리나 레거시 객체는 전혀 다름.
- > 어댑터 패턴은 이 차이를 중간 객체 하나로 해결을 함.

클라이언트가 기대하는 인터페이스를 Target, 이미 존재하지만 맞지 않는 객체를 adaptee

타켓 구현하면서 내부에 어댑티를 호출하는 반환 객체를 adapter라고 함.

사용 이유:

기존 수정 없이 시스템이 기대하는 인터페이스를 사용하기 위해서.

서비스 코드를 외부 라이브러리 모양에 맞추면 동작은 하지만..

외부 이름과 형식을 알아야 함.

이 상태에서 버전이 바뀌거나 하면 서비스 코드도 수정을 해야함.

어댑터 패턴은 이 결합을 끊기 위함임

서비스는 PaymentClient 라는 계약을 바라보게 하고 외부 호출 규격을 모아서 처리 가능함.

기존 코드를 고치기 어려운 상황에 유용,

사용 방법:

(순차적으로)

1. 외부 객체를 보는게 아니라 우리 시스템이 무엇을 원하는지 정해야 함.
2. 호환되지 않는 인터페이스 상황

제일 먼저 인터페이스가 맞지 않는 상황을 분명히 봐야함.

1. Target 인터페이스 정의
    1. 클라이언트가 기대하는 인터페이스를 고정 하는 것.
    2. 시스템이 결제 객체에게 기대하는 계약
    3. (우리 시스템의 안쪽의 언어를 먼저 정한다는 점, 우리가 기준이다.)
2. 기존 객체(Adaptee) 확인
    1. LegacyPgClient가 그 대상, 객체.. 레거시 코드라고 보면 됨.
3. Adapter 구현
    1. 타켓 인터페이스를 implement하고, adaptee를 내부에 품음.(파라미터로)
    2. adaptee는 나중에 선언 해줘야 함.
4. 클라이언트 호출 구조

외부 객체의 호출 형태를 우리 스셑ㅁ이 기대하는 인터페이스에 맞게 바꾸는 경우가 어댑터임. requestPayment 직접 호출하던 페이먼트 서비스랑 비교하면 paymentClient에 의존함.

더 큰 개념이 포트 앤 어댑터 구조와의 연결.

나중에 규모있는 서비스가 있으면, 서로 다른 성격의 코드가 있으면..

문제는 이 둘이 한 덩어리로 엉킴. 비즈니스 로직 한 가운데 특정 결제사 문법이 섞여 있으면 번거로움..

어댑터 패턴은 객체 하나 수준에서 인터페이스 불일치 해결하는 방향.

포트 앤 어댑터는 어플리케이션 전체를 바깥 세계랑 어떻게 나눌지 정하는 방법이고 스타일.

둘이 같은게 아니라 아이디어가 아키텍쳐 안에서 외부 기술을 내부 계약에 맞추는 구현 방법으로 쓰임.

어댑터는 외부 계약을 우리 계약에 맞추는 역할만 함. 비즈니스 판단이 모이는 자리가 되어서는 안됨.

**Observer Pattern**

어댑터 패턴은 모양이 안맞는 것을 끼워 맞추는 구조 패턴.

옵저버는 행위에 대한 패턴. 앞에서 배운 전략 패턴이랑 조금 비슷함.

- 옵저버는 한 객체의 상태가 바뀌었을 때 변화에 반응해야하는 객체가 여러개일 때를 다룸.

정의 : 어떤 대상의 변화를 지켜보는 사람, 또는 존재를 말함.

변화가 일어난 쪽이 등록된 관찰자들에게 알려주는 구조임.

Subject : 상태를 갖고 있고 옵저버의 등록, 해제, 통지를 관리하는 객체.

- 변화의 중심. 누가 나의 변화를 듣고 싶어 하는지

Observer : 서브젝트의 변경통지를 받아 정해진 반응을 수행하는 객체.

- > Subject는 자기 변화에 반응하는 observer가 구체적으로 무슨 일을 하는지 자세히 알 필요가 없다.
- > 옵저버들이 공통으로 따르는 인터페이스가 하나만 알고 있고 상태가 바뀌면 등록된 옵저버들에게 바뀌었다는 사실만 정리

하나의 서브젝트 상태 변화에 여러 옵저버가 동시에 반응 할 수 있고 새로운 observer 추가 하더라도 크게 건들이지 않음.

사용 이유 :

상태 변화에 따른 후속 처리를 Subject 내부에 직접 쌓지 않고, 책임을 나누기 위해

변하는 것 - 그 다음에 무엇을 할지의 후속 처리

변하지 않는 것 - 주문 상태가 바뀐다는 핵심 흐름이 예시

subject는 상태가 바뀌었다는 사실을 통지하는 것 까지.

그 변화에 어떻게 반응할지는 각각의 Observer가 가져감

- 새로운 후속 처리 필요하면 기존 코드 고치는게 아니라 새로운 옵저버 만들어서 등록하면 됨

subject는 상태 변경과 통지라는 한가지 이유를 갖고, observer는 후속반응이라는 자기 변경 이유만 갖음.

- 기존 반응을 계속 추가하는게 아니라 observer를 추가하는 방식으로.

사용방법

Observer 인터페이스를 정의하고 subject가 목록 관리하면서 상태 변경시 알림 통지.

1. 상태 변경 주체 식별
    1. 어떤 객체의 상태변화가 후속 처리를 만들어 내는지
2. Observer 인터페이스 정의
    1. 옵저버들이 공통으로 따라야 할 계약을 인터페이스로 정의
    2. 인터페이스가 하는 일은 주문 상태 변경 이벤트를 받았을 때 무엇을 할지의 형태를 고정 하는 것..
3. 구체 Observer 구현
    1. 실제로 반응할 객체들을 하나씩 구현
4. 구독 / 해지 구성
5. 상태 변경 시 알림 전파
    1. 서브젝트는 주문 상태를 바꾸고 등록된 새 옵저버에게 변경 이벤트를 전달
    2. 새로운 알람이 필요하더라도 그냥 새 옵저버 클래스 만들고 등록해주면 된다.
    3. 서브젝트는 건드리지 않고 할 수 있음.
    4. 변경 지점이 상태 변경 메소드 안에서 새 옵저버 만들고 등록하는 자리로 옮겨갔다.

기본적인 옵저버 패턴 -> 외부 API호출 처럼 오래 걸리는 일 하면 흐름 자체가 느려지고, 중간에 예외 터지면 알림이 안 갈수도 있음.

실시간 알림 시스템과의 연결

예를 들면 어떤 글에 댓글이 작성되었을때 알림, 앱푸시 등..

- > 객체 설계 관점에서는 댓글 작성 상태 변화, 여러 옵저버가 거기에 반응함.

브라우저 실시간 알림

- 우리가 평소에 알고 있는 웹은 요청과 응답으로 돌아감
- 브라우저가 서버에 무언가를 요청하면 서버가 그에 대한 답을 주고 대화 끝
- 보통 요청하는 쪽이 브라우저.
- 근데 실시간 알림은 반대.
- 서버가 알고 브라우저에 알리는것.
- 폴링은 자주 브라우저가 서버에 물어보는 것. (새 소식이 없으면 낭비가 큼)
- 문제를 해결하기 위해서 쓰는 기술이 WebSocket이랑 SSE.

웹 소켓은 브라우저와 서버 사이에 연결을 한번 열어두고 끊지 않은채 자유롭게 메시지를 주고 받음.

통로 뚫어두면 서로 메시지 왔다갔다.

SSE - Server sent Events의 약자

- 말 그대로 서버가 보내는 이벤트 라는 뜻. 서버에서 새로운 일이 있을 때마다 브라우저로 연락함.
- 알림이나 실시간 피드 같은 경우에 잘 어울림.

브라우저는 미리 연결 열어두는 것으로 등록해둔게 됨

- 서버가 상태 변경 마다 소식을 보냄
- 서버는 브라우저가 뭘 하는지 알 필요가 없음. (옵저버 패턴이랑 비슷함)

디자인 패턴에 대한 면접 질문을 하는 건.. 다른 확장된 기술도 받아들일 준비가 되어 있는가.. 아니면 기술 써봣다고 하는데 그 근원에 대해서 아는가? 에 대해서 묻는 것.

- 옵저버 패턴 제대로 이해했다 라고 하는건 상태 변화를 관심있는 여러 대상에게 전달한다는 사고 방식.
- 이걸 알고 있어야 나중에 익숙한 모양을 볼 수가 있음.
- 서버와 서버 사이에서의 이벤트 브로커, 메시지 큐도 비슷한 발상임.

가져가야 할 핵심

- 전략 패턴은 변하는 처리 방식을 고정된 목적에서 떼어내는 패턴.
- Ex) 결제 한다는 목적과 카드, 계좌이체냐 하는 건 따로
- 전략 패턴은 if문 끊임없이 늘어나면서 번지는 문제를 막기 위해서 사용 -> 구조적인 측면.
- 전략 패턴 적용하고 나면 코드 고칠 지점이 분리가 됨.
- 전략 패턴과 Di를 구분할 수 있어야 함.
- 프록시 패턴이 무엇인가 - 실제 객체 앞에 그 객체와 같은 인터페이스를 가진 대리 객체를 하나 세우는 구조
- 다른 관심사를 가진 처리가 섞이면 오염됨.
- 어떤 책임을 어떤 객체로 나누는가. 프록시는 접근 정책만 가져가야 한다는 분리를 설명.
- 어댑터 패턴은 새 기능 만드는 패턴이 아니라 이미 있는 것을 연결하는 패턴이다. (돼지코 어댑터 생각하면 될듯 )
- 세가지 요소로 나뉘어져 있음.
- 우리가 기대하는 계약인 target, 이미 존재하지만 그 계약과 맞지 않은 adptee, 그 사이에서 바꿔주는 adapter
- 지금 패턴의 효과는 변경 지점 한 곳으로 모으는데 있음. 외부 규격이 바뀌었을 때 고쳐야 할 곳이 흩어진게 아니라 하나로 좁힐 수 있음.
- 옵저버 패턴은 상태를 바꾸는 객체랑 그 변화에 반응하는 객체를 떼어놓는 패턴임. 앞에 있는걸 서브젝트, 뒤에 있는걸 옵저버 라고 함 둘 사이를 이어주는 변경 사실을 담은 Event 까지 해서 3가지 요소.
- 뭘 해결하는기? 코드 안에 후속 처리가 계속 쌓여서 비대해지는 것을 해결함.
