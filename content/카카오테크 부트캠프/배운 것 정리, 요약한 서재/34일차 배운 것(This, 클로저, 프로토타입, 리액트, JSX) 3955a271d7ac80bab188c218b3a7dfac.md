**This**

어떤 변수에 접근 할 수 있을지가 코드의 선언 위치를 기준으로 결정

- 위치가 정해지면 결과도 정해짐
- this는 무엇을 가르키는지 함수를 어디에 적었는지가 아닌 어떻게 불렀는지로 결정.

정의:

함수 실행 시 함수 내에서의 실행 맥락을 참조하는 자동으로 할당 되는 지역 변수

- > this는 직접 만들거나 선언하지 않아소 자동으로 만들어지는 변수..

안의 값이 실행되는 맥락, (보통은 어떤 객체)

스코프는 함수를 적어둔 위치로 정해졌다면 this 안에 무엇이 들어갈지는 함수를 어떻게 호출 했는지가 관건임.

- > 같은 함수를 두고도 부르는 방식은 this를 달라지게 한다

사용 이유

함수 안에서 내가 원하는 변수를 찾기 위해서 씀.

- > 함수 본문을 그대로 두고 누구를 대상으로 실행됐는지에 따라서 알맞은 객체를 가르켜 줌.

첫번째 사용자로부터 메소드를 적용하면 첫번째 기준, 두번째 사용자로 부르면 두번째 기준으로 나옴.

- 같은 코드인데 어떻게? This 적용해서..
- 하나의 함수를 여러 객체가 공유해서 쓸 수 있다는 장점.

- 생성자 함수는 특정 형태의 객체를 만들고 초기값을 채워넣는데 쓰는 함수.
- new를 붙여서 호출하면 js는 비어있는 새 객체를 하나 만들고, 그 새 객체를 this 에 연결 해줌
- 그래서 안에서 this.name이랑 this.age는 새 객체의 속성이 됨.
- new는 함수 끝날때 객체 자동으로 돌려줌

**Arrow Func This**

화살표 함수는 this의 규칙을 따르지 않는다.

자신만의 this를 가지지 않고, 자신이 선언될 상의 바깥 스코프에 있던 .. 선언된 위치의 this를 그대로 따라감.

호출 방식과 무관하게 arrow func  계속

자기 this가 없어서.. call, apply this 써도 바꿔지지 않음.

- 화살표 함수 안의 this는 그 객체가 아님.

사용 이유

- > 메소드 안에서 또 다른 callback 넘길때 씀.
- > 어떤 메소드 안에서 setTimeout이나 배열 매소드에 call back 넣을 때..

메소드 안에서 일반 함수를 콜백으로 넘기면 단독 호출 처럼 동작

안쪽 콜백 함수가 바깥 함수의 self를 기억하고 접근 할 수 있는건 함수가 내부의 선언된 변수에 접근 할 수 있음

정리 :

- This가 무엇을 가르키는지, 함수 어떻게 호출 했는지.
- 일반 단독 호출은 기반 바인딩.. stritct는 undefined
- 객체의 메소드 부분으로 부르면 객체를 this로 가르킨다.
- Capp, apply, bind로 직접 지정 우리가 넘김 this가 됨.
- New 로 만들면 새로 생성된 객체가 this로 return
- 화살표 함수는 자기 this가 없어서 바깥 this를 따름.

**클로저**

힘수가 자신이 만들어진 환경을 기억하는 성질.

함수가 자리에서 벗어나 실행되어도 여전히 변수에 접근 가능.

정의 : 일급 객체 함수의 개념을 이용해 스코프에 묶인 변수를 바인딩하기 위한 기술

함수를 반환 할 수 있어야 클로저가 만들어진다.

스코프에 묶인 변수 : 스코프 시간에 배웠던거 처럼 특정 함수 안에서만 접근 가능한 지역변수.

함수를 하나 만들 때 자기가 볼 수 있는 변수들을 함수가 챙겨서 들고 다님.

(바깥 함수의 지역 변수)

클로저는 렉시컬 스코프 라는 토대 위에서 나타나는 현상.

- > 클로저를 이해하기 위해 새로운 무언가를 배우는 것보다.. 스코프와 실행환경을 톺아보는 느낌.

사용 이유

전역 변수의 과도한 사용을 방지하고 변수의 값을 은밀하게 보호하기 위해서

값을 은밀하게 보호..

- > 이렇게 데이터를 숨기고 허락된 방법으로만 접근하게 만드는 것을 캡슐화..
- > 스코프 라는 캡슐화를 클로저가 구현해 주는 도구가 되는 것.

일반 스코프와의 사용 예시 차이 - 일반 스코프는 그대로 함수 호출해서 결과 사용, 클로저는 함수를 반환 받아서 출격

**React**

브라우저가 관리하는 화면의 설계도 -> DOM

화면이 조금만 복잡해져도 내가 원하는 요소를 집어서 직접 갱신하고 하는건 힘들다.

지금 배우는 리액트가 이 지점에서 출발.

리액트 에서는 내가 DOM을 고치는게 아니라 상태만 바꾸면 화면은 React가 알아서 다시 그린다는 것.

정의 :

컴포넌트 단위로 구성된 사용자 인터페이스를 선언적으로 구축 할 수 있는 자바 스크립트 라이브러리

컴포넌트 단위 : 화면 전체를 한 덩어리로 만들지 않고 헤더나 검색창, 목록, 버튼처럼 역할이 있는 작은 UI 조각으로 나눠서 만든다는 뜻.

이 각각의 조각을 컴포넌트라고 함.

화면의 한 부분을 만들어서 돌려주는 함수 하나. 이 함수가 자기가 맡은 ui조각을 결과로 내놓고 조립해서 화면을 구성.

리액트는 이 상태일때 화면은 이렇게 생겼다만 알려주면 그 결과를 실제로 그리는 과정은 리액트가 처리함.

- > useState를 만들어 놓고 setCount를 통해서 값을 변경 시켜야됨

예시 )

사용자가 버튼을 클릭하면 serCount에 count + 1 이 실행됨. 변수 하나를 그 자리에서 즉시 바꾸는 것 과는 조금 다름.

버튼을 눌렀으면 ..

- count가 serCount로 인해서 바뀌고 거기서 화면이 바뀌는 것임..

사용 이유:

복잡한 UI를 선언적으로 구성하여 유지 보수성과 재사용성을 높이기 위해 사용

- > 컴포넌트 기반 아키텍쳐

앞에서 화면을 작은 조각으로 나눠서 만든다. 그 조각 하나하나가 컴포넌트.. 같은 조각으로 여러 곳에서 사용해, 파일이 비대해지는걸 방지

- > 단방향 데이터 흐름

상태를 한곳에서 관리하고 그 값이 필요한 화면쪽으로만 흘러 내려가게 하는 구조

장바구니 바꾸더라도 모든 변화가 중앙 장바구니 상태를 거쳐서만 반영되었다면 그 값이 어디서 바꿨는지 추적하기 편함

- >Virtual Dom

리액트는 상태가 바뀌었다고 해서 실제 DOM을 다 뜯어고치지 않음.

메모리 안에 DOM의 가벼운 사본을 하나 만들어 두고 이전 결과와 새 ㅕㄹ과를 비교해서 실제로 달라진 부분만 골라서 진짜 DOM에 연결.

다른 도구들이 부분적으로 푸는 문재를 3가지 정리

1. 컴포넌트 기반 아키텍쳐 - 화면을 독립한 자금 조각
2. 단방향 데이터 흐름 - 데이터가 한 화면으로만 흐르게 하여 예측 가능성 확보한 단방향 데이터 흐름
3. VDOM - 실제 DOM직접 건드리는 대신 가짜 버츄얼 돔 건드림

items, setItems useState등.. 화면에 뿌릴 문자열

Return 안에서 html 처럼 생긴 코드를 ..

개발자는 이 데이터를 이런 목록으로 보여달라는 결과만 적었고 실제 화면을 그리는 일을 리액트가 했음.

- 선언전 방식

정리 :

- 리액트는 컴포넌트 단위로 UI를 선언적으로 만드는 JS 라이브러리
- 컴포넌트는 화면의 한 조각을 만들어서 반환해주는 함수
- DOM은 브라우저가 그 화면을 트리 구조로 들고 있는 설계도
- 바닐라 JS에서는 내가 이 돔을 직접 고쳤지만 리액트에서는 상태만 바꾸면 리액트가 알아서 다시 그린다.
- 개발자는 어떻게 보여줄지가 아니라 무엇을 보여줄지
- 명령형과 선언적의 차이고 리액트를 쓰는 이유

JSX를 사용하는 이유

1. 변환

JSX는 HTML 처럼 보이지만 실제로는 JS의 확장 문법이고 브라우저는 이걸 이해못함.

그래서 빌드 과정에서 JS형태로 바꿔줘야함.

js로 변역하는 과정,..

1. 개발자 경험 향상

모든 UI를 함수 호출로 작성해야하면 코드 가독성 떨어지고 읽기 어렵다.

1. 빌드 도구 측면에서 최적화

JSX를 JS로 바꾸기만 하는게 아니라 코드를 가볍게 하는 것 같이 이뤄짐

- > 트리 셰이킹 : 실행되지 않은 부분 제거. 가지치기

빌드 과정을 거치면서 변환과 최적화가 함꼐 일어난다.

어느쪽이든 실행 결과는 똑같지만 전송 되는 코드가 작아져서 로딩과 실행이 빨라짐.

1. 컴포넌트 기반 아키텍쳐의 장점

리액트에서 사용할때 했던 이야기와 비슷. JSX에서는 UI를 컴포넌트라는 작은 단위로 쪼개는 방식을 권장.

한페이지를 헤더 , 본문, 푸터(footer) 컴포넌트로 나눌수 있음

JSX의 단점

1. 학습 곡선의 가중

JS문법의 확장 이므로 처음 배우면 혼란스러움.

class대신 className 등..

1. 도구 의존성

브라우저가 직접 이해하지 못해서 Babel이나 SWC로 변환을 해야함

- > 그렇게 하려면 빌드 도구 설정들이 같이 따라옴. Web pack, vite 같이 써야됨
- 단순 바닐라 JS 쓰는 것보다 의존성이 생김
1. 관심사 혼합

화면 그리는 코드랑 데이터 다루는 로직을 한 파일에서 섞어씀.

규모가 커지면 관리가 어려워짐. UI와 비즈니스 로직 분리 필요.

정리 :

- JSX는 HTML이 아니라 JS이다.
- HTML 처럼 생겼지만 빌드 과정에서 전부 함수 호출로 변환됨
- JSX의 모든 규칙은 JS규칙에서 나옴.
- 중괄호 안에는 JS 표현식을 넣는 자리. 문장 불가
- class대신 className, 이유는 : DOM이 쓰는 property이름을 따랐기 때문.

가져가야 할 핵심

- This는 함수가 호출되는 순간에 정해짐.
- 코드를 작성하는 시점이 아닌, 부르는 시점이 기준
- 호출 방식이 여러가지로 나뉘로 this가 가르키는 대상을 정하는 규칙이 따로 있음
- 동시에 적용될 수 있을 때를 위한 우선 순위가 존재, 어떤 방식이 먼저 적용 되는가?
- this는 우리가 직접 통제, call, apply, blind라는 도구로 this를 원하는 객체 불러 옴.
- 함수가 자신의 환경 거이에 있는 변수를 계속 쓸 수 있다.
- 코드 볼 때 신경 써서 봐보삼.
- 왜? 전역 변수를 늘리지 않으면서 어떤 방송 도구로 쓸 수 있다.
- 프로토타입은 객체들이 공통으로 물려받는 속성과 메소드의 묶음.
    - 객체가 자기것만으로 시작하는게 아니라 물려받은 공통 기능 위에서 시작함.
- 프로토타입의 이유는 효율. 똑같은 기능을 마다 복사하지 않고 한 곳에 둬서 쓰기 위해서
- 객체는 자기에게 없는 값을 프로토타입 위에서 갖는다.
- 클래스는 객체를 찍어내는 설계도
- 왜 쓰는가.. - 재사용성, 유지보수성, 가독성
- 상속과 확장에서 주요함.
- 클래스는 새로운 무언가가 아니라 방금의 프로토 타입을 가독성 좋게 표현해주는 문법적 설탕
- 리액트가 무엇인가. 화면을 컴포넌트라는 작은 조각으로 나눠서 선언적으로 만드는 JS 라이브러리
- 리액트는 왜 쓰는가 - DOM직접 조작하면 화면 복잡해질 수록 코드 흩어지고 감당하기 어려워짐
- 무엇이 좋은가 - 명령형은 내가 dom을 직접 고치는 방식, 선언적은 상태만 바꾸면 화면은 리액트가 알아서 다시 그리는 방식.JSX는 HTML이 아니라 JS.화면에서 아무리 HTML 태그처럼 보여도 빌드 과정에서 js 함수 호출로 바뀜.
- 규칙 - 중괄호 안에만 값을 넣을 수 있다라던가 .. if , for는 못넣고 class가 아니라 className을 써야 하는지, 왜 style에만 문자열이 아니라 객체를 넣는지. -> 이런 규칙들이 전부 JSX는 자바 스크립트다 라는 한가지에서 나옴
