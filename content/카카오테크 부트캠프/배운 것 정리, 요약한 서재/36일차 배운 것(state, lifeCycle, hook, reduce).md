**State**

useState 라는 훅으로 선언, 지금은 리액트 기능을 함수 안에서 꺼내 쓰게 해주는 함수.

useState를 쓰면 2개를 돌려줌.

1. 현재 값을 기억하는. 변수
2. 그 값을 바꾸는 함수

setState는 다음 값을 React에게 요청하는 함수.

state는 현재 렌더링에서 사용 할 값

initialValue는 첫 렌더링에서 사용할 초기 값.

Count는 무조건 setCount를 이용해서 변경 해야 함.

만약에 count를 직접 +1를 해주면 리액트는 다시 그리는 신호가 없어 그걸 모름.

그래서 눈에 보이는 숫자도 0.

이러한 문제를 해결하는게 state.

setCount를 호출해서 count 값을 바꿔주면.. 리액트에게 다음 렌더링에서 count를 이렇게 바꿔주세요 라는 의미를 전달하게 된다.

- 요청을 받은 리액트는 카운터 함수를 다시 호출함.
- 이번 호출에서 useState는 아까 기억해둔 새 값을 돌려줌.
- 그러면 새 값으로 JSX다시 계산하고 이전 화면과 달라진 부분만 반영.
- State 변경 - 지금당장 바구는게 아니라 다음 화면에서 새로 계산해달라는 예약.
- useState는 렌더링이 일어나도 일반 변수를 기억해줌.

Todos 라는 배열 상태가 있고 값을 넣으려 할 때, push 대신 … 과 같은 전개 연산자를 사용함.

- 상태를 직접 수정하기 보다 새로운 값을 전달해야 하기 때문. (Spread)
- 객체의 요소를 하나씩 풀어서 복사하는 문법
- 원래 배열을 건드리지 않고 새 객체를 넘겨야 리액트가 정확히 판단함.

상태를 업데이트 할 때 이전값을 참조하려면..

setter대신 함수를 넘기는 것이 더 안전함.

prev는 이전값의 줄임말. 개발자가 넣는게 아니라 React가 알아서 넣어주는 그 시점의 최신 state값.

- > 그래서 바깥의 count를 참조하는 대신 리액트가 건네 주는 값을 받아서 계산한다.

조건부 렌더링에도 사용.. boolean값 이용해서 렌더링 하는 듯.

- State는 비동기적으로 처리 됨.

React에서 setState를 호출해도, 내부적으로는 비동기적으로 처리된다.

- 리액트는 모아서 처리함.

setCount(count +1)을 두번 실행해도 +2가 되지 않는 것 처럼

이벤트 처리 끝난 뒤에 모아둔 변경사항을 바탕으로 다음 렌더링을 한번 수행함.

왜 이렇게? - 성능 때문.

setCount 할 때마다 렌더링 한다면 클릭 한번에 state 변경이 여러번 발생 할 수 있음.

주의해야할 점 :

- 이벤트 핸들러 안에서 바라보는 count 값은 바로 바뀌지 않는다.
- 이번 렌더링에서 count가 0이었다면 안의 count는 0임.

만약에 이전 값을 기준으로 값을 누적해야하면.. 콜백 방식의 prev를 쓴다.

state가 비동기적으로 처리 된다는 말은 리액트가 성능을 위해서 여러 state 변경을 모아서 처리하고, 그 결과로 필요한 렌더링을 한번만 수행한다.

state는 불변성을 지켜야 한다.

- 불변성은 기존 값을 직접 고치지 않는다는 뜻.
- 순수함수랑도 연결이 됨.

순수 함수는 같은 입력이 들어오면 항상 같은 결과를 반환하고 함수의 바깥을 직접 바구지 않는 함수.

리액트는 기본적으로 state가 이 값이면 이렇게.. 라는 흐름으로 동작을 함.

state가 바뀌면 값 보존이 안됨

state가 바뀌었는지 판단 할 때 빠르게 비교하고 같은 배열을 넘기며 변화를 모른다.

따라서, 기존 값을 수정하면 참조가 바뀌는게 아니기 때문에 알아차리지 못할 수도 있음. 즉, 새로운 배열이나 객체를 만들어서 넘겨야 함.

state의 불변성을 지킨다는 것은 리액트 컴포넌트를 props와 state를 입력으로 받아서 UI가 반환하는 순수함수처럼 예측 가능하게 유지하기 위한 방법이다. - memoization

state는 최소한으로 관리하는 것이 좋음.

- 꼭 필요한 값만 state로 둠.
- 다른 값에서 계산해낼 수 있는 값은 state로 두지 않는다. (파생값)
- 관리할 상태가 늘어난다. 원본 state만 두고 나머지는 렌더링 시점에 계산을 하는게 관리 부담에도 좋다
- 불필요한 state의 변경은 불필요한 렌더링으로 이어질 수도 있음.

리액트는 개발자가 직접 돔을 찾고 랜더링 하는 수고를 덜어주고,

상태가 이러면 ui는 이렇다 라는걸 도와주는 라이브러리이다.

- > 그 안에서 상태, state 덕분에 ui 변동성 가능.

**LifeCycle**

컴포넌트 하나가 화면에 처음 나타나서 값이 바뀌면서 살아 있다가 화면에서 사라지기 까지의 전체 흐름.

- 컴포넌트의 생명 주기

설명 할 수 잇는 것.

- 컴포넌트가 언제 생성, 갱신, 삭제 되는지 3 시점으로 구분해서 설명 가능.
- 각 시점에 왜 다른 코드가 필요한지
- 그리고 함수형 컴포넌트에서는 어떻게 다루는지

컴포넌트는 props와 state 바탕으로 화면을 계산한다고 했는데, 그 계산이 한번에 끝나지 않고 시간의 흐름을 가짐.

- 이 전체가 라이프 사이클.
- 컴포넡느가 한번 그려지고 끝나는게 아니라 살아서 움직이는 시간을 갖고, 그 시간이 구간을 갖고 쪼개진다는 뜻.

Mount - 채팅방 에시로 ) 채팅방 열어서 화면이 나타나는 순간, 지난 대화들 불러오고 실시간 연결을 여는 준비

Update - 방에 있는 동안 새 메시지가 와서 다시 그려지는 순간

알아야 하는 이유

- 같은 코드라도 어느 시점에 실행 되는가에 따라 결과가 완전히 달라짐.
- 데이터 불러오는 코드 잘못된 자리에 두면 화면이 그려질 때마다 서버를 계속 호출하게 되고 … 메모리 누수가 일어날 수 있음.

**Mount**

컴포넌트가 화면에 처음 등장하는 시점

- 리액트는 jSX를 실제 돔요소로 바꿔서 브라우저 화면에 붙이고 state는 우리가 정한 초기값으로 세팅.
- 여기가 컴포넌트의 처음 준비 구간
- 서버에서 데이터 가져와서 하는 초기화 작업
- 이 시점을 놓치면 초기화가 필요한 코드를 작동 못할수도 있음.
- 이 시점에 fetch 를 통해 서버에서 가져와서 빈 배열을 가져오던가 하는거임.

Mount 시점 이해하는건 초기 1회 실행을 설정한다.

useEffect… -> 컴포넌트가 화면에 처음 Mount 될때 실행되는 코드를 작성.

- 화면 계산하는 일 말고 특정 순간에만 따로 실행하고 싶은 코드..
- 렌더링이랑은 좀 성격이 다른 코드.
- 특정 순간에 실행 할 코드를 걸어두는게 useEffect
- 앞에는 그 순간에 하고 싶은 일을 적고, 뒤의 배열이 그 코드를 언제 실행 할지를 결정.
- 그래서 같은 useEffect라도 배열을 어떻게 두느냐에 따라서 화면에 처음 붙을 때만 실행되기도 하고 특정 값이 바뀔 때 실행되기도 함.
- useEffect로 특정 시점에 실행되도록 할 수 있다.
- 지금은 useEffect를 사이프 사이클 다루는 일종의 도구 중 하나이다.
- useEffect 통해서 mount, update, unmount 순간에 코드 얻을 수 있다.

**Update**

화면에 있는 컴포넌트가 state나 props가 바뀌면서 다시 렌더링 되는 시점

useEffect에서 빈배열이 아닌 다른 변수를 넣었을 때 그것이 변할 때마다 update가 된다는 것..

update는 자신의 state 바뀔 때만 일어나는게 아니라 props에 의해서도 바뀐다. - 예시 코드로 빈배열이 아니라 seconds. useEffect의 [seconds]

**Hooks**

use로 시작하른 함수들을 리액트에서는 hook이라고 부름

설명 할 수 있어야 하는 것

- Hook이 무엇이고 왜 쓰는지 - 우리가 만든 함수 컴포넌트가 리액트의 기능을 끌어다 쓸 수 있게 해주는 연결 장치
- Hook 사용하면서 지켜야 하는 규칙. - 규칙을 외우는게 아니라 왜 그런 규칙이 필요한지를 리액트의 내부동작이랑 살짝 연결해서 이해.

정의 :

- React에서 함수 컴포넌트가 상태, 라이프 사이클, 컨텍스트 같은 기능에 접근 할 수 있게 해주는 특별한 함수 규칙.

각 기능들은 리액트가 이미 갖고 있음. 값을 기억해주는 기능, hook은 리액트 안쪽의 기능을 우리가 만든 컴포넌트 안으로 끌어와 주는 연결 장치

React에서 함수 컴포넌트가 상태 라이프 사이클, 컨텍스트 같은 기능에 접근 할 수 있게 해주는 특별한 함수 규칙.

2. 함수형 컴포넌트

과거에는 클래스형, 이제는 함수형.

이제는 클래스 형 더 이상 지원안함

- 상태 기억하거나 생명 주기 다루는 기능들이 예전에는 클래스형 컴포넌트에서만 쓸 수 있었음.

함수형 컴포넌트는 단순히 화면 그리는 역할만 했다.

Hook이 등장 하며 함수 컴포넌트도 모든걸 다 할줄 알게 됨

알아야 하는 이유

:

클래스 없이도 상태 관리와 부수 효과를 다룰 수 있고, 로직을 재사용 하여, 코드 가독성과 유지보수성을 높일 수 있기 때문.

동작 방식

Hook이 그냥 함수 한번 호출 하는 것처럼 보일 수 있는데, 리액트 내부에서는 다르게 관리가 됨.

- > 초반에 이야기 한 규칙.

한가지 전제

- > 리액트는 컴포넌트를 화면에 보여줄 때마다 함수 전체를 처음부터 다시 실행.
- 값 바뀌면 컴포넌트 함수 통째로 호출..
- 매번 다시 실행되는데 useState로 만든 값은 어떻게 계속 유지되는가?

컴포넌트가 몇번 실행 되던 간에 첫번째 칸에는 count 두번째 칸에는 name이 들어감.

순서가 꼬이게 되면 에러 발생.

상태가 이어지는 이유

- 함수를 매번 다시 실행하는데 값은 어떻게 이어지는가?
- 처음 useState 실행하면 react는 이 칸에 이런 값이 들어있다고 기록을 해둠
- useState(0)하면 첫번째 칸에 0 기록, 버튼 눌러서 serCount(1)를 하면 값을 바꾸고 다시 같은 칸에 넣어둠.
- 칸에 있는 내용을 같은 위치에서 갱신함.
- 컴포넌트 함수 안의 변수는 매번 새로 만들어지는게 아니라 실제 값은 함수 변수 바깥에서 저장되어 있어서 상태가 계속 이어지는 것처럼 보임
- 렌더 페이즈 - 함수 컴포넌트 실행해서 화면을 어떤 모습으로 바꿔야 하는지 계산.
- 커밋 페이즈 - 계산된 결과를 실제 돔에 적용
- 훅 중에서는 등록만 해뒀다가 화면이 실제로 바뀐 다음이 실행 되는 것도 있음.
- 어떤, 화면이 그려진 다음에 실행된다.
- useEffect , 화면에 먼저 반영되고 그 뒤에 effect안의 코드가 실행 됐던거, 그리고 의존성 배열에 따라서 실행 됐던거 생각 하면 됨.

Hook 사용할 때 지켜야 하는 규칙

1. Hook은 함수의 맨 위에서 작성, 조건문이나 반복문 안에 넣지 않음.
2. hook은 매번 같은 순서로 실행되어야 함.

(******리액트는 순서로 값을 찾으니까 순서 흐트러뜨리지 말자.*****)

정리

- Hook은 우리가 만든 함수형 컴포넌트가 리액트의 기능을 쓰게 해주는 연결 장치의 개념
- 규칙을 지키면서 써야함.
    - 규칙의 이유는 리액트를 훅을 변수 이름이 아니라 불린 순서대로 값을 찾는다.
    - 함수의 맨 위에서 같은 순서로 불러야 함.

Reducer useState

설명할 수 있어야 하는 것.

- useReducer 무엇이고 왜 쓰는지
- 어떤 상황에서 useState 대신 useReducer를 선택하는지.

정의 :

이전까지 누적된 값과 이번에 들어온 새 값을 결합해서 하나의 결과로 줄여나가는 함수.

이 형태가 react에 그대로 넘어옴.

리액트에서도 비슷함. 누적된 값이 현재 상태가 되고 새로운 값은 액션이 됨.

화면에서 통제하는 상태가 하나 일 때, 액션에 따른 상태의 규칙이 어딘가에는 있어야 함.

- 여러 동작에 대한 상태 변경 규칙을 한 함수에 모아둔 것.
- Reducer
- 여러 상태 변화 로직을 하나의 함수로 모아, 액션이라는 입력에 따라 새로운 상태를 반환하는 함수,
- 액션에 따라 그에맞는 새 상태를 만들어 돌려주는 함수
- State, action = newState 이 그 예시.
- action은 직접 설계하는 JS 객체,
- reducer는 현재 상태를 직접 고쳐쓰지 않고 언제나 새로운 상태를 만들어서 반환.
- state 받아서 바꾸는개 아닌 state를 재료로 삼아 새 결과를 만들어 내는 함수
- useReducer - 상태 기억, 액션 받아 새 상태로 갱신.
- 상태 변경 규칙을 모아두는 reducer 함수
- 함수를 컴포넌트에 담아..

사용 이유 :

복잡한 상태 관리 로직을 한곳에 모아 코드의 가독성과 유지보수성을 높이고, 예측 가능한 상태 변화를 만들기 위해 사용

- > reducer 상태 변경의 규칙을 한곳에 관리하기 위해 존재.
- 상태 추가 수정이나 삭제 같은 여러 상태 변경을 흩어놓지 않고 하나의 흐름으로 묶어 제어하겠다. (추적 용이)

- > 불변성이라는 개념이 중요해서

Reducer도 새 함수를 반환하니까,, 컴포넌트 쪽에서는 dispatch 라는 함수로 신호만 보내면 됨

여기까지 봤을 때는 reducer를 쓰는게 리액트 보다 낫나?

싶지만 아님. 상태를 바꾸는 규칙이 많아지고 흩어질 때 그 규칙을 한곳에 모으는 것이 reducer임.

- 그럼 리액트가다 낫나..?
- 그것도 아님. 상태변경 로직이 다 보임. ( reduce의 강점 )

+ 액션이랑 로직이 분리됨. 컴포넌트는 뭘 할지 의도만 전달하고 어떻게 할지는 reducer가 책임 짐

복잡한 상태 관리가 상대적으로 쉬워짐 (case 문 안에 switch로 구분)

사용 방법

1. Reducer 함수
2. useReducer로 상태랑 dispatch 받아오고 (컴포넌트 안에서 연결 / reducer 힘수 만으로는 화면이 바뀌지 않음. hook에 넘겨줘야함.)
3. dispatch로 액션 전달 (이름 그대로 reducer에게 이 액션을 보내는 함수.. 우리가 만든게 아니라 useState가 사용하는..
4. 현재 상태의 reduce랑 이전의 값을 비교해서 새 객체를 만들어서 반환으 ㄹ함.
5. 액션에는 type만 담을 수 있는게 아니라 함께 넘기고 싶은 데이터도 같이 넘길 수 있다.
6. Payload 는 관용적 이름.

단, reducer의 단점 : 간단한 경우에는 오히려 복잡해진다. 단순 카운터나 토글, 입력값이런거는 단일 useState로 처리가 가능 useState처럼 변수 선언하듯이 쓰는 것도 안돼서 action, state 구조 설계 해야하는 것도 진입 장벽

상태 바꾸고 싶을 때도 dispatch 로 신호만 보내고 실제 변경은 reducer 함수 안에서 일어나는 구조

- reducer가 너무 늘어나면 다시 합치고 구조화 하는 일이 생긴다.
- 여기서 부터는 그냥 상태 관리 라이브러리 쓰는게 편함.
- 다크 모드 토글, 카운터, 입력값 이런건 그냥 useState 입력 필드가 여러개, 검증, 성공과 실패, 같이 상태 전환 규칙이 잇는건 useReducer를 고려 해봐야 한다는 것임.
