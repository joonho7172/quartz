**Reducer**

여러 상태를 모아서 처리해주는 작업

useReducer - 상태를 기억하고 액션을 받아서 새 상태로 갱신하는 기능.

액션에 따라 - 넘겨주는 값이 다르다.

Const [state, dispatch] 등으로 정의해서 시작.

기본적인거는 state로 그냥 구현해도 됨..

따로 노는 state를 모아서 보여주기 위함.

상태 들이 서로 물려서 움직여야 할 때가 있는데 그런 상황에서 reducer를 쓰면 베스트.

- 이렇게 하면 컴포넌트는 dispatch로 의도가 담긴 명령을 내려주기만 하면됨.
- reducer는 순수 함수여야함 (같은 입력이면 같은 결과, 바깥에 영향 주지 않음)
- 네트워크 요청이나 타이머는 reducer 금지.
- 같은 요청이 중복으로 나가거나 결과를 예측하기 어려움.
- Reducer 는 받은 상태를 새 상태로 계산하는 순수한 역할에만 두는게 안전함
- 즉, 사이드 이펙트, 부수효과는 useEffect에서 처리하고 결과만 액션으로 reducer에게 전달.

정리

- Reducer는 함수. (State, action) => newState 형태의 함수. 현재 상태 직접 고치지 않고 새로운 상태 만들어서 반환 - 새로 반환한다는 성질은 리액트의 변경 감지를 위해 필수
- 동작 흐름은 dispatch가 무슨 일이 필요한지 액션을 보내면 react가 reducer불러서 상태 계산하고 화면을 다시 그림
- useRecuer는 useState로 처리하기 복잡하거나 상태 규칙 변화가 많으면 사용함.

**Effect**

지금까지는 컴포넌트 안에서 상태를 다루는 이야기

- Effect는 방향이 좀 다름. 컴포넌트가 화면을 그린 다음에 리액트 바깥에 있는 세계랑 어떻게 맞물려서 돌아가는가

설명할 수 있어야 하는 것

- useEffect가 무엇이고 왜 필요한지
- 어떤 코드는 Effect에 넣고 어떤 코드는 넣지 말아야 할지
- 정리 함수랑 의존성 배열 각각 무슨 역할을 하는지

카카오톡 채팅방 들어가는 상황

- > 방에 들어가면 화면에는 메시지 목록 그려짐.
- > 새 메시지 실시간으로 받으려면 앱은 서버랑 연결을 맺어야 함. 방을 나가면 연결 종료 안 끊으면 리소스 낭비

화면을 그리는 일 - 메시지 목록, props랑 state 계산해서 JSX 그리면 됨

서버와 연결을 맺고 끊는 일 - 바깥에서 effect가 처리함.

react에서 렌더링 이후, 화면 그리기 외에 추가적으로 일어나는 동작을 처리하기 위한 것이 useEffect. 라는 훅.

함수 컴포넌트는 props랑 state 받아서 화면 그려주는 함수

- 실제 서비스는 화면 그리는것에서 끝이 아닌 일들이 있어서 올바른 시점에 실행하고 정리 해야됨

사용 이유 :

컴포넌트가 화면에 단순히 UI 그리는 것을 넘어서, 상태 변화를 감지해 부수적인 작업을 예측 가능하게 하기 위해서

Effect에 넣을 것과 넣지 않을 것

컴포넌트 안에 들어가는 코드를 3종류로 나눔.

1. props랑 state로 화면 계산 코드

3. Effect의 영역 webapi 만지거나 네트워크로 fetch해서 데이터 주고 받거나 외부 라이브러리나 websocket 구독에 연결하거나 하는 일은 effect 에서 다룸 .

Effect는 렌더링 끝난 뒤에 실행되고 컴포넌트 사라질 때 정리 함수 자동으로 불러줌.

- mount랑 unmount 흐름을 조절할 수 있다는 것.
- 등록과 해제를 한쌍으로 묶어주는 것.
- 의존성 배열로 언제 실행 할지를 선언적으로 제어

두번쨰 인자로 배열을 넘기면 그 값이 바뀔 때만 useEffect가 다시 실행된다는 것.

**Memo**

memo도 의존성 배열이라는 개념을 사용함.

대신 목적이 다름

- effect는 외부 시스템과 동기화 하기 위해서 사용하는 도구. memo는 같은 계산, 같은 렌더링을 불필요하게 반복하지 않도록 막아주는 도구
- 성능이랑 직관적으로 연결이 됨

설명할 수 있어야 하는 것.

- memo가 무엇을 기억하는 도구이고 언제 써야 하고 언제 쓰면 안되는지
- useMemo, React.memo의 차이점. 각각 무엇을 메모이제이션 하는지
- 캐싱과 메모이 제이션의 차이점

정의

- 실제 서비스에서 같은 입력이면 결과를 저장해 두었다가 재사용해 불필요한 재계산은 피하는 기법.
- 지출 내역도 그대로 집계 기준도 그대로. 사이드 열었다가 닫았다고 해서 수천건을 처음부터 다 다시 합산하는 건 낭비.

즉, 값이 안바뀌었ㅁ으면 아까의 통계를 그대로 재활용 하자는 뜻.

합산이라는 계산에서 입력은 지출 내역과 집계 기준. 입력이 그대로면 굳이 다시 계산하지 말고 저장해둔 통계 결과를 그대로 쓰자..

- 계산 결과를 메모해둔다 라는 뜻에서 메모이제이션
- 그럼 캐시랑 비슷한거 아니오?
- 있는 레이어랑 목적이 조금 다름
- 캐시는 서버 바깥에서 긴 생명주기로 다양한 요청이나 데이터를 저장,

사용 이유

리액트 컴포넌트는 기본적으로 props랑 state로 그림을 그림

- 함수는 state나 prosp가 바뀔 때마다 처음부터 다시 실행됨
- 화면만 그리는 컴포넌트면 문제가 안됨
- 실제 서비스 생각하면 수백개짜리 리스트 그리거나 무거운 계산을 하거나 자식 컴포넌트가 많이 얽혀 있는 경우가 있음.
- memo가 이 반복을 줄여줌

리액트는 원래 필요한 만큼 다시 계산함.

memo는 이걸 우리가 직접 지정해줘서 성능을 최적화함.

Memo의 장점

1. 성능 최적화
    1. 컴포넌트 안에서 무거운 계산 해야할 때 useMemo로 감싸두면 의존성이 바뀌지 않는 한 결과를 저장해 재사용.
2. 불필요한 렌더링 방지
    1. React.memo 쓰면 props 바뀌지 않는 한 컴포넌트는 다시 그리지 않고 이전 결과를 그대로 씀.
3. 협업할 때 의도를 드러낸다.
    1. 어떤 계산을 useMemo로 감싸두면 이 계산은 값들이 바뀔 때만 다시 하면 된다는 의도를 코드로 드러낼 수 있음.

사용 방법

1. useMemo로 값 계산.
2. 다른 하나는 React.memo로 컴포넌트의 렌더링 결과를 기억

무엇을 기억하는가가 다름.

useMemo는 입력값이 바뀔 때만 다시 하라고 선언하는 훅.

렌더링 할 때 계산 한 번 하고 결과 기억.. 같으면 계산 건너뛰고 기억해둔 값 쓰기.

Q. useMemo왜 씀? 어떤 경우에 쓰나

React.memo

기본형 , props가 바뀌지 않았다가 다시 그리지 말라는 뜻을 가짐.

React.memo에 컴포넌트 넣으면 props가 바뀔 때만 다시 그리는 컴포넌트를 만들어줌.

props에 담긴 값들의 참조를 비교하는데 내용이 같아도 매번 새로 만든 객체라면 참조가 달라서 react.memo는 바뀌었다고 판단하고 다시 그려버림.

그리고 얕은 비교만으로 잡기 어려운 상황을 우리가 직접 판단 기준을 만들어줘서 해결하는 방식….

보통 useMemo + React.memo 함께 쓰기.

부모에서 자식으로 넘겨줄 값이랑 함수의 참조를 고정해두고 자식은 React.Memo로 감싸서 불필요한 렌더링을 막음.

정리 :

useMemo는 값을 기억해서 불필요한 재계산 막는다

useCallback은 함수의 참조를 유지해서 자식이 다시 그려지는걸 막는다.

React.memo는 props가 그대로면 컴포넌트 렌더링 자체를 건너 뛴다.

단점

메모이제이션은 훅으로 작동하는 동작.

따라서, 잘못 쓰면 성능 저하. Memo 자체도 지난번 값과 지금 값을 비교하는 연산.

여기에 메모이제이션 붙이면 아끼는 것도 불필요한 비교연산만 합니다.

의존성 배열 관리의 어려움.

만약에 의존성 배열을 자주 바뀌는, 매번 새로운 참조로 만들어진다면, 캐싱 효과가 없어짐 ㅇㅇ memo 쓰는 이유가 없음.

정리

- 메모이제이션은 같은 입력이면 같은 결과를 기억해뒀다가 재사용 하는 최적화.
- useMemo는 값을 기억하고 React.memo는 컴포넌트의 렌더링 결과를 기억.
    - 이 둘을 관통하는 개념은 같음.
- useMemo는 계산값을 기억, react.memo는 컴포넌트를 기억
- 다 좋은건 아니고 비용이 드니까 필요한 곳에서만 사용 할 줄 알아야 함.

**Callback**

memo는 계산한 값 기억하고 React.memo는 컴포넌트의 렌더링 결과를 기억

- > 리액트가 무언가를 그릴지 말지 판단 할 때 내용이 같은지가 아니라 참조가 같은지를 확인. 메모리 주소가 같은지.
- UseCallback은 여기의 연장선에 있음.
- useMemo가 값을 기억하면, useCallback은 함수를 기억한다.
- 함수에는 값보다 까다로운 문제가 있다.
- 리액트 함수 컴포넌트는 다시 렌더링 될 때마다 내부에서 만든 함수를 매번 새로 만들어냅니다.
- 겉으로는 똑같은 함수인데 참조는 매번 달라짐.
- 최적화 자식 컴포넌트가 다시 그려지는 일이 생김.

설명 할 수 있어야 하는 것

- UseCallback이 무엇이고 왜 필요한지 그리고 어떻게 쓰는지
- useCallback이 함수 자체를 안만들게 막는 도구가 아니라 같은 참조를 돌려줘서 메모제이션 된 자식이 렌더링을 건너뛰게 해주는 도구

Q. useMemo, React.memo, useCallback의 차이점을 설명 할 수 있어야 함.

정의

- 검색 결과로 상품 카드가 수십개, 카드마다 찜 버튼 있을 때..
- React.memo로 카드 컴포넌트를.. 감싸뒀다.
- props가 그대로 다시 그리지 않게 하기 위해 react.memo 사용
- 검색 창에서 사용자가 한 글자를 칠 때마다 목록의 카드 전체가 다시 그려지면 화면이 버벅거림.
