**Error Boundary**

Context - 컴포넌트 트리 위쪽에서 provider로 감싸면 그 안에서 값을 꺼내 쓸 수 있었음.

errorBoundary는 오류가 바깥으로 번지지 못하게 막는 울타리

정의 :

각각 다른 컴포넌트에서 서버에서 데이터를 받아와서 그림.

후기 목록에서 문제가 생기면.. 렌더링 도중에 오류를 던짐

그때의 화면? - 리액트의 성질은 트리 안 쪽 컴포넌트 하나가 렌더링 도중에 오류를 던지면 리액트는 오류를 위쪽 트리 전체를 포기 함.

- 후기 하나 때문에 상품 이미지, 가격, 장바구니 담기 버튼까지 전부 사라지고 사용자는 아무것도 없는 화면만 보게 됨..
- 부수적인 후기 컴포넌트 하나 때문에 서비스에서 제일 중요한 구매 흐름까지 통째로 날라갔다.
- 이러한 상황을 막기 위해서 문제가 날 수 있는 부분만 울타리로 감싸둠.
- 그럼 오류가 난 부분에는 오류 메시지만 뜨고 나머지 부분은 정상적으로 작동 함
- React에서 컴포넌트 하위 트리(예시 상 후기 영역)에서 발생하는 렌더링 관련 오류를 감싸서, 전체 앱이 무너지는 것을 막음.
- 대체 UI는 후기를 불러오지 못했다는 메시지

ErrorBoundary는 어떤 오류가 어디에서 났는지 정보 수집하고 이걸 로그로 남기거나 모니터링 서비스로 보낼 수도 있다.

Error Boundary는 오류 감지하고 번지지 못하게 막고 대신 복구용 fallback UI 보여주는 컴포넌트 이다.

Error Boundary를 사용 하는 이유

사용자는 최소한의 기능을 사용하고 서비스는 살아있는 형태를 유지 할 수 있음. (사용자 경험 ux 보호) 오류가 났을 때 어떻게 보이게 할지를 미리 설계..

- 비즈니스적 가치

영역별 격리와 선택적 적용

- 위험한 영역마다 별도로 적용 가능함.

에러 바운더리는 주로 어디를 타켓하느냐?

- 렌더링 도중에 발생한 에러를 잡음. 화면을 그리는 도중에 발생하는 것.
- 버튼 클릭 같은 이벤트 핸들러, fetch, settimeOUt 같은거는 잡아주지 못한다는 것. (비동기 코드 같은거)
- 이벤트 핸들러나 비동기 콜백은 이미 끝난 다음에 렌더링과는 분리된 흐름으로 실행이 되기 때문임..
- 지금 화면을 그리다가 난 오류가 아니어서 감지하는 범위 밖.
- 그래서 이런 오류는 우리가 직접 경계로 올려줘야 함.
- 렌더링 중 오류는 자동으로 막아주는데 이벤트랑 비동기 오류는 show Boundary로 명시적으로 연결 해줘야만 같은 폴백으로 처리가 가능함.
- 에러 바운더리의 목적은 모든 오류 없애는게 아니라 어디에서 난 오류든 결국 화면 전체가 죽지 않고 그 자리에서 사용자가 이해할 수 있는 대체 화면을 세우는것이 목적이다.

정리

- 에러 바운더리는 컴포넌트 트리의 한 영역을 감싸서 렌더링 중 난 오류 번지지 못하게 막고 폴백 UI 보여준다.
    - 없으면 전체가 터짐
- 사용 할 때는 오류가 날만한 컴포넌트 ErrorBoundary로 감싸고 폴백을 그대로 태그 작성, 함수로 넘겨주거나 컴포넌트를 넘겨준다.
- 폴백 안이 restErrorBoundary 나 경계에 key를 걸어서 다시 시도할 수 있게 만들 수 있음.
- 이벤트나 비동기 오류는showBoundary로 직접 올려서 처리 해야함.

**Suspense**

errorBoundary - 에러 나더라도 앱 전체 무너지지 않도록 문제가 된 영역만 잘라내고 대체화면 폴백 보여주는 경계

Suspense - 아직 준비되지 않은 상태.. 로딩을 다루는 경계

정의 :

비동기 작업 중 대기 상태를 다루고 준비되지 않은 UI 대신 폴백을 보여주는 기능

- > 데이터ㅏ 없어서 곡 목록 그릴 수 없는 부분을 서스펜스로 감싸고 기다리는 동안 대신 보여줄 임시 화면을 폴백에넣음.
- > 데이터 오기전까지는 임시 화면을 보여줌

임시 화면을 폴백이라고 부르고 폴백을 언제 보여줄지 관리하는 경계가 suspense

Suspense는 이 영역이 아직 준비되지 않았으니 준비될 때까지 잠시 대기시킨다는 구간을 화면 위에 정해두는 것.

- > 사용자에게 UX 단절 대신 기다리는 경험을 주고 흐름을 맡아줄 곳을 담당한다.

Suspense는 화면 위에 스피너 하나 얹는 부품이 아니라 특정 영역을 감까서 그 부분이 준비되지 않았을 때 통쨰로 대기시키는 경계.

자식 컴포넌트에서 아직 렌더링 준비가 안됐다는 신호를 서스펜에게 보내는 것.

리액트에서 렌더링 도중에 promise가 던져지면 이걸 에러로 취급하지 않고 아직 준비가 안됐으니까 이 부분의 렌더링을 잠시 멈추고 기다리라는 신호로 받아들여집니다.

만약 요청에 실패하면 읽기 함수는 promise가 아니라 실제 에러를 던지고 에러는 suspense가 아니라 지난 시간에 배운 error boundary가 된다.

- 같은 throw지만 던지는 것이 promise 가 아니면 반응이 달라짐

실제로는 직접 래퍼를 만드는게 아니라 use나 데이터 패칭 도구가 이 역할을 대신 해줌. 이 코드는 suspense가 왜 컴포넌트를 대기 시킬 수 있는가 이해하기 위한 예시 코드 이다.

서버 컴포넌트는 줄여서 RSC 서버에서 실행 되어서 서버가 직접 UI 만들어서 내려줌

use는 promise나 컨텍스트 같은 값을 읽어서 suspense 대기를 걸 수 있는 리액트 api

컴포넌트는 use로 데이터를 기다리는 동안 suspense 그 기다리는 화면으로 처리

세부 문법보다는 대기를 suspense가 서버 컴포넌트에서는 이렇게 처리하는구나 라는 구조를 보는게 좋음.
