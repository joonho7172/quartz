**Form**

제어 컴포넌트와 비제어 컴포넌트의 차이

사용 방법

훅의 역할

useForm 훅이 하는 일 : 큰 그림

역할은 다섯가지

1. Register 라는 함수가 input에 붙일 속성 묶음을 만들어줌
    1. 그러면 input이 form 시스템에 등록됨
    2. register는 form에 이름표 달아주는 함수.
2. 사용자가 타이핑하면 값은 ref에 저장됨. -> 리렌더링 x
3. 에러메시지만 state로 관리함. 그래야 필요할 때 리렌더링 가능.
4. 제출 시점에 handleSubmit 만들어, 모든 필드 통과하면 성공 콜백, 실패하면 실패 콜백 부름.
5. Reset 만들어서 내부 값이랑 실제 input 초기화해서 폼을 비우는 기능도 만들음.

값은 ref, 에러는 state

- useRef는 상태 저장소로, 값이 바뀌어도 리렌더링을 일으키지 않는 상태 저장소임.
- 에러미시지는 형식이 틀렸을 때 빨간 글씨로 화면에서 보여줘야 하니까 state로 관리함.

화면에. 즉시 반영되어야 하는 값은 state.. 들고만 있으면 되는 값은 ref

valuesRef = 모든 필드의 현재값을 담는 상자

rulesRef =  필드별 검증 규칙 보관소

inputsRef = 필드별 실제 DOM input 노드

register(name, rules) 사용하기

1. 사용자 입력
    1. 컴포넌트가 렌더링 되는 순간. Register 는 name, ref, onChange 같은 속성 묶음을 계산해서 돌려줌. 이 시점에서는 아직 dom input
2. 커밋 이후
    1. 렌더 페이즈, 커밋 페이즈로 화면을 그림.. 실제로 보이는 값이랑 내부 값을 맞춰두기 위함
3. 사용자 입력 처리
    1. onChange가 실행이 되면서 ref에 넣은 값을 검증함. 에러는 state니까 바로 보여주게.

내부(ref)와 DOM을 동시에 초기화 하기

제출이 끝나면 폼을 비워줘야함 - 그럴 때 쓰는 함수가 reset

ref사용하면 화면이 안바뀌기 때문에 초기에 저장해둔 inputsRef를 이용하면  돔을 직접 비워줘서 화면을 초기화 한다.

제출 하기

제출하는 순간에는 모든 필드를 한번에 검사

- > ValidateAll

register 할 때 저장해둔 rulesRef를 돌면서 각 필드의 현재 값을 방금 본 validateField로 검사

정리 :

- 리액트에서 폼은 폼 태그 하나가 아니라 입력 UI, 상태, 검증, 제출을 하나로 묶은 개념
- 리엑트로 만든 SPA에서는 페이지 새로 고침 없이 입력을 실시간으로 검증하고 부분만 갱신해야해서 이런것을 직접 설계 할 줄 알아야 함.
- 입력 값 다루는 방식
    - state로 다루는 제어 방식 -> 렌더링 매번 일어나고
    - Ref로 다루는 비제어 방식 -> 리렌더 없음. 대신 초기화 할 때 DOM을 직접 맞춰줘야 함.
- 값은 변하지만 리렌더링 원하지 않으면 ref로 다룸.

**Fetch**

화면을 채우는 데이터는 서버에서 받아서 처리를 해야함

- > 서버에 요청해서 가져오는 도구가 Fetch

고유 명사

SNS 프로필 페이지 만드는 FE 개발자

- 디자이너가 기획자랑 같이 해서 피그마에 화면 넘기고 화면에 보니까 사용자 이름, 팔로워, 최근 게시글 목록
- 이 데이터를 가져오려면 백엔드 DB에서 가져옴.

이 과정에서 서버에 요청해서 응답 받아오는 도구 표준이 fetch

- > fetch라고 하면 fetch() 함수 자체를 이야기 함. 브라우저나 nodes 환경에 내장되어 있는 함수.
- > 골격 자체가 데이터 요청해서 응답 받고 그 응답을 다시 꺼내서 사용.

서버에서 데이터를 가져오기 위한 표준 도구

XML HttpRequest 대신 fetch를 쓰는 이유

Fetch 나오기 전에 XMLHttpRequest가 있음. XHR. 콜백 기반이여서 코드가 길음.

fetch는 promise 기반.

콜백 미리 등록하는 XHR방식이랑 다르게 ayncs/await 사용 가능.

비동기 데이터 상태 업데이트

Fetch 로 데이터를 비동기적으로 가져온 다음에 그 결과를 state에 저장하면 화면이 갱신.

state는 컴포넌트가 렌더 사이에 기억하는 값. setState 호출하면 다음 렌더링이 예약

- > 서버에서 데이터가 도착한 순간에 setState을 호출하면 React가 그 컴포넌트 다시 렌더링하면서 이번에는 데이터가 채워진 화면을 보여줌

fetch를 어디에 두어야 하는가?

- > 렌더링 중에 바로 호출하면 안됨. 서버요청은 props랑 state로 계산 할 수 있는 값이 아님. useEffect등..

요청을 안전하게 관리

: 요청 보냈는데 응답 오기전에 페이지 떠나면 컴포넌트 이미 사라졋는데 요청은 이미 진행 될 수 있음 - 그걸 막기 위한게 AbortController, (요청 취소 도구) signal 끊은 요소.

서버 정책을 제어해 성능을 최적화 할 수도 있음.

사용 방법

기본 패턴

1. 요청을 보냄,
2. 응답을 json으로 파싱.
3. State 넣어서 화면 갱신.

Async/ await가 아니라 then절 쓰는 이유 :

- > useEffect의 콜백함수는 정리 함수 or 아무것도 반환하지 않아야 함.

근데 콜백을 async로 만들면 반환 값이 자동으로 promise가 됨..

그래서 Effect 안에서 then을 사용하거나 콜백 안에 별도의 async 함수를 선언해서 곧바로 호출하는 방식을 써야 함.

데이터 요청을 하나의 흐름.

데이터 요청은 순간이 아니라 흐름. 요청 보내고 응답 기다리고 성공 실패로 나뉨.

기본 패턴처럼 data가 있는지 없는지만 보면 구분이 안됨.

사용자에게는 새 경우가 완전히 다른 화면이어야 함.

- 즉, 로딩 에러, 데이터 값을 같이 관리해야함.

캐시 정책으로 최신성 vs 속도 선택

최신 데이터 필요하면 fetch 에 cache : no- store 옵션 추가.

- 같은 API를 부르더라도 캐시 정책만 다르게 해서 캐시의 시점을 나눔.
- 실제로는 이렇게 안함 ㅋㅋ

주기적으로 자동 재조회 사용하기 (폴링)

화면이 실시간에 가깝게 갱신 되어야 할 때가 있음. 실시간이 필요하면 웹소켓 같은 기술을 검토해야하는데 실시간 처럼 보이기만 하면 되는 경우에는

- 일정 간격으로 다시 요청하는 방법.

축구 스코어 경기 중계 웹으로 본다고 하면 스코어 업데이트 되는 부분

이떄, setInterval, AbortController 를 함께 써서 누수 없이 관리해줌.

정리

- Fetch 서버에서 데이터를 가져오는 도구. 요청 보내서 응답 받고 응답을 본문에서 꺼낸다.
- 요청은 렌더링 중이 아니라 네트워크 라는 외부 시스템과의 작업이기 때문에 useEffect 안에서 실행하고 받아온 데이터는 state에 담아서 화면 갱신.
- 데이터 요청을 하나의 순간이 아니라 흐름으로 봐야 한다. 요청전 -> 진행중 -> 성공 / 실패

**CSR**

잠깐 뜨는 빈 화면 - 데이터가 CSR . Client Side Rendering의 약자.

우리가 지금까찌 바왔던 리액트 앱이 CSR로 동작하는 예시.

이 말을 일상에 비유하면, 식당에서 요리를 주문 할 때, 주방에서 완성된 요리를 가져 주는 게 아닌 자리(브라우저)에 키트와 설명서를 주고, 손님이 완성하는것과 같다.

전통적인 웬 방식이다 라고 하면 사용자가 다른 페이지로 넘어갈 때 화면을 처음부터 새로 그림.

- 화면도 한번 깜빡임. 요구사항이랑 달라짐.
    - 페이지 이동할 때마다 앱 자체는 브라우저안에 계속 살려두고 바뀌는 부분만 갈아끼움.
- 자리만 바꾸고 재생부분은 남기는 식으로.

초기 페이지 로딩 시, HTML의 기본 틀과 React.js 스크립트 파일을 클라이언트로 내려보내고, 이후 브라우저가 필요한 데이터를 서버에 요청하여 직접 화면을 구성

---

브라우저는 화면에 필요한 데이터를 API로 따로 요청해서 받아옴 그리고 받아온 데이터 갖고 브라우저 메모리 안에서 컴포넌트를 갱신함.

- 페이지 이동할 때도 주소창의 주소 바뀌어도 브라우저는 새로 요청하지 않고 갖고 있었던 HTML, CSS, JS를 갖고 클라이언트 라우터가 필요한 데이터만 받아와서 바뀐 부분만 보여줌.
- 그러면 사용자는 끊김 없이 빠르게 페이지 전환처럼 느껴짐

화면 조립하는 일을 서버가 아니라 브라우저가 함.

1-6 까지는 초기 로딩

7-10 화면이 다 뜬 다음에 사용자가 클릭하고 이동하는 과정

1. 사용자가 주소를 입력
    1. 브라우저는 서버에게 첫 화면 보여달라고 요청 보냄
2. 서버는 해당 주소에 맞는 HTML이랑 JS를 응답.
    1. 하나는 비어있는 html 뼈대를 보내고,
    2. 다른 하나는 react 스크립트 파일이랑
    3. 또 Css 보내줌.
3. 브라우저가 HTML 읽으면서 JS를 실행
    1. 뼈대는 만들어졌는데 알맹이는 없는 상황
4. JS 실행
    1. 리액트의 기능이 담긴 코드
    2. 설계도 트리가 만들어짐.
    3. 버튼이나 입력창에 이벤트 리스너 연결할 준비를 함.
    4. 조립 설명서 펼쳐놓은 상태. 설명서 준비 됐는데 아직 본격적인 조립 시작 전
5. 필요한 데이터 요청
    1. Api 요청해서 페이지에 필요한 데이터를 비동기로 가져오는 것임.
6. 데이터가 도착하면 화면을 채움,
    1. 바뀐 부분만 다시 그림.
    2. 전체 새로 고침 없이 목록이 보여지거나 카드가 채워지는 것처럼 보임.

여기까지가 초기 로딩 구간.

처음에 빈 껍데기만 받고 js가 데이터 요청해서 데이터로 화면을 채움.

- 로딩 표시나 fetch 수업때 봤던 “불러오는 중”구간이 여기.
1. 상호작용
    1. 여기까지 진행 하면 초기화면이 출력이 됨
    2. 앞 단계에서 이미 이벤트 리스너 연결되어 있음. 그래서 버튼 클릭하거나 검색 필터 선택, 모달 열기 같은 행동에 즉시 반응.
    3. 상호작용은 이미 브라우저 안에서 다 준비되어 있으므로 필요할 때만 데이터 요청해서 갱신하면 됨.
    4. 훨씬 빠르게 느껴진다.
2. 링크 눌러도 페이지 전체를 다운로드 하지 않음.
    1. 링크를 눌러도 브라우저 안의 클라이언트 라우터가 처리하게 됨.
    2. 전체 페이지 내려받지 않고 필요 부분만 교체
3. 재 방문시 페이지 속도 증가.
    1. 한번 받은 리액트 스크립트랑 css는 브라우저가 캐시에 저장해둠
    2. 같은 사이드 다시 방문하면 큰 파일들 다시 받지 않고 재사용해서 더 빨리 뜸.
4. 실패나 지연을 보여주는 화면도 브라우저의 책.
    1. CSR 방식 사용하면 서버가 판단해서 내려주는게 아니라 브라우저, 클라이언트가 로딩이나 성공 실패에 대한 것도 책임짐.
    2. 화면에 대한 모든게 브라우저쪽에서 이루어짐.

정리

- CSR은 브라우저 안의 JS가 화면을 직접 조립하는 방식
- 서버는 첫 요청에 완성된 화면이 아닌 뼈대는 내려주고 브라우저가 그 스크립트 실행해서 화면을 채움..
- 초기에는 데이터를 따로 요청하느라 여러번 API Call하고 그 사이에 사용자는 로딩 화면 본다.
- 이후에 상호작용 구간은 이미 리액트 앱이 브라우저 안에 비 되어 있어서 다른 필요한 조각만 갈아 끼움
- 리액트는 이런 CSR 방식이라 성능 개선을 위해 맨 처음 전달하는 HTML, css, js를 묶어서 번들의 크기 자체를 줄이는게 성능 개선에서 필요한 요소 중 하나 이다.

리액트로 구성된 앱에 처음에 접근 할 때 느끼는 로딩 속도가 훨씬 짧아짐

**SSR**

주도권이 서버에 있다. Server Side Rendering 이름 그대로 서버 쪽에서 화면을 먼저 만들어서 내려줌.

ssr은 csr의 상위 버전이 아님.

정의

- 사용자가 네이버에서 쿠팡 상품 클릭해서 들어옴
- 이 상황에서 상품 상세 페이지를 CSR로만 만들면 손해를 봄.
- 크롤러가 페이지 수집을 할 때 처음 수집하는 HTML은 비어 있음.
- 사용자가 상품 상세 페이지 요청하면 서버가 먼저 그 상품 데이터 가져오고 컴포넌트 트리를 서버에 요청. 상품명이랑 가격이 이미 들어가 있는 완성된 HTML 을 만들어서 내려 보냄.

즉, 크롤러도 SSR로 만들어진 페이지라면 처음부터 읽을 내용이 있는 화면을 받음.

- 서버가 아직 리액트 이벤트 상태가 붙지 않은 정적인 상태이기 때문에

정리하면 sst은 서버가 데이터가 담긴 HTML을 먼저 준비하고 브라우저가 그걸 동작하도록 살려내서 완전한 리액트 앱으로 만드는 렌더링 패턴.

CSR과의 비교

- > CSR은 브라우저가 빈 HTML이랑 스크립트 받아서 화면을 처음부터 직접 그림. 화면 뜨기 전까지 로딩 스피너나 화이트 스크린.

SSR은 서버가 이미 내용이 채워진 HTMl을 보내주어 사용자가 빈 화면 대신 컨텐츠를 바로 볼 수 있음.

- > 대신 SSR은 3가지를 감수함.
1. 서버가 매 요청마다 렌더링을 하니까 서버의 부담 증가
2. 이벤트가 안붙어서 아직 작동하지 않는 구간도 생김.
3. 서버 렌더링을 위한 구성 자체가 CSR보다는 상대적으로 복잡
4. 로그인 이후에 인터렉션이 복잡하면 CSR이 맞음.

사용 이유

SEO, 링크 미리보기

검색 엔진에 검색을 했을 때 상위권에 노출되거나 검색에 잘 걸리는 과정

- > 구글에 크롤러 따로 계속 웹을 돌면서 수집 -> 그걸 기반으로 노출 여부 정함.

SEO. 검색 엔진이 내 사이트 잘 이해하고 상위에 노출되도록 만드는 작업.

SSR - 서버가 보내는 HTML 안에서 이미 제목이랑 본문이 들어있으니까 크롤러가 읽을 내용이 처음부터 존재.

작동 방식

1. 사용자가 주소 입력함
    1. csr과 동일 함.
2. 서버가 데이터까지 포함된 HTML 생성
    1. 리액트에서 서버를 따로 갖고 있고 API 호출해서 필요한 데이터 가져ㅕ오고 컴포넌트 트리를 렌더링 해서 완성된 HTML을 만들음
    2. html에는 콘텐츠랑 구조가 다 있고 csr에서 서버가 빈 뼈대랑 스크립트 보냈던거랑 차이가 있음.
3. 브라우저가 HTML을 먼저 그림.
    1. 즉시 그려서 사용자에게 일단 보여줌.
    2. 사용자 눈에는 이미 완성된 화면이 보임.
    3. ** 버튼 눌러도 동작 하지 않을수도..?***
4. 리액트 스크립트 실행 준비
    1. 브라우저가 리액트 번들 내려받고 해석함.
    2. CSR이랑은 다르게 HTML이 먼저 나왔기 떄문에 보이는 것이랑 작동하는 것이 분리
    3. ssr에서는 화면은 이미 있는 그걸 움직이게 할 스크립트를 준비하는 상태가 생김.
5. 하이드레이션 시작.
    1. 왜 이것이 필요한가?
    2. 서버기 브라우저로 보낸건 HTML. HTML은 화면이 어떻게 생겼는지를 담음.
    3. 담지 못하는건 그 버튼을 눌렀을 때 어떤 함수가 실행되어야 하는지…
    4. 하이드 레이션은 서버가 이미 그려놓은 html에 react가 이벤트랑 상태를 얹는거임.

하이드레이션이 성립하려면 서버가 만든 HTML이랑 브라우저가 그리려고 하는 React의 앱이 서로 맞아야 함 아니면 오류 발생함,

1. 이벤트, 상태 활성화된 앱 완성
    1. 하이드레이션 끝나면 모든 리액트 기능 활성화 됨
