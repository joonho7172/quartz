CI/CD 파이프라인 구축 (단일 인스턴스)

CI : 지속적 통합. 여러 사람들의 코드 변경을 자주 합치고 합쳐진 결과가 정상인지 	실제 CI에서 진행한 검증을 통과한 어플리케이션들이 배포가 알아서 됨

1. 코드 푸쉬하면 워크 플로우가 깨어남
    1. 앞에서는 사람이 직접 배포 했는데 지금은 코드가 깃헙에 저장 됐다는 사실이 실행 시섲ㅁ을 정함.
    2. 코드 빌드, 실행
    3. 통과하면 이미지 생성되면서 도커 허브에 올라감
        1. 자동으로 바뀐 것
    4. 깃헙 액션이 EC2 쪽으로 배포 이어지고 Ec2는 이미지 받아서 컨테이너 띄움.
    5. 자동화된 흐름으로 처리 사람이 하면 정해진 순서로만 감.
    6. 일관성이랑 추적 가능성이 생김. - 자동화의 이점

무중단 배포 - Blue/Green 파이프라인 구칙(다중 인스턴스)

무중단 배포를 한다는 것은 서비스가 새로운 버전으로 업데이트 되고 배포 된다고 하더라도 멈추지 않고 운영되는 것을 이야기 함.

덧붙여서 장애가 났을 때 되돌아갈 길을 확보 한다는 것에서 의미가 있음.

Blue/Green

운영되고 있는 사용자 요청을 받고 있는 서버 환경을 Blue, 새거를 받는게 Green

앞부분은 동일함. 코드 올리면 깃헙 액션 워크 플로우 트리거. 빌드 테스트 거쳐서 이미지 만들어져서 docker hub 올라감. 새버전이 있으면 기존 환경에 덮어 쓰는게 아니라 멀티 인스턴스 여서 Green에 먼저 따로 띄움.

Blue는 멀쩡히 돌면서 계속 기존 사용자 요청을 받고 있습니다. 그리고 헬스 체크를 함. 새로 올린쪽이 정상적으로 응답하는지 먼저 확인 함.

확인 끝나면 다음 단계에서 nginx가 요청을 받아서 전달하는 대상을 green으로 바꿈. 짧은 순간의 전환이라 끊김을 느끼지 못함. - 무중단 배포

전환이 끝났다고 해서 이전 버전이 되는 Blue 를 곧바로 지우거나 중지하지 않고 일단 그대로 둠

- 오류 생기면 다시 트래픽 전환해서 복구하기 위해서
- 어쨌든 두 환경을 동시에 유지해야해서 서버 자원도 많이 들고 관리할 대상도 늘고 운영도 복잡해짐.
- 롤백하기 위해서 트래픽 방향 바꾼다고 하더라도 데이터는 또 다름.
- 무중단 배포도 여러가지 방법이 있음.

정리

- 개념에 대한 지도를 배우는거지 깊게 배우는 시간은 아님.
- 첫번째 방법은 구성 요소가 제일 적은 대신 배포하는 중간에 중단도 있고 사람의 개입이 제일 많음.
- 두번째는 어플리케이션 이미지로 포장해서 실행 환경 일관성 얻고 만든곳이랑 실행하는 곳 사이에서 레지스토리 도커 허브라는 창고
- 세번째는 여러 컨테이너의 구성을 파일에 선언해서 누가 언제 하든 결과가 같게 함.
- 네번째는 코드가 올라갔다는 시작점을 트리거로 해서 검증과 배포를 자동으로 하고 일관성이랑 추적 가능성을 얻는다.
- 다섯번째는 무중단 배포. 환경 두개 만들고 요청 방향 바꿔서 중단 줄이고 롤백 경로까지 확보 하는 것.
- 서비스 규모에 따라서 결국은 선택하는게 필요하다.

**DevOps**

개발자가 작성한 코드가 사용자에게 어떻게 전달되는 방식이 어떻게 발전해왔는지..

devops는 설치해서 쓰는 도구나 프로그램이나 그런게 아니라 개발이랑 운영을 어떻게 연결할 것인가 에 대한 하나의 일하는 방식.

서버, 컨테이너, 자동화 파이프라인, 배포 전략 배울 건데 모두 이 Devops 라는 틀 위에 있음.

기술 배우기 전에 이게 왜 필요한지 Devops 통해서 이야기를 할 것이다.

설명할 수 있어야 하는 것

- Devops 가 무엇인지
- Devops 가 어떤 문제를 풀려고 등장했는지
- 개발과 운영이라는 영역이 각각 어떤 책임을 지고 어떻게 이어지는지

정말 기초적인 개념, 공부하고 배워나가는데 있어서 자연스럽게 체득하는 부분..

개념에 대해서는 한번쯤 정리를 하고 가는게 편리하다.

- 막상 devops라는 개념을 몰라도 배포하고 운영은 할 수 있음.
- 무엇인지 물어봤을 때 대답할 줄 알아야 하는 것,.

정의

개발과 운영의 협업을 통해서 소프트 웨어 배포 속도랑 안정성을 높이는 문화 및 방법론

devops는 단순히 특정 직무의 이름이 아니라 개발이랑 운영이 협력해서 배포를 빠르고 안정적으로 만들자는 문화이고 방식임.

우리가 개발하는 프로젝트에 기능을 넣는게 개발의 영역.

준비된 기능을 사용자가 실제로 쓸 수 있게 만들고 올린 뒤에도 관리하는게 운영의 영역.

같은 기능에서의 만드는 책임이랑 돌리는 책임이 나뉘어져 있음.

Devops는 이 두가지 책임 중간에 끊기지 않고 연결되게 하는 것.

개발 영역

- 지속적인 통합 CI - 작성한 코드를 자주 합치고 빌드함.
- 애플리케이션 설계 개발
- 배포 준비

운영 영역

- 배포 , 릴리즈 관리
- 인프라 관리
- 모니터링과 유지보수
- 인프라를 코드로 정의 하는 관리 방식 - IaC
- 왜 코드로 관리? - 별도의 문서로 남는 것 이니까

사용 이유 :

개발이랑 운영을 왜 굳이 붙이는가?

- Devops라는 개념이 사용되는 이유는 운영간의 소통 지연, 책임 분산, 수작업으로 발생하는 시간과 자원 낭비를 없애서 빠르게 배포하기 위해서
- 전체 개발 프로세스 생산성을 높이기 위해서 -> 생산성이 높아지면 새로운 기능 출시가 빨라지고 반영도 빨라짐.

그리고 개발이 넘긴것을 운영이 다시 이해하고 손으로 배포하는데 시간이 걸림

- 문제가 생기면 크리티컬.
- 둘의 소통이 또 관건.. 어디에서 문제 생겻는지 서로 떠넘기면 답이 없음.
- 이런 벽을 허물자는데서 출발.
- 사람 손으로 하던거 통합, 검증 배포 자동화 하자고 하는게 devops의 필요성.

정리

- Devops는 개발이랑 운영을 연결해주는 문화, 방법론
- 개발이랑 운영이라고 하는 영역이 빠르고 안정적인 배포라는 공동의 목표.
- 개발 영역은 기능 설계, 배포 가능한 상태까지 준비해주는 쪽.
- 운영 영역은 결과물을 실제 서비스 환경에서 배포하고 인프라 관리하고 모니터링 하면서 안정적으로 유지하는 쪽.
- 이 두 영역을 자동화로 이어주는 축이 Ci/CD

**AWS EC2**

서버가 있어야 한다. 배포할 곳이 있어야 한다.

- > AWS EC2

정의

EC2는 사용자가 필요에 따라서 쉽게 가상 서버 생성하고 구상해서 관리할 수 있도록 해주는 aws의 서비스 이다.

EC2 자체로 만들어진 가상 서버 한대를 인스턴스라고 부름.

EC2는 서버 만드는 창구고 인스턴스는 창구를 통해서 받아온 서버 한대

인스턴스?

- 인스턴스는 클라우드에서 실행중인 가상 서버 한대를 이야기 함.
- OS, CPU, 메모리 저장소 다 있음
- 

설명 할 수 있어야 하는 것

- EC2가 무엇인지
- 왜 물리 서버를 직접 사는 대신 클라우드에서 서버를 빌려 쓰는지
- 서버 켜지고 꺼지고 사라질 때 무슨 일이 일어나는 지

쉽게 이야기 하면, 배포할 서버를 AWS에게 빌리는 것. 빌렸는데 접근을 terminal로 발급받은 주소가 있으면 그걸로 들어가서 우리가 명령어로 git, pull도 하고 배포도 하고 함.

워크로드 - 시스템이 처리해야하는 일의 양이나 종류

Elastic - 인스턴스를 줄였다가 늘렸다가 할 수 있음.. (물리서버가 아니기에 가능)

Compute - 처리 능력. 인스턴스 한대는 CPU, 메모리, 네트워크 성능 갖고 있는 가상 컴퓨터.

- 원하는 운영체제 올리고 어플리케이션 실행 함. 물리 장비 안갖고 있어도 자원 쓸 수 있게 해줌

Cloud - 이 모든 것을 인터넷에서 필요할때 쓸 수 있게 해주는 환경.

- 온디멘드라는 표현. 온디멘드는 필요할 때 즉시 만들고 쓴 만큼 비용을 내는 방식. 필요하면 서버 만들고 다 쓰고 지우면 그만큼 비용을 내는 방식.

EC2 인스턴스가 빨간 박스 안의 서버를 클라우드 환경에서 만들어주는 것.

우리가 계속 이야기 하는 운영환경에 해당하는 요소 중 하나

서버를 EC2 쓰면 물리 장비 구매 안하고 클라우드에서 확보해서 쓸 수 있다.

그럼 왜 쓰는가?

- 필요한 시점에 서버를 즉시 확보, 확장해 비용 부담 없이 유연한 컴퓨팅 환경 제공
- 필요한 시점
    - 서비스 운영하면 트래픽이 일정하지 않음. 이벤트 있는 날은 사용자 몰리고 새벽에는 거의 없음.
    - 서버를 쓴 만큼 비용을 내는 것도 가능.

유연한 컴퓨팅 환경

- 인스턴스 타입이 여러가지. CPU 성능이 중요할 수도.. 메모리가 많이 필요할 수도.. GPU가 필요할 수도.. 골라서 하면됨 ㅇㅇ
- EC2는 혼자 떨어져 있는 서비스가 아님

**IAM(Identity Access Management)**

누가 어떤 AWS 작업을 수행 할 수 있는가를 정하는 것.

VPC는 EC2가 놓이는 네트워크 공간이랑 경로가 어떻게 생겼는가

보안 그룹은 어떤 출발지에서 어떤 포트로 들어오는 연결 을 허용 할 건지.

정의

어쨌든 회사에서 AWS 갖고 여러 서비스 사용하고 관리하고 비용도 많이 나갈텐데 아무에게나 접근하고 관리하는 권한을 주면 안됨.

1. 인증
2. 권한(인가)

IAM이 서비스가 돌아가는 경로 안에서 어디에 위치하고 있는가..

우리가 AWS 사용하면서 콘솔에서 버튼을 누르든 터미널에서 명령을 보내든 어플리케이션 코드 안에서 AWS sdk 사용하든 다 같은 api 요청임

- 인스턴스 종료 한다는 것은 결국 EC2 서비스에 종료 요청을 보내는 일.

IAM이 네트워크에 놓여있는 지원이 아님.

자원의 범위

- > EC2 인스턴스르 만들 때 리전이나 가용 영역을 고름. 인스턴스는 특정 리전 안에서 만들어 지고 서울 도쿄 등등이 있음..
- > IAM은 이런 개념이 아니고 자원이 아님.
- > AWS 계정 전체에 적용이 되는 글로벌 서비스.

IAM은 AWS API 작업에 대한 권한을 판단함. 네트워크 연결 자체를 다루는 건 아님.

- 인스턴스를 종료 할 권한이 있다는 거랑(IAM) 인스턴스에 접속 할 수 있다는 것이랑은(VPC) 다른 이야기.
- 권한은 있는데 인스턴스에 접속이 안되는 상황이랑, 접속은 되는데 작업이 거부되는 것이랑은 다른 문제.
- 봐야 할 곳도 다름.

사용자는 AWS 리소스에 접근 할 수 있는 개별적인 계정, 신원.

그룹은 여러 사용자 묶어서 공통 권한 관리하는 집합.

역할(role) 임시적으로 특정 권한을 위임하는 개념.? 필요한 순간에 )

정책은 사용자가 어떤 리소스를 어떻게 사용 할 수 있는지 규정한 권한 규칙.

정책 문서가 실제로 표현하는 것

정책 문서 이해하기 위한 예시로 코드가 있음. 어떤 내용을 담고 있는가를 보면 된다.

Effect에는 Allow인지 Deny인지.. 권한의 명시.

Action에는 서비스가 받는 API 작업 이름이 명시.

Resource 에는 권한이 미치는 범위..

EC2 인스턴스에 역할을 연결하면 어플리케이션이 실행 중, 임시 자격증명을 받아서 잠깐 동안 서비스를 호출함. (만료도 알아서 됨)

- 자격증명이 코드나 설정파일에 남지 않고 깔끔하게 처리가 가능함.

역할에는 정책이 하나 더 붙음 - 누가 이 역할을 넘겨 받을 수 있는지를 정하는 정책.

- > 앞에서 본 정책이 무엇을 할 수 있는가를 정의했으면 지금 이 정책은 누가 이 역할을 쓸 수 있는가를 정하는 문서
- > principal 에 ec2 서비스를 적혀 놓음. 사람이 쓰는 자격증명이 아니라

요청이 평가 되는 순서

1. 먼저 주체가 AWS로 요청을 보냄. 사람일수도, EC2위의 어플리케이션 일수도 요청에는 자격증명이 같이 감.
    1. AWS는 자격증명으로 신원 확인 - 여기까지 인증
    2. 신원이 확인이 되면 IAM이 그 주체에게 연결된 정책들을 모음. 사용자에게 직접 붙어 있는 정책, 역할을 통해 받은 정책이 전부 함께 평가가 됨
    3. 허용으로 판정되면 요청을 처리함.
    4. 거부되면 권한이 없다는 오류.

설명 할 수 있어야 하는 것

- iam이 무엇인지
- 사용자의 그룹과 역할과 정책이 어떤 책임을 맡는지
- AWS로 보낸 요청이 어느 시점에 iam이 개입하는지
- 최소 권한 원칙.

정리 :

- IAM은 AWS 계정 전체에 적용되는 서비스고 aws api 요청이 처리되기 직전에 이 요청을 받아 들일지 아니면 거부하는 판단하는 단계, 관문
- IAM은 그 자원에 대해서 누가 무엇을 할 수 있는가를 다루는 것
- 구성요소
    - 사용자 - 개별 신원
    - 그룹 - 사용자를 묶어서 공통 권한 관리
    - 역할 - 사람이나 aws 서비스가 필요할 때 넘겨 받아 임시 자격 증명으로 사용
    - 정책 - 실제 권한 내용을 채워넣는 규칙 문서
- 요청 흐름 - 자격증명으로 신원 확인하는 인증 먼저 하고 다음에 연결된 정책들 모아서 허용 여부 판단하는 경로까지

**VPC(virtual private Cloud)**

EC2 - 가상 서버

IAM - 누가 서버 만들고 바꾸고 지울 수 있는지 판단하는 계층

EC2 인스턴스 하나 띄웠다고 가정

- 이 서버는 어디에 있는가
- 외부에서 오는 요청은 어떤 경로를 지나는가
- 서버 바깥으로 요청 보내야 할 때는 어떤 경로를 자나는가

VPD는 EC2 같은 자원이 있으면 네트워크 공간을 정의하고 트래픽이 어디로 갈 수 있고 어디로는 갈 수 없는지 경로를 정하는 서비스

- 앞으로 DB, s3, 트래픽 나눠주는 자원들을 하나씩 붙여가면서 전체 구조를 만드는데 그 자원이 어디에 어떻게 놓이는지 이야기 하려면 네트워크에 대한 큰 그림을 알아야 한다.

설명 할 수 있어야 하는 것

- vpc가 무엇이고 왜 필요한가
- vpc안에 어떤 구성요소가 있고 각각 무엇을 책임지는가
- 외부에서 들어온 요청이 EC2 같은 자원까지 도달하려면 어떤 경계를 어떤 순서로 알아야 하는가

정의

클라우드는 여러 사용자가 함꼐 쓰는 자원 덩어리

- 나만 쓰는 전용 구역을 가상으로 잘라내는것이 VPC임.

사용자가 AWS 클라우드 내에서 자신만의 논리적으로 격리된 네트워크를 생성하고 관리할 수 있도록 해주는 서비스

VPC 안에서 외부 접속이 허용되는 퍼블릭 서브넷이랑 내부 통신만 하는 프라이빗 서브넷을 만들고 라우팅이랑 방화벽으로 제어함.

가용 영역 : 한 리전 안에서 물리적으로 분리된 데이터 센터 단위.

EC2 인스턴스는 클라우드 어딘가에 막연하게 떠 있는게 아님.

- 특정 리전 안의 특정 가용 영역에 속한 특정 서브넷 하나에 놓여 있음
- 서브넷 안에 있는건 흔한 서버가 아니라 워크스페이스 라는 개념.

VPC는 네트워크 인터페이스를 갖는 AWS 리소스가 존재하는 공간

공간을 나누는 구성 요소

- > VPC, 서브넷이 공간을 나누는 구성 요소

VPC 만들때 사용할 IP 주소 범위를 정함.

서브넷은 그 범위를 다시 잘라낸 조각. vpc가 만든 몇만개 안에서 사용 할 수 있는 주소를 더 좁혀서 사용 가능.

이 범위를 다시 조각으로 나누는 이유는 용도별, 가용 별로 자원을 나눠서 배치하고 싶기 때문에,

여기서 퍼블릭, 프라이빗 서브넷이 나옴.

인터넷, 외부로 나가는 경로가 연결되어 있으면 퍼블릭 서브넷, 경로가 없으면 프라이빗 서브넷임.

경로를 정하는 구성 요소 - 라우팅 테이블, 인터넷 게이트 웨이, NAT 게이트 웨이

라우팅 테이블 같은 경우는 목적지 IP 대역별로 이 패킷을 다음에 어디로 보낼지 적어둔 규칙 목록

- 서브넷이 라우팅 테이블 하나를 참조, 기본적으로 VPC 자기 대역으로 가는 트래픽은 내부, 로컬로 보내도록 되어 있음.
- 같은 VPC 안에서 서브넷 끼리는 별도 설정 없이도 통신 가능
- 나머지 트래픽을 인터넷 게이트 웨이로 보내라는 규칙이 추가되면 그 서브넷이 퍼블릭 서브넷이 됨.
- 인터넷 게이트 웨이
    - VPc랑 인터넷 사이에 있는 문, VPC에 연결되고 안에서 밖으로 나가는 통신이랑 밖에서 안으로 오는 통신이랑 둘다 지나감.
- NAT 게이트 웨이
    - 방향이 한쪽으로만 열려 있음.
    - EC2 인스턴스가 보안패치를받거나 외부 API 호출해야하는 상황에서.
    - 밖에는 노출 x 근데 나갈 경로는 필요할 경우.
- 보안 그룹
    - 인스턴스에 붙은 네트워크 인터페이스 단위로 적용되는 방화벽
    - 들어오는 요청 허용하면 그냥 나갈 수 있음.
- 네트워크 ACL
    - 적용범위가 다름 서브넷 전체에 적용됨
    - 들어오는 트래픽에서 요청 허용해줘도 그에 대한 응답 규칙은 별도로 열어줘야 함.
    - 허용 or 거부 둘다 사용가능
    - 서브넷 단위로 구역의 오고 가는 출입을 챙기고 보안 그룹은 그 구역 안에 있는 자원의 문을 지키는 역할

vpc가 하는 일은 결국에는 경계를 만드는 것임.

- 왜 굳이..? 만약 aws 쓰는 모든 사람의 자원이 하나의 네트워크 안에만 있으면.. 의도와는 다르게 동작 가능.
- 첫번째로 필요한게 선을 긋는 일. 그 선이 VPC 라고 함..

퍼블릭, 프라이빗 서브넷.

- 구분 해야하는건 결국 서비스에 들어가는 모든 서버가 인터넷에 노출 될 필요가 없기 떄문
- 외부 요청을 직접 받아야하는건 일부 서버, 노출은 필요한 만큼만 하면 됨
- 자원을 하나씩 만들 때마다 외부에서 받아야 한다, 아니면 내부 프라이빗 서브넷으로만 처리해야한다는 걸 매번 판단하면 실수가 나니까 서브넷 단계에서 미리 성격을 정해줌

자원을 어디에 두느냐만으로 기본 노출의 수준이 결정됨 (실수를 줄이기 위해서)

공간을 나눴고 패킷을 어디로 보내면 되나?

- 목적지가 정해져야지 움직임. 라우팅 테이블은 목적지에 대한 답을 미리 적어놓은 표
- 퍼블릿 , 프리이빗 서브넷이 결정되는게 이 라우팅 테이블의 결정방식에 대해서..
- 라우팅 테이블에 어디로 갈 수 있는지 명시적으로 적어두는 것 자체가 통제가 됨

검사하는 구성 요소

방금 설명했던 경로를 지정하는 구성 요소 말고도 검사하는 계층은 필요함

- 그래서 퍼블릭 서브넷에 서버 열어 놓으면 경로가 열려 있다는거랑 아무나 들어오라.

보안 그룹은 같은 서브넷 안에 있어도 자원마다 열어줘야 하는 경로가 다를 수 있음.

- VPC 는 어디까지나 내 네트워크 인가를 정하고 서브넷은 그 안을 어떤 기준으로 나눌 것인가..
- 라우팅 테이블은 이 트래픽을 어디로 보낼 것인가, 인터넷 게이트 웨이랑 NAT 게이트 웨이는 어느 방향으로 열어 줄 것인가 에 대한 이야기

**요청이 VPC안으로 들어오는 순서**

퍼블릭 서브넷에 웹서버 역할을 하는 EC2 인스턴스가 있고 프라비잇 서브넷에 데이터베이스가 있는 구조..

사용자가 브라우저에 요청을 보내면 VPC경계의 인터넷 게이트 웨이 도착

- 라우팅 테이블로 어디로 보낼지 결정
- 서브넷의 acl이 인스턴스 허용 여뷰 판단, 이모지와 출발지 허용하는지 다시 판단.
- 모두 통과해야 인스턴스 위에 잇는 웹서버가 요청을 받음.

이 순서들을 알아야 하는건 나중가서의 오류 해결을 위해서임.

지금 VPC에서 이야기 하는건 전부 네트워크 계층의 통제.

앞에서 배운 IAM은 이 사람이 권한 있는지 판단하는 것

IAM은 AWS에 보내는 작업 요청 판단하는 거고 VPC는 그 실제 규칙이 오가는 것.

권한이 있어도 네트워크가 막혀잇으면 연결 안됨.

다른 계층임.

사용 이유

서비스간 격리를 통해 보안 위험을 최소화하고 제어 가능한 폐쇄형 네트워크 환경을 구성하기 위해서

- > 클라우드 서비스는 여러 프로젝트랑 여러 서비스 다른 회사의 계정이 같은 물리적인 인프라를 공유
- > 여기서 네트워크 수준 격리 없으면 문제가 생김.
- > 의도하지 않은 외부 노출이나 접근 권한 새어나갈 수도 있고 한곳에서 장애 발생하면 격리 하지 않았을 때 장애가 전파 될 수도 있음.

이런 문제들에 대해서 왜 어플리케이션 레벨이 아닌 네트워크 레벨에서 막는가?

- 어플리케이션에서 로그인 검사를 한다라고 가정을 하면 로그인 검사라고 하는 요청은 서버까지 도달한 다음에 이루어짐.
- 공격자가 있다면 공격자가 일단 문 앞까지는 와본 상태이다,
- DB를 프라이빗 서브넷에 두면 외부에서는 비밀번호를 알고 있는지와 관계 없이 연결 자체를 시작 할 수 없음…

그니까 좀 사전에 공격자를 차단하기 위해ㅔ서 라고 볼 수 있겠죠?

정리

- EC2는 어플리케이션이 실행되는 자원. IAM은 자원을 누가 만들고 바꿀 수 있는지 판단하는 계층
- VPC는 그 자원이 놓이는 공간과 그 트래픽을 결정하는 층.
- 다음 시간에 배우는 보안 그룹은 경로의 끝. 자원 바로 앞에서 어떤 연결을 허용할지 결정하는 규칙
- VPC는 AWS 클라우드 안에서 사용자가 직접 정의하는 논리적으로 격리된 네트워크 공간
- 구성요소
    - 공간을 나누는 VPC, 서브넷,
    - 경로를 정하는 라우팅 테이블, 인터넷 게이트웨이(퍼블릭 , NAT 게이트웨이(프라이빗
    - 검사하는 보안그룹, 네트워크 ACL

**AWS Security Group**

서버로 실제 트래픽이 올때 deny와 access할 것들 정하는 것이 보안 그룹

정의 :

- Security Group 클라우드 환경에서 인스턴스에 대한 네트워크 트래픽을 제어하는 가상 방화벽
- 방화벽.. 통과해도 되는 트래픽과 막아야 할 트래픽을 규칙에 따라서 구분해주는 장치
- 물리로 하는게 아니라 설정으로 제공 해주는 것.
- 가상 방화벽이다 라는 말이 붙은 것.

가상 서버가 네트워크에 연결되도록 해주는 가상의 네트워크 장치

EC2 인스턴스가 바깥이랑 통신 할 수 있도록 IP 주소 붙이는 장치

소스, 프로토콜, 포트

한대의 서버 안에는 웹서버도 있을 수 있고 그 안에 DB처럼 여러 프로그램이 동시에 돌아갈 수 있음.

- > 포트는 그 중에서 어떤 프로그램으로 가는 창구인지를 가르키는 번호, 일반적인 웹은 80, HTTP 면 443, SSH 원격 접속하면 22번
- > 로컬에서 스프링 실행 할 때는 8080 포트 붙거나 아니면 로컬에서 라이브 서버 플로그인 실행하면 포트 붙는 거 처럼.

프로토콜은 통신 규약.

보안 그룹의 규칙은 결국 소스랑, 프로토콜, 포트의 조합.

인바운드, 아웃바운드, stateful

트래픽을 두 방향으로 나눠서 볼 수 있음.

하나는 인바운드. 바깥에서 인스턴스로 들어오는 트래픽

아웃바운드. 인스턴스에서 바깥으로. 나가는 트래픽.

보안그룹은 stateful 한 방화벽이다.

- 사용자가 우리 웹서버로 요청을 보냄 요청은 인바운드 규칙에서 허용돼서 서버 안으로 돌아옴.
- 서버는 이 요청에 응답을 돌려줘야합니다. (아웃바운드 응답)
- stateful한 방화벽이 아니라고 하면 또 확인해야함.
- 그러나 보안 그룹은 stateful 한 방화벽…

설명 할 수 있어야 하는 것

- 보안그룹이 무엇이고
- 네트워크 경계 중 어느 위치에서 어떤 방향의 트래픽을 통제 하는지

기본저긍로 모든 인바운드 트래픽은 차단되며, 명시적으로 허용된 트래픽만 인스턴스에 도달 할 수 있다..
