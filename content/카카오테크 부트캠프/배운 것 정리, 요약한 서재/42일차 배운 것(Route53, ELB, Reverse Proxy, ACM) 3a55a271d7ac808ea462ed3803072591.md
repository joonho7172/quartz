정리

- Route 53은 요청이 인프라에 닿기 전에 이름을 주소로 바꾸는 가장 앞 단계에 있다.
- Route 53은 우리 도메인에 대해서 최종 답을 내놓는 네임 서버 이다.
- 하는 일은 어떤 주소로 응답할지 고르는 것 까지. 요청 자체를 받아서 전달하지는 않음. 이름을 붙이는 역할.
- 사용자 도메인 주소 이름 입력하면 리졸버가 여러 단계 거쳐서 route 53 도달하고 정책이랑 인스턴스 상태 반영해서 주소 응답함.

**Reverse Proxy**

잘 알아보자.

Route 53으로 바뀐 ip주소를 가지고 진짜 요청을 보냄

- 요청이 도착한 시점에서 가장 먼저 받아주는건? 받은 요청을 어디로 넘기는가에 대한 답이 Reverse Proxy

사용자 요청이 서버까지 어떻게 전달되는가..

- > 이름을 주소로 바꾸고, 주소로 도착한 요청을 받아내는게 리버스 프록시 AWS가 어떻게 분산해서 전달하는가>

설명 할 수 있어야 하는 것.

- 리버스 프록시가 무엇이고 어느 위치에 있는지
- 왜 서버 앞에 이런 중계 계층을 두늕
- 공개 진입점에 도착한 요청이 내부 서버까지 어떤 순서로 전달되는지

정의 :

클라이언트의 요청을 대신 받아 서버에 전달하고, 서버의 응답을 클라이언트로 반환하는 서버.

약간 창구 같은 역할임.

왜 리버스냐? 원래 프록시는 클라이언트 쪽인데, 서버 앞단에 서고 서버를 대신하니까.

서버 앞에서 클라이언트 요청 대신 받아서 백엔드 서버로 전달하고 그 응답을 돌려주는 구조.

Nginx나 apache .. caddy 같은 웹서버는 그다음

만약에 리버스 프록시가 없는 구조라면?

- 바깥에 알려진 주소가 곧 실제 서버의 주소

장비 대응이나 설정이 어려울 수 잇다.

요청을 받는 창구는 하나인데 실제로 일을 처리하는 서버는 여러대라면 서버는 여러대 일 수 잇음.

클라는 리버스 프록시 주소만 알면되고, 사용자 입장에서는 리버스 프록시가 서버에게 보임.

반대로 앞에 창구를 하나 세워두면 사용자가 아는 주소는 그 창구 하나임.

사용 이유

왜 필요한가?

- 서비스가 성장하면서 바뀌는 쪽은 뒤쪽의 어플리케이션 서버임
- 서버의 주소는 함부로 바꿀 수가 없움,,’
- 둘 사이에 완충지대를 두는 것.
- 리버스 프록시 구조의 출발점.
- SSL 종단 - 원래라면 서버 마다의 암호화 요청을 보내 복호화해서 백엔드에 전달함.

결론 : 보안과 로드밸런싱 암호화 통신이 가장 큰 이유

- 어플리케이션 자체가 원래 하려던 일과는 거리가 있는 일임. 요청을 어디에 보내고 정할지도 이런 일들이 있다.
- 이걸 서버 마다 두면 복잡하니까..

리버스 프록시 경로

처음부터 출발하면 사용자가 도메인 입력하고 DNS가 그 이름은 IP주소로 해석을 해줌 (route 53)

- 브라우저가 알아낸 주소로 실제 요청을 보냄
- 요청을 받는 공개 진입점에 있는게 리버스 프록시
- 요청을 받은 리버스 프록시는 자기가 가진 전달 규칙을 확인
- 어떤 경로의 요청인지를 보고 어디로 보낼지를 정함 (nginx 안에 파일에서 있음
- 같은 리버스 프록시 창구로 들어와도 경로에 따라서 서로 다른 서버로 나눠서 갈 수 있다는 점임..
- 백엔드가 처리한 응답은 다시 리버스.프록시 거쳐서 돌아간다.
- 만약 백엔드 자체가 제대로 된 응답을 반환하지 못한다고 하면 502 반환.

그럼 Forward 프록시와의 차이점은 무엇이느냐.

WebServer랑 WAS의 차이점도 리버스 프록시 정리 할 때 참고 해보기

보통 nginx로 구현하긴함.

정리 :

- 리버스 프록시는 서버 앞단에 위치하고 클라 요청 대신 받아서 하나 이상의 백엔드 서버로 전달. 응답을 다시 전달해주는 구조
- 특정 서비스가 아니라 역할의 개념
- 왜 두는가? 외부에 열리는 진입점을 하나로 모으고 요청을 여러 서버로 나누고 암호화 통신 하는 것도 한 자리에서 정리해주고 자주 나가는 응답이 있으면 캐시도 하고 압축도 해줌.

**ELB(Elastic Load Balancer)**

리버스 프록시 - 클라이언트가 내부 서버에 직접 연결하지 않고 중개자가 요청 대신 받아서 내부 대상으로 전달 하는 구조

- > 리버스 프록시가 넘길 내부 서버 대상이 하나가 아니라 여러곳이라면 그 중 어디로 보낼지?

여러 대상 중에서 하나가 응답하지 못하는 상황이라면 그 사실을 누가 알까

ELB, AWS의 서비스.

구조 정리 VPC로 네트워크 공간 만들고 EC2 인스턴스 띄우고 보안 그룹으로 어떤 방향으로 포트 연결 허용할지.. 그리고 ip 주소 고정하고 route53으로 도메인 연결

- 여기까지 하면 도메인 접속 가능.
- 이 구조는 EC2 한대가 계속 살아있어야 함.

설명 할 수 있어야 하는 것.

- ELB가 요청 경로의 어느 지점에 있고 요청을 받아서 어떤 기준으로 대상에 넘기는지
- 그리고 대상 하나가 응답하지 못할 때 ELB가 무엇을 하는지

정의

- 여러대의 서버로 들어오는 네트워크 트래픽을 자동으로 분산해주는 서비스
- 들어오는 트래픽이라는 말은 ELB가 서버 뒤쪽이 아니라 서버 앞쪽에 있다라는 뜻.
- 분산한다라는 말은 그 요청을 한 대상에게 몰아 주지 않고 여러 대상에게 나눈다는 뜻. 나누는 단위가 요청이다..~ 사용자 한명이 특정 서버에 묶이는게 아니라 같은 사용자가 연달아서 보낸 요청도 서로 다른 대상으로 갈 수 있음.
- 그래서 두대든 열대든 대상이 받아가는 양이 비슷하게 유지가 됨
- 한대는 바빠지고 나머지는 놀고 있는 상황을 막는 것. 부하 분산이라는 말에 의미가 됨
- 자동으로 라는 말은 나누는 판단을 어플리케이션 코드나 클라가 하지 않는 다는 뜻.
- 판단은 ELD가…

왜 필요할까..?

서버가 한대일 때는

- 트래픽 몰리면 서버 한대의 CPU랑 메모리는 정해져 있음. 요청 몰리면 터지거나 응답이 느려짐.
- 두번째로는 그 한대가 죽으면 서비스 전체가 멈춤. 대체 할 곳이 없음..
- 그래서 서버를 여러대를 둔다.
- 사용자가 어느 서버로 가야할지 누가 정하는가의 문제가 발생함.
- DNS는 지금 서버가 죽었는지 살았는지 판단은 부족함.
- ELB는 요청 여러 대상에 나눠서 보내고 응답 못하는 대상에게는 요청 보내지 않음.
- ELB는 특정 EC2 인스턴스에 붙는게 아니라 리전 안에서 동작하는 독립된 리소스
- VPC 안에서 자리를 잡고 지정한 가용 영역의 서브넷에 요청을 받는 노드를 따로 둠.
- 가용영역은 두 곳 이상 지정 가능.

사용자가 브라우저에 우리 도메인 입력

- Route 53이 모데인 어떤 주소로 가야 하는지 알려줌.
- 지금까지는 EC2의 퍼블릭 ip로 갓는데 elb가 잇으면..
- 트래픽 상황에 따라 AWS가 내부적으로 노드를 늘줄 하기 때문에 IP자체가 바뀔 수 있음.
- 그래서 route 53을 쓴다고 하면 IP를 직접 적는 대신 AWS 리소스를 직접 가르킴.
- 그 다음 ELB가 대상을 고르고..
- EC2 앞에 잇는 보안 그룹과 만나게 됨..
- 요청 경로가 사용자 -> route 53 -> ELB -> 보안 그룹 -> EC2 이런 과정이라고 생각해보자~

ELB 구성 요소

첫번째는 리스너, ELB가 어떤 프로토콜과 어떤 포트로 요청을 받을지 정하는 부분. 80, 443 HTTPS 받을지 여기서 결정됨

두번째는 대상 그룹. 요청을 실제로 처리할 대상들을 묶어놓은 목록. EC2 인스턴스 여러개면 ELB가 골라줌

세번째가 헬스 쳌!. 대상 그룹에 등록되어 있다고 해서 무조건 요청을 받는건 아니고 주기적으로 확인 요청을 보내서 정상 응답이 오는지 확인함.

- 정상이면 정상 상태로 두고 요청 보내고 응답 없거나 실패하면 비정상 상태로 표시하고 요청 보내지 않음.
- 판단의 주체가 ELB에게 있음.

ALB와 NLB의 차이점 정도는 정리를 하고 말 할 수 있어야 함.

ELB는 로드 밸런서의 여러 유형을 묶은 이름.

ALB(Application Load Balancer) - HTTP와 HTTPS의 트래픽을 다룸. URL경로나 해더를 기준으로 서로 다른 대상 그룹에 보낼 수 잇음.

- 슬래시 API로 시작하는 요청은 API 서버 그룹으로 보내고 나머지는 웹서버로 보내는 등..

대부분의 선택지임.

NLB(Network Load Balancer) - TCP와 UDP 수준에서 동작함. 요청의 내용을 해석하지 않고 연결 자체를 그대로 넘김.

- 이렇게 하면 더 빠르고 지연 시간이 낮음.
- 아주 많은 연결 처리해야하거나

사용 이유

자동 분산해서 장애 시에도 서비스 가용성을 유지하기 위해서.

고가용성 및 자동 장애 조치, 자동으로 트래픽 전환함..

- 여러 가용 영역 걸쳐서 인스턴스 배치 가능
- 가용 영역 같은 리전 안에 있지만 분리된 그룹.
- 서버 두대를 같은 가용 영역에 두면 그 영역 전체에 문제가 있을 때 함께 영향을 받음.
- 서로 다른 가용 영역 안에 두면 장애 범위가 분리가 됨

**AWS Certificate Manager(ACM)**

지금까지 사용자가 요청 보내면 서버 도착 과정까지 필요한 요소들을 배웠음.

설명 할 수 있어야 하는 것.

- SSL/TLS 인증서가 무엇을 증명하는 역할을 하는가

정의

인증서를 손쉽게 생성하고 배포할 수 있도록 지원하는 서비스

TLS - Transport Layer Security 웹에서 데이터 암호화해서 전달하는 규약

SSL

인증서는 통신 시작 할 때 서버쪽이 사용자에게 내미는 신분증

- 신분증에는 인증서가 어떤 도메인의 것인지가 적혀 있음.
- 브라우저는 이미 CA 목록을 갖고 있어서 서버가 내민 인증서의 서명을 확인함

AWS 서비스에 배포하는 과정을 대신 처리해주는 관리형 서비스

- 원래는 인증서를 직접 발급 받고 직접 확인해야 함.

인증서가 실제로 붙는 위치

- 원래 발급 받으면 EC2에 직접 올려야함.
- ACM 인증서는 AWS 서비스에 연결해서 사용함.

요청 경로에 사용자가 브라우저에 주소 입력하면 route 53이 주소 던져주고 ELB로 감.

- ELB에서 TLS 연결이 맺어짐. 이때 ELB가 브라우저에게 전달하는게 ACM에 인증서.

리버스 프록시도 요청 받아서 뒤로 전달하고 그 기점에서 TLS 처리 가능함.

이런 경우에는 인증서 파일 직접 준비하고 서버에 올리고 설정해야한다.

AWS 관리형 구성으로 쓰는 ACM 같은 경우에는 ACM에 있는 자원을 ELB에 연결함.

퍼블릭 인증서, 프라이빗 인증서

- > 외부 사용자들이 접근하는 도메인, 공개된 웹사이트나 공개 API사용함

프라이빗은 사내망의 내부 서비스 처럼 외부에 공개되지 않은 도메인에 사용, 별도로 설정해줘야함.

정리

- Route 53이 도메인 이름은 진입점에 연결하고 사용자 요청이 ELB에 도착하면 TLS 연결이 맺어지고 이때 사용되는 인증서가
    - EC2안에 파일 복사해서 넣지 않아도 사용자가 인프라랑 만나는 진입점에서 인증서가 연결됨.
- 인증서에는 신원 확인이랑 전송 내용의 기밀성, 무결성을 제공하는 역할을 함.
