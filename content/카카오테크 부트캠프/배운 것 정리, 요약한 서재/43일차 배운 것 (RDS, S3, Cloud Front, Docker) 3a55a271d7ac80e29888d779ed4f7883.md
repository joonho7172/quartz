관계형 데이터베이스

- 달라지는 건 DB가 어디에 올라가는가..

- 이런 반복 운영을 AWS에게 넘긴 완전 관리형 서비스.
- 테이블 만들고 쿼리 짜는건 여전히 개발자 몫이지만 다른 영역의 책임을 덜었다.

EC2랑 똑같이 네트워크 경계 안에 놓이는 자원이다.

정리

**S3 (Simple Storage Service)**

거의 필수적으로 사용을 함.

RDS를 배웠고 원래 RDB에 저장하던 데이터들을 RDS에 저장했었음.

- 서비스 개발하면 파일을 저장해야함. RDB에는 안들어감.
- 통째로 저장했다가 통째로 꺼내 쓰는 데이터

전체 아키텍처에는 EC2 데이터는 RDS, 파일은 S3

설명 할 수 있어야 하는 것

- s3가 뭘 저장하는지
- 서버 디스크나 DB가 아니라 왜 s3 두는지

구조화되지 않은 데이터 대규모 객체 단위로 저장함. 이미지나 로그 파일 자체를 RDB의 row에 넣기에는 적절하지 않다.

- 이런거는 통쨰로 저장하고 통쨰로 꺼내 씀.

객체 단위

- 데이터 덩어리 통째로 올리고 통째로 내려 받기 때문에 객체 단위로 다룸. 파일 시스템 처럼 동작하지는 않음

서버 어플리케이션 돌아가는 EC2의 디스크

Or DB 자체에 그냥 메모리 올리기

Or S3

- 어플리케이션은 사진을 올리고 S3에 객체를 가르키는 키를 저장하면 됨.
- 서버가 직접 파일을 읽을 필요는 없음. 그냥 주소만 알려주면 브라우저가 S3에서 받아가면 됨.
- 프론트 엔드 에서 S3로 바로 업로드가 가능하면 고해상도 이미지 같은 경우는 메모리 먹고 처리 해줘야됨/

사용자가 올리는 파일이나 로그, 백업 같은 데이터는 관계 없이 다루니까 s3에 올려서 처리, RDS에서 key나 url만 문자열로 다루면 됨

4. 암호화 키 만들고 안전하게 보관해주는 서비스가 있음.

VPC 밖의 별도의 서비스 API처럼 접근한다고 했음.

- 두군데에서 처리가 됨.

- 요청이 들어오면 누가 보내고 어떤 작업 요청했고 어떤 버킷과 키를 대상으로 하는지 보고 허용 여부를 결정함.

Principal, action, resource 가 한묶음. -  잘 다뤄야 함.. 신경 써서 알아야 한다.

정리

- S3는 이미지, 로그, 백업 파일 처럼 데이터 파일 단위를 보관하는 스토리지 서비스
- 버킷이라는 컨테이너 안에 객체를 두고 키로 그 객체를 찾는다.
- 위치는 VPC안에 있는게 아니라 리전 단위로 있고 우리가 설정한 네트워크 바깥에서 api 요청한 것처럼 가져오고 처리한다.
- S3 쓰는 건 용량 걱정 없이 저장할 수 있고 내구성이랑 가용성 좋음.

**CloudFront**

S3버킷에 올려둔 이미지나 정적 페이지가 있는데 서비스가 글로벌 서비스여서..

- 각 도시에서 받아감..
- 저장은 s3로 했는데 문제는 전달
- 멀리 있을 수록 응답이 느려짐
- 사용자가 많으면 더 느려짐
- 객체를 외부에 공개해야한다는 문제점도 있음.
- 데이터 전세계 사용자에게 빠르고 안전하게 전달하는 책임은 서로 다른
- S3는 저장을 하고 이제 배우는 Cloud front는 전달하는 계층을 담당함.
- cdn임..

설명 할 수 있어야 하는 것

- Cdn이 무엇이고 cloud front는 어떤 역할을 하는지
- 같은 요청이라도 캐시의 유무에 따른 역할.
- 엣지 로케이션 - 어느 범위에 존재하는지

CDN - content delivery network

- 이미 만들어진 컨텐츠를 사용자에게 전달하는 일만 전담하는 네트워크
- CloudFront는 aws가 제공하는 CDN 서비스
- isp는 통신사 cdn자리에 클라우드 프론트가 들어감.
- CDN 같은 경우에는 그보다 더 앞에서 사용자와 가까운 곳에서 컨텐츠 사본을 갖고 응답해서 요청이 뒤에까지만 안가게 할 수 ㅇ있는 계층

CDN이 왜 필요한가?

- 없으면 모든 요청을 원본 서버가 직접 처리를 해야함
- Origin - 원본 서버
- S3 버킷도 origin 될 수가 있음.
- EC2 될 수도 로드밸런서가 될 수도 있음. 온프레미스 서버가 될 수도 있음.
- 원본 서버를 갖고 처리하는 구조는 문제가 생김.
- 첫번째는 거리.
- 사용자랑 원본 서버의 거리가 멀면 멀 수록 응답이 느려짐.
- 두번쨰는 집중 부하.
- 글로벌 서비스 이므로 전 세계의 요청이 한 곳으로 오면 부하를 받을 수밖에 없음.

클라우드 프론트 쓰면 문제를 해결

컨텐츠의 사본을 전 세계 여러 지점을 올려두고 사용자가 자기랑 가까운 지점에서 받아가게 처리 할 수 있다.

이 지점을 엣지 로케이션이라고 부름.

클라우드 프론트가 컨텐츠를 캐시 해두기 위해서 전 세계에 분산해둔 데이터 센터

캐시 한다는 이야기는 원본 옮겨오는게 아니라 자주 요청되는 데이터를 가까운 데이터 센터에서 가져 온다는 것.

원본은 여전히 S3 버킷에 있고 엣지에 있는 건 사본..

클라우드 프론트 자원의 범위

대부분이 리전 이었음.. VPC랑 RDB등..

- > 클라우드 프론트는 구분 자체가 다름

S3 버킷은 서울 리전 안에 있고 그 안에 붙은 클라우드 프론트가 글로벌 하게 퍼져 있는 구조가 됨

S3을 origin으로 두는 상황에서 요청이 이동하는 경로

브라우저에서부터 출발하고 DNS 거쳐서 IP주소 받음

- 중요한건 DNS 거쳐서 받는 IP 주소가 버킷이 아니라.. 클라우드 프론트.
- 원본의 주소로 처리되는게 아님.
1. 캐시가 있고 캐시가 적중한 상황.
    1. 엣지에 요청한 객체의 유효한 사본이 이미 있는 경우
    2. 이때는 바로 클포가 응답..
2. 캐시 미스 난 상황
    1. 클포가 S3로 객체를 요청해줌 받아오는 결과를 사용자에게 전달. 동시에 엣지에 사본으로 저장해둠 같은 지역의 다음 사용자는 1번 캐시에 히트하는 상황으로 가게 됨.

클포를 쓰면  origin까지 만나는 요청의 비율을 낮추는 서비스.

어떤 컨텐츠가 얼마나 오래 사본으로 있을 지도 따로 설정을 해줘야 함.

정리

- 클라우드 프론트는 객체를 사용자에게 전달하는 곳. S3는 객체를 저장하는 곳. 저장이랑 전달은 다른 개념이고 전달을 담당하는 CDN에게 나눠줄 수 있다.
- 클라우드 프론트는 특정 리전에 묶이지 않고 전 세계 엣지 로케이션에 걸쳐서 동작을 함. Origin s3 버킷은 특정 리전 안에 있음. 요청 경로 생각하면 사용에서 엣지까지 그리고 엣지에서 리전까지 origin 까지 나눠 줄 수 있다.
- 엣지에 유효한 사본이 있으면 거기서 바로 cache hit해서 반환을 하고 만약에 없으면 오리진까지 가서 원본 가져오고 사본 넘김.

**Docker**

애플리케이션이 실행되는데 필요한 모든 요소를 하나로 묶어 어떤 컴퓨터에서든 동일하게 실행되도록 도와주는 도구..

AWS를 통해서 어플리케이션이 실제로 유저에게 사용되게 하기 위해서 돌아가는 구조..

어플리케이션을 클라우드에 올리는 자리는 준비가 됐음..

- 그 자리에서 어플리케이션이 항상 똑같이 실행되게 하려면 어떻게 해야하는가
- 실행에 필요한 것들을 어떻게 포장하고 다른 서버에서도 어떻게 그걸 재현 할 것인가

문제 상황

- 내 노트북에서는 잘 되는데 서버 올라가면 갑자기 안되거나
- 내 자리에서는 잘 되는데 다른 동료가 pull 받아서 실행 시키면 안되는 경우들이 생김.
- 언어 런타임 버전이 다르거나 마이너 버전이 다르거나 라이브러리가 빠져 있거나 설정값이 미묘하게 달라서..
- 컴퓨터에서는 되는데 라는 문제
- Docker 해결하려고 하는 것도 이런 문제

설명 할 수 있어야 하는 것

- Docker가 무엇이고 어떤 문제를 푸는지
- Docker를 이루고 구성요소들이 어떤 책임을 맡고 잇는지
- 예전부터 쓰던 가상 머신과 구조가 어덯게 다른지

각각의 구성요소들은 별도의 그거다…

맥북으로 자바 어플리케이션 하나 만들었다고 가정

- 런타임이 필요함.
- EC2 서버와 컴퓨터의 환경이 다르다면?
- 코드 바꾸지 않앗는데 정상적으로 돌아가지 않음..
- 예전에는 리드미로 설치 방법을 알려줬었음.
- 설치하는 일도 서버가 10대면 10대 다 맞춰야 함. 그럼 EC2 다 업데이트 햇어야 했음.
- 이걸 도커가 해결.
    - 서버마다 환경을 맞추는게 아니라 어플리케이션 코드에 다 포함해서 컨테이너에 다시 포장해서 그댈

실행하는 단위를 컨테이너

: 어플리케이션이랑 그 실행에 필요한 모든 것이 함께 들어있는 서버 안의 격리된 작은 공간

- 격리됏다는건 서버에 잇는 라이브러리나 버전이 아닌 컨테이너의 버전과 라이브러리를 따라 격리해서 실행을 시킨다.
- 화물에 필요한 것들은 컨테이너에 담아서 보내는 것이랑 같음.

도커에서 OS는 따로 얹지 않음. 도커라는 층 위에 여러개가 나란히 올라갈 수 있고 프로세스로 다뤄서 올릴 수 있음.

도커를 사용하면 세팅하기도 편함.

다른 버전 언어 사용 할 떄마다 vm 만들어서 실행시키는거 무거웠다.

- > 그걸 해결 할 수잇음

도커로 가져와서 띄워놓고 배포..

- > 컨테이너 안에 자바, mysql, nginx , jar파일 같이이 함.

도커 구성 요소

이미지, image

- > 실행할 코드랑 필요한 라이브러리, 결과물, 바뀌지 않는 불변 파일.

아직 실행되는 상태는 아님.

컨테이너

- > 이미지를 실제로 실행해서 메모리 위에서 코드가 돌고 살아잇는 프로세스

이미지 하나로 여러개의 컨테이너 띄울 수 있음.

컨테이너가 실행중에 안에서 파일을 만들어 낼 수 있음.

만들어낸 파일은 컨테이너의 쓰기 계층이 있고 그곳에 쌓임.

쓰기 계층은 컨테이너를 삭제하고 다시 만들면 유지되지 않음.

컨테이너는 언제든지 지우고 띄울 수 있는 대상으로 다루는게 기본

그래서 사라지면 안되는 데이터는 컨테이너 안에 두면 안됨.

필요한 데이터는 RDS나 S3에 올려서 영속적 저장, 아니면 도커의 기본 볼륨을 다룸.

도커파일, Dockerfile

- > 이미지를 어떻게 만들지 적어둔 설계도, 청사진.. 역할을 하는 텍스트 문서

무엇을 바탕으로 사고. 어떤 설정을 넣을지 단게별로 적어줌..

도커 레지스트리 , registry 만들어진 이미지를 보관하고 필요한 곳에 나눠주는 중앙 저장소..

- > 레지스트리 라는 말 자체가 데이터 저장소임

도커는 이미지를 여기에 올려두고 필요한 서버가 내려받아서 쓰는 창구 같은 역할

공용 레지스트리.. 자체 레지스트리를 두기도 함

도커 데몬 Daemon

Daemon : 백그라운드에서 계속 돌면서 맡은 일을 처리하는 프로그램

Docker 파일 읽어서 이미지만들어내는 빌드 과정

Build : 도커 파일에 적힌 순서대로 필요한 재료들 모아서 하나의 완성된 결합문

도커가 만들어지고 실행되는 순서

일반은 도커 파일이 있어야 함 설계도.

- > 개발자가 프로젝트 안에 DockerFile을 작성함.
- 설계도가 먼저, 이미지가 그 다음
- 이미지ㅡ여러 곳에 쓸 수 있게 옮기는 단계
- 내려받은 이미지 실행하면 서버 위에서 컨테이너가 돌아감.
- 컨테이너 들어가면 어플리케이션이 사용자 요청 처리함

레지스트리 거치지 않고 EC2에서 pull 땡겨서 거기에서 이미지 빌드 해도 됨.
