**Docker**

사용 이유

정보1 : VPS와 Docker 비교

교재 보면 Docker를 가상머신 VM이랑 비교를 함.

- 이해하려면 가상머신을 알아야 함..

도커 같은 가상화 기술이 없던 시절에는 물리 서버 한대가 곧 서버 한대 였음.

- 한대의 서버에 여러 어플리케이션을 올리면 골치 아픈 일이 생김
- 중요한 서비스는 서버 한대에 어플리케이션 한대만 올리는게 안전한 방식.

문제는 비용. 서버는 비싼데 어플리케이션 하나가 서버의 자원을 다 쓰는 경우는 드뭄

- 비싼 서버의 일부분이 자원이 놀고 있는 상황이 됨.
- 이런 낭비를 해결하려고 나온 것이 가상화, 그리고 가상 머신.
- VM은 소프트 웨어로 흉내낸 가짜 컴퓨터 한대.
- 진짜 컴터는 1대인데 CPU나 메모리, 디스크가 달린 것 처럼 보이는 가짜 컴퓨터를 여러대 만들어 내는 것.
- 물리 서버 한대를 서로 침범하지 못하는 독립된 서버 여러대로 사용 가능.
- 격리도 할 수 있고 놀던 자원도 활용 가능..
- 쪼갠 가상 서버를 빌려주는 상품이 VPS 가상 사설 서버
- 즉, EC2가 VPS의 개념

한대의 서버가 있으면 여러 실행 환경을 서로 격리하면서 자원을 아끼는 문제를 해결

- 방식의 차이에서 무게랑 속도가 달라진다.
- 이걸 비교 했을 때 컨테이너 라는 개념을 더 명확히 알 수 있음.

VM은 격리를 어떻게 만드는가?

- 물리 서버 하나 위에 가짜 컴퓨터 여러개를 만들어내는 흉내를 담당하는 관리자 - ㅎㅏㅇㅣㅍㅓ 바이저
- 가짜라도 앱 돌리려면 운영체제는 설치 해야함.
- Vm 안에 설치된 운영체제를 게스트 OS라고 하고 반대로 물리 서버에 원래 깔려 있던 OS를 Host OS

VM 방식은 단독 주택을 여러개 짓는 거랑 비슷함. 집마다 보일러, 배관, 전기 설비 전부 따로 설치함.

컨테이너 방식은 한 건물 안에 원룸을 여러개 두는거랑 비슷함

- 중앙 설비가 커널, 방 하나하나가 컨테이너

어플리케이션 밑에 있던 게스트 OS가 있는가 없는가 의 차이가 있다.

컨테이너 방식은 어플리케이션이 6개가 되어도 OS는 여전히 하나다.

컨테이너는 운영체제 없이 어떻게 돌이가는가..

- 커널의 역할
- 프로그램이 파일을 읽거나 네트워크로 데이터를 보낼 때 실제로 그 일을 처리해주는게 커널.
- VM은 게스트 OS를 통쨰로 갖고 있으니까 이 커널도 VM 마다 따로 하나씩 있음.
- 파일을 읽고 쓰는 일은 호스트의 커널에게 부탁하고 자기 컨테이너 안에는 어플리케이션의 런타임, 라이브러리만 담음.
- 무거운 게스트 OS가 없음.

메모리 차지 하는 것 자체가 달라짐.

컨테이너는 커널을 공유하니까 컨테이너 안에 담을게 훨씬 적고 그만큼 한 서버에 더 많이 띄울 수 있음.

- 시작시간에도 차이가 남. VM 하나 켠다는거는 컴퓨터 한대 부팅하는 일이라서 시간이 오래 걸림.

컨테이너는 부팅할 운영체제ㅏㄱ 없어서 빨리 켜지고..

커널을 공유한다는건 vm만큼 격리의 벽이 두껍지 않다라는 뜻.

상황에 따라서 강한 격리가 필요하다 라고 하면 VM이 더 맞을 수도 있음.

- 가볍고 일관되고 빠른 배포를 원하면 - docker

정리

- 도커는 어플리케이션 실행에 필요한 모든 것을 하나로 포장해서 어디서 실행하던 같은 결과가 나오게 만드는 컨테이너 기술이다.
- 구성요소
    - 이미지 - 실제 실행 전의 불변한 결과물
    - 컨테이너 - 이미지를 실행해서 지금 돌아가고 있는 컨테이너
    - 도커 파일 - 이미지를 만드는 설계도 파일
    - 레지스트리 - 이미지 보관하고 공유 Docker hub
    - 작업을 실행하고 빌드하는 daemon이 있음.
- 가상 머신과 도커의 차이

**Image**

도커에서는 Image

- 실행에 필요한 것들이 통째로 담겨서 더 이상 바뀌지 않는 결과물 하나가 옮겨짐
- 지금 컨테이너 자체를 다루는 구간. 앞에서 도커의 전체 그림을 봤고 그림 안에서 옮기고 실행하는 단위인 이미지가 뭔지 설명
- 다음 시간에는 image를 실제로 실행한 컨테이너를 배움.

설명 할 수 있어야 하는 것

- image가 정확히 무엇인지
- 왜 이렇게 내용이 고정된 결과물을 따로 만드는지.

정의

애플리케이션 실행에 필요한 바이너리 설정 라이브러리등을 미리 포함한 읽기 전용 스냅샷

도커를 사용하지 않으면 파일을 실행하는 라이브러리를 따로따로 준비를 해야함..

image는 이 준비물 전체를 하나로 묶음.

jar랑 실행할 런타임 , 설정까지 담은 스프링 부트 이미지..

이미지가 잇으면 자바 없어도 돌아감.

읽기 전용

- 이미지는 한번 만들어지면 그 내용이 바뀌지 않음.
- 내용이 고정되어 있으니까 같은 이미지를 가져오기만 하면 언제 어디서 실행하던 같은 환경이 만들어짐
- 도커에서 이미지를 빌드 할 때 캐싱을 하는데 연관이 있음.

스냅샷

- 어떤 시점의 상태를 그대로 찍어둔 것.
- 이미지는 특성 시점의 환경을 그대로 찍어서 굳혀 둔 것.

이미지는 담아두기만 하는게 아니라 컨테이너를 만들어 내는 템플릿.

- 하나의 이미지를 갖고 컨테이너 하나 or 여러 개 만들음.

전체 흐름에서 Image는 실행 환경이 통째로 굳어 있는 결과물이고 이걸 실행하면 컨테이너가 된다.

이미지는 하나의 전체 덩어리가 아니라 여러개의 읽기 전용 레이어로 구성이 되어 있다.

쌓인 층들은 그림에 해당..

- 이미지로 컨테이너를 실행하는 순간에 쓰기 가능한 레이어가 하나 얹히고 실행중에 생기는 변경은 맨 위의 쓰기 레이어 기록이 됨

이 구조 때문에 하나의 읽기 전용 이미지를 여러 컨테이너가 함께 바탕으로 삼으면서 자기만의 쓰기 레이어를 가짐.

같은 이미지로 컨테이너 여러개 ㅅ띄워도 간섭하지 않음.

- 여러 이미지가 같은 하위 레이어에 공유하면 레이어는 디스크에 한번만 저장됨

스프링 부트 앱을 하다가 매주 이미지를 만들었다고 가정하면,,,매번 만든 이미지 마다 공통의 계층이 존재함

지금처럼 원본을 건드리지 않는 방식을 copy onwrite cow.

아래쪽 읽기 전용.

실행중의 변경은? 애초에 이미지 만드는 도커 파일에 변경해서 넣어야 함. (읽기 전용이라 수정이 불가능함)

이름이랑 태그

- 이미지를 어떻게 부르고 구별하는지 짚고 감.
- 이미지는 보통 이름과 태그를 붙힘.
- 태그는 버전 구분하기 위해서 씀.
- 이름이랑 태그만으로는 부족함. 이름이랑 태그는 사람이 나중에 다른 이미지에 옮겨 줄 수도 있음.
- 이미지 마다 내용으로 계산되는 고유한 값이 있는데
- 이걸 다이제스트 라고 한다.
- 다이제스트 : 이미지 내용이 같으면 언제나 같은 값이 나옴.

정리

- Image는 어플리케이션 실행에 필요한 코드랑 런타임 라이브러리 설정을 담아둔 스냅샷.
- 여러 단계 결과 거쳐서 만들어진 결과물. 그 자체로는 실행중인 프로세스 아님.
- 구조 - 이미지는 여러개의 읽기 전용 레이어, 이미지로 컨테이너 실행하면 그 위에 얇은 쓰기 레이어가 하나 얹힘
- 실행 중 변경은 쓰기 레이어에 기록 되고 아래 원본 이미지 레이어 copy-on-write방식으로 안전하게 보존된다,
- 이미지는 읽기 전용이고 불변, 어디서든 실행 가능하게 하기위해서 필요함.이미지가 공유하는 하위 레이어가 있다면 용량을 아끼고 전송량 절약 할 수 있다.

**Container**

이미지를 실행을 해야 컨테이너가 됨.

설명 할 수 있어야 하는 것.

- 컨테이너가 무엇인지, 이게 기존 vm이랑 다른점이 무엇인지?
- 도커랑 컨테이너가 왜 같은 말이 아닌지

정의

애플리케이션과 그 실행에 필요한 모든 종속성을 포함하여 경량화되고 독립적으로 실행되는 단위

어플리케이션 실행하는데 있어서 코드만 달랑 들어가는게 아니라 코드 돌리는 필요한 것들 함께 들어가고 그게 다른것들이랑 섞이지 않음

컨테이너는 실행 인스턴스

- 실행되는 동안에 파일을 만들거나 고치는 변경이 생김
- 그 변경이 기본적으로 컨테이너에 얹혀 있는 임시 쓰기 계층에 쌓임
- 컨테이너 지우면 사라짐

컨테이너는 컨테이너 마다 독립적인 실행 공간을 갖지만

하이퍼 바이저랑 컨테이너 엔진은 결국 뭔가를 여러개로 나누어 주는거 같은데 뭔가 다른가?

차이는 나누는 층이 다름. 하이퍼 바이저는 물리 서버 위에서 운영체제 자체를 통째로 띄우도록 하고..

- 가상머신마다 OS가 부팅이 됨
- 반면 컨테이너 엔진은 호스트의 커널은 그대로 공유하고 어플리케이션이랑 격리된 상자로 나눠서 진행
- 나누는 단위가 운영체제냐.. 아니면 어플리케이션 실행단위냐..

컨테이너 사용 이유

- 어플리케이션 실행 환경을 표준화해서 어디서든 동일한 환경에서 작동하도록 하기 위해서.

정리

- 컨테이너는 어플리케이션의 실행에 필요한 라이브러리, 설정을 하나로 묶어서 독립적으로 실행되는 단위
- 컨테이너가 가벼운 이유는 구조에 있음. vm은 os 여러 올리는데 컨테이너는 호스트 os 커널 공유하고 실행환경만 나눠서 실행됨.
- 컨테이너 쓰는 이유는 실행 일관성, 환경 의존성 문제 해결하기 위해서 씀.
- 도커는 컨테이너 그 자체가 아니라 컨테이너 라는 기술을 다루는 도구이고 도커 말고도 다른 도구를 라는 것도 존재함.

**DockerFile**

image를 누가 어떻게 만들었는가..

라이브러리 버전을 하나 올려야 할 때, 아니면 반년 뒤에 다른 팀원이 똑같은 이미지를 만들어야 할때,파일에 저장을 해두는 것.

설명 할 수 있어야 하는 것

- 이 파일이 무엇을 담고 있는지, 왜 환경을 코드로 적어두는지
- 각 줄이 언제 실행되는지

정의

- 도커 이미지를 생성하기 위한 명령어 및 설정이 담긴 텍스트 기반의 스크립트 파일
- 내용은 명령과 설정
- 형태는 그냥 텍스트 파일
- 사람이 읽고 쓰고 고칠 수 있는 평범한 텍스트

이 안에는 이미지 내부에 어떤 운영체제, 어떤 소프트 웨어, 라이브러리가 필요한지

만약에 개발하는 스프링 부트 api 서버를 image로 만든다고 하면 docker 파일을 만들어야 함.

- 도커의 빌드엔진이 읽음. 빌드 시점에.
- 컨테이너가 돌아가는 순간이 아니라 만드는 순간.
- copy와 run으로 이미지 생성함. (빌드 시에)

리액트는 자바랑 다름. 필요한 환경이 아예 다르기 때문에 아까 이미지 배울 떄 읽기 전용 레이어가 여러 겹으로 쌓인다는 걸 봤음..

- 레이어는 ㅇㄷ에서 생기는가?
- 도커 파일은 위에서 아래로 실행
- 레이어를 파일 시스템에서 일어난 변경 사항을 저장하는 단위
- 전체 파일 시스템을 통째로 담는게 아니라 그 명령이 바뀐 부분만 담는다는 이야기
- 이렇게 하면?
- 캐싱의 이점이 있음.
- 바뀐 지점부터 아래쪽만 빌드하면 되잖음.

즉 의존성 빌드가 같으면 굳이 다시 빌드 할 필요 없음.

- CI/ CD랑 연결이 됨.. 소스 복사 맨위에다가 두면 의존성도 낮아져서..

도커 파일은 그 자체로는 아무 것도 실행하지 않고 텍스트로 적힌 설계도

설계도 자체를 빌드하면 이미지가 만들어지고, -> 리드 온리 스냅샷

이미지를 실행하면 컨테이너가 된다. -> 메모리 위에서 도는 프로세스

사용 이유

컨테이너 이미지를 코드로 정의해서 수동 설정 없이도 항상 동일한 환경을 재현하고, 빌드 과정을 표준화 하기 위해서.

- 누군가 서버나 컨테이너에 들어가서 이것저것 설치하고 설정 만졌다면 그 과정은 명령 히스토리에만 남게됨..
- 도커 파일은 이 과정을 텍스트로 적어두기 떄문에 반 영구적 지속

도커파일은 이 과정을 애초에 텍스트로 적어둠.

자동화 이점 ..

유지보수가 쉬워짐 환경 바꿔야 실행중인 곳에 들어가 만지는게 아니라 파일 고쳐서 빌드하면 됨

- 레이어 캐싱 덕분에 안바뀐 부분은 재사용해서 빌드가 빨라짐

도커파일 존재 이유는 환경을 사람의 기억이 아니라 코드로 관리함.이라는 측면의 이점이 있다.

Overlays 하나의 파일 시스템으로 합쳐지는지..

이미지는 읽기 전용인데 컨테이너 안에서는 왜 파일을 바꿀 수 있는지.

- 이 원리에 대해서 풀어내는 내용
- 기술 이름은 overlayfs 여러개의 읽기 전용 디렉터리
- 이미지 레이어들 위에 쓰기가 가능한 디렉터리 하나를 겹쳐 올려서 마치 하나의 통합된 파일 시스템 처럼 만드는 기술.
- lowerdir가 이미지 디렉토리들의 집합.
- 전부 읽기 전용
- dockerfile의 각 명령이 만들어낸 레이어가 여기에 해당

Upperdir -

컨테이너가 시작될 때 새로 생기는 쓰기 가능한 최상위 레이어’

컨테이너 안에서 파일 만들거나 고치면 원본 이미지 레이어를 건드리는게 아니라 전부 이 upperdir에 기록.

동작 방식

- 파일을 읽을 때는 위쪽 upper, 없으면 lowerdir 에서 순서대로 찾음
- 수정 하려는 파일을 위쪽 쓰기 레이어로 복사한 다음에 복사본을 고침.
- Cow.
- 이렇게 해서 원본 이미지는 계속 읽기 전용으로 안전하게 남고 변경은 각 컨테이너에 쓰기 레이어에만 쌓임
- 같은 이미지 하나로 여러 컨테이너 안전하게 띄울 수 있는 이유

이미지 레이어는 여러 컨테이너가 공유하니까 잘 안바뀌는 레이어 위에 두고 재사용 함.

결론은 자주 안바뀌는건 위에, 자주 바뀌는 건 아래에 작성을 해야됨.

정리 :

- 도커 파일은 이미지 만들기 위한 명령어랑 설정을 담은 텍스트 설계도.
- 이미지랑 컨테이너에 출발점.
- 도커 파일 안에서 빌드 시점과 실행 시점의 명령어들이 섞여 있다.
    - From, copy, run은 이미지 빌드하는 동안 실행되고, CMD나 ENTRY Point는 그 이미지로 컨테이너를 띄운 직후에 실행된다.
- 도커파일 쓰는 이유는 환경을 사람의 기억이 아니라 코드로 관리하기 위해서 쓴다. -> 재현성 자동화 유지보수 협업측면
- 각 명령이 레이어로 쌓이고 캐싱되기 대문에 자주 안바뀌는건 위에 자주 바뀌는 건 아래에 두는 배치가 빌드 성능에 영향을 끼침.
