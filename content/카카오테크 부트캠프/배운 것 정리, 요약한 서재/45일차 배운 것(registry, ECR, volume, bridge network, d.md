**Registry**

빌드 절차를 파일로 장해두면 누가 언제 빌드하든 같은 이미지를 만들어 낼 수 있다는 것.

이미지 실행 -> 컨테이너, 사용자 요청 처리하는건 컨테이너.

이미지 빌드하면 한대의 컴퓨터, 로컬에 있음.

만드는 곳이랑 실행하는 곳이 다르다.

Docker file 있어서 같은 이미지 다시 만들 수 있지만, 이미지가 서버로 가진 않음.

registry는 이 관점에서 전달하는 문제를 맡는 주제.

컨테이너 이미지를 중앙에 저장하고 나눠쓰는 저장소

등기 사무를 맡아보는 관청..

컨테이너 이미지를 저장하고 배포하기 위한 중앙 저장소

컨테이너 이미지를 중앙에서 저장하고 관리하면서 필요한 이미지를 언제든 올리거나 내려받을 수 있게 해주는 이미지 전용 저장소

- Push, pull로..

이미지를 구성하는 레이어, 버전 태그를 이해하고 다루도록 만들어진 저장소

- 저장소가 다루는 대상이 어디까지나 실행 가능한.

두영역으로 나뉭져 있음, 개발영역과 로컬 영역..

위에 있는 배포 환경. 배포 대상 서버가 레지스트리에서 이미지를 내려 받음.

- 서버는 이미지를 직접 빌드할 필요가 없음. 이미 만들어져서 검증된 이미지를 저장소에서 가져와서 컨테이너로 실행.

이미 저장소에 올라가 있는 레이어는 다시 올리지않고 다시 바뀐 레이어만 주고 받음.

- 이미지 전체 크기가 크더라도 실제로 오가는 양은 훨씬 적어지고 push, pull 속도만 빨라짐.

레지스트리는 이미지 쌓는데서 끝나는게 아닌 버전 관리 기능을 통해서 이미지의 변경 가능을 추적 가능.

- 이떄 버전을 구분하는게 태그, 새버전 올려도 이전 버전은 그대로 있음. (롤백 유리)
- 공개 범위도 정할 수 있음. Private나 public으로..

접근 권한

저장소가 원격에있고 중앙에 있다는건 아무나 함부로 올리거나 내려서는 안됨.

- private으로 둔 저장소면 이미지 올리려는 개발자도 내려받으려는 배포 대상
- 인증을 거쳐야 저장소에 접근이 가능

저장소에 접근하기 위한 자격 증명은 이미지 안이나 소스코드 안에 넣어두면 안됨

- 이미지는 여러 곳으로 공유되는 결과물. 수평확장하는 사례..
- 비밀번호나 토큰이 있으면 자격증명도 함께 퍼짐

사용 이유

컨테이너 이미지를 중앙에서 관리하여 배포의 일관성을 유지하기 위해서

registry가 없다면 무슨 일이 생기나..

- 우리가 만든 spring boot 어플리케이션 이미지를 서버 3대에 똑같이 띄워야한다고 생각..
- 이미지를 빌드한 로컬 맥북에만 그대로 두면
- 공유가 번거로워짐. 서버가 한대 늘어나거나 팀 동료가 같은 이미지를 써야 할때마다 옮겨야 할 수도 있음.
- 각자 자기 컴퓨터에서 따로 이미지를 만들다보면 환경에 따라서 달라질 수 있다는 변수가 생길 수도 있음.
- GitHub 중앙 저장소 쓰는거 생각하면 됨.

레지스트리 쓰면 좋은 이유

1. 일관성 - CI/CD 시스템이든 모두 같은 중앙 저장소에서 동일한 이미지 받아서 실행하기 때문
2. 자동화 - 배포 자동화 파이프라인은 코드가 바뀌면 자동으로 이미지 빌드해서 레지스트리에서 올리고 서버가 내려받도록 구성
3. 롤백 편의성 -
    1. 정상 흐름 - 새버전 이미지 올려두고 서버가 그걸 내려받아서 실행하면 끝.
    2. 새로 올린 버전에서 문제가 발견됏다면.. 레지스트리가 이전 버전 이미지를 어디서 가져와야 할지 머리 아픔.
    3. 레지스트리가 잇으면 앞에서 새 버전 올려도 이전 버전 남아잇어서 되돌릴 대상 명확.

정리

- registry는 컨테이너 이미지를 중앙에 저장하고 나눠쓰는 저장소.
- 도커파일로 재현 가능한 이미지를 만드는데 까지 왔다면 레지스트리는 그 이미지를 만든 곳에서 실행할 곳으로 옮기는 역할
- 깃헙이랑 비슷하게 개발환경에서 만든 이미지 저장소로 올리는 push, 배포 대상 서버가 내려받는 pull
- 일관성 자동화 롤백 편의성, 이 3가지가 레지스트리 쓰는 이유가 됨.

레지스트리가 어디에 위치하는가

자원의 범위. AWS 자원은 어디에 속해잇는지가 중요함..

- ecr은 리전 단위 서비스.

레지스트리 입장에서 보면 수많은 계정과 리전, repo, 버전 가운데 정확히 어느 하나인지 특정 할 수 있어야 함.

사용 이유

컨테이너 이미지를 AWS 환경 안에서 안전하게 저장하고, ECS, EKS, EC2 등 다양한 서비스에서 빠르고 안정적으로 가져와 실행 할 수 있기 때문

1. 저장과 보안
    1. 이미지에는 어플리케이션 전체가 들어옴. 누가 올릴 수 있고 누가 내려받을 수 있어야 하는지..
    2. ECR은 이 통제를 IAM에게 맡김. 이미 사용하고 있는 사용자 역할에 이미지 접근 권한을 붙이는 방식
    3. 이미지에 취약점 있는지, 검사하는 기능도 제공
    4. 우리가 작성한 코드 말고도 베이스 이미지나 그 안의 패키지까지 함께 배포되기 때문에 검사가 필요함
2. 통합
    1. AWS에서 컨테이너 실행하는 서비스들은 ECR에서 이미지를 받아오는 방식을 이미 알고 있음. 실행환경 쪽에 별도의 인증 서버나 중계서버를 둘 필요가 없음
    2. Fargate: 서버 직접 관리 안하고 컨테이너 실행하는 방식.
3. 확장성이랑 가용성
    1. ECR이 여러 가용영역에 걸쳐서 이미지를 안정적으로 보관 할 수 있어야 함. - 이 뜻은 저장소 자체가 잘 죽지 않는 다는 뜻. 그 이미지로 실행되는 어플리케이션이 고가용성을 가진다는건 아님.

레지스트리를 서버에 직접 올려서 private 레지스트리 스스로 운영도 가능,

근데 왜 ECR? - 관리형이니까~

ECR은 프라이빗 레지스트리. EC2같은 실행환경이 어떻게 정당하게 pull할 수 있다는걸 증명하나?

핵심은 이미지를 주고 받는 통신 자체가 우리가 이미 알고 있는 컨테이너 도구의 방식이랑 그대로

IAM 자격증명을 가진 주체가 ECR에 인증 토큰을 요청하고 그 토큰으로 레지스트리에 로그인한 상태가 되어 이미지를 주고 받는다.

실제로 확인한느 것은 토큰 요청 주체가 iam에서 어떤 권한을 가지고 있나..

권한은 최소한으로 주는 것이 원칙.

- 이미지 만들어 올리는 쪽이랑, 이미지 받는 쪽의 권한이 다름..
- 토큰 요청 순간이랑 읽어가는 순간에 iam이 확인함.

정리

- ECR은 컨테이너 이미지를 등록해두고 인증된 대상에게만 내주는 완전 관리형 프로이빗 레지스트리
- 레지스트리라는 역할 자체는 지난 시간에 배운 그댜로도 배운 ㄱㄷ, 달라지는건 레지스트리가 aws안에 잇다.
- 자원 범위는 리전 단위. 계정이랑 리전이 정해지면 그 안에 레지스트리가 잇고 repo로 앱 나누면 태그로 버전 구분함.

**Volume**

ECR 에서 보관해주는 것은 이미지고 이미지는 한번 만들어지면 내용이 바뀌지 않은 결과물

- 그래서 언제 어디서 내려 받아도 같은 실행환경이라는 것을 만들 수 있다.
- 그 이미지로 컨테이너 띄우고 나서 실행중에 새로 생기는 데이터는 어떻게 되는가..?
- 사용자가 만든 파일이나 쌓이는 로그나 DB에 들어간 레코드 값은 ECR에 올라가지 않음.

이미지는 읽기 전용, 컨테이너는 그 위에 쓰기 레이어 얹음

설명 할 수 있어야 하는 것

- 컨테이너 안의 데이터가 왜 사라지는가?
- 볼륨은 그 데이터를 어디에 어떻게 남기는가?
- 데이터를 컨테이너에 연결하는 방식에는 어떤 선택지가 있고 무엇이 다른가?

정의

컨테이너 간 데이터 공유 및 영속성을 제공하기 위해 호스트 파일 시스템에 생성되는 독립적인 저장소

- 볼륨은 호스트. 컨테이너를 실제로 돌리고 있는 그 컴퓨터의 파일 시스템 위에 만들어지는 저장 공간
- 컨테이너 안이 아니라 컨테이너 바깥에 있음.

컨테이너의 데이터가 사라지는 이유

볼륨이 왜 필요한지 이해하려면 컨테이너가 데이터를 어떻게 다루는지 알아야 함.

이미지는 여러층의 읽기 전용 레이어로 쌓임.

- 실행중에 생기는 변경은 맨위의 쓰기 레이어에만 쌓임
- 컨테이너 안에서 만든 데이터는 컨테이너의 임시 쓰기 레이어에 들어가고, 컨테이너를 지우면 레이어와 함께 데이터도 사라짐.
- 컨테이너의 수명과 데이터의 수명이 하나로 묶여 있는 것.
- 같은 이미지로 컨테이너를 만들었다가 삭제하고 다시 띄우는 상황을 생각해보면 됨

볼륨은 데이터를 컨테이너 바깥에 둠.

컨테이너랑 볼륨을 연결하는 동작을 마운트라고 함

마운트는 호스트의 특정 디렉터리나 도커 볼륨을 컨테이너의 내부의 어떤 경로에 연결해서 그 위치의 데이터를 자기 것 처럼 사용함.

- 컨테이너를 삭제하거나 재시도 해도 볼륨에 잇으면 연결

맨 위에 컨테이너 A랑 B가 있음.

- 두 컨테이너 모두 내부에서 마운트 지점.

방금 그림에서 Volume의 위치가 호스트의 특정 디렉토리로 표시가 되어 있음..

- 볼륨이 도커 엔진이 관리하는 전용 디렉토리에 만들어진다는 내용

저장위치를 docker가 관리한다는 말

- 볼륨을 쓸 때 우리는 호스트의 어느 디렉터리에 데이터를 둘지 직접 고르지 않음.
- 도커가 자기 관리 영역 안에 자리를 잡아주고 우리는 그 저장소를 이름으로 가르킴.
- 실행 구성이 호스트의 디렉터리 구조에 묶이지 않게 됨
- 저장소는 호스트마다 디렉터리 구조가 달라도 같은 구성을 그대로 쓸 수 있어야 함.
- 특정 경로에 묶이지 않는다는거지 데이터 자체가 옮겨간다는건 아님
- 데이터는 만들어진 호스트에 남아 있음.

사용 이유

컨테이너 종료 및 재시작에도 데이터를 영구적으로 유지하고 공유하기 위해서

- 문제는 저장해야하는 데이터가 생긴다고 하면 그때 고려를 해야 함.
- 저장해야하는 데이터가 무엇인지, 남아잇어야 하는 데이터가 무엇인지.
- 예시로 로그나 데이터 베이스 등등..
- 볼륨은 남아야하는 데이터를 관리하기 위해서 존재함.

실제로 도커 쓸 때 어떤 데이터를 볼륨에 맡기는가?

- 사용자가 올린 업로드 파일의 원본, temp -> s3에 올려도 저장 실패하는 경우에 따로 관리가 필요 할 수도 있음.
- 어플리케이션 로그,
- 컨테이너 공유 설정파일
    - JVM등 생각하면 캐시가 아무것도 없어서 초반 성능 떨어질 수도 있음. JVM 안에서 성능 좋게 만들기 위해서 jit 쓰는것 처럼..
- 컨테이너 사이에 협업이 필요하다라고 하면 볼륨 써볼 수도 있음.

정리

- 컨테이너 실행중에 생긴 데이터는 쓰기 레이어에 들어가고 컨테이너 지우면 사라짐.
- 실행 단위의 수명이랑 데이터의 수명이 묶여 있음.
- 볼륨은 이런 묶음 분리.
- 컨테이너 지우거나 다시 띄워도 데이터 그대로 유지, 같은 볼륨을 여러 컨테이너에 연결하면 데이터도 공유

**Bridge Network**

컨테이너들이 서로 어떻게 대화하는가?

- 웹서버 컨테이너와 Spring Boot 컨테이너는 서로 어떻게 통신하는가?
- 실제 서비스는 컨테이너 하나만 띄우는 경우는 없고요. 여러개가 서로 요청을 주고 받아야 하나의 서비스가 돌아감.

설명 할 수 있어야 하는 것.

- 브릿지 네트워크가 무엇인지
- 한 Host 안에서 격리된

정의

컨테이너들이 동일한 호스트내에서 서로 통신 할 수 있도록 연결해주는 도커의 기능

동일한 호스트 내

- 지금 우리가 다루는 범위가 서버 한대안. EC2 안.
- 여러 서버가 아니라 EC2. 한대 안에서 여러 컨테이너가 함께 떠 있는 장면을 생각하면 됨

가상 네트워크

- 랜선을 새로 꽃거나 물리 이더넷 스위치를 한 대 더 사는게 아니라 소프트웨어로 만들어낸 네트워크다.
- 격리된 컨테이너들을 하나의 가상 내부망에 묶어서 서로 사설 IP로 통신할 수 있게 해주는 것이 브릿지 네트워크

EC2 안에 컨테이너가 3개 떠있다고 가정

- 하나는 리액트를 빌드해서 나온 정적 파일을 사용자에게 내려주는 웹서버 nginx 하나,
- 실제 로직 처리하는 스프링부트 api,
- Db 역할하는 컨테이너 하나.

통신이 필요한 지점을 생각

사용자의 API 요청은 결국 스프링 부트 컨테이너까지 닿아야 하고 스프링부트는 조회 저장을 위해 DB 컨테이너에 말을 걸어야함.

앞에서 배운 AWS 네트워크랑은 계층이 다름.

VPC는 EC2 같은 AWS리소스가 놓이는 클라우드 상의 네트워크 경계 ,

브릿지 네트워크는 컨테이너들을 연결하는 가상 네트워크

be라고 적힌쪽인 Spring Boot API 컨테이너

fe라는 부분이 리액트 서비스 컨테이너

각각의 컨테이너 안에는 이더넷 하나 씩.

그 아래에는 가상 이더넷이 잇음.

각각의 역할

1. Docker0(bridge)
    1. 호스트에 만들어진 가상 브릿지
    2. 소프트웨어 만든 가상의 스위치 같은 역할
    3. 여기에 연결된 컨테이너들 사이에 트래픽을 중계해주고 동시에 컨테이너가 바깥으로 나갈 때 호스트의 물리 랜카드로 넘겨주는 게이트웨이 역할도 함.
    4. 컨테이너들 사이에 통신 할 때 중계하는 역할, 바깥으로 요청 나갈 때 실제 인터넷 수준으로 나갈 수 있께..
2. 컨테이너 안에 이더넷은?
    1. 엔드포인트 역할을 하는 것임. 네트워크로 뭔가를 보내고 하는.
3. 버츄얼 이더넷은 이더넷 페어임.
    1. 컨테이너랑 브릿지 사이에서 실제로 데이터가 흐르는 통로 역할
4. Host의 eth0
    1. 얘는 실제로 호스트 머신, 컴퓨터가 갖고 있는 실제 물리 랜카드.
    2. Docker0을 거쳐서 올라온 트래픽이 이 물리랜카드를 통해서 바깥 인터넷이나 외부 인터넷으로 나감.

요청이 이동하는 경로

컨테이너끼리 통신하는 경우

- 스프링 부트 컨테이너가 데이터베이스 컨테이너에 조회 요청을 보낸다고 가정.
- 컨테이너가 둘만 있지만 경로는 같음.
- 요청은 스프링 부트 컨테이너에서 출발하고 eth0에서 출발해서 물려 있는 veth을 타고 docker 브릿지로 올라감.
- 브릿지는 요청을 다시 DB 컨테이너쪽의 veth로 내려감.
- 둘다 같은 브릿지로 몰려있기 때문에 가능
- 호스트 내부의 가상 스위치 안에서만 처리가 가능.

컨테이너가 바깥 인터넷으로 나가는 경우

- not통해서 나감.

스프링 부트는 데이터 베이스를 내부에서 어떤 주소로 부르는가

- 컨테이너 이름으로 상대 컨테이너를 인식하고 연결할 수 있음.
    - 가상 사설 IP로 짚어서 연결하는게 아니라 사용자가 만든 브릿지 네트워크는 내부에서 자동 DNS 기능으로 IP몰라도 컨테이너 이름만으로 연결 할 수 있다.
- 편의성이 있는데 내부망 사설 IP주소는 컨테이너를 다시 띄울때마다 바뀔 수 있음.
- 사용자가 만든 브릿지 네트워크는 자동 DNS 기능 제공해서 IP몰라도 컨테이너 이름만으로 찾아 갈 수 있게 해준다.

사용 이유

컨테이너 간 통신을 격리된 네트워크 환경에서 안전하고 간편하게 관리하기 위해서 ..

1. 컨테이너 간 안전한 격리 통신
2. 서비스 간 간편한 연결
3. 호스트 포트 충돌 방지 및 노출 최소화
4. 확장성과 운영 편의성

정보 1. 다른 네트워크 방식

도커 컨테이너가 통신하는 방법이 여러가지가 있는데 가장 일반적이고 많이 사용하는게 브릿지 네트워크이다..

브릿지는 도커의 기본 네트워크인데 조건이 달라지면 다른 방식을 고르기도 함.

- 아래 있는 방식들을 보면 브릿지 네트워크는 이런 존재구나 더 명확하고 선명하게 개념을 만드는 것.
- 별도의 가상 네트워크 만들지 않고 호스트의 IP를 그대로 쓰는 방식
- 호스트 네트워크는 중간 계층 없이 호스트와 그냥 공유하는 방식
- 거쳐가는 단계가 없어서 네트워크 성능이 조금이나마 좋아질 수 있음.

Overlay network

오버레이는 서로 다른 물리 호스트에 있는 컨테이너들을 같은 가상 서브넷으로 묶어서 마치 한 네트워크에 있는거처럼 통신하게 만들어줌.

- 호스트들이 패킷을 한번 감싸서 전달하는 방식으로 동작을 함.
- 캡슐화라고도 함.
- 다른 서버 위에 있는 컨테이너 끼리도 같은 서브넷에 있는 것 처럼 통신이 반응을 함.

MacVlan network

컨테이너에게 별도의 Mac address랑 ip를 부여해서 컨테이너를 물리 네트워크의 일부처럼 동작 시키는 방식

브릿지에서는 컨테이너가 docker0을 거쳐서 바깥과 통신했습니다.

호스트가 많이 늘어나거나 물리망에 직접 붙여야 하는 상황이라면 고려 할 수 있는 선택지가 있구나

정리

- 브릿지 네트워크는 한대의 도커 호스트 안에서 서로 격리된 컨테이너들을 하나의 기상 내부망에 묶어서 통신하게 해주는 도커의 기본 네트워크
- 이런 구조에는 docker0 라는 가상 스위치가 있고 veth pair 라는 가상 케이블이 각 컨테이너의 eth0이랑 그 스위치에 연결한다.
- 브릿지 네트워크 쓰면 내부 DNS가 아니라 이름으로 연결된다.

**Docker Compose**

정의 : 여러 컨테이너로 구성된 애플리케이션을 YAML 형식의 파일로 명확하게 정의하고, 단일 명령어로 동시에 실행 및 관리할 수 있도록 지원하는 Docker의 공식 오픈소스 도구.

설명 할 수 있어야 하는 것

- 도커 컴포즈가 무엇이고 왜 필요한지
- 그리고 파일 하나에 어떤 시스템 구조랑 관계를 표현하는지
- 도커 컴포즈 쓰는 방법은 yaml 파일로 정의하는 것.
- 필요한 구성을 원하는 상태로 파일에 적어두면 됨.
- 도커 컴포즈 결과는 그 구성을 하나의 단위로 실행하고 관리하는 것.

공식 오픈소스 도구

- 원래 별도 엿는데 도커가 인수함.
- > docker-compose.yml 파일이 스스로 컨테이너를 만드는 건 아님.

compose도구가 파일에 적힌 구성이 되도록 지시.

엔진이 직접 만들음.

포트는 호스트의 포트랑 컨테이너의 포트를 어떻게 연결할지..

컨테이너 이름은 뭐라도 부를지…. -> 포트는 외부에 들어온 요청이 어떤 경계를 지나서 어떤 프로세스에 닿는지를 나타냄

서비스 (무엇은 가르키는 단위) : services 아래의 항목 하나를 서비스라고 부르는데 컨테이너 하ㅣ나도 생각하는게 편함

기본 형태에서는 정의 하나가 실행 인스턴스 하나로 이어지지만 같은 정의를 여러 인스턴스로 늘려 실행하는 것도 가능..

정리하면 docker-compose.yml 파일 안에서 어떤 이미지를 쓰는지 어떤 포트로 요청이 들어오는지 어떤 네트워크로 서로 연결되는지..

- > 그리고 어떤 순서 관례가 있는지가 들어있다.

도커 컴포트 파일에 적힌 내용들은 여러개를 띄운다는 의미도 잇지만 compose라는 도구는 한 파일에 적힌 서비스들의 묶음.

사용 이유

다수의 컨테이너로 구성된 어플리케이션을 코드로 명확하게 정의하고, 한번에 쉽게 관리하기 위해서

이 이유를 체감하려면 컴포즈가 없는 상황을 가정

- 컨테이너를 하나씩 개별적으로 실행하는 방식에서는 컨테이너마다 어떤 이미지를 쓰고 어떤 포트를 열고 붙히는지 지정함

이렇게 할 때 문제가 무엇이냐?

- 사람이 하는거라서 실수하기 쉽다. 연결 하나 빠뜨리면 컨테이너들이 서로를 찾지 못하거나 요청이 엉뚱한곳에 도달함.
- 또 다른 하나는 세팅한 구성을 묶어서 문서로 남기기 번거로움
- compose는 이런 문제를 yaml 파일에 명시적으로 선언하는 방식으로 해결함.
- 파일 안에 컨테이너는 어떤 이미지로 만드는지, 그리고 어느 네트워크로 연결되는지 어떤 순서 관계가 있는지 전부 파일에 적는다.
- 이 파일이 있으면 다른 사람도 같은 구성을 그대로 재현 할 수 있다.
- 그 관점에서 보면 컴포즈도 IaC의 일종으로 볼 수 있기는 함.
- 컨테이너 구성이나 볼륨, 네트워크 같은 자원을 코드로 적어두고 관리하기 때문에 그렇게 볼 수도 있음.

정리

- 도커 컴포즈가 무엇이냐 라고 하면, 여러 컨테이너로 이루어진 어플리케이션의 구성을 yml 파일 하나에 선언하고 그 구성을 하나의 단위로 다루는 도구
- 선언적으로 작성, 어떤 구성이 있어야 하는지를 적어둠
- 실제로 컨테이너나 네트워크 다루는 주체는 도커 엔진
- 컴포즈는 그 파일 읽어서 전달하는 역할
- 파일의 중심이자 시작은 service 그 아래에 어떤 이미지에서 출발하는지 어떤 포트로 요청이 들어오는지 어떤 네트워크 연결되는지 작성
- 이렇게 작성하면 일관성과 재현 가능성을 얻는다.

**빅뱅 배포**

전체적인 그림 그려나가기 위함. CI/CD 구축 전에 하는 것.

외울 필요 없고 흐름을 이해하기 위해서 시간 투자 할 것.

누가 어떤 자원에 접근 할 수 있을지 권한 나누고 네트워크 경계를 통해서 외부 요청이 들어오는 길도 열었음.

- 그 요청이 실제 어떤 프로시스에 전달되는 지도 봤고 사라지면 안되는 데이터 어디에 남길지도 다뤘음.

이미 사용자가 쓰고 있는 서비스가 있다면 새로 업데이트 해야하는 변경사항 에대해서 어떻게 반영 할 것인가

- 어떻게 배포를 할 것인가
- 여러 가지 배포 방식들 좋은 방법들이 있지만 왜 좋은지를 알려면 시작점을 알아야 함.

설명 할 수 있어야 하는 것.

- 빅뱅 배포가 무엇,
- 왜 이렇게,
- 뭐가 단점?

정의:

여러 기능이나 변경사항을 한꺼번에 운영환경에 배포하는 방식.

그동안 돌고 있던 기존 버전을 전체적으로 교체.

사용자 목록 보여주는 어플리케이션

- 빅뱅 배포로 ver2 를 반영한다는 것은 버전 1의 일부를 조금씩 손보는게 아니라
- 쌓아둔 변경 전체가 들어간 2번을 준비해뒀다가 어느 시점에 1번 자리를 2번으로 통째로 바꾸는 것.
- 배포 끝나면 서비스에서는 버전2만 남는다.
- 두 버전이 트래픽을 같이 받는 구간이 없이 한번에 갈아 치우는 것을 말함.
- 빅뱅이라는 키워드는 변경 범위랑 전환 방식 자체를 나타냄.
- ec2에 올린다고 빅뱅 배포도 아님. 컨테이너 안쓴다거 빅뱅배포도 아님.
- 한번에 변경되는 기준을 보는 것.

장점과 단점

장점

- > 배포 준비 과정은 단순해질 수 있음.
- 빅뱅 배포로 하면 상대적으로 배포를 자주 하지 않는 환경이많고 개발 내용이 쌓이면 정해진 시점에 내보냄.
- 단순해질 수 있음.

단점

- > 너무 한번에 많이 바뀌어서 예상치 못한 문제가 발생하면 원인 파악이나 해결이 어려워서

운영 리스크가 너무 높아짐.

- 어디서 부터 어디까지 문제인지도 접근하기가 어려움
- 좋은 변경 사항과 나쁜 변경 사항을 분리하는 것도 시간이 걸림

전환하는 순간

- 돌고 있던 버전을 내리고 새 버전을 올리는 방식이여서 그 사이에 서비스가 잠깐 끊기는 구조가 됨
- 딱 그 타이밍에 접속한 사용자가 있으면 화면을 보는게 안됨

지금 환경에서는 어떻게 달라졌는가

클라우드 환경으로 넘어오면서 조건이 달라짐

- 서버 유연하게 늘리는 것도 가능하고 배포 과정을 자동화 하기도 쉬워짐.
- 그래서 배포에 들어가는 비용이 줄어들어서 변경을 작게 나눠서 자주 내보내는 방식을 씀.
- 이유도 단순함. 한번에 나가는 커밋이 적으면 문제가 생겨도 어디가 원인인지 좁히기 쉽고 되돌릴때 같이 돌아가는 기능도 적음.

어디서 실행하든 같은 환경이 만들어지기 때문…

그래서 요즘은

도커 컨테이너 기반으로 ci/cd를 통해서 짧은 단위로 자주 배포가 나가는 방법을 택함.

정리

- 빅뱅 배포는 여러 변경사항을 큰 묶음으로 한 시점에 운영 환경에 적용하고 기존 버전을 통째로 교체하는 방식
- 특정 서버나 도구의 이름이 아니고 변경 범위랑 전환 방식을 가르키는 말 컨테이너 이미지를 쓰더라도 전체를 한번에 갈아 끼운다면 빅뱅배포
- 장점은 단순화 되어서 편함
- 단점은 문제 생겼을 때 원인 좁히기 어렵고 롤백할 때 멀쩡한 기능까지 같이 롤백됨
- 과거에는 이런 방식을 택할 수밖에 없던 환경.. (데이터 센터 환경)
