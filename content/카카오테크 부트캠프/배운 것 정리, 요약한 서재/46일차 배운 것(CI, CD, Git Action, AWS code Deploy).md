**Continuous Deployment**

CI가 CD에게 넘겨주는 것은 소스코드가 아니라 실제로 넘기는건 결과물이다.

설명 할 수 있어야 하는 것.

- CD가 무엇이고 CI와의 책임 분리
- 왜 배포를 자동화 하는지

정의 :

- 코드가 자동화된 테스트를 통과하면 운영 환경 까지 자동으로 배포되는 소프트웨어 배포 프로세스
- 문장안에 조건이 두개가 있음
- 첫번째는 테스트를 통과하면 이라는 조건
- 두번째는 운영환경까지 자동으로 라는 조건

cd는 아무 결과물이나 배포하지 않음

- 빌드가 되고 테스트를 통과해서 배포해도 되겠다는 판단이 된 것만 배포함
- 그 판단을 ci가 함.

두 단계의 책임을 갈라줘야함.

변경을 자동으로 통합하고 자동으로 검증하는 일을 맡음. - ci

배포하는 환경을 - cd

이런 흐름을 크게 이야기 할 때 CI/CD 파이프라인이다. 배포 파이프 라인이다.

- 배포 파이프 라인을 구축해봤다는 action에서 개발하고 빌드랑 테스트 action의 러너에서 들게 하고 배포 나가게 하면 그게 배포 파이프라인임.

운영 배포를 여전히 사람이 엄격하게 통제하면 CI만 따로 쓰기도 함.

CD를 통해서 자동화되는 범위

- CD라고 하면 모든게 자동으로 처리되는게 아니라 파이프라인을 어떻게 설계했는가에 따라서 다름
- 파이프라인에 포함이 되는게 컨테이너 이미지 만들어서 repo나 버전올리는 일.
- 팀에 따라서는 인프라 변경까지 파이프 라인에 넣어두긴함.

깃헙 액션 기준.

- 새로운 기능 만들어서 메인 브랜치에 머지했다고 가정. 여기까지가 사람이 하는 동작의 마지막
- repo가 이벤트 감지하면 러너 준비되고 코드 내려 받아서 빌드해서 실행하고 jar 만들어서 테스트..
- 여기까지가 ci고
- 다 성공하면 도커파일로 컨테이너 이미지로 만들고 태그 붙여서 레지스토리에 올림
- 배포 가능한 결과물의 위치가 러너에서 레지스트리로 옮겨감

- 이렇게 되면 배포 끗

사용 이유

코드가 준비되는 즉시 운영 환경에 반영 함

Cd, delivery는 수동으로 되어 있음. 상태까지는 자동으로 준비, 얘는 반영은 수동,

정리

- CD는 검증을 통과한 결과물을 목표환경까지 자동으로 전달하고 배포하는 과정
- CI는 변경의 통합과 검증을 맡고 CD는 그 결과로 나온 빌드 산출물이나 컨테이너 이미지 정보를 받아서 실행 환경에 올림
- CD사용이유는 사람이 손으로 하던 배포에서 생기는 지연이나 절차의 변동을 줄이고 반복작업에서 오는 실수를 걷어내기 위해서 씀.
- CI/CD를 통해서 작은 변경을 자주 내보내기 좋은 환경이 되고, 문제가 생겼을 때 원인이랑 영향범위 좁히기 좋음.

워크플로우 - 워딩 그대로 일의 흐름. 어떤 일이 생겼을 때 무엇을 어떤 순서로 처리한다는 끝과 시작이 잇는 것.

코드가 바뀌면 바뀐 코드를 테스트 하고 통과하면 이미지 빌드 해서 레지스트리에 올린다 ..

각각이 언제 시작해서 무엇을 하는지가 서로 다른 독립된 흐름임. 워크플로우는 여러개 일 수도 있다.

Github내에서라는 표현은

- > 방금 이야기 한 워크 플로우의 정의. 어떤 사건이 생기면 어떤 작업을 하겠다는 선언은 repo 안의 yaml 파일로 관리됨.
- 그리고 이벤트 감지하고 워크 플로우 시작하고 실행 이력이랑 로그 남기는 일은 깃헙이 담당함.
- 실제 작업이 도는 곳은 깃헙 안에서 웹 화면이 아닌, 러너라고 부르는 별도의 실행 환경에서 돌아감.
- 정의랑 관리는 깃헙에서 하고 실행은 러너쪽에서 함.

깃헙 액션의 구성 요소

1. Event
    1. 자동화를 시작하게 만드는 사건.
2. Workflow
    1. 이벤트에 대응해서 자동화 흐름을 담은 하나의 단위.
    2. Repo 안에 정해진 위치의 yaml 파일로 존재하고 깃헙이 그 위치를 보고 워크플로우로 인식
3. Job
    1. 워크플로우 안에서 독립적으로 실행되는 작업 단위
    2. 책임 단위로 나누는게 보통. 검증하는 job, 결과물을 만드는 job, 배포하는 job 나눌 수 있음.
4. Runner
    1. 러너는 두 종류
    2. Github 가잇고 팀에서 직접 서버를 등록해서 쓰는 self-hosted-runner
    3. 러너가 실행 환경이라고 햇는데 실행 환경이라고 하면 컴퓨터나, 서버
5. Step
    1. 잡 안에서 위에서 아래로 하나식 실행되는 개별 단계
6. Action
    1. 자주 쓰는 작업을 미리 만들어둔 재사용 가능한 조각
    2. Repo 코드 가져오거나 특정 런타임 설치하는 일처럼 모두가 반복하는 작업은 플로그인처럼 가져다 쓸 수 있음.

이렇게 하나로 묶으면 이벤트가 워크 플로우를 깨우고 워크 플로우가 각각의 잡을 실행 시켜서 진행된다.

파이프라인은 책임에 따라서 잡을 나눔

- 변경 사항 검증 하나 잡, 검증을 통과한 코드가 배포 가능한 결과물을 만들어서 레포에 올림 결과물을 환경에 반영하는 잡
- 크게 3개로 나눌 수 있음.

시작은 repo 에서 이벤트가 발생합니다.

- Push 하면 워크 플로우 시작
- 첫번째 잡은 러너 위에 코드를 가져와서 의존성을 준비하고 테스트를 수행.
- 두번째 잡은 검증을 통과한 코드를 배포 가능한 형태로 만듬
- 세번째 잡은 배포
- 대상 환경에 접속해서 레지스트리에 올라간 결과물을 가져와서 실행중인 버전을 교체하도록 지시
- 이 전까지는 깃헙이랑 러너의 영역이었다면.. 우리가 운영하는 EC2 서버의 영역도 있음.
- 도구가 하는 일은 새로운 걸 만들어내는게 아니라 지금까지 우리가 배운 것들을 정해진 순서로 이어주는 역할…

깃헙 액션은 그 사이에 순서랑 조건을 관리하는 역할

- 검증은 폭넓게 돌리는데 실제 반영은 정해진 경로로 이동

정리 :
