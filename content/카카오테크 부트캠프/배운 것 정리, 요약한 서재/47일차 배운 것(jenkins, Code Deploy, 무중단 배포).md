**Jenkins**

젠킨스는 같은 CI/CD 흐름을 구현할 수 있는 두가지 선택지가 있는데 어떤 차이가 있는지 중점적으로 봐도됨

별도로 젠킨스 서버를 세팅해서 쓰는가.?

정의

- 소프트웨어 개발 프로세스의 빌드, 테스트, 배포 작업을 자동화하는 오픈소스 CI/CD 도구.

젠킨스의 성격을 정의하는 문장을 이야기 해보면, 젠킨스는 직접 어딘가에 설치해서 띄워두는 독립된 자동화 Ci/CD 소프트웨어

- 깃헙 액션에서는 워크플로우가 실행되는 러너 환경을 깃헙이 관리형으로 제공을 해줬음. 우리가 서버 만들지 않아도, 환경에 대한 업데이트나 보안도 신경 안씀.
- 깃헙 액션이 제공해주던 러너의 영역을 회사, 팀이 가져옴 즉, 계속 관리해줘야함

배포 흐름에서의 젠킨스의 위치

똑같이 개발자가 깃에 코드 올림.

다른쪽에는 서비스가 실제로 돌아가는 대포 대상 Ec2서버가 있음.

이 사이에는 빌드랑 테스트 실행되는 환경 - 깃헙 액션 기준으로 러너

빌드를 통해서 결과물 보관하는 곳 - 레지스트리

빌드가 끝난 직후에 이미지가 처음에 놓이는 곳이 작업 수행한 에이전트, 그 에이전트의 워크 스페이스임.

- 잡을 위한 공간.. 배포 대상 서버가 볼 수 없음.
- 이미지는 레지스트리로 올라가야함.
- 그래야 배포 대상 서버가 레지스트리에서 이미지 pull 가능.

젠킨스가 하는 일은 이것들을 정해진 순서로 이어주고 조율하는 역할

- Git repo에서 코드 가져오라 하고 검증, 빌드하고 레지스트리 올림.
- 각 단계가 성공 확인도 젠킨스의 몫
- 자동화 CI CD 소프트웨어라는 말이 조율하는 역할

구성 요소

1. Job 잡
    1. 젠킨스가 실행하는 하나의 작업 단위
    2. 예를 들면 특정 repo를 빌드하고 배포하라는 한 묶음을 이야기
2. Pipeline 파이프라인
    1. 코드 통합하고 배포하는 과정을 코드로 정의한 형태
    2. 보통 배포 파이프 라인이라고 하면 push부터 배포까지의 전 과정을 추상적으로 말함.
    3. Git 기준, yaml 파일.
3. Node
    1. 작업이 실제로 실행되던 환경
    2. 젠킨스는 전체를 지위하는 컨트롤러랑 실제 작업을 수행하는 에이전트로 나뉨
    3. 컨트롤러는 어떤 job을 언제 어느 에이전트에 맡길지..결정함.
    4. Git 기준, 러너로 생각하기
4. Plugin
    1. 기능 확장 모듈. 알림 전송이나 컨테이너 작업 등.. (이거 때문에 편리하고 관리부담이 잇음)
5. Trigger
    1. 깃헙액션의 이벤트와 같은 개념. 작업을 시작시키는 조건..
6. Artifact
    1. 빌드랑 테스트로 만들어진 결과물을 젠킨스에서 부르는 이름.
    2. jar나 컨테이너 이미지
7. Workspace
    1. 작업하는 동안 소스 코드랑 중간 산출물 위치하는 디렉토리.

사용 이유

- 빌드 테스트, 배포 과정을 하나의 플랫폼에서 자동화하여 소프트웨어 개발과 배포를 안정적으로 관리하기 위해서
- 깃헙 액션이랑 같은 이유
- 깃헙 액션이랑 같은 결과를 얻을 수 있은데 왜 젠킨스 써서 서버를 따로 만들어야 하는가?
1. 네트워크

보안이나 규제 때문에 내부망 안에서 해야하는 경우가 있음.

- 네트워크 안에 세워두고 쓰는 자동화 서버가 필요함
- 깃헙 액션은 외부 서비스, 깃헙도 결국 깃이라는 기술로 함.
1. 통합

이미 쓰고 있는게 젠킨스면 뭐..

1. 실행 환경에 통제

많이 있는 상황은 아닌데 특정 운영체제나 하드웨어 아니면 특수한 빌드 도구가 설치된 환경에서만 써야 한다면.. 젠킨스 사용

1. 복잡가 높지만 자유도도 많음.

단점

- 서버 멈추면 팀 전체 빌드랑 배포가 멈춤. 서버 가용성 신경 써야함.
- 플러그인 유연한데 버전 충돌인데 업데이트 관련 일도 따라옴

자격 증명 보관하고 설정이나 이력 백업하고 보안 패치 적용하는 것도 계속 하게 되는 작업.

정리

- 젠킨스는 Ci CD 프로세스 구현하는 도구
- Git repo, 빌드랑 테스트 실행되는 환경, 이미지 위치하는 레지스트리, 배포 대상 EC2 까지 해서 4가지ㅣ가 있고 순서 조율시키는 자동화 서버
- 트리거가 실행을 열고 컨트롤러가 잡을 맡을 에이전트를 정하고 그 위에 워크 스페이스에서 빌드랑 테스트 이루어져서 아키텍쳐 만들어줌.
- 깃헙 액션과의 차이는 실행 환경에 대한 운영 주체가 다름. 젠킨스는 회사나 조직이 직접 관리하고 다뤄야 함. 상관ㅇ에 따라서 맞게 쓰는게 필요함.

**CodeDeploy**

깃헙 액션으로 어제 워크 플로우 구성하는 흐름. 젠킨스도 성격은 같음. - 어떤 순서로 이어붙일지 적용하는 자동화 도구

- 워크플로우에서 배포라고 적어둔 내용에서는 배울내용이 많음..
- 이런 일을 워크 플로우 도구가 스크립트로 전부 해야하는가..? 아니면 이 단계만 전담하는 서비스에 맡길 수 없나..
- AWS Codeploy. 알고 있는 Ci/CD 흐름 중에서 배포 실행 단계의 일부분을 AWS 관리형 서비스가 어떤 방식으로 처리하는지..

설명 할 수 있어야 하는 것

- 코드 디플로이가 파이프라인 전체가 아니라 어느 부분을 담당하는지
- 담당하는 부분 안에서 어떤 구성 요소가 어떤 책임을 맡는지

정의

AWS에서 제공하는 자동화된 애플리케이션의 배포 서비스

배포 - 개발자가 만든 결과물을 실제 실행 환경 서버에 올려서 사용자 요청받게 만드는 작업.

AWS Lambda : 서버를 직접 띄우지 않고 코드만 올려서 실행하는 방식.

자동화

- 서버 접속해서 이전 버전 내리고 새 파일 옮기고 설정바꾸고 서비스 다시 실행함.
- 서버 한대면 ㄱㅊ은데 서버 열대면 번거로움
- 코드 디플로이 쓰먄 Ci/CD다른 도구도 가능하지만 순서 한번만 정의 해두고 대신 실행 가능.

CI/CD CodeDeploy 가 맡는 영역.

코드 디플로이가 CD를 전부 다 먹는건 아님.

- 깃헙 액션 같은 도구도 배포 가능. 디플로이 없어도 됨. 스크립트 써서 서버에 접속 하지 않고 파일 옮기고 서비스 재시작하게 만들면 그것도 CD

코드 디플로이는 단순히 순서를 조정하는 도구- 배포 영역 일부를 담당하는 대신 배포 과정을 코드 디플로이가 갖고 있는 개념으로 채운다.

코드 디플로이 쓰면 지금 배포하려는 버전이 어느 EC2에 어디까지 올라갔는가? 라는 상황이나 상태를 볼 수 잇음.

나중에 서버 한대 더 늘더라도, 같은 태그만 붙여두면 그 서버는 자동으로 배포 대상에 포함됨

- 실제 배포 수행하는 주체는 대상 서버 안에 있고 서버 안에 코드 디플로이 에이전트라는 소프트웨어가 미리 설치되어 있고 에이전트가 주기적으로 코드 디플로이 쪽에 자기 자신 서버에 온 배포 지시가 있는지 확인함.
- 배포 지시가 있으면 pulll 받아서 실행하고 처리함.

서버가 외부에서 들어오는 접속 통로 따로 열어두지 않아도 배포가 진행이 됨

- 에이전트는 pull받은 파일이 있으면 배포 묶음 안에 어떻게 처리를 해야하는지..
- 경계를 나누면 어플리케이션을 어떻게 설치하고 어떻게 시작하는지까지는 개발자가 알고 절차를 어떻게 할지는 코드 디플로이가 알고 있다.

저일하면 코드 디플로이 본체는 무엇을 어느 그룹에 어떤 순서로 배포하라고 지시하면서 결과를 수집함.

에이전트는 그 결과를 보고 하는 쪽

코드 디플로이가 실행 할 수 있는 배포 방식

자동으로 올려주기는 하는데 올리는 동안 서비스 멈추면 사용..

어떻게 올리느냐가 중요함. 무중단 배포에서 배울 건데 코드 디플로이가 처리 할 수 있는 방식 무엇인지

블루 그린 배포에서

코드 디플로이가 맡는 역할은 새버전을 어느 환경에 올릴지 결정하고 그 환경이 정상인지 아닌지, 확인하고 이전코드로 바꿈

그래서 규모가 크면 서버 따로 띄우는게 힘들음.

따로 환경을 두개 만드는게 아니라 이미 돌아가고 있는 서버들을 하나씩 교체

- 처음에는 모든 서버가 v1으로 운영, 한대를 v2로 교체,

여기서의 책임은 코드의 진행 관리

한번에 몇대씩 교체하고 정하고 각 단계가 성공했는지 확인한 다음에 다음 대상으로 넘어감.

교채하는 동안에 서버가 동시에 떠있으면 문제가 됨.*

코드 디플로이가 ec2를 대상으로 할때는 옵션이 있다.

사용 이유

- 어플리케이션 배포 과정을 자동화해서 배포 중단 없이 신속하고 자동화하기 위함.
- 배포관리, 모니터링, 온프레미스 클라우드 지원.\

정리

- 코드 디플로이는 배포 자동으로 수행해주는 AWS 관리형 서비스
- CI CD 흐름안에서 검증이 끝난뒤에 배포 실행 단계 하나하나를 맡아서 처리함
- 깃헙 액션이랑은 다른 영역을 맡아서 담당. 코드 디플로이는 어느 배포 대상 서버를 모니터링함.
- 배포영역을 누가 관리하느냐에 따른 차이임 (깃헙 액션이랑)
- 빌드 결과물이 배포 묶음이 되어서 저상소에 올라가고 에이전트가 그 방식을 확인함.

**무중단 배포**

코드 변경 어떻게 검증되고 빌드 되어서 배포 가능한 결과물이 되는지, 그리고 그 과정 자동으로 이어주는 도구가 어떤 책임 갖고 있는지를 배웠다고 하면은

- 새로운 버전의 어플리케이션이 있으면 배포가 어떻게 되는지 알아야 함.

여러가지 전략이 있음. 어떤 전략을 고를지는 자유

설명 할 수 있어야 하는 것.

- 무중단 배포가 어떤 개념인지
- 그리고 이게 성립하려면 어떤 조건이 갖춰져야 하는지
- 대표적인 전략 3가지가 있는데, 큰 틀에서 이해 하는 게 필요

정의 : 서비스 중단 없이 어플리케이션 업데이트하거나 배포하는 방식

- 사용자 입장에서라는 부분이 있음. 서버 안에서는 분명히 무언가가 멈춤. 어떤 프로세스는 종료되고 새 프롯스는 뜨고 그 사이에 특정 인스턴스는 요청을 받지 못함
- 무중단 배포는 서버 안에서 중단이 일어나긴 하는데 사용자 입장에서는 모름.. 사용자 입장에서는 계속 돌아가는걸로 느껴짐

전체 흐름에서의 위치

앞에서 코드 빌드하고 결과물 만들고 저장하고 배포 대상까지 전달해서 띄움. 그러면 새로운 버전의 결과물 이미지라는건 준비되어 있는 상태.

- 무중단 배포는 배포 대상에서 새 버전 띄우고 사용자 트래픽을 다루는 일을 설명하는 구조
- 이미 만들어진 것을 어떻게 안전하게 갈아타느냐에 대한 문제

무중단 배포에 대한 도식

결국 두 버전에 일정시간 겹쳐서 서버에 올라가 있는 시간이 존재함.

- 이렇게 처리하면 중단 시간 없고 사용자 입장에서도 자연스럽게 새 버전 쓰고 있는게 됨.
- 두 버전이 겹칠 수 있어야 한다는 말의 의미
    - 필요한건 겹쳐서 돌아갈 수 있는 실행 여유
    - 프로세스 두개가 될수도 있고 로드 밸런서가 바라보는 두개의 대상 그룹이 될 수도 있음
    - 새 요청을 받을 수 있는 대상이 둘 이상 공존을 해야한다.
- 단일 ec2 위에 컨테이너 두개 띄우는 구성으로도 신버전 구버전 전환은 가능.
- 호스트 ec2 서버가 죽으면 컨테이너가 같이 죽음.
- 이런 경우를 호스트 서버가 단일 장애점이 됨.
- 무중단 배포랑 고가용성은 같은 말이 아니다.
- 무중단 배포는 배포라는 계획된 변경 중에 사용자 요청 끊기지 않게 하는 것.
- 물론 연관관계가 있지만 학습하는 시점에서는 개념을 명확하게 하는게 필요

요청을 어느 버전으로 보낼지는 로드 밸런서, 리버스 프록시 같은 친구들이 맡아서 처리.

무중단 배포를 하면 빠른 롤백에도 유리, 빠른 복구에도 유리.

새로운 버전의 프로세스, 어플리케이션만 미리 띄워둔다고 무중단이 아님.

- 프로세스가 떴다랑 요청을 제대로 처리 할 수 있다는 다른 이야기
- 새로운 어플리케이션 띄우데는 몇초 걸릴 수 있고 그 사이에 DB 연결이나 초기화가 아직 끝나지 않을 수 있음.

무중단 배포의 조건.

- 새로운 트래픽은 준비가 확인된 대상에게만 보내야함. 이걸 판단하는게 헬스 체크
- 트래픽을 뺄 때도 조심.. 구버전 내릴 때 이미 처리중이던 요청이 남아 있을 수 있음.
- 구버전이랑 신버전 같이 공존한다는 것은 두버전 동시에 같은 데이터 다룬다는 뜻 .
- 배포 했다고 끝이 아니라 배포 이후를 봐야함. 모니터링 해서 오류율이나 응답지연 시간 지표 보면서 안정적인지 확인

사용 이유

서비스 이용자에게 중단 없이 안정적인 기능 업데이트를 제공하기 위해서..

- 일반적인 웹서비스 커머스 같은건 ux가 중요.
- 특히 금융권. 돈이 걸리면 다운 타임이 비즈니스적 요소가 매우 큼..

3가지 전략

(공통 된 점은 미리 새 버전 준비해두고 트래픽을 옮긴다는 원리는 같음)

- 차이는 무엇을 얼마나 겹쳐두느냐, 트래픽을 어떤 단위로 옮기느냐
1. 블루 / 그린 배포
    1. 완전 독립된 두개의 환경을 두고, 한쪽이 사용자 요청을 처리하는 동안 다른 쪽이 트래픽 목적을 넘김.
2. 롤링 배포
    1. 전체를 한번에 바꾸지 않고 기존 버전이 돌아가는 대상을 하나씩, 아니면 소수 단위로 점진적으로 교체해나가는 방법
3. 카나리 배포
    1. 새 버전을 아주 소수의 사용자 에게만 먼저 노출을 해서 이상 없는지 확인하고 점차 비율을 올려가는 방식.
    2. 전체 인스턴스에서 1대, 아니면 퍼센테이지로 0.1퍼 인스턴스만 새로운 버전으로 바꿔보고 문제 없으면 비율을 늘려 나가는 방식

전략 비교

세부 절차를 설명 하는게 아니라 이제 수업 들을 때 무엇을 보면 되는지에 대한 기준

실행 환경을 겹쳐두는 방식이 다름

- 블루그린은 환경 하나 더. 추가, 롤링은 잠시 겹치게 함. 카나리는 천천히..

트래픽 전환 단위, 블루그린 -> 롤링 -> 카나리

롤백 속도, 롤링 -> 카나리 -> 블루그린

운영 복잡도,  카나리 -> 롤링 -> 블루그린

롤링 방식 가장 많이 쓰긴 함.

블루 그린은 추가 자원을 쓰는데 롤링은 안 쓰고 할 수 있으니까~

카나리는 규모가 크면 많이 씀. (글로벌 서비스 같이)..

왜그런가? 라고 하면 사용자가 많으면 많을 수록 사용자 환경이 엄청나게 다양하고 기기 성능도 다 다름

모니터링 되어 있으면 훨씬 유효하게 잘 쓸 수 있음.

정리

- 무중단 배포는 이미 배포 준비되어 있는 상태에서 다운 타임 없이 사용자 입장에서 중단되지 않고 서비스 제공하는 배포
- 무중단 배포 전략에서 봐야 하는건 핵심은 다운 타임. 기존 버전 먼저 내리고 새 버전 올리면 빈 시간이 장애로 취급되어서 무중단 배포는 기존 버전 살려두고 새 버전 겹쳐두고 트래픽 옮겨서 사용자 관점에서는 문제 없이 돌아가는 그림
- 헬스체크로 준비 상태 확인하고 진행 중인 요청 정리하고 버전간 호환성까지 생각 배포 이후 관찰 해야됨
