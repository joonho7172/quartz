# 6/29(2) CORS, CSRF, JWT

**CORS(Cross origin resource Sharing)**

정의 : 서로 다른 출처 사이에서 자원을 공유하는 것.

출처 -> origin은 세가지 모두 같아야 같은 출처로 판단을 함

프로토콜, 호스트, 포트

동일 출처 정책 Same-Origin Policy란?

- 하나의 출처에서 로드된 문서나 스크립트가 다른 출처의 자료와 상호작용 하는 것을 제한 하는 보안 모델
- My-site 에서 받은 페이지의 JS가 다른 사이트로 보내는 API 교청은 막힌다.
- 브라우저의 기본 방어벽.

요즘 React 랑 Spring 따로 출처가 다른데.. 어떻게 해결?

- > CORS

CORS는 다른 출처의 리소스에 접근 할 수 있도록 하는 HTTP헤더를 통해 권한 부여.

- 누가 허락하고 누가 판단?
- 집행하는 주체는 브라우저, 허용 여부를 결정하는 건 서버.
- 서버가 응답 헤더에 “ 출처 허용을 명시 “
- 브라우저가 그걸 보고 요청을 통과 시킬지 막을지 최종적으로 결정.

브라우저가 관여하는 정책이라고 하는게 의미가 있음.

- > 서버가 다른 서버를 직접 호출 할 때 CORS 적용안됨.

CORS는 어디까지나 브라우저에서 실행되는 JS가 요청을 보낼 때임.

서버 to 서버는 안됨

사용 이유

브라우저의 동일 출처 정책을 안전하게 완화해서 요즘의 웹 어플리케이션 구조 가능하게 하기 위함.

SPA, react에서 사용하기 위함.

- > 프론트 엔드는 배포가 되고 데이터는 별도의 API 서버를 씀.

MSA처럼 기능별로 API서버 쪼개두고 하나의 프론트엔드가 다 호출하는 경우 .. 지도나 소셜 로그인 같은 외부 API를 클라이언트에서 직접 부르는 경우..

SOP 라는 제약 안에서도 정상적으로 동작하게 만들어주는 표준화된 약속이 CORS..

동작 방식 :

핵심은 요청을 두가지로 나눠서 다르게 처리함.

**단순 요청(simply Request)**

말 그대로 별다른 사전 절차 없이 바로 본 요청을 보내는 경우

- > 아무 요청이나 단순 요청이 되지는 않고 조건을 만족

조건 1. 메소드가 GET, POST, HEAD 셋 중 하나

조건 2. ContentType이 multipar/form-data, text/plain, www-form-urlencoded 중 하나 여야함..

조건 3. 기본 헤더만 포함 되어야 함.

- 브라우저가 요청을 보낼 때 자동으로 Origin 헤더에 지금 요청을 보냄.
- 서버는 이 요청을 받고 출처를 허용한다면 응답 헤더에 Access-Control_Allow-Origin 이라는 항목을 허용하는 출처를 담아서 응답.
- 판단은 브라우저가,, Acces_control-allow-origin라는 응답값 확인 일치하면 데이터 넘겨줌. 헤더가 없거나 값이 안맞으면 CORS 에러, 반환 받은 응답 거절.

서버가 응답을 안준게 아니라 줬어도 브라우저가 Access-control-allow-origin 확인 하고 안되면 막음.

즉, cors 에러는 브라우저 단계의 차단임

**예비 요청(Preflight Request)**

단순 요청의 조건을 벗어나는 요청.,.

- > 이때는 실제 요청을 보내기 전에 OPTIONS 메소드로 예비 요청을 보냄
- > 예비 요청이 한느 일이 무엇인가?
- 서버에게 미리 요청 보내기 전에 물어 보는 것임.
1. 예비 요청. 실제 PUT 전에 브라우저가 OPTIONS 요청을 보냄.
    1. 어느 출처에서 보내는지, 실제로 어떤 메소드를 쓸 것인지, 헤더를 쓸 것인지 담은 정보를 보냄
2. 서버는 이 예비 요청을 받고 자기 허용 정책을 응답헤더에 담아서 돌려줌.
    1. 허용하는 출처 Access-Control-allow-origin , 허용하는 메소드.. 헤더.. 담아서 반환함.
3. 브라우저가 실제 요청을 보냄
    1. 예비요청의 응답을 보고 판단
    2. 허용되지 않으면 CORS에러.

사용 방법

MVC 레벨에서 처리하면 간단하지만 설정이 여기저기 흩어지고 보안 필터를 거치기 전에 처리될 한계가 있음.

Security 레벨에서 처리하면 보안 규칙이랑 CORS 정책을 한곳에서 중앙 관리

정리 :

- CORS 허용하는 매커니즘. 브라우저의 동일 출처 정책 때문에 막혀있는 교차 출처 요청을 서버의 허락을 받아서 안전하게 열어주는 표준 약속
- 판단과 결정의 주체가 다름. 허용정책을 정하는건 서버 그 정책을 응답헤더로 받아서 최종적으로 차단할지 통과 시킬지 브라우저가 집행
- CORS 에러는 서버 통신 실패가 아니라 브라우저 단계의 차단이다.
- 요청은 단순 요청이랑 예비 요청으로 나뉨. 예비 요청은 OPTIONS로 먼저 요청을 보내고 허락 맡는 과정을 거참.

**CSRF(Cross Site Request Forgery)**

정의 :

교차 - 사이트 요청 위조, 다른 사이트 거쳐서 위조된 요청을 보내는 것.

- > 자신의 의지와 무관하게..

사용자는 자신이 뭘 하는지 모름. 그치만 그 사람의 권한으로 송금이나 글 삭제 같은 요청을 던질 수 있음

- > 어떻게?

사용자가 악성 사이트에서 악성 url을 눌렀을 때,… src 주소로 요청을 보냄 -> 악성. 코드 전에 로그인한 사이트의 쿠키를 붙여서 url 요청을 보내는 것임.

유효한 세션 쿠키가 담긴 이체 요청이 들어오면 처리가 될 수 있음.

- get이든 post든 브라우저가 쿠키를 자동으로 붙여보내는 특성 때문에 이러한 공격이 유효한 것.
- CSRF는 사용자가 로그인만 되어 있으면 클릭 한 번으로 사고가 난다.

CSRF 방어가 필요한 이유

사용자가 이 요청을 보내려고 의도 했는지는 모름.

따라서 서버는 추가적인 증표를 하나 더 요구해야함.

이 요청이 사이트의 정상적인 절차를 거쳐서 만들었다는 증거 - CSRF 토큰.

동작 방식

이 증표를 어떻게 만들고 검증하는지가 CSRF 방어의 핵심

- > Spring Security는 싱크로 나이저 토큰 패턴이라는 방식을 씀.
- > 서버랑 클라이언트가 같은 토큰을 한장 씩 들고 있다가 요청이 오면 둘을 맞춰봄
1. 토큰 생성하고 전달
    1. 사용자가 사이트에 처음 접속하거나 로그인하면 서버는 예측 불가능한 임의의 문자열로 CSRF 토큰을 하나 만들음. 이 토큰을 두 군데 두는데 하나는 서버 자신의 세션, 다른 하나는 브라우저.
    2. 같은 토큰을 서버와 브라우저가 한 장씩 나눠 갖는다.
2. 클라이언트의 토큰 포함한 요청
    1. 사용자가 상태를 바꾸는 요청을 보냄. Post, put, delete 같은 요청.
    2. 클라이언트는 JS에서 아까 받아둔 CSRF 토큰을 요청에 같이 보내게 됨
    3. X_CSRF-Token 헤더에 담거나 해서 HTTP 요청 헤더를 보냄
3. 서버는 토큰 검증..
    1. 다르면 요청 거부. - 출처가 다르면 SOP 때문에 HTML 읽을 권한이 없음

정리 :

브라우저는 쿠키를 자동으로 붙여주지만 CSRF 토큰까지는 붙혀주지 않음

그렇게 방어하는 원리임.

설정 방법:

원래 CSRF는 켜져있는게 default임.

비활성화 하는 방법이 있음.

언제 끄고 언제 키는가?

판단 기준은 인증 정보가 브라우저에 의해 자동으로 전송 되는가?

1. 세션이랑 쿠키 기반으로 인증
    1. 로그인하면 서버가 세션 ID를 쿠키에 담아주고 그 다음부터 브라우저가 모든 요청에 이 쿠키를 자동으로 실어보냄.
    2. CSRF 보호 무조건 켜야함
2. 토큰 기반 인증
    1. 로그인 하면 서버가 토큰을 발급하고 클라이언트는 이 토큰을 저장함
    2. 요청을 보낼 때마다 자바 스크립트가 직접 Authorzation 헤더에 보냄.
    3. 여기서 개발자가 명시적으로 헤더에 넣어야 함.
    4. 애초에 CSRF 성립하지 않음.

JWT 같은 경우에는 쿠키 인증이 아니면 꺼도 됨 ㅇㅇ 근데 쿠키에다가 저장하는 방식이라면 CSRF 켜야함.

jWT는 헤더로 전달하면 안전함. 즉, 기준은 토큰의 종류가 아니라 전송방식이다.

정리 :

- CSRF 공격이 성립하는 이유는 브라우저가 쿠키를 자동으로 요청에 실어 보내기 때문.
- 이러한 특성 때문에 로그인 된 상태면 그 사람 권한으로 위조된 요청을 보낼 수도 있다.
- 서버가 이걸 막기 어려운 이유는 유효한 쿠키만 보고, 인증된 사용자라는 것 까지만 알 수 있지 의도 여부는 모름
- 이걸 막기 위한게 CSRF 토큰.
- 쿠키는 브라우저가 자동으로 붙여주지만 CSRF는 그렇지 않아서 SOP 때문에 공격자가 이 토큰을 읽을 수 없다.
- 상황에 따라 CSRF 비활성화 할 수 있음.
- 브라우저에 따라서 자동으로 쿠키로 전송 되는가를 따져야함.

**Spring Security - JWT**

로그인에 성공하면 그 인증 정보를 Http 세션에 저장.

다음에 로그인해도 세션 쿠키로 판단 후 상태 유지

- 세션에 기억하지 않는 도구가 JWT

실제로는 둘 다 씀.

정의 :

제일 널리 쓰이는 웹에서 토큰이 Json Web Token

헤더는 토큰의 타입이랑 서명에 사용한 알고리즘 정보

페이로드는 실제 데이터, 사용자 ID, 권한

시그니처 : 헤더 + 페이로드, 그 후 비밀키로 서명한 값.

시그니처가 하는 일

- > 토큰의 내용을 누가 바꿨는지 검증하는 용도

JWT가 보장하는 건 내용이 위변조 되지 않았다는 무결성.

Stateless 무상태 가능성에서 사용됨.

서버 입장에서는 사용자의 로그인 상태 기억하지 않음.

사용 이유 :

세션 기반 인증은 서버가 사용자의 상태를 메모리나 DB에 저장함.

사용자가 늘어나면 부담이 생김

수평 확장 할 때 서버들끼리 세션을 공유해야되는 세션 클러스터링을 또 해줘야됨

토큰 기반 인증을 하면 문제가 해결.

세션 방식과의 차이

세션 - 서버가 상태를 통제 하기 때문에 강제 로그 아웃이나 중복 로그인 막을 수 있음

JWT - 한번 발급되면 만료될 때 까지 무효화 어려움.

작동 방식

1. 클라이언트가 요청 보낼 때, 헤더에 Authourization : Bearar토큰 내용해서 보냄
2. 요청이 JwTFilter 에 도착하면 필터는 토큰 프로바이더로 토큰 유효한지 검사 하고 정보 꺼내달라함.
3. 유효하면 객체 꺼냄.
4. 요청 끝나면 context삭제

인증/인가 예외 처리

보통은 전역 예외 처리기로 예외처리..

@ControllerAdvice나 @ExceptionHandler 등..(controller에 접근 한 다음 예외 잡을 수 있었음.)

JWT 검증 실패나 권한 부족은 컨트롤러 전에서 예외처리

정리:

- 토큰 기반 인증, JWT는 서버가 로그인 상태를 세션에 저장하지 않는 stateless 전략을 통해서 확장성을 확보
- 세션이 한번 로그인하면 서버가 기억한다라면 JWT는 매 요청마다 토큰으로 다시 증명한다.
- 시큐리티 이거 구현하려면 세션 끄고 커스텀 JWT Filter가 매요청 마다 authentication 만들고 시큐리티 컨텍스트 홀더에 넣어줌.
- 필터 단계에서 터지는 예외는 따로 처리 해줌.

가져가야 할 핵심 

- CORS는 여는 기술, 막는 기술이 아님.
- 브라우저가 기본적으로 막아둔 “ 다른 출처로의 요청 “ 을 서버의 허락을 받아서 안전하게 열어주는 약속
- 결정하는 쪽과 집행하는 쪽이 다름. “ 출처 허용 “은 서버인데 판단은 브라우저.
- 브라우저는 요청을 두 갈래로 나누어서 처리 (단순 요청, 예비 요청)
- 서버가 로그인 상태를 어디에 두느냐? 세션 방식은 서버가 기억하고 JWT는 매 요청마다 토큰으로 다시 증명
- JWT는 암호화된 비밀 상자가 아니라.. Header, payload, signature로 이루어져 있음. 민감 정보 넣으면 안됨
- 이 방식이 실제로 동작하는 중심에는 JWTFilter가 있다. 매 요청마다 헤더에 베어러 토큰 검증하고 유효하면 Authentication 객체에 넣어서 Security context에 넣음
- JWT 검증 실패 같은 예외는 필터 단계에서 터짐. @RestController에서 못잡음.
