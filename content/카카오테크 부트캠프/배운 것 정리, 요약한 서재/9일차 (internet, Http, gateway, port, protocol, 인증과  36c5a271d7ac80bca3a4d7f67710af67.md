**Internet**

인터넷의 정의 : 전 세계 컴퓨터 네트워크들이 서로 연결되어 데이터를 주고 받는 거대한 네트워크

사용 이유 : 정보 검색 등 다양한 정보에 접근하기 위해

동작 방식

1. 인트라넷 내부 요청 :
    1. 사람이 [google.com](http://google.com/)을 치면 컴퓨터는 ip주소를 가짐 135.~~~.~~……
    2. 이때 등장하는게 DNS, 도메인 네임 서버. ->인터넷에 있어서 주소록 같은 개념
    3. 컴퓨터의 내부 네트워크나 통신가가 지정한 DNS서버에 이 서버에 있는 [google.com](http://google.com/)의 ip주소를 물어보고 dns가 주소를 찾아서 반환해주는 것임
2. 게이트웨이를 통한 이동 -> 요청이 게이트웨이 통가, 라우팅하고 검사 가능
    1. 구글 서버 ip주소를 열었으면 -> 주소로 조회 요청을 보냄 . 브라우저 창에 입력을 했으니 주소값에 대한 반환값을 받아야 함.
    2. 어쨌든 컴퓨터는 특정한 내부 네트워크에 포함되어 있기 때문에 마음대로 외부 인터넷 세상으로 연결하려면 -> 게이트 웨이를 거쳐야함 -> 방화벽 같은 개념. 허용된 요청이면 연결 시켜주는거임. -> 이 과정에서 보안 검사를 할 수도 있고 .. -> 이러한 과정을 NAT라고 함
3. 외부 네트워크 접속 -> 게이트웨이 거친 요청이 다양한 외부 네트워크를 거침
    1. 게이트웨이 통과해서 [google.com](http://google.com/)으로 가는 요청이 외부로 나감. -> 패킷이라는 단위로 나눠서 전송 됨. -> 패킷에는 출발지 ip, 목적지 ip 이런 정보들이 담겨져 있음.
    2. 이 패킷들이 전 세계에 있는 수많은 라우터를 거쳐 목적지로 이동 -> 목적지 주소를 보고 효율적인 다음 경로로 패킷을 전달해줌
4. 응답의 변환
    1. 패킷이 도착하면 홈페이지를 구성하는 html, css, 등을 패킷으로 나누어 다시 보내줌

**Protocol**

통신 규약, 대화의 규칙. 웹에서는 HTTP 기반으로 요청을 주고 받음

서버는 클라이언트의 이전 요청을 기억하지 못함. -> 모든 요청을 독립적인 것으로 취급함.

예를 들어 우리가 어떤 서버에 로그인 유지가 되어있는 상황.. -> 쿠키랑 세션이나 JWT 토큰 같은 기술을 써서 HTTP가 갖는 stateless하다는 특징을 가짐.

**인증과 인가**

인증 -> 당신은 누구인가 -> 병사가 마패를 갖고 신분을 증명하는 과정. -> 웹에서 아이디나 비밀번호를 갖고 로그인하거나 지문 인식 .. 모두 인증.

(시스템에 등록된 사용자가 맞는지 확인하는 절차)

인가 -> 인증을 통해서 들어왔다 하는 권한을 구분하기 위한것. -> 권한 느낌임.

인증에 성공해도 인가는 받아야됨.

1. 도메인 이름 입력
    - 사용자가 웹 브라우저에 https 프로토콜을 사용해서 도메인 이름을 입력함
2. DNS 조회
    - 입력된 도메인의 ip주소를 조회함
3. Forward Proxy 통과 (선택적)
    - 설정에 따라 Forward Proxy 서버를 거쳐 웹 서버에 전달된다
4. 홈페이지의 서버와 3-way-handshake
    - 클라이언트가 서버에 연결하고 싶어 요청 -> 서버가 요청받고 자신의 요청도 확인. 요청 -> 클라이언트가 잘 받았으니 연결 시작하자.
    - 세번의 통신을 통해서 신뢰성 있는 연결을 만드는 과정. 이후에 http 요청을 주고 받음.
5. 서버와의 TLS handshake
    - 사용자의 웹 브라우저와 안전한 연결을 시작하기 위함
    - tcp는 됐는데 암호화는 안된 상황.
    - 통신하려는 서버가 진짜 서버인지. 키를 공유하여 안전하게 소통
6. 서버의 공개키 및 인증서 요청
    - 서버로부터 ssl/tls 인증서와 공개키 요청
    - Tls handshake 첫단계.
    - 서버에게 증명할 수 있는 인증서랑 공개키를 달라고 요청.
    - 인증서 안에는 서버 도메인 주소 인증서를 발급한 기관과 공개키가 있음.
7. CA 인증서 검증
    - CA의 공개키로 인증서를 검증 (서명을 풀어봄)
8. 암호화된 세션 생성
    - 인증서가 유효하면 암호키 생성해서 통신을 암호화 함
9. 안전한 HTTPS 통신
    - 사용자와 웹 서버 간의 데이터 교환이 이루어짐

**모놀리식, MSA**

정의 : 회원, 상품, 주문, 결제, 등 모든 하나의 거대한 프로젝트로 묶어서 하나의 서버에 올려두는 것.

처음 서비스를 시작할때는 당연히 모놀리식. 단일 repo. 빠르게 서비스 내려면 모놀리식으로.

결국은 한계, 단점을 맞이함.

1. 단일 장애점. 모놀리식 구조에서는 이 에러 하나 때문에 서버 전체가 다운이 됨. -> 결제만 안되는게 아니라 상품을 조회 하는 것도 안됨
2. 비효율적인 확장. 트래픽 감당하려면 여러 대 복사해야하는데 쓸모없는 로직까지 복사함
3. 배포의 부담. 코드 한줄 고쳤는데 서버에 반영하려면 전체 빌드, 재시작해야함

MSA

- 모놀리식의 한계를 극복하기 위한 구조
- 서버를 기능별로 잘게 나눔 -> 각각 독립적인 어플리케이션으로 나눔 (이럴 때 api gateway가 단일 진입점 역할을 함)

장점.

1. 장애 격리 : 결제 서버에서 버그 생겨서 다운이 되어도 상품 서버는 다른곳에서 돌아감(전체 마비를 격리)
2. 독립적인 확장: 트래픽이 몰리면 다른 서버는 가만히 두고 필요한 서버만 복사해서 늘리면 됨. 자원을 효율적으로
3. 기술의 자유 : 서버마다 각자 다른 언어로 만들고 서로 소통할 수 있음 (굳이 긴함)
- > 시스템 여러개로 쪼개면 그 만큼 관리 포인트가 있어서 특별한 일 아니면 잘 안씀….

**네트워크 프로토콜**

정의 : 전 세게에 다양한 기기들이 서로 소통하기 위해 지켜야 할 규칙.

예시 : 교통 신호등 or, 우편 서비스

네트워크에서 데이터를 보내는 것은 우편서비스에 비유 할 수 있다.

편지 보낸다 라고 가정하면 편지 봉투 위에 정해진 위치에 받는 사람 주소, 보내는 사람 주소, 우표를 붙여야함. -> 이런 약속들과 같은 거임

- 받는 사람 주소 - 목적지 ip 주소
- 보내는 사람 주소 - 출발지 ip주소
- 우표 - 데이터 전송할 권한이나 비용이나 인증, 인가
- 편지 봉투는 패킷이라는 데이터 단위
- 편지의 내용물은 실제 보내려는 데이터, payload

TCP/IP 4계층

1. 어플리케이션 계층 : 우리가 직접 사용하는 서비스, 웹 브라우저나 이메일
2. 전송 계층 : 데이터가 안전하고 정확하게 전달되도록 책임 지는 계층 (tcp or udp)
3. 인터넷 계층 : 데이터가 가야 할 최종 ip주소 우편물 분류하는 느낌
4. 네트워크 인터페이스 계층 : 실제로 데이터를 케이블에 실어 보내는 물리적 역할.
- > 계층을 나눈 덕분에 새로운 어플리케이션 프로토콜이 나와도 기존의 인터넷 망을 그대로 이용 할 수 있음. -> 관심사의 분리

사용 이유 : 데이터를 안전하고 신뢰성 있게 전송하기 위해 필요

TCP

- 연결 지향형 프로토콜, 신뢰성 있는 전송
- 3-way-handshake 기반으로 통신 연결을 맺고 4-way-handshake 갖고 연결을 마침.-> 이러한 과정이 신뢰성이 높음
- 데이터의 안전성이 중요하면 TCP기반의 프로토콜을 사용함

UDP

- 비연결형 프로토콜. 사전에 약속 없이 데이터를 보냄, 받는 쪽에서 확인 안함
- 절차가 없어서 속도가 빠름.
- 유튜브 라이브 스트리밍 or 게임 할 때.

**HTTP**

HyperText Transfer Protocol의 약자임

1. 요청과 응답 구조.
    1. Http 통신은 반드시 클라이언트가 서버에게 요청하는 걸로 시작. 그 후 요청 처리해서 응답을 보냄.
2. 무상태성
    1. 상태가 없다. 서버는 방금 요청을 보냈던 클라이언트가 다음에 또 요청을 보내도 이전을 기억 못하기때문에 -> 모든 요청을 완전히 독립적으로 취급함. -> 유지보수성이나 개발 복잡성이 높아짐 -> 서버의 구조가 단순해지고 편리해짐 -> 확장성이 높아질 수 있음.
    2. 이러한 단점을 보완하기 위해 쿠키, 세션, jwt토큰 같은 기술을 사용함.

예시 : [https://example.com/priducts?id=123](https://example.com/priducts?id=123)

Https -> 프로토콜

[Example.com](http://example.com/) -> 도메인, 호스트, 서버 컴퓨터 주소

/products -> 서버 내부에 있는 자원의 경로 ) example서버에 products 자원

?id = 123 -> 쿼리 스트링. 서버에 추가적인 정보를 전달할때 사용

HTTP도 버전이 있음

1. 1버전 -> 하나의 연결당 하나의 요청만 처리 좀 느림
2. 2버전 -> 멀티 플렉싱 사용 -> 대부분 2버전 사용
3. 3버전 -> 기존에는 http가 tcp기반이었으면 udp기반임

**HTTP - Request Method**

http 자원을 주고 받기 위한 약속, 규약이다 -> request method라는 것을 통해서 요청의 의도를 명확하게 함

사용 이유 : 요청 본문 열어보기 전에 get이나 post 메소드만 갖고 어떤 작업인지 빠르게 판단 할 수 있다. -> 서버 효율을 높이고 요청의 의도를 명확하게 정의해서 문제를 줄임

REST의 핵심 철학과도 같음. -> REST에서는 HTTP Method이용해서 자원에 대한 행위를 표현함.

/Users 라는 api가 있다면 유저 자원에 get은 사용자 조회, post 요청은 생성하는 식

**GET**

데이터 조회에서 이용함

URL입력하고 엔터치면 GET요청을 보내는 것임.

서버에 있는 특정 리소스를 가져오기 위해서 사용.

읽기 작업에만 사용을 해야하고 GET요청 때문에 서버의 데이터가 삭제 되거나 수정되면 -> 잘못된 설계

GET은 멱등성을 가짐 - 여러번 조회해도 같은 결과를 가진다는거지

**POST**

리소스 생성. -> 회원가입, 게시글. 장바구니 등..

Post 요청 중에 통신이 끊기거나 해서 클라이언트가 함부로 retry하면 중복데이터가 생길 수 있다.

POST는 멱등성을 가지지 않음 - 여러번 누르면 여러번 생기는거야

**PUT**

서버로 데이터를 전송하여 리소스를 전체 업데이트 할 때 사용하는 메소드

- > 수정이긴한데 **전체**를 업데이트 함. -> 하나의 데이터 row 전체

PUT은 멱등성을 가짐 - 결국 최종 결과는 동일함

**PATCH**

서버의 리소스를 부분적으로 수정 또는 업데이트 할 때 사용하는 메소드

put대신 사용하는 부분적 교체임.

예시로… age +1 인 요청이면 멱등성을 가지지 않고

Age 20 이런 식의 요청이면 멱등성을 가짐.

**DELETE**

얘는 뭐 당연히 멱등성을 가짐.

근데 실제로 일할 때는 데이터를 삭제하진 않음. Soft delete 와 같이 삭제됐다는 상태를 변경하고 그대로 둠..

**멱등성**

웹 - 어떤 요청을 한번 보내던 여러번 보내던 결과는 같다.

예시 ) 엘리베이터 버튼. - 멱등성 o, 결제, 추가 버튼 - 멱등성 x

왜 중요하냐? 네트워크는 언제든 끊길 수 있음. -> 클라이언트 입장에서는 알 수 없으니.. 멱등성을 가졌으면 맘 편히 다시 요청. -> 그러나 보낸 요청이 멱등성이 없으면 참사가 생길 수 있음.

- > 개발자는 이 요청이 멱등한가?를 항상 고민하고 나누어야 함.

왕과 장군 예시

장군이 전쟁하다가 왕한테 물 100L 보내달라고 함..

2. 개발자의 디버깅 효율. 에러를 분류해 놓으면 처리하기도 편함
- > 상태코드만 봐도 문제의 원인과 책임이 누구에게 있는지 판단 가능.

**Query String과 Path Variable**

Query String은 웹 페이지에 대한 추가 정보를 서버에 전달하기 위한 문자열.

Path variable은 경로 부분에 포함되어있는 , 특정 자원을 식별하는 변수

Path variable -> 식별을 위한 것임 url 경로 가 자체에 포함되어서 자원의 정체성을 규정.

Query String -> 추가 정보를 전달하는 문자열. 조건 검색이라고 보면 편할듯

사용 이유 : Query String : 검색, 필터링, 정렬, 페이지네이션 등의 추가적인 정보

필터링 : 쇼핑몰에서 신발 카테고리에 들어가서 나이키 브랜드의 270mm 사이즈만 보고 싶을때 .. product?category=shoes&brand=nike 등등

정렬 : /posts?sortBy=likeorder=desc 등

페이지네이션 : /posts?page=10&size=20 등..

사용 이유 : Path Variable : 특정 리소스 접근

근본적인 차이점 : Query String가 여러 자원의 목록에 접근이면 path는 특정 자원을 지목

RestFul 아키텍쳐 : rest라는 것은 웹의 자원을 고유한 주소(url)로 표현하고 http 메소드로 그 자원을 다루자는 설계 원칙

GET /posts/123

PUT /posts/123

등.. url이 깔끔해지고 예측 가능해짐.

결론 — Query String -조건 Path Variable - 식별 할 때 사용

**API**

정의 : 어플리케이션 간 소통하기 위한 창구

식당에 비유

- > 메뉴판 : (interface 명세)
- > 점원에게 주문 : (API에게 명세를 보고 요청)
- > 점원이 주방에 알아들을 수 있도록 작성하고 전달
- > 요리 완성되면 점원이 음식 전달(response)
- > 메뉴판과 점원이 인터페이스 역할을 함. -> 손님과 주방이라는 다른 시스템이 소통 할 수 있도록 만들어 진 약속이 API

결국에는 우리가 입력한 url에 따라서 html, css, js를 반환을 받음.

결론 : 내가 만든 어플리케이션과 이미 만들어진 어플리케이션이 서로 통신할 수 잇도록 만들어진 규칙.

수업에서 가져가야 할 핵심

- 인터넷은 전 세계의 네트워크가 프로토콜이라는 공통의 약속으로 연결된 인프라
- web은 인터넷이라는 인프라를 달리는 수많은 서비스 인프라 중 하나임.
- 컴퓨터에서 출발한 데이터가 게이트웨이, 라우터 거쳐서 목적지 서버까지 도달하는 흐름을 알아야함.
- 네트워크 프로토콜은 전 세계에 다양한 기기들이 문제 없이 소통하기 위해서 반드시 지켜야하는 공통 약속
- HTTP는 클라이언트 요청에 서버가 응답하는 구조. 이전 상태를 기억하지 않는 무상태성을 갖는다.
- Request method는 클라이언트가 서버에게 어떤 작업을 해달라고 명확하게 지시하는 동사의 역할을 한다…(서버에서 요청을 받을 때 어떤 의도인지 명확하게 드러내기 위한 규약이고 약속이다)
- 개발 할 때 Rest Api에서는 crud 작업에 get, post, put, delete를 매핑해서 사용해야함
- 상태 코드는 클라이언트의 요청에 대해서 서버가 어떻게 처리를 완료했는지 알려주는 3자리 숫자….
- 200번, 400번, 500번대 각 번호대가 의미하는 큰 틀을 이해 할 필요가 있음.
- 401(인증 실패), 403(인가 실패), 404(찾을 수 없음), 500(서버 내부 오류)의 차이를 알아야 함
- Path Variable - /users/123 처럼 URL 경로 자체에 변수를 넣어서 단 하나의 특정 자원을 명확하게 지목 할 때 사용하는 개념
- Query String - /posts?category=tech 처럼 URL 끝에 ?를 붙여서 자원 목록에 대한 검색, 필터링 등 부가 옵션을 줄 때 사용함.
- 이 값이 없으면 자원 자체를 특정할 수 없는가? 라는 질문을 통해서 두가지 방식을 상황에 맞게 쓸 줄 알아야 함.
- API는 내 프로그램과 외부프로그램이 서로 데이터를 주고 받기 위해 만들어놓은 창구이다
- API 활용해서 날씨 정보, 소셜 로그인 등 남이 잘 만들어둔 거대한 기능을 레고 블럭 처럼 쓸 수 있다.
- API 문서 읽고 정확한 endpoint, method, header, body를 세팅해서 요청 보내고 응답데이터를 파싱해서 사용하는 전체 흐름 이해
