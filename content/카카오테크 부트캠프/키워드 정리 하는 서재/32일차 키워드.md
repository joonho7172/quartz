테스트 코드가 무엇인지, 실제 서비스에 배포되는 프로덕션 코드가 어떻게 구분 되는지?

- 테스트 코드란 검증 로직이나 실행 시간등 비즈니스 로직의 상태를 검증하기 위한 코드이다.

동료가 테스트 코드는 결국 버그를 찾으려고 하는거 잖아 라고 할 때 그 외의 장점 2가지 ?

- 테스트 코드는 주는 가치는 첫번째로 유지 보수성 증가, 그리고 디버깅도 있지만 디버깅 위치가 특정 되어서 버그를 수정하는데 유리하다

테스트가 안전한 리팩토링을 가능하게 한다는 말의 의미? 테스트가 없을 때 리팩토링이 왜 두려운 작업이 되는지?

- 테스트 코드가 있으면 리팩토링과 동시에 제대로 된 값이 전달이 됐는지 확인이 가능하다. 만약에 테스트 코드가 없으면 리팩토링과 동시에 결과를 확인 할 수 없어 나중에 결과를 확인 할 때나 확인이 되기 때문에 부담감이 생기고 두려움이 생긴다

테스트 코드가 살아있는 문서라고 불리는 이유를 ,코드가 바뀌어도 그대로 남는 일반 문서와 비교해서 설명.

- 테스트 코드가 곧 가이드 역할을 한다. 일반적인 설명서는 코드가 바뀌어도 그대로지만 테스트 코드는 코드가 변경과 동시에 테스트 코드의 여건도 수정하며 해야하기 때문에 잘 짜여져 있는 테스트 코드는 살아있는 가이드 라인이자 설명서가 되기도 함.

테스트의 동작 방식인 준비 0 실행0- 검증 세 단계가 각각 무엇을 하는 단계인지 설명, 간단한 예시로 어느 줄이 어느 단계에 해당하는지 짚어보자..

- 테스트의 준비 단계는 테스트랑 주체를 불러오는 단계, 실행은 테스트 코드와 함께 주체를 실행, 검증은 assertEquals()와 같이 결과를 확인 하는 것.

assertEquals를 사용한 검증에서 기대값과 실제값이 각각 무엇을 의미하는지 설명하고, 두값이 다를때 테스트 실패가 개발자에게 무엇을 알려주는지?

- 기대값은 개발자가 예측하는 리턴 값, 실제값은 함수가 실제로 어떤 값을 돌려보내는 값, 두 값이 다를때 비즈니스 로직의 오류를 알려줘

어떤 테스트가 통과했다고 해서 그 기능이 모든 경우에 완벽하다고 말할 수 없는 이유와 그래서 하나의 기능에 어떠하게 테스트를 작성하는 것이 좋은지?

- 어느때나 예외가 있다. 음수라던지, 0으로 나눈다던지, 그래서 하나의 기능에 예외를 염두에 두며 테스트를 작성하는 것이 옳다

단위 테스트, 통합 테스ㅡㅌ, e2e 테스트를 검증 범위 관점에서 비교 설명, 테스트 피라미드가 단위 테스트를 가장 많이 두라고 권하는 이유를 작성 비용과 속도 관점에서 설명

- 단위 테스트는 하나의 작은 메소드에서의 테스트, 통합 테스트는 하나의 모듈 관점, E2E는 전체적인 프로그램 테스트를 검증 한다. 단위 테스트가 테스트 코드의 요건인 FIRST 중에 Fast 빠르고, independent 독립적이기 때문에 가장 많이 쓰이고 유용하다.

TDD의 RED green, refactor 사이클을 단계 별로 설명하고, 기능 코드를 먼저 만들고 테스트를 나중에 붙이는 순서와 무엇이 다른가?

- Red, 일단 테스트하려는 객체의 구현되지 않은 오류 부분을 먼저 작성해 하나씩 메꾸고 green 오류가 없을때 까지 작성, refactor 최종 작성, 기능 코드를 먼저 만드는 일반적 방식과는 테스트 코드 작성 순서가 다르다. TDD를 하면 기능의 목표가 명확해지고 리팩토링이 쉬워짐./

좋은 테스트의 기준 (FIrst 의 원칙)

테스트는 “쓰기만 하면 충분 한 것 “이 아니라는 말의 의미를 설명하고, 나쁜 테스트가 오히려 어떤 악영향을 주는지 설명

- 좋은 테스트가 주는 영향이 많기에 쓰기만 하면 충분 한 것은 아니다. 하나의 가이드가 될 수 있기 때문, 나쁜 테스트는 오히려 성능에 영향을 끼친다.

First 원칙의 다섯 글자가 각각 무엇을 의미?

- fast - 테스트 코드는 빨라야 함.
- independent - 테스트 되는 객체는 독립적이어야함
- repeatable -어떤 상황에서도 작동 해야함
- self-validating  - 개발자가 로그를 보며 올바른지 검증 하는게 아닌 테스트 코드가 직접 개발자에게 알려주는 형태여야함
- Timely - 적절한 시기에 테스트 되어야함

fast 원칙이 단순히 성능 문제가 아닌 피드백 주기의 문제라는 말의 의미와 무엇이 테스트를 느리게 만드는지, 그 해결방향을 설명 해주삼

- 예를 들어 어떤 repository에서 값을 가져오고 그 값을 검증하고 싶다면 실제 respoitory에 연결하면 시간이 오래 걸린다. repository의 작동유무를 파악하고 싶은게 아닌데.. 그럴때 가짜 객체를 만들어서 연동시키곤 한다. 즉, 외부 의존성을 줄인다. 그리고 단순 성능 문제가 아니라 빠르게 테스트 코드가 작동해서 피드백 주기를 짧게 한다.

테스트가 independetn 이어야 하는 이유와 static 필드를 공유하는 테스트가 왜 위험한지, @beforeEach가 이 문제를 어떻게 해결하는지

- 외부에 의존을 받으면 테스트 코드가 항상 일정하지 않을 수 있다. 대표적인 예시가 static 필드 공유,
- 변경 가능성이 있는 외부에 영향을 받기 때문에 @beforeEach로 매 테스트가 실행하기 전에 초기화를 해준다는 입장

어떤 테스트 코드가 내 pc에서는 항상 통과하는데 ci서버에서는 성공 실패 반복, 어떤 원칙이 깨진걸까? 어떤 부분 의심해야하는지?

- 아마도 independent와 repeatable, 외부 변수에 영향을 받나보다 외부에 의존성이 있는 코드가 있는지 검증해야 할것.

flaky 테스트가 무엇인지, 한두번 이유없이 실패하는 테스트가 왜 위험한지 “개발자의 신뢰 관점에서 “ 설명해보삼.

결과를 system.out.println과 같이 출력해서 사람이 눈으로 보는 코드는 정상적이라도 왜 좋지 않은 테스트 코드 인지? 어떤 원칙에서?

- self-valdiation이랑 연관이 있음. 직접 눈으로 찍어서 보는 것이랑 테스트 코드가 알아서 판단해주는거랑은 차이가 큼

self-validating 원칙이 ci서버에서의 자동화와 어떤 관련이 있지? println으로는 자동화 왜 못함

- println은 결국 사람이 판단하고 값을 비교해야하는데 self-validating이 있으면 알아서 오류에 대한 메뉴얼이 있기 때문에 자동화가 가능하다.

timely 원칙이 “단순히 타이밍 맞게 쓰자”를 넘어 더 나은 설계를 끌어낸다는 의미를 결합도와 응집도 관점에 대해서 설명 좀..

- 단순히 타이밍을 맞게 쓰는것도 맞지만 적절한 때에 써야함.. 응집도가 높으면 책임이 강하니까 timely하게 테스트 가능하고 결합도가 낮아야 의존성이 낮으니 적절하게 사용가능 그게 아니면 언제 이걸 테스트 해야할지 간만 보다가 못함.
