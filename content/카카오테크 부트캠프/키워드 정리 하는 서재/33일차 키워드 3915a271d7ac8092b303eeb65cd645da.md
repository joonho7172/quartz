# 33일차 키워드

Factory 패턴이 호출부로부터 분리하는 책임이 무엇인지 설명하고, 서비스 코드가 if문으로 구현체를 직접 new로 생성하는 구조에서 결제 방식이 하나 추가될 때 어떤 일이 벌어지고 왜 변경에 취약한지 설명해주세요.

- 주요 주현체, 주 객체가 부수적인 구현체의 기능과의 분리를 통해, 서비스 코드가 if문으로 구현체를 직접 생성 하면 결제 방식이 추가 될때마다 서비스 코드의 책임이 늘어난다. 코드가 비대해지고 정책이 바뀌어 구현체의 세부 코드가 변경 될때마다 수정해줘야함.

Spring 컨테이너가 이미 객체 생성과 의존 관계 조립을 대신 해주는데도, 우리가 직접 Factory 클래스를 만드는 것이 적절한 상황은 언제인지 구체적인 예를 들어 설명해주세요.

- 구현체가 기본 생성 규칙만으로는 안될때, 복잡한 상황일 때, 직접 지정해주려면 factory 클래스를 만드는 것이 적절하다.

순수한 Factory 패턴과 spring 환경에서 만드는 Factory의 결정적인 차이(생성 책임 vs 선택 책임)를 설명하고, 그럼에도 두가지가 공유하는 공통목적이 무엇인지..

- 먼저 factory는 생성규칙에 따라서 직접 만든다. 즉, 우리가 주입하고 싶은 객체들의 규칙을 직접 설정하고 주입한다는 것, 그러나 spring에서는 의존성 주입DI 가 호출부로부터 생성 책임을 분리해준다. 그치만 복잡한 주입이나, 기본적인 생성 규칙으로 되지 않을 때는 factory를 직접 만들기도 함  즉, 객체의 생성책임은 factory가, 선택 책임은 spring이..

@Component로 구현 클래스를 등록하는 방식과 @Configure 클래스에서 @Bean으로 생성 규칙을 정의하는 방식의 공통점을 누가 객체를 만들고 관리하는가..

- 둘 모두 구현된 클래스는 스프링 컨테이너가 관리함.. 그러나 @Component는 스프링 컨테이너가 직접 찾아서 bean으로 등록해 가져다가 붙혀주는 방식이고, @bean 방식은 클래스에서 직접 정의해주는 방식이라는 관점이다. 생성 규칙이 복잡할수 있음. 외부 라이브러리 같은 경우에는 component 붙힐 수 없으니..

결제 로직은 if/else 분기로 처리하던 코드를 strategy 구조로 바꾸었을 때, 컨텍스트가 더이상 몰라도 되는 정보가 무엇인지 나열하고, 몰라도 되는 것이 많아 질수록 코드가 안정적이 되는 이유..

- 이건 전략 패턴중 일부인데 if else로 처리하던 코드를 외부로 빼내서 컨텍스트가 안에 어떤 구현체를 사용하는지 몰라도 된다는 것. 몰라도 되는 것이 많아질수록 의존성이 줄어들기 때문에 결합도가 낮아지고 유지보수성이나 확장성이 좋아져

새로운 결제 방식이 추가될 때 if/else 구조에서는 어디를 고쳐야 하고 strategy구조에서 어디를 고쳐야 하는지 비교, 변경 지점 이동이 실무에서 갖는 의미..?

- if else 구조에서는 새로운게 추가 될 때마다 if문을 추가해야하고 삭제될 때마다 지워줘야해.. strategy 구조에서는 구현체 하나만 interface로 추가해주면 되고 그걸 참조하기만 하면돼, 즉 원래는 서비스 코드를 바꾸는걸 변경 지점 이동으로 구현체를 고쳐야 하는 것으로 바꾸는것이야.

strategy pattern은 결국 di와 같은 것 아닌가요 ? 라는 질문에 두 개념의 차이를 각각 한 문장으로 구분해 답하고, strategy 없이 di 만 존재하는 경우와 di 없이 strategy만 존재하는 경우를 각각 예시를 들어서 설명해주세요.

- strategy 패턴은 의존성 주입 없이 서로 다른 구현체를 컨텍스트에서 끼워넣는다는 의미이고, di는 구현체를 끼워넣는게 아닌 맞는 객체를 생성자로 생성하는 것 없이 주입 해 준다는 개념이다.
- strategy 없이 Di만 존재하는 경우는 userService가 userRepository를 new 하지않고 선언만 해서 di가 의존성을 주입해주는 경우일 때,
- di 없이 strategy만 존재하는 경우는 payService에서 kakaopay, tosspay등 구현체를 di 의존성 없이 New로 객체 생성해서 주입하는 경우가 있다.

모든 조건 분기를 strategy pattern으로 바꾸는 것이 왜 바람직 하지 않은가, strategy 패턴이 갖는 실질적인 가치 3가지.

- 만약 경우의 수가 적거나, 불변의 조건들, 추가되거나 수정되지 않을 구현체들은 굳이 strategy pattern으로 바꾸지 않는 것이 낫다. 가독성도 그렇고 테스트 코드도 그렇고 그것의 이점이 더 크기 때문. strategy 패턴이 갖는 실질적인 가치는. 행위를 분리, 유동적인 주입, 변경 영향 예측..

실제 객체 안에 권한 확인, 캐시 조호ㅣ, 로깅 코드를 직접 넣었을 때 생기는 문제점를 변경 이유 라는 표현을 사용해 설명하고 프록시 패턴이 이 문제를 어떻게 해결하는지 설명.

- 실제 객체 안에 다양한 처리를 넣었을 때, 원본이 손상될 가능성이 있다. 즉 관심사를 분리하여 원래 객체를 유지하기 위해서 변하는 조건들과 원래 객체를 분리한다.

프록시는 단순한 호출 전달자가 아니라 실제 객체의 호출 여부까지 제어할 수 있습니다. 캐시가 존재할 때 실제 객체를 호출하지 않고 결과를 반환하는 경우를 예로, 프록시의 "접근 제어"가 갖는 의미를 설명해주세요.

- 프록시 객체가 실체 객체를 호출 당할때 그 호출을 가로 채서, 실제 객체와의 전후 후속 처리의 접근을 제어하고 통제한다.

프록시가 반드시 실제 객체와 동일한 인터페이스를 구현해야 하는 이유를 설명하고, 인터페이스를 공유하지 않으면 클라이언트 입장에서 무엇이 달라지는지 설명해주세요.

- 인터페이스를 같이 공유하지 않거나 실제 객체와 다르면 클라이언트 입장에서는 프록시에 요청을 할수가 없다. 가짜인것을 알아 채기 때문에.

@Transactional이 붙은 메서드를 같은 클래스 안의 다른 메서드에서 this로 호출하면 트랜잭션이 적용되지 않을 수 있습니다. "호출 경로 고정"이라는 프록시 패턴의 전제 조건과 연결해서 왜 이런 일이 생기는지 설명해주세요.

- 프록시는 외부에서 호출 될 때만 작동한다. 내부에서 생성된 클래스들을 호출 할 때는 호출경로가 내부로 고정 되어 있기 때문에 프록시 객체가 생기지 않는다.

MVC의 Controller가 Service의 메서드를 대신 호출해 준다고 해서 프록시라고 볼 수 없는 이유를 "같은 인터페이스를 구현하며 대신 행세하는가"라는 기준으로 설명하고, 필터/인터셉터와 프록시의 차이를 적용 대상(객체 단위 vs 요청 흐름) 관점에서 설명해주세요.

- mvc의 contoller는 service의 메소드를 직접 호출해 진짜 객체에 접근하게 하는 것이고, 프록시는 같은 인터페이스를 구현하며 대신 행세하는 것으로 호출을 가로챈다는 차이가 있다. 프록시는 객체 단위 호출에 적용된다. 어떤 서비스 시작전에 프록시가 가로채는 것 생각. 필터나 인터셉트는 요청 자체를 가로채서 검사하는 방식

서비스 코드가 외부 PG 라이브러리의 메서드 이름과 파라미터 형식(requestPayment, 문자열 금액)에 직접 의존하는 코드는 동작에 문제가 없는데도 변경에 취약하다고 말합니다. 무엇이 어디에 묶여 있어서 문제가 되는지 설명해주세요.

- 외부 라이브러리에 직접적으로 의존을 하는 것은 사용하는 변수명이나 내부 객체가 다르기 때문에 .. 내부 서비스의 로직이 외부 라이브러리의 구현체에 묶여있기 때문에 변경에 취약하다.

Adapter Pattern의 Target, Adaptee, Adapter가 각각 무엇을 알고 있고 무엇을 몰라도 되는지 설명하고, 최종적으로 클라이언트가 몰라도 되는 것이 무엇인지 중심으로 정리해주세요.

- 우선 target은 외부 라이브러리, adaptee가 어떤 메소드를 사용하고 변수를 사용하는지 몰라도됨, adaptee도 마찬가지, adapter는 양쪽을 모두 알고 있을 필요가 있다. 최종적으로 클라이언트가 몰라도 되는것은 adaptee가 무슨 메소드명을 쓰는지.

Target 인터페이스를 정의할 때 외부 라이브러리의 모양이 아니라 "우리 시스템 안쪽의 언어"를 먼저 정해야 하는 이유와, 이 순서가 뒤집혔을 때 발생하는 문제를 설명해주세요.

- Target인터페이스가 곧 주체가 될 인터페이스이기 때문에 외부 라이브러리를 몰라도 된다. 순서가 뒤집히면 target 인터페이스가 외부 라이브러리의 메소드나 구현을 알게 됨

양쪽 코드를 모두 우리가 통제할 수 있는 상황에서 Adapter를 만드는 것이 왜 과한 설계가 될 수 있는지 설명하고, Adapter 안에 도메인 정책이 쌓이기 시작하면 어떤 문제가 생기는지 설명해주세요.

- 양쪽 코드를 모두 우리가 통제 할 수 있으면 Adapter를 만드는 것도 성능상의 문제나 비용의 문제가 있을 수 있다.
- 각각의 도메인 정책이 변경 되기 시작하면 Adapter를 수정해줘야 하는데 그러면 기존 객체의 의존성이 adapter 객체에 강하게 묶이게 된다.

주문 상태 변경 메서드(changeStatus)에 이메일 발송, 감사 로그, 쿠폰 발급 호출이 계속 쌓이면서 비대해졌습니다. 단순히 코드가 길어져서가 아니라 어떤 성격의 책임들이 한곳에 섞여 있었기 때문인지, 근본 원인을 설명해주세요.

- 주문 상태 변경 메서드에서 핵심은 주문 상태 변경 로직인데 그 외 후속 처리 이메일 발송, 감사 로그, 쿠폰 발급이 서비스 로직에 의존하게 되면서 나중에 유지보수성이나 성능에 영향이 있을 수 있음.

Subject가 EmailNotifier나 CouponIssuer 같은 구체 Observer 클래스를 알지 못하게 만드는 것이 왜 중요한지, 새로운 후속 처리가 추가될 때 수정 지점이 어디로 이동하는지와 연결해 설명해주세요.

- 나중에 정책이 추가되거나 바뀌게 되면 수정지점이 서비스ㅜ 코드가 아닌 후속 처리 코드로 바뀌게 된다

"Observer Pattern은 무조건 비동기로 동작한다"는 말이 왜 틀렸는지 설명하고, 기본형(동기) Observer 구조에서 발생할 수 있는 문제 2가지(한 Observer의 예외가 뒤 Observer 통지를 막는 문제, 느린 Observer가 전체 흐름을 지연시키는 문제)와 실무에서의 보완 방향을 설명해주세요.

- 동기로 작동하기도 한다. 만약 transactional로 묶여 있으면 하나의 observer예외가 뒤의 observer 통지를 막고 , 비동기로 처리하면 하나의 observer가 끝날때까지 전체를 기다리게 됨. aysnc 붙여서 해결하자..

Spring의 ApplicationEventPublisher / @EventListener 방식과 직접 구현한 Observer 구조를 비교했을 때 무엇이 같고 무엇이 다른지 설명하고, "Observer Pattern"과 "Spring 이벤트 기능"을 같은 것으로 묶으면 안 되는 이유를 설명해주세요.

- 둘다 옵저버에게 상태 변경을 알려준다는 것은 같지만 기존의 observer방식은 subject가 observer를 알고 있는다는 점. spring의 event는 observer가 누군지 몰라도 된다는 점에서 다르다. 애초에 옵저버 패턴은 서브젝트가 주요 로직이고 spring의 이벤트 기능은 스프링 컨테이너가 관리해주기 때문에 같은 것으로 묶으면 안된다.

Observer 등록(addObserver)만 있으면 되지 해지(removeObserver)는 왜 필요한지, 해지 없이 Observer가 목록에 계속 남아 있을 때 발생하는 문제 2가지를 설명해주세요.

- 옵저버 등록이 있으면 해지도 있어야 한다. 만약에 해지 없이 쌓이기만 한다면 불필요한 알람까지 가게 될 수 있음. (옵저버에게 많은 알람이 갈 수 있다는 점. 성능상의 문제)
