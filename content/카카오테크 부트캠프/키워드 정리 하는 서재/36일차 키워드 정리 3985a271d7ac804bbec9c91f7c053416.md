# Component

1. 화면 전체를 하나의 큰 컴포넌트로 만드는 방식과 의미 있는 단위로 여러 컴포넌트로 나누는 방식을 비교하고, 컴포넌트로 나눴을 때 유지보수·협업·UI 일관성 측면에서 얻는 이점을 캡슐화·재사용성·조합·단방향 흐름 중 두 가지 이상과 연결하여 설명해주세요.
    1. 화면 전체를 하나의 큰 컴포넌트로 만들면 외부에서 상관이 없는 변수를 건들 수도 있고, 여러 컴포넌트로 나누는 방식보다 재사용성과 유지보수성이 안좋을 수 있다.
2. 컴포넌트가 DOM을 직접 조작하지 않고 “현재 데이터 기준의 UI 구조를 선언한다”는 것이 무슨 의미인지 설명하고, 개발자가 DOM을 직접 찾아 수정하는 방식과 비교했을 때 어떤 장점이 있는지 Virtual DOM 동작과 연결하여 설명해주세요.
    1. DOM을 직접 찾아 수정하는 방식은 사용자가 사소한 행동 하나의 변화에도 화면 전체를 렌더링 해야하는 비용이 있다. VDOM을 사용하면 이전과 현재의 바뀐점을 diff, 해서 바뀐 점만 patching 해주면 된다는 이점이 있다.
3. 컴포넌트의 캡슐화란 무엇인지 설명하고, 내부 구현(상태·스타일·로직)을 변경해도 이 컴포넌트를 사용하는 쪽 코드를 수정하지 않아도 되게 하려면 무엇이 유지되어야 하는지 설명해주세요.
    1. 컴포넌트의 캡슐화는 외부에서 내부의 요소를 몰라도 되는 것으로, 내부 구현을 변경해도 컴포넌트쪽에서 수정하지 않으려면 외부 인터페이스,, props state등이 바뀌지 않아야 한다.
4. 단방향 데이터 흐름에서 자식이 값을 바꿔야 할 때 데이터를 직접 수정하지 않고 콜백으로 부모에게 변경을 요청하는 이유를 설명하고, 만약 자식이 부모의 데이터를 직접 고칠 수 있다면 어떤 문제가 생기는지 데이터 추적 관점에서 설명해주세요.
    1. 단방향 데이터 흐름에서 자식이 값을 바꿀 때 부모의 데이터를 직접 고칠 수 있다면 부모는 어떤 자식이 값을 고쳤는지 알 수 없기에 데이터 추적에 용이하지 않는다. 데이터 추적 용이와 디버깅 관점에서 단방향 데이터 흐름이 유리하다. 
5. 이벤트 핸들러에 `onClick={handleClick}`처럼 함수의 참조를 넘기는 것과 `onClick={handleClick()}`처럼 함수를 실행한 결과를 넘기는 것의 차이를 설명하고, 후자가 왜 렌더링 시점에 즉시 실행되어 무한 렌더링 같은 문제로 이어질 수 있는지 설명해주세요.
    1. 함수의 참조를 넘기는 것은 onClick이 일어났을 때 이 함수를 실행 시켜 달라는 요청을 하는 것이고, 후자는 함수를 직접 바로 실행 시키는 것이다. 후자는 함수 즉시 실행 → state 변화 → 다시 렌더링 → 다시 실행… 식으로 무한 렌더링에 빠질 수 있다. 
6. children이 무엇이고 어떻게 자식 컴포넌트로 전달되는지 설명하고, Card 같은 “틀” 컴포넌트를 만들 때 일반 props로 값을 받는 것과 children으로 내용을 받는 것을 어떻게 나눠 쓰는 것이 좋은지 설명해주세요.
    1. children은 자식이 받는 props 값이다, Card 같은 틀 컴포넌트를 만들 때는 일반 props로 받는 것이 좋고 그 내부에서 변할 수 있는 값들은 children으로 받는 것이 낫다.
7. 여러 형제 요소를 함께 반환할 때 Fragment(`<>...</>`)를 사용하는 이유를 설명하고, 의미 없는 `div`로 감쌌을 때와 비교하여 어떤 차이가 있는지 설명해주세요.
    1. Fragment를 사용할 때 아무 의미도 없는 div를 사용하고 싶을 때 사용한다. 
    2. 의미 있는 div로 묶다가는 오류가 생길 수도 있다. 다른 컴포넌트와 충돌

# Props

1. 구조는 같고 데이터만 다른 화면(예: 여러 상품 카드)을 만들 때, 상품마다 별도의 컴포넌트를 만들지 않고 하나의 컴포넌트를 props로 재사용할 수 있는 이유를 함수와 매개변수에 비유하여 설명해주세요.
    1. 똑같은 구조를 공유하는 틀은 하나의 컴포넌트를 만들어 공유하고 그 안의 데이터만 매개변수로 props로 받아서 값을 정의한다.
2. props가 읽기 전용(불변)이어야 하는 이유를 설명하고, 자식 컴포넌트 안에서 props 값을 직접 바꾸려 하면 왜 권장되지 않는지, 값을 바꾸고 싶다면 대신 어떻게 해야 하는지 설명해주세요.
    1. props가 바뀌게 되면 단방향 데이터가 깨져 추적 용이성이 사라진다. 자식 컴포넌트에서 props값을 바꾸고 싶으면 부모에게 이 값을 바꾸고 싶다고 요청하고 할당 받아야 한다.
3. 부모에서 자식으로 값을 넘길 때 문자열은 따옴표로, 숫자·불린·객체·함수는 중괄호로 넘기는 차이를 설명하고, 계산이 필요한 숫자를 따옴표로 넘기면 어떤 문제가 생기는지 설명해주세요.
    1. 숫자와 문자열 구분을 위해서, 중괄호로는 JS의 값을 넣겠다는 것, 따옴표는 문자열이라는 것. 만약 계산이 필요한 숫자를 따옴표로 넘기면 문자열 과 숫자의 합으로 값이 이상해질 수 있다. 
4. props는 부모에서 자식으로만 내려가는데도 자식에서 발생한 이벤트를 부모가 처리할 수 있습니다. 이것이 어떻게 가능한지 함수를 props로 전달하는 패턴과 단방향 데이터 흐름 관점에서 설명해주세요.
    1. 함수의 props를 매개변수 처럼 단방향으로 전달하므로 부모에서도 사용이 가능하다. 어차피 자식이 부모에게 값 변경을 요청 하는 것 이므로.
5. props를 “컴포넌트의 공식 인터페이스”라고 부르는 이유를 설명하고, 어떤 컴포넌트가 받는 props 목록이 왜 그 컴포넌트의 사용 설명서 역할을 하는지 설명해주세요.
    1. props가 결국 부모가 자식에게 내려주는 틀 ( 목록 ) , 기본 뼈대 이므로 설명서 역할을 할 수 있다. 
6. Props Drilling이 무엇이고 어떤 상황에서 문제가 되는지 설명하고, 이를 완화하기 위해 어떤 접근이나 도구가 사용되는지 설명해주세요.
    1. props를 자식에서 부모로 타고타고 가 요청을 하게 되는데 그게 너무 깊어질 경우에 props drilling 이 발생 할 수 있다.  이를 해결하기 위해 상태 관리 도구들이 사용됩니다.

# state

1. State가 무엇인지 정의하고, Props와의 차이를 “누가 값을 소유하고 누가 변경하는가”라는 소유권 관점에서 설명해주세요.
    1. state는 렌더링을 요청하는 상태 값이다. props는 자식이 값을 전달받고 부모가 직접 변경 하는데, state는 컴포넌트가 직접 값을 소유하고 직접 변경 한다.
2. 같은 카운터를 하나는 일반 변수로, 하나는 State로 만들었을 때 버튼을 눌러도 화면에 보이는 숫자가 다르게 동작하는 이유를 설명하고, 일반 변수가 가진 두 가지 한계(변화 미감지 · 렌더링 사이 값 미보존)를 설명해주세요.
    1. 일반 변수로 하면 리액트가 값의 변화를 알아 차리기 어렵다. state로 만들고 setter를 통해 state의 값이 변동 되면 리액트가 변경을 감지하고 리렌더링을 시도한다.
3. State를 `count = count + 1`처럼 직접 대입하지 않고 반드시 setter로 변경해야 하는 이유를, “State 변경은 지금 값을 바꾸는 것이 아니라 다음 렌더링을 요청하는 것”이라는 관점에서 설명해주세요.
    1. state를 직접 바꿔버리면 위와 같이 일반 변수 취급으로 리액트가 값의 변동을 알아차리기 어렵다, state값의 변화는 값 변경이 목적이 아니라 다음 렌더링을 요청하기 위한 상태 변경이다.
4. setState가 비동기적으로 처리된다(배치 업데이트)는 것이 무슨 의미인지 설명하고, 한 이벤트 핸들러 안에서 `setCount(count + 1)`을 두 번 호출했을 때 결과가 2가 아니라 1이 되는 이유와, 2가 되게 하려면 어떻게 해야 하는지 설명해주세요.
    1. setState는 성능을 위해 비동기적으로 쓰기지연 처럼 한번에 렌더링 할 때 업데이트 하므로, 한 이벤트 핸들러 안에서 1씩 2번 증가하고 싶다면 count+1을 2번 호출 하는게 아니라 prev 를 써서 가장 최신의 이전 값을 불러와야 한다. 
5. State의 불변성을 지켜야 하는 이유를 설명하고, 배열에 `push`로 항목을 추가한 뒤 setter에 넘기는 방식이 왜 문제가 되는지 전개 연산자로 새 배열을 만드는 방식과 비교하여 설명해주세요.
    1. 리액트는 참조를 기반으로 값들을 렌더링 하기 때문에 push와 값이 참조 변경이 아닌, 값 수정은 setter에 넘기는 방식과는 차이가 있어 변화가 적용되지 않을 수 있다. 따라서 전개 연산자로 새 배열을 만드는 것이 낫다.
6. State는 최소한으로 관리하는 것이 좋다고 합니다. 다른 값에서 계산해 낼 수 있는 파생 값을 별도의 State로 두지 않는 이유를 설명하고, 원본 목록과 검색어가 있을 때 필터링 결과를 어떻게 다루는 것이 좋은지 설명해주세요.
    1. 동일한 데이터를 여러군데에 두면 값이 바뀌면서 충돌이 일어날 수 있음.. 그래서 원본목록과 검색어는 state에, 계산 할 수 있는 파생 값들은 별도로 관리하는것이 안전하다.
7. 이전 State 값을 기반으로 값을 누적할 때 `setCount(count + 1)` 대신 `setCount(prev => prev + 1)` 콜백 방식을 쓰는 것이 더 안전한 이유를 배치 업데이트와 연결하여 설명해주세요.
    1. 4번과 동일한 답변.
