# 배경

![[Pasted image 20260929164814.png]]

그룹에 속한 물품 목록을 조회하는 API에서 500 오류가 발생했습니다. 데이터를 변경하지 않는 GET 요청이었고, 서비스 메서드에도 `@Transactional(readOnly = true)`가 선언되어 있었습니다. 그런데 데이터베이스는 이 요청을 읽기 전용 트랜잭션에서 실행할 수 없다고 응답했습니다.

원인은 목록을 조회하기 전에 호출한 그룹 검증 메서드에 있었습니다. 그룹 가입·탈퇴의 동시성을 제어하기 위해 설정한 비관적 쓰기 락이 단순 조회 경로에도 적용되고 있었습니다.

이 글에서는 당시 코드와 로그를 바탕으로 오류가 발생한 이유와 수정 방향을 정리합니다. 핵심은 **조회라는 메서드 이름보다 실제 SQL과 트랜잭션의 실행 조건을 함께 살펴보는 것**입니다.

## 물품 목록을 조회하기도 전에 실패한 요청

문제가 발생한 엔드포인트는 `GET /groups/{groupId}/items`였습니다. 서비스는 물품 목록을 조회하기 전에 해당 그룹이 존재하고 삭제되지 않았는지 확인했습니다.

```java
// ItemService.findByGroup() — 관련 부분만 발췌
@Transactional(readOnly = true)
public ItemPageResponse findByGroup(Long userId, Long groupId, String cursor) {
    groupRepository.findByIdAndDeletedAtIsNull(groupId)
            .orElseThrow(() -> new ApiException(GroupErrorCode.GROUP_NOT_FOUND));

    // 물품 목록 조회 및 응답 생성 생략
}
```

서비스 코드만 보면 일반적인 존재 여부 검증입니다. 하지만 호출한 저장소 메서드에는 다음 설정이 있었습니다.

```java
@Lock(LockModeType.PESSIMISTIC_WRITE)
Optional<Group> findByIdAndDeletedAtIsNull(Long groupId);
```

이 메서드는 그룹을 가져오면서 비관적 쓰기 락도 요청합니다. 호출자는 단순히 그룹의 존재 여부만 확인하려 했지만, 저장소 메서드는 동시성 제어까지 수행하고 있었습니다.

## 로그에서 찾은 단서: SELECT 뒤에 붙은 FOR UPDATE

서버 로그에는 `JpaSystemException`과 함께 다음 원인 예외가 기록되어 있었습니다.

```text
Caused by: java.sql.SQLException:
Cannot execute statement in a READ ONLY transaction.
```

![[Pasted image 20260928183240.png]]

같은 로그에 출력된 SQL의 끝에는 `for update of g1_0`가 붙어 있었습니다. 컬럼과 별칭을 생략하면 다음 형태입니다.

```sql
-- 실제 로그의 SQL을 이해하기 쉽게 축약한 예시
SELECT *
FROM `groups`
WHERE group_id = ?
  AND deleted_at IS NULL
FOR UPDATE;
```

`SELECT ... FOR UPDATE`는 결과를 읽으면서 배타적 잠금을 획득하는 **잠금 조회(locking read)**입니다. 일반적인 비잠금 조회와 달리, 같은 레코드에 대한 다른 트랜잭션의 수정이나 충돌하는 잠금 요청을 대기시킬 수 있습니다. 획득한 잠금은 커밋 또는 롤백 시 해제됩니다. 다만 일반적인 MVCC 비잠금 조회까지 모두 차단하는 것은 아닙니다.

즉, 이 요청에는 `UPDATE` 문이 없었지만 **쓰기 잠금을 요청하는 SQL은 있었습니다.** HTTP 메서드가 GET이라는 사실만으로 데이터베이스 작업의 성격을 판단할 수 없는 이유입니다.

# readOnly는 힌트인데, 왜 실제 오류가 발생했을까?

### Spring의 선언과 데이터베이스의 제약은 구분해야 한다

실제로 Spring의 `@Transactional(readOnly = true)`를 뜯어보면, 트랜잭션이 읽기 중심이라는 의도를 하위 트랜잭션 시스템에 전달합니다. Spring API 자체가 모든 쓰기 시도를 반드시 차단한다는 의미는 아닙니다. 이를 해석하지 못하는 트랜잭션 관리자는 힌트를 무시할 수도 있습니다. 

그렇다고 힌트가 항상 무시되는 것도 아닙니다. 실제 효과는 트랜잭션 관리자, JPA 구현체, JDBC 드라이버와 데이터베이스 설정에 따라 달라집니다.

![[Pasted image 20260929165046.png]]

예를 들어 Spring과 Hibernate의 연동에서는 읽기 전용 트랜잭션에 맞춰 flush 모드를 `MANUAL`로 조정하는 최적화가 적용됩니다. 따라서 원래 코드의 `readOnly`는 조회 의도를 표현하고 불필요한 변경 감지 비용을 줄이는 데 의미가 있습니다. 구체적인 엔티티 읽기 전용 처리와 적용 범위는 구현 및 버전에 따라 확인해야 합니다. 

JDBC 계층에서도 읽기 전용 설정을 서버로 전달할 수 있습니다. MySQL Connector/J는 `readOnlyPropagatesToServer` 옵션을 제공하며, 지원되는 서버에서 `Connection.setReadOnly()`의 설정을 서버의 트랜잭션 접근 모드로 전달할지 제어합니다.

이번 로그는 읽기 전용 트랜잭션 제약에 의해 잠금 조회가 거부되었음을 보여줍니다. 다만 로그만으로 드라이버 옵션이나 트랜잭션 관리자의 전체 설정까지 확인할 수는 없으므로, 전달 경로를 세부적으로 확정하려면 실행 환경의 설정도 함께 살펴봐야 합니다.

`예시로는, 기존 테스트 환경에서는 로컬 인메모리 DB H2를 사용했는데, H2에서는 readOnly를 ignore 한다고 합니다.`

### PESSIMISTIC_WRITE는 조회 결과에 쓰기 잠금을 건다

`Lockmode.PESSIMISTIC_WRITE` 를 실제로 파보면, JPA에서 “이 조회가 데이터를 수정한다”는 뜻이 아닙니다. 조회하면서 해당 엔티티의 데이터베이스 행에 배타적 잠금을 요청해, 같은 데이터를 수정하거나 삭제하려는 다른 트랜잭션과의 처리를 직렬화하려는 뜻입니다. 잠금은 트랜잭션이 끝날 때까지 유지됩니다. 

![[Pasted image 20260929171613.png]]

Spring Data JPA에서는 저장소 조회 메서드에 `@Lock`을 붙여 사용할 잠금 모드를 지정할 수 있으며, MySQL InnoDB에서는 이 잠금 조회가 보통 `SELECT ... FOR UPDATE`로 실행됩니다. 

```text
트랜잭션 A: SELECT ... FOR UPDATE → 대상 행의 배타적 잠금 획득
트랜잭션 B: 같은 행을 수정하거나 잠금 조회 → A가 끝날 때까지 대기할 수 있음
트랜잭션 A: COMMIT 또는 ROLLBACK → 잠금 해제
```

여기서 잠기는 범위와 다른 읽기 쿼리가 대기하는지는 데이터베이스와 격리 수준에 따라 달라집니다. InnoDB의 일반적인 비잠금 `SELECT`는 잠금 조회와 다르게 처리되므로, `PESSIMISTIC_WRITE`가 모든 읽기까지 막는다고 이해해서는 안 됩니다. 잠금은 요청한 행을 대상으로 하는 동시성 제어이며, 관련된 다른 행이나 비즈니스 규칙까지 자동으로 보호해 주지는 않습니다.

### FOR UPDATE는 non-locking SELECT가 아니다

MySQL 문서에서 말하는 **non-locking SELECT는 `FOR UPDATE` 같은 잠금 절을 사용하지 않는 조회**입니다. `SELECT`로 시작한다는 이유로 `SELECT ... FOR UPDATE`까지 이 범주에 포함되는 것은 아닙니다.

![[Pasted image 20260929170842.png]]

MySQL의 `READ ONLY` 트랜잭션은 다른 트랜잭션에도 보이는 일반 테이블의 변경이나 잠금을 제한합니다. 세션 전용 임시 테이블에는 예외가 있지만, 이번에 조회한 그룹 테이블은 이에 해당하지 않습니다.

이번 실패 경로는 다음과 같습니다.

```text
물품 목록 조회 서비스: readOnly = true
    → 그룹 존재 여부 확인을 위해 저장소 메서드 호출
    → PESSIMISTIC_WRITE 설정에 따라 FOR UPDATE 실행
    → 읽기 전용 트랜잭션 제약으로 실행 거부
    → 예외가 전파되며 API에서 500 응답
```

트랜잭션과 락 자체가 잘못된 조합은 아닙니다. 문제는 **읽기 전용으로 실행되는 경로에 비관적 쓰기 락을 요구하는 조회가 포함된 것**입니다.

## 기존 락은 왜 필요했을까?

기존 잠금은 그룹 가입과 탈퇴가 동시에 발생할 때의 정합성을 지키기 위한 것이었습니다. 프로젝트에는 그룹원이 0명이 되면 그룹을 논리 삭제하는 정책이 있습니다.

동시성 제어가 없다면 마지막 그룹원이 탈퇴하면서 그룹 삭제를 판단하는 동안, 다른 사용자가 같은 그룹에 가입하는 경쟁 상황이 생길 수 있습니다. 가입과 탈퇴가 모두 같은 그룹 레코드의 잠금을 먼저 획득하고, 상태 검증과 변경을 하나의 트랜잭션에서 수행하면 해당 그룹을 기준으로 처리를 직렬화할 수 있습니다.

따라서 기존 메서드에서 `@Lock`을 일괄 제거하면 이 메서드에 의존하는 변경 경로의 동시성 보장이 약해질 수 있습니다. 반대로 목록 조회 서비스에서 `readOnly = true`만 제거하면 오류를 피할 수 있는 환경에서도 단순한 존재 확인 때문에 가입·탈퇴와 잠금 경합을 일으킬 수 있습니다.

필요한 것은 잠금의 일괄 제거가 아니라, **존재 확인과 상태 변경을 위한 조회의 분리**였습니다.

# 해결: 존재 여부만 필요한 경로를 분리한다

물품 목록 조회에서는 그룹 엔티티의 필드를 사용하지 않았습니다. 그룹이 존재하고 삭제되지 않았는지만 확인하면 되므로, 잠금을 선언하지 않은 존재 확인 메서드를 추가했습니다.

```java
// GroupRepository
boolean existsByIdAndDeletedAtIsNull(Long groupId);
```

서비스에서는 기존 잠금 조회 대신 이 메서드를 호출하도록 변경했습니다.

```java
// ItemService.findByGroup() — 관련 부분만 발췌
@Transactional(readOnly = true)
public ItemPageResponse findByGroup(Long userId, Long groupId, String cursor) {
    if (!groupRepository.existsByIdAndDeletedAtIsNull(groupId)) {
        throw new ApiException(GroupErrorCode.GROUP_NOT_FOUND);
    }

    // 물품 목록 조회 및 응답 생성 생략
}
```

이 변경은 조회 서비스의 읽기 전용 의도를 유지하면서, 존재 확인에 필요하지 않은 비관적 잠금 요청을 제거합니다. 가입·탈퇴 등 상태 변경 경로에서 사용하는 기존 잠금 메서드는 유지했습니다.

`existsBy...`라는 이름이 모든 환경에서 비잠금 실행을 보장하는 것은 아닙니다. 여기서의 핵심은 별도의 잠금 설정 없이 존재 여부를 조회하는 메서드로 호출을 바꿨다는 점입니다. 최종적으로 생성되는 SQL과 격리 수준도 확인해야 합니다.

### 존재 확인이 보장하지 않는 것

`existsBy...`가 `true`를 반환했다고 해서 요청 처리가 끝날 때까지 그룹의 상태가 고정되는 것은 아닙니다. 존재 확인 이후 다른 트랜잭션에서 그룹을 삭제할 수 있으며, 이후 조회가 어떤 상태를 보는지는 격리 수준과 쿼리 구성에 영향을 받습니다.

따라서 이 방식은 목록 조회에 그룹의 동시 변경을 막을 필요가 없다는 요구사항을 전제로 합니다. “목록을 조회하는 동안 그룹이 삭제되면 안 된다”는 요구가 있다면, 별도로 트랜잭션과 잠금 전략을 설계해야 합니다. 존재 확인은 접근 권한 검사도 대체하지 않으므로 그룹원 여부 등의 검증과도 구분해야 합니다.

## 재발 방지를 위해 확인할 항목

이 유형의 문제는 저장소 메서드의 반환값만 검증하는 테스트로 놓치기 쉽습니다. 같은 데이터를 반환하더라도 실제로 잠금을 요청하는지는 다를 수 있기 때문입니다. 다음 항목을 운영과 같은 데이터베이스 종류·버전 및 주요 연결 설정을 사용하는 통합 테스트에서 확인할 필요가 있습니다.

| 확인할 시나리오 | 검증할 내용 |
| --- | --- |
| 활성 그룹의 물품 목록 조회 | 정상 응답과 함께 그룹 존재 확인 SQL에 `FOR UPDATE`가 붙지 않는지 확인 |
| 존재하지 않거나 논리 삭제된 그룹 조회 | 기존 `GROUP_NOT_FOUND` 예외 처리가 유지되는지 확인 |
| 마지막 그룹원의 탈퇴와 신규 가입이 경합 | 양쪽 경로가 같은 그룹의 잠금을 먼저 획득하고, 삭제된 그룹에 가입이 성립하지 않는지 확인 |

위 항목은 회귀 검증을 위한 제안이며, 이 글에서 실행 완료한 테스트 결과를 의미하지는 않습니다. 특히 H2 등 다른 데이터베이스에서 테스트가 통과했다는 사실만으로 운영 MySQL의 읽기 전용 제약과 잠금 동작까지 검증했다고 볼 수는 없습니다.

## 조회 메서드에도 동시성 정책이 담겨 있다

이번 오류는 그룹 가입·탈퇴를 보호하던 잠금 조회를 물품 목록의 존재 확인에도 재사용하면서 발생했습니다. 호출부에서는 단순 조회처럼 보였지만, 저장소 메서드에는 쓰기 경로를 위한 동시성 정책이 함께 들어 있었습니다.

해결에 필요한 변경은 존재 확인 메서드 하나와 호출부 교체였습니다. 작은 변경이 가능했던 이유는 `readOnly`나 락 중 하나를 무조건 없애기보다, 각 경로에서 무엇을 보장해야 하는지 구분했기 때문입니다.

앞으로 잠금이 있는 조회 메서드를 공용으로 사용할 때는 반환 타입뿐 아니라 트랜잭션 조건과 잠금 의도도 함께 검토해야 합니다. 필요하다면 잠금 전용 조회임을 메서드 이름에 드러내고, 해당 메서드를 호출하는 경로 전체를 점검하는 것이 같은 실수를 줄이는 방법입니다.
