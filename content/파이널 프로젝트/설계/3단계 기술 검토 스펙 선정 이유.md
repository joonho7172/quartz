

# JAVA
java를 선정한 이유

###### 선정 기준
1. 타입 안정성과 오류 조기 발견 
	- Python 같은 경우는 동적 언어이고, Java는 정적 언어이기 때문에,
	- python은 직접 실행해봐야 오류를 알 수 있다. (런타임 오류)
	- java는 직접 실행해보기 전에 오류를 알 수 있다. (컴파일 오류)
	런타임 오류 vs 컴파일 오류?
		컴파일 오류는 실행 전에 컴파일러가 오류를 감지하고 실행 자체를 막는다. 
		런타임 오류는 프로그램 실행은 되지만 특정 상황에 JVM이나 OS에서 오류가 터지기 때문에 위험도가 크다.

	따라서 JAVA는 컴파일러가 모든 코드 경로를 정적으로 분석해서, 실행 여부와 무관하게 오류를 찾고 타입이 안맞는 코드의 빌드는 실패 시킨다.
	
2. 실행 최적화 처리 능력
	- 전통적인 Python 은 jit 자체가 활용적이지 않음.
		- Python의 jit은 동적인 타입과 객체 구조를 실행 중 추측해야하기 때문에 jit이 과감하게 최적화하기 어려움.
	- Java의 [[Jit compiler]]는..
		- JAVA의 jit은 정적 타입과 JVM의 강한 런타임 profiling 을 이용해 hot code를 공격적으로 최적화함.

3.  메모리 및 자원 관리의 안정성
	* C언어 같은 경우는 메모리와 자원 관리를 수동적으로 해줘야함.
		* 다 썼으면 malloc이나, free등으로 자원 할당 해제.
	* JAVA는 [[Garbarge Collection]] 로, 자동적으로 자원 할당을 해제한다. 그리고 다양한 알고리즘이 있어서 GC로 인한 애플리케이션 정지 시간을 극도로 줄일 수 있다.
		* C#과 비슷하게, 세대별 GC, Java와 유사..
		* Python은 참조 카운팅을 통해서 자원을 정리하기 때문에, 모든 객체 참조가 일어날 때마다 카운트를 증감 시키는 오버헤드가 있다. 

4.  장기 운영과 장애 분석 편의성
	* JAVA는 운영 중인 서비스에서 문제가 생겼을 때 원인을 진단하는 표준화된 방법이 매우 잘 갖춰져 있다.
		* Thread Dump - 스레드가 멈췄을 때, 실행 중인 모든 스레드의 현재 상태를 그대로 캡쳐 가능.
		* Heap Dump - 메모리 누수 의심될 때, 힙 메모리의 스냅샷을 통째로 가져와 어떤 객체가 참조를 받아 GC 처리가 안되는지 알 수 있음. 
		* GC Viewer - GC 로그를 참고해서 메모리 회수가 얼마나 자주/ 오래 일어나는지 정량적으로 추적 할 수 있다.
	* Python은 런타임 이후에야 타입이 결정되므로, 추적 할 때 훨씬 제한적인 정보만 얻을 수 있다. 

객체 지향 이란? [[OOP]]
프로그램을 객체 단위로 나뉘어서 서로의 상호작용으로 서술 하는 방법.
왜 이걸 지켜야 할까?
소프트 웨어는 계속 변경되는데 그 변경이 시스템 전체로 퍼지지 않고 국소적으로 막기 위해서.

객체지향의 특성
다형성, 캡슐화, 상속, 추상화
1. 다형성 : 같은 역할을 여러 구현으로 처리, (구현체 교체, 확장성 증가)
2. 캡슐화 : 객체 내부 상태를 숨김 (잘못된 직접 수정을 방지하고, 변경 영향을 최소화)
3. 추상화 : 중요한 역할만 드러냄 (복잡성이 감소하고 구현과 사용을 분리)
4. 상속 : 기존 기능을 물려 받음 (코드 재사용, 계층 표현)


### JAVA 버전 : 25

JDK는 21부터 공식적으로 virtual thread를 지원한다.

다만.. 21-23까지는 synronized 블록에서 virtual thread를 사용할 경우에, JVM 모니터락이 걸려서 virtual thread가 carrier thread에서부터 떼어내지지 못했다.. 그래서 어플리케이션 단계의 락인 reentrant로 바꿔서 virtual thread를 풀어줬다면, 24부터는 공식적으로 JVM에서 virtual thread를 떼어낼 수 있게 되면서 pinned 문제가 개선되었다.
##### 21이 아닌 25를 선택하는 이유
1. JDK24에서 실험적으로 도입했던 Compact Object Headers, 25에서 정식 기능이 되었다.
	1. 객체 헤더 크기를 128비트에서 64비트로 줄여, 힙 효율과, CPU 성능을 개선.
2. JDK25가 더 늦게 나온 만큼 프리미어 지원이 더 늦춰짐.
3. [[Virtual thread]] 에서 pinning 진단 개선 등 안정성이 계속 다듬어짐

# Spring 을 쓰는 이유
		spring이란.. 자바 언어를 기반으로 웹 어플리케이션을 쉽게 개발 할 수 있도록 도와주는 오픈소스 Framework 이다.. 

왜 쓰나요? - IoC와 DI를 통해서 객체간 결합도를 낮추고, 트랜잭션 보안 웹 MVC 데이터 접근 같은 인프라를 표준화해서 비즈니스 로직에 집중 할 수 있게 해주기 때문에

1. POJO기반의 구성
	1. 코드를 개발할 때, 개발자가 특정한 라이브러리나 컨테이너의 기술에 종속적이지 않음을 의미한다.
	2. Java 코드를 이용해서 객체를 구성하는 방식 그대로 스프링에서 사용 가능!
	3. 덕분에 유연한 테스트와 높은 생산성을 할 수 있음.

2. [[DI]] 를 통한 객체 관계 구성
	1. 의존성 주입은 [[IoC]] 가 일어나는 것을 전제로 스프링 내부의 객체들 간의 관계를 관리 할 때 사용한다.
	2. 생성자를 따로 만들고 참조하게 하는것을 스프링 컨테이너가 대신 해주는 것임.

	[[DI]] 에는 3가지 방식이 있는데,
	1. 생성자 주입
		1. @Autowired, @RequiredArgsConstructor 등으로 자유롭게 생성자 주입이 가능하다. final 이어도 상관없다. 스프링 컨테이너의 reflection 때문에 주입 생성자 주입 가능하다.
	2. setter 주입
		1. 무분별한 setter는 객체 지향 원칙의 캡슐화를 깨트릴 수 있기 때문에 지향하지는 않는다.
	3. 필드 주입
		1. 필드 주입은 접근 제어자 final 이 불가능하다.
		2. test에도 spring container없이 필드 주입은 안되기 때문에 test에서도 불편하다. 
	

4. [[IoC]] 제어 역전.
	1. 원래는 내 코드 -> 객체를 생성 -> 객체를 연결 -> 객체를 관리 였는데,
	2. [[IoC]] 에서는 Spring Container -> 객체 생성 -> 객체 연결 -> 객체 생명 주기 관리 -> 내 코드에서는 "내가 무엇이 필요한지만 선언"
	3. 즉, 제어권이 개발자 코드에서 프레임워크./컨테이너로 넘어간다.

		장점: 객체 생성 코드가 사라짐
		```java
		PaymentRepository repository = new PaymentRepository(); 
		PaymentService service = new PaymentService(repository);
		OrderService orderservice = new OrderService(service);
		```
		장점2 : 의존 관계 교체가 쉽다.
	 ```java
		class kakaopayment implements PayService{};
	 ```
	등, 카카오페이와 결제기능의 구현체가 있을 때, [[IoC]] 가 없을 때는, orderService가 어떤 구현체를 받는지 알아야 했던 반면, Spring Container 가 대신 객체 관리를 해주면서 어떤 구현체가 파라미터로 들어오는지 상관이 없어진다.








# DB 선정 (mySQL)

관계형 데이터베이스란? 
데이터를 테이블 형태로 저장하고, 테이블끼리 관계를 맺어 관리하는 데이터 베이스.
지금 서비스에서는 회원과 게시글, 그룹, 물품 교환 요청, 채팅 등 여러 관계가 서로를 의존하고 있기 때문에 관계형 데이터 베이스가 어울림.

장점 : 
1. 데이터의 정합성과 무결성을 강하게 보장하기 좋다.
	1. foreign key,  references로 관계를 강하게 묶을 수 있다.
2. 트랜잭션의 강점
	1. 작업 단위로 묶고 commit 처리와 실패시 rollback이 가능하다.
	2. ACID와 연결됨.
		1. 원자성, 일관성, 독립성, 영속성
3. SQL이라는 표준화된 질의 방식이 있다.
	1. 여러 테이블을 JOIN하고 정렬하는 복잡한 질의를 비교적 편하게 할 수 있음.

단점 :
1. 유연한 스키마 구조 변경이 되지 않는다.
	1. 이미 정해진 스키마 그대로...
2. JOIN이 많아지면 성능 부담이 커진다.
	1. 여러 테이블을 JOIN 할수록 쿼리 최적화가 중요해짐.
3. 수평 확장도 까다롭다.
	1. scale OUt이나 샤딩에서, 관계나 JOIN, 트랜잭션 때문에 복잡해짐



# Redis

인메모리 DB로 사용하는 이유 : 인메모리 DB란 말 그대로 메모리에 데이터를 저장하는 것.
사용하면 이점 : 다른 DB서버로 거치지 않고 메모리에서 꺼내기 때문에 속도가 매우 빠르다.
사용하면 단점 : 그만큼 영구적이지 않다. 서버가 꺼지면 사라짐.

지금 시나리오에서 어디에 사용 할 것인가?
1. 위치 인증 후, 그룹 가입 할 때 발급하는 위치 인증 토큰을 redis에 저장..
	1. TTL 지정하고, 만료와 재사용, 다른 그룹으로의 토큰 전용을 방지한다.

2. refresh token은 영구적으로 저장될 필요가 없으므로 redis 에 저장
