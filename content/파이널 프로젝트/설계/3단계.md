## 1. 타입 안정성과 오류 조기 발견

Python은 동적 타입 언어이고 Java는 정적 타입 언어다. Java는 변수와 메서드의 타입을 컴파일 시점에 확인하기 때문에 타입이 맞지 않거나 존재하지 않는 메서드를 호출하면 빌드 단계에서 오류가 발생한다.

다만 컴파일러가 모든 오류를 찾아주는 것은 아니다.

| 컴파일 시점에 확인할 수 있는 오류 | 실행 중 발생할 수 있는 오류 |
|---|---|
| 타입 불일치 | NullPointerException |
| 문법 오류 | DB 연결 실패 |
| 존재하지 않는 메서드 호출 | 네트워크 오류 |
| 일부 변수 초기화 오류 | 논리 오류와 동시성 오류 |

따라서 “Java는 실행 전에 모든 오류를 찾는다”라고 하기보다는 다음과 같이 설명하는 것이 정확하다.

> Java는 정적 타입 검사를 통해 일부 오류를 실행 전에 발견할 수 있지만, 런타임 오류와 논리 오류까지 모두 제거하는 것은 아니다.

Python도 mypy나 pyright 같은 정적 검사 도구를 사용하면 일부 타입 오류를 실행 전에 확인할 수 있다. 따라서 “Python은 직접 실행해봐야만 오류를 알 수 있다”라는 표현은 수정할 필요가 있다.

## 2. 실행 최적화 처리 능력

Java의 HotSpot JVM은 실행 중 메서드 호출 횟수와 코드 실행 정보를 수집한다. 자주 실행되는 코드는 JIT 컴파일러가 네이티브 코드로 변환하고, 인라이닝이나 분기 최적화 등을 적용한다.

Python에 JIT가 전혀 없는 것은 아니다. PyPy는 JIT를 지원하고, 최근 CPython에도 실험적인 JIT 기능이 제공된다. 다만 일반적인 Java HotSpot 환경과 동일한 방식으로 동작하는 것은 아니므로 “Java에는 JIT가 있고 Python에는 없다”라고 비교하면 부정확하다.

Java의 장점은 정적 타입만이 아니라 JVM의 런타임 프로파일링과 JIT 최적화가 오랫동안 발전해 왔다는 점에 있다. 단, JIT는 워밍업 시간이 필요할 수 있고 모든 작업에서 성능 향상을 보장하지는 않는다.

## 3. 메모리 및 자원 관리의 안정성

C는 일반적으로 개발자가 메모리를 직접 할당하고 해제해야 한다. 반면 Java는 더 이상 참조되지 않는 Java 힙 객체를 Garbage Collector가 자동으로 회수한다.

하지만 GC가 파일이나 소켓 같은 외부 자원까지 자동으로 닫아주는 것은 아니다.

| 자원 | 관리 방법 |
|---|---|
| Java 힙 객체 | Garbage Collector가 회수 |
| 파일 | close 또는 try-with-resources 사용 |
| 소켓 | 명시적으로 종료 |
| DB 커넥션 | 커넥션 풀 정책에 맞게 반환 |
| 네이티브 메모리 | 별도 해제 정책 필요 |

따라서 정확한 표현은 다음과 같다.

> Java는 일반적인 객체 메모리를 자동으로 관리하지만, 파일·소켓·DB 연결과 같은 외부 자원은 별도로 정리해야 한다.

또한 Python도 하나의 방식으로만 메모리를 관리하지 않는다. CPython은 참조 카운팅을 기본으로 사용하고, 참조 순환으로 남는 객체를 처리하기 위해 순환 참조 GC도 사용한다.

## 4. 장기 운영과 장애 분석 편의성

Java는 운영 중인 서비스를 분석하기 위한 JDK 도구가 잘 갖춰져 있다.

| 도구 | 용도 |
|---|---|
| Thread Dump | 스레드의 상태, 스택, 락 대기 상황 확인 |
| Heap Dump | JVM 힙의 객체와 참조 관계 분석 |
| GC 로그 | GC 발생 횟수와 소요 시간, 회수량 확인 |
| JFR | CPU, 메모리, 락, I/O, 예외 등 JVM 이벤트 기록 |
| jcmd | 스레드 덤프와 JVM 상태 확인 |

GC Viewer는 JDK에 포함된 표준 도구가 아니라 GC 로그를 분석하는 외부 도구다. 문서에서는 jcmd, JFR, JDK Mission Control을 중심으로 설명하는 편이 정확하다.

Python에도 faulthandler, tracemalloc, cProfile 같은 진단 도구가 있다. 따라서 Java만 장애 분석이 가능하다고 하기보다는, Java는 JVM 수준의 표준 진단 도구를 함께 제공한다는 점을 장점으로 보는 것이 적절하다.

## 5. Java 선정 결론

Python은 빠른 개발과 데이터·AI 활용에 강점이 있고, C는 하드웨어 제어와 낮은 수준의 최적화에 강점이 있다. C#도 CLR, JIT, GC를 제공하므로 Java와 비슷한 기술적 장점을 가지고 있다.

그럼에도 본 프로젝트는 장기간 운영되는 웹 백엔드로서 타입 안정성, 동시 요청 처리, 메모리 관리, 운영 도구, 유지보수성을 중요하게 고려한다. Spring Boot와 JVM 생태계를 활용할 수 있다는 점까지 종합하면 Java를 선택하는 것이 합리적이다.

이는 Java가 다른 언어보다 항상 우수하다는 뜻이 아니라, 현재 프로젝트의 요구사항과 개발 환경에 가장 잘 맞는다는 의미다.

# 객체지향 프로그래밍

객체지향 프로그래밍은 프로그램을 객체 단위로 나누고, 객체 사이의 상호작용으로 동작을 표현하는 방식이다.

소프트웨어는 계속 변경되기 때문에 변경 사항이 시스템 전체로 퍼지지 않도록 객체의 책임과 의존 관계를 적절하게 나누는 것이 중요하다. 다만 객체지향을 사용한다고 변경 범위가 자동으로 줄어드는 것은 아니며, 낮은 결합도와 높은 응집도가 함께 필요하다.

| 개념 | 의미 | 효과 |
|---|---|---|
| 캡슐화 | 객체 내부 상태를 직접 수정하지 못하게 하고 정해진 방법으로 접근 | 잘못된 상태 변경 방지 |
| 추상화 | 사용에 필요한 역할만 드러내고 구현을 숨김 | 사용 코드와 구현 코드 분리 |
| 다형성 | 같은 역할을 여러 구현체가 수행 | 구현체 교체와 확장 용이 |
| 상속 | 기존 타입을 기반으로 하위 타입을 정의 | is-a 관계 표현과 코드 재사용 |

상속은 단순히 코드를 재사용하기 위한 기능이라기보다 상위 타입과 하위 타입의 관계를 표현하는 기능이다. 코드 재사용만을 목적으로 한다면 상속보다 합성이 더 적절한 경우가 많다.

# Java 버전: 25

JDK 21에서 Virtual Thread가 정식 기능으로 추가되었다. Virtual Thread는 CPU 작업을 빠르게 만드는 기능이 아니라, DB나 외부 API처럼 I/O를 기다리는 작업을 많이 동시에 처리하기 위한 기능이다.

JDK 21부터 23까지는 synchronized 내부에서 블로킹이 발생할 때 Virtual Thread가 carrier thread에 고정되는 pinning 문제가 있었다. JDK 24에서는 synchronized로 인한 pinning 문제가 개선되었다. 다만 네이티브 메서드나 Foreign Function 호출로 인한 pinning 가능성은 여전히 확인해야 한다.

따라서 Virtual Thread를 사용한다는 이유만으로 모든 synchronized를 ReentrantLock으로 바꿀 필요는 없다.

Compact Object Headers는 JDK 24에서 실험적으로 도입되었고 JDK 25에서 제품 기능으로 변경되었다. 64비트 환경에서 객체 헤더 크기를 기존 96비트 또는 128비트에서 64비트로 줄여 힙 사용량과 데이터 지역성을 개선할 수 있다. 실제 성능 향상 여부는 애플리케이션의 객체 사용 패턴에 따라 다르므로 부하 테스트가 필요하다.

Java 25를 선택하는 이유는 다음과 같이 정리할 수 있다.

1. Java 21 이후의 Virtual Thread와 JVM 기능을 사용할 수 있다.
2. Java 25는 LTS 버전이므로 장기 운영에 적합하다.
3. JDK 24에서 실험된 Compact Object Headers가 JDK 25에서 제품 기능이 되었다.
4. Java 21보다 최신 기능과 개선 사항을 사용할 수 있다.

※ 현재 저장소의 build.gradle은 Java 26으로 설정되어 있다. 이 문서를 Java 25 기준으로 사용할 경우 실제 Gradle 설정도 함께 맞춰야 한다.

# Spring을 사용하는 이유

Spring은 Java 애플리케이션 개발을 돕는 오픈소스 프레임워크이고, Spring Boot는 Spring 애플리케이션의 설정과 실행을 단순하게 해준다.

Spring을 사용하는 가장 큰 이유는 IoC와 DI를 통해 객체 간 결합도를 낮추고, 웹 MVC, 트랜잭션, 보안, 데이터 접근과 같은 공통 기능을 일관된 방식으로 사용할 수 있기 때문이다.

## 1. POJO 기반 구성

POJO는 특정 프레임워크의 클래스를 반드시 상속하거나 특정 인터페이스를 구현해야만 동작하는 객체가 아닌 일반적인 Java 객체를 의미한다.

Spring은 애플리케이션 객체를 일반적인 Java 클래스 형태로 작성할 수 있도록 지원한다. 다만 Service나 Repository 같은 어노테이션을 사용하면 Spring과의 의존성이 생길 수 있으므로 “Spring에 전혀 종속되지 않는다”라고 표현하는 것은 정확하지 않다.

## 2. DI를 통한 객체 관계 구성

의존성 주입은 객체가 필요한 의존성을 직접 생성하지 않고 외부에서 전달받는 방식이다. Spring 컨테이너는 Bean을 생성하면서 생성자, Setter 또는 필드에 필요한 객체를 주입한다.

| 주입 방식 | 특징 | 사용 판단 |
|---|---|---|
| 생성자 주입 | 필수 의존성을 표현하고 final 사용 가능 | 기본적으로 권장 |
| Setter 주입 | 선택적이거나 재설정 가능한 의존성에 적합 | 필요한 경우 사용 |
| 필드 주입 | Reflection으로 주입되며 테스트와 불변 객체 구성에 불리 | 일반적으로 지양 |

생성자 주입에서 final을 사용할 수 있는 이유는 생성자에서 값을 할당하기 때문이다. Spring의 Reflection이 final을 가능하게 만드는 것은 아니다.

RequiredArgsConstructor는 Spring 어노테이션이 아니라 Lombok이 생성자를 만들어주는 기능이다. 생성자가 하나뿐인 경우에는 일반적으로 Autowired를 붙이지 않아도 Spring이 해당 생성자를 사용한다.

## 3. IoC, 제어의 역전

Spring을 사용하지 않는다면 객체 생성과 의존 관계 연결을 개발자 코드에서 직접 처리한다.

```java
PaymentService paymentService = new KakaoPaymentService();
OrderService orderService = new OrderService(paymentService);
```

Spring을 사용하면 Spring 컨테이너가 Bean을 생성하고 의존 관계를 연결한다. 개발자 코드는 어떤 객체가 필요한지만 생성자를 통해 선언한다.

이때 OrderService는 KakaoPaymentService라는 구체 클래스가 아니라 PaymentService라는 역할에 의존한다. 실제 구현체의 선택은 Spring 설정, Primary, Qualifier, 프로파일 등에 의해 결정된다.

## 4. AOP와 트랜잭션

Spring의 Transactional은 AOP 프록시를 통해 동작한다.

1. 외부 코드가 Spring Bean의 프록시를 호출한다.
2. 프록시가 트랜잭션을 시작한다.
3. 실제 메서드를 실행한다.
4. 정상 종료 시 커밋하고 설정된 예외가 발생하면 롤백한다.

같은 클래스 내부에서 자기 메서드를 호출하는 self-invocation은 프록시를 거치지 않아 Transactional이 적용되지 않을 수 있다. 또한 메서드 안에서 새 스레드나 Virtual Thread를 만들면 기존 트랜잭션이 자동으로 전파되지 않는다.

# DB 선정: MySQL

## 관계형 데이터베이스를 사용하는 이유

관계형 데이터베이스는 데이터를 테이블 형태로 저장하고, 기본 키와 외래 키 등의 제약 조건으로 테이블 사이의 관계를 관리한다.

현재 서비스의 회원, 게시글, 그룹, 물품 교환 요청, 채팅은 서로 연관되어 있다. 또한 교환 상태 변경처럼 여러 데이터를 하나의 작업 단위로 처리해야 하는 경우가 있기 때문에 관계형 데이터베이스가 적합하다.

## MySQL의 장점

1. 데이터 무결성
   - 기본 키, 유니크, 외래 키, 체크 제약 조건을 사용할 수 있다.
   - 외래 키를 통해 존재하지 않는 회원이나 그룹을 참조하는 데이터를 제한할 수 있다.

2. 트랜잭션
   - InnoDB에서는 여러 작업을 하나의 트랜잭션으로 묶을 수 있다.
   - 작업이 모두 성공하면 commit하고, 문제가 발생하면 rollback할 수 있다.
   - InnoDB는 ACID 특성과 MVCC, 행 단위 잠금을 지원한다.

3. SQL과 JOIN
   - 여러 테이블을 JOIN하여 관련 데이터를 조회할 수 있다.
   - 정렬, 집계, 서브쿼리 등 복잡한 조회를 SQL로 표현할 수 있다.
   - JOIN이 많다고 항상 느려지는 것은 아니며 인덱스와 실행 계획의 영향을 크게 받는다.

## MySQL의 한계

1. 스키마 변경에 관리가 필요하다.
   - 스키마 변경 자체가 불가능한 것은 아니다.
   - 운영 중인 데이터와의 호환성을 고려해 마이그레이션해야 한다.

2. 수평 확장이 복잡해질 수 있다.
   - 복제, 읽기 전용 Replica, 파티셔닝, 샤딩을 사용할 수 있다.
   - 다만 샤딩 후에는 여러 데이터베이스에 걸친 JOIN과 트랜잭션 관리가 어려워진다.

3. 트랜잭션과 무결성 제약 조건에도 비용이 있다.
   - 데이터 안정성을 높이는 대신 잠금과 로그 기록에 따른 처리 비용이 발생할 수 있다.

## H2의 역할

H2는 Java로 작성된 SQL 관계형 데이터베이스다. 임베디드 모드와 인메모리 모드를 지원하기 때문에 로컬 개발과 테스트에 사용하기 좋다.

현재 프로젝트의 기본 설정은 H2 인메모리 DB이며, 애플리케이션이 종료되면 데이터가 사라진다. 또한 현재 ddl-auto 기본값이 create-drop이므로 애플리케이션 시작 시 스키마를 만들고 종료 시 삭제한다.

H2는 MySQL과 문법, 데이터 타입, 정렬 방식, 락 동작이 다를 수 있다. 운영 DB를 MySQL로 사용할 경우 MySQL 환경에서도 통합 테스트를 진행하는 것이 좋다.

H2는 Redis와 같은 종류의 기술이 아니다.

| 기술 | 역할 |
|---|---|
| H2 | SQL을 사용하는 관계형 데이터베이스. 로컬·테스트에 적합 |
| Redis | 메모리 기반 자료구조 서버. 캐시·TTL·세션 등에 적합 |

# Redis

## Redis를 사용하는 이유

Redis는 메모리 기반의 자료구조 서버다. 메모리에서 데이터를 처리하기 때문에 단순한 조회와 갱신이 빠르고, TTL·카운터·캐시와 같은 기능을 제공한다.

다만 Redis가 항상 휘발성인 것은 아니다. RDB 스냅샷과 AOF 로그 방식으로 데이터를 디스크에 저장할 수 있으며, persistence를 사용하지 않는 경우에는 장애나 재시작 시 데이터가 사라질 수 있다. persistence를 사용하더라도 장애 직전의 최신 데이터가 손실될 가능성은 설정에 따라 남아 있다.

## 사용 시나리오

### 1. 위치 인증 토큰

위치 인증 후 그룹 가입 과정에서 발급하는 토큰을 Redis에 저장할 수 있다.

- 토큰에 TTL을 설정해 일정 시간이 지나면 자동 만료
- 토큰과 사용자·그룹 정보를 연결
- 다른 그룹에서 사용할 수 없도록 그룹 정보 검증
- 사용이 끝난 토큰은 원자적으로 삭제해 재사용 방지

토큰을 확인한 뒤 삭제하는 과정은 GETDEL이나 Lua Script 등을 사용해 경쟁 상태가 생기지 않도록 처리해야 한다.

### 2. Refresh Token

Refresh Token은 만료 시간과 회전 정책이 있기 때문에 Redis에 저장할 수 있다. 서버에서 강제 로그아웃이나 토큰 회수를 지원하려면 토큰 또는 세션 정보를 서버 측에 저장해야 한다.

다만 Redis 장애가 발생했을 때 사용자를 모두 로그아웃시켜도 되는지 먼저 결정해야 한다. 데이터 손실이 허용되지 않거나 감사 기록이 필요하다면 MySQL 등 영속 저장소와의 역할을 구분해야 한다.

### 3. 캐시

상품 상세나 채팅 목록처럼 조회가 많고 변경 빈도가 상대적으로 낮은 데이터는 Redis에 캐시할 수 있다. 이 경우 원본 데이터는 MySQL에 저장하고, 데이터 변경 시 캐시를 삭제하거나 갱신해야 한다.

# Kafka

## Kafka란?

Kafka는 분산 이벤트 스트리밍 플랫폼이다. 메시지 브로커처럼 사용할 수 있지만, 단순한 메시지 큐라고만 설명하면 Kafka의 로그 보존과 재처리 기능이 빠진다.

| 개념 | 의미 |
|---|---|
| Event 또는 Record | 전달되는 하나의 데이터 |
| Topic | 이벤트를 저장하는 논리적인 스트림 |
| Partition | Topic을 나눈 순서가 있는 로그 |
| Producer | 이벤트를 Topic에 기록하는 애플리케이션 |
| Consumer | 이벤트를 읽고 처리하는 애플리케이션 |
| Consumer Group | 여러 Consumer가 Partition을 나누어 처리하는 단위 |
| Offset | Consumer가 어디까지 읽었는지 나타내는 위치 |

Producer가 이벤트를 Topic에 기록하면 Kafka는 이를 Partition에 저장한다. 같은 Partition 안에서는 순서가 보장되지만, 여러 Partition 전체의 순서가 항상 보장되는 것은 아니다.

Consumer가 이벤트를 읽었다고 해서 이벤트가 바로 삭제되는 것도 아니다. Topic의 보존 정책에 따라 일정 기간 저장되므로 Offset을 이동해 과거 이벤트를 다시 처리할 수 있다.

## Kafka와 일반적인 메시지 큐

| 기준 | Kafka | 일반적인 작업 큐 |
|---|---|---|
| 핵심 모델 | 보존되는 이벤트 로그 | 처리 대기 중인 메시지 |
| 소비 후 데이터 | 보존 기간까지 남음 | ACK 후 삭제되는 방식이 일반적 |
| 재처리 | Offset 이동으로 가능 | 제품과 설정에 따라 다름 |
| 확장 단위 | Partition | Queue와 Consumer |
| 적합한 용도 | 이벤트 스트리밍, 여러 Consumer, 대규모 비동기 처리 | 단순 작업 분배와 비동기 실행 |

## 사용 시나리오

교환 상태가 완료되었을 때 교환 완료 이벤트를 발행하고, 여러 Consumer가 후속 작업을 처리할 수 있다.

```text
ExchangeCompleted
 ├─ 알림 Consumer: 시스템 메시지 생성
 ├─ 캐시 Consumer: 상품·채팅 목록 캐시 삭제
 └─ 추천 Consumer: 완료 거래를 추천 데이터에 반영
```

DB 상태 변경과 Kafka 발행을 별도로 처리하면 DB 변경만 성공하거나 Kafka 발행만 성공하는 문제가 생길 수 있다. 따라서 운영 환경에서는 MySQL 트랜잭션 안에 Outbox 이벤트를 저장한 뒤 별도의 Publisher가 Kafka에 발행하는 방식을 고려할 수 있다.

Consumer는 같은 이벤트를 두 번 받을 수 있다는 전제로 구현하고, 이벤트 ID를 이용해 중복 처리를 방지해야 한다. 실패한 이벤트를 재시도할 수 있도록 재시도 정책과 Dead Letter Topic도 함께 고려해야 한다.

단순한 후속 메서드 하나를 비동기로 실행하는 정도라면 Kafka가 과할 수 있다. 여러 Consumer가 필요하거나 이벤트 재처리, 높은 처리량, 서비스 간 결합도 감소가 필요할 때 Kafka를 도입하는 것이 적절하다.

# 추가로 정리할 내용

## AOP와 트랜잭션

- Transactional은 Spring AOP 프록시를 통해 동작한다.
- 같은 클래스 내부의 메서드 호출은 프록시를 거치지 않을 수 있다.
- 새 스레드나 Virtual Thread에는 기존 트랜잭션이 자동 전파되지 않는다.
- DB 트랜잭션만으로 Kafka 발행과 Redis 저장까지 하나의 원자 작업이 되는 것은 아니다.

## 공유 잠금과 배타 잠금

- 공유 잠금은 여러 트랜잭션이 동시에 획득할 수 있는 읽기 잠금이다.
- 배타 잠금은 변경을 위한 잠금이며 다른 트랜잭션의 읽기·쓰기 잠금과 충돌한다.
- InnoDB의 일반 SELECT는 MVCC를 이용해 잠금 없이 읽을 수 있다.
- 명시적인 잠금 읽기에는 FOR SHARE와 FOR UPDATE를 사용한다.

## 데드락

데드락은 트랜잭션들이 서로가 가진 잠금이 풀리기를 기다리는 상태다. 여러 테이블을 항상 같은 순서로 잠그고, 트랜잭션을 짧게 유지하며, 데드락 발생 시 한 트랜잭션을 롤백하고 재시도하는 방식으로 대응한다.

## 직렬화

직렬화는 객체를 네트워크 전송이나 저장이 가능한 형태로 바꾸는 과정이다.

- HTTP API: DTO를 JSON으로 변환
- Redis: 객체를 문자열이나 JSON으로 변환
- Kafka: 이벤트를 byte 데이터로 변환
- 역직렬화: 전송·저장된 데이터를 다시 객체로 변환

Java 기본 직렬화는 외부 API나 장기 저장 포맷으로 무분별하게 사용하지 않는 것이 좋다. 일반적으로 API와 이벤트에는 JSON, Avro, Protobuf처럼 형식과 스키마가 명확한 방식을 사용한다.

## 외래 키

외래 키는 자식 테이블의 값이 부모 테이블에 실제로 존재하는지 확인하는 제약 조건이다.

- RESTRICT: 참조 중인 부모 삭제 금지
- CASCADE: 부모 삭제 시 자식도 삭제
- SET NULL: 부모 삭제 시 외래 키를 NULL로 변경
- NO ACTION: MySQL InnoDB에서는 사실상 RESTRICT처럼 동작

회원 삭제 시 채팅과 거래 기록까지 함께 삭제되는 것이 맞는지 확인한 뒤 CASCADE를 사용해야 한다.
