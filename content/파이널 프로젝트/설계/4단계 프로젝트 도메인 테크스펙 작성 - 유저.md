### 회원가입/ 로그인 API

- **API 명세:**
    
    - `POST /api/auth/oauth`
    - API 문서 링크: [API Docs 링크 - 회원가입]
- **권한:**
    - 비로그인 사용자 허용 (`PermitAll`)

- **Request Header:**
    

```
Content-Type: application/json
Accept: application/json
```

- **Request Body:**

```
{
  "provider": "KAKAO",
  "authorizationCode": "카카오에서 전달받은 인가 코드"
}
```

- **구현 상세:**

	* 요청 (Request Body) : 기업으로 부터 제공받은 사용자의 인가코드, 회원가입 정보를 제공한 기업의 이름과 state 
		* 서버가 예측할 수 없는 일회성 state (SecureRandom)으로 값을 생성하고 서버 callback의 URL에 Query parameter로 넣습니다.
		* 일회성 state이므로, redis에 저장 후 ttl을 5분으로 잡습니다. 브라우저 세션 ID와 provider를 함게 저장합니다
		* 서버가 로그인 요청 URL에 state를 포함하고, callback URL의 state를 비교해 검증합니다.
	    
    1. `provider`와 `authorizationCode`의 유효성을 검증함.
    2. 카카오 OAuth API에 인가 코드를 전달해 카카오 Access Token을 발급받습니다.
    3. 서버가 받은 카카오 Access Token으로, 카카오 사용자 정보 API를 호출해 `provider_user_Id`, 닉네임, 프로필 이미지를 가져옵니다. (프론트 응답으로 하지 않고 서버에서 처리)
    4. `provider`와 `providerId`로 기존 회원을 조회합니다.
    5. 기존 회원이 없으면 `users` 테이블에 회원 정보를 저장합니다.
    6. 서비스용 Access Token을 발급합니다. (카카오 Access Token이 아닌, 우리 서버 API 호출을 위한 Access Token)
    7. Refresh Token은 HttpOnly 쿠키로 발급하고, 서버에는 만료 시간·폐기 시간 등 토큰 정보를 저장합니다. (Refresh Token은 body에 넣지 않고 Httponly, secure, samsite 옵션이 적용된 쿠키)
	    1. 카카오 로그인을 위한 Access Token을 위한 Refresh token이 아닌 우리 서비스만의 refresh 토큰.
    8. 동일한 카카오 계정으로 동시에 가입 요청이 들어오는 경우 `provider`와 `providerId`에 Unique 제약조건을 적용해 중복 회원 생성을 방지합니다.
    9. 회원가입이 완료되면, 신규 회원 여부를 true로 처리하고, 기존 회원 이면 false로 처리한다.

-  **트랜잭션 및 외부 API 처리:**
  - `authorizationCode` 검증과 카카오 OAuth API 호출은 DB 트랜잭션 외부에서 처리합니다.
  - 카카오 API 호출이 끝난 뒤, 우리 서비스의 회원 조회·회원 생성·Refresh Token 저장 또는 갱신을 하나의 트랜잭션으로 처리합니다.
  - 회원 생성 또는 Refresh Token 저장에 실패하면 전체 트랜잭션을 롤백합니다.
  - 트랜잭션이 성공적으로 커밋된 후에만 Access Token 응답과 Refresh Token 쿠키를 반환합니다.
  - 동시에 동일한 카카오 계정으로 요청이 들어오는 경우 `oauth_provider`, `oauth_provider_id`의 Unique 제약조건으로 중복 회원 생성을 방지합니다.
  - 중복 키 오류가 발생하면 기존 회원을 다시 조회하여 로그인 처리할 수 있습니다.


- **Response:**
    
    - 신규 회원가입: `201 Created`
    - 기존 회원 로그인: `200 OK`
    - 신규 회원 여부는 DB 컬럼이 아니라 응답용 `isNewUser` 값으로 판단합니다.

```
{
  "data": {
    "accessToken": "우리 서비스 Access Token",
    "tokenType": "Bearer",
    "expiresIn": 1800,
    "isNewUser": true,
    "user": {
      "userId": 101,
      "nickname": "닉네임",
      "profileImageUrl": "https://example.com/profile.png"
    }
  },
  "error": null
}
```

응답 헤더:

```
Set-Cookie: refresh_token={refreshToken}; HttpOnly; Secure; SameSite=Lax; Path=/api/auth; Max-Age=1209600
```

- **주요 오류 코드:**
    
    - `400 BAD_REQUEST`: 인가 코드 형식 오류
    - `401 UNAUTHORIZED`: 카카오 인증 실패 또는 인가 코드 만료
    - `409 SOCIAL_ACCOUNT_CONFLICT`: 이미 다른 회원과 연결된 카카오 계정
    - `500 INTERNAL_SERVER_ERROR`: 회원가입 처리 중 서버 오류

## 로그아웃 API

- **API 명세:**
    
    - `POST /api/auth/logout`
    - API 문서 링크: [API Docs 링크 - 로그아웃]
- **권한:**
    
    - Refresh Token 쿠키를 보유한 사용자
    - Access Token이 만료된 상태에서도 로그아웃할 수 있도록 `PermitAll`로 처리할 수 있습니다.
- **Request Header:**

```
Accept: application/json
Cookie: refresh_token={refreshToken}
```

`Content-Type`은 Request Body가 없으므로 사용하지 않습니다.

- **Request Body:**

```
없음
```

- **구현 상세:**
    
    1. 요청 Cookie에서 `refresh_token`을 가져옵니다.
    2. Refresh Token을 해시하여 DB에서 조회합니다.
    3. 유효한 토큰이면 `revokedAt`을 기록하여 폐기합니다.
    4. 동일 사용자의 현재 세션만 로그아웃하거나, 정책에 따라 모든 Refresh Token을 폐기합니다.
    5. 응답에서 Refresh Token 쿠키를 삭제합니다.
    6. Access Token은 JWT인 경우 즉시 폐기하지 않고 만료될 때까지 유효할 수 있으므로, 필요하다면 Redis에 블랙리스트를 저장합니다.
- **Response:**
    

```
204 No Content
```

```
Response Body: 없음
```

- **Response Header:**

```
Set-Cookie: refresh_token=;
              Max-Age=0;
              Expires=Thu, 01 Jan 1970 00:00:00 GMT;
              HttpOnly;
              Secure;
              SameSite=Lax;
              Path=/api/auth
```

- **주요 오류 코드:**
    
    - Refresh Token이 없거나 이미 폐기된 경우에도 로그아웃은 성공한 것으로 처리할 수 있습니다.
    - `500 INTERNAL_SERVER_ERROR`: 로그아웃 처리 중 서버 오류

로그아웃은 여러 번 요청해도 결과가 같도록 만드는 것이 좋으므로, 이미 로그아웃된 상태에서도 `204 No Content`를 반환하는 방식이 적절합니다.

## 회원 탈퇴 API

- **API 명세:**
    
    - `DELETE /api/users/me`
    - API 문서 링크: [API Docs 링크 - 회원 탈퇴]
- **권한:**
    
    - 로그인한 사용자 (`IsAuthenticatedUser`)
- **Request Header:**
    

```
Authorization: Bearer {accessToken}
Accept: application/json
Cookie: refresh_token={refreshToken}
```

Request Body가 없으므로 `Content-Type`은 사용하지 않습니다.

- **Request Body:**

```
없음
```

- **구현 상세:**
    
    1. Access Token을 검증하여 탈퇴 요청 사용자를 확인합니다.
    2. 해당 사용자의 활성 Refresh Token을 모두 폐기합니다.
    3. `users` 테이블의 회원 상태를 탈퇴 상태로 변경합니다.
    4. 서비스 데이터의 참조 관계를 고려하여 회원 정보는 Soft Delete 또는 익명화 처리합니다.
    5. 회원 탈퇴 후에는 해당 카카오 계정으로 다시 로그인했을 때의 처리 정책을 확인합니다.
        - 재가입 불가: 탈퇴 회원으로 판단하여 로그인 거부
        - 재가입 허용: 기존 회원을 복구하거나 새 회원으로 처리
    6. 카카오 앱과의 연결 해제가 필요하다면 카카오 연결 해제 API를 호출합니다.
    7. 카카오 API 호출은 DB 트랜잭션 외부에서 처리하고, 우리 DB의 회원 상태 변경과 Refresh Token 폐기는 하나의 트랜잭션으로 처리합니다.
    8. 응답에서 Refresh Token 쿠키를 삭제합니다.
- **트랜잭션 처리:**
    
    - 회원 상태 변경과 Refresh Token 폐기는 하나의 트랜잭션으로 처리합니다.
    - DB 처리에 실패하면 회원 상태와 토큰 폐기 작업을 모두 롤백합니다.
    - 카카오 연결 해제 API를 동기 호출한다면 해당 API 실패 시 탈퇴를 중단하거나 재시도 대상으로 저장해야 합니다.
    - 트랜잭션이 성공적으로 완료된 후에만 쿠키 삭제 응답을 반환합니다.
- **Response:**
    

```
204 No Content
```

```
Response Body: 없음
```

- **Response Header:**

```
Set-Cookie: refresh_token=;
              Max-Age=0;
              Expires=Thu, 01 Jan 1970 00:00:00 GMT;
              HttpOnly;
              Secure;
              SameSite=Lax;
              Path=/api/auth
```

- **주요 오류 코드:**
    
    - `401 UNAUTHORIZED`: Access Token이 없거나 유효하지 않음
    - `404 USER_NOT_FOUND`: 탈퇴 대상 회원을 찾을 수 없음
    - `409 ACCOUNT_WITHDRAWAL_CONFLICT`: 현재 상태에서 탈퇴할 수 없음
    - `502 KAKAO_UNLINK_FAILED`: 카카오 연결 해제 요청 실패
    - `500 INTERNAL_SERVER_ERROR`: 회원 탈퇴 처리 중 서버 오류

- **성능:**
    - 외부 카카오 API를 연동하므로 전체 로그인 응답 시간은 1초 이하로 목표를 설정합니다.
    - DB에서 provider와 provider_user_id에 복합 UNIQUE 인덱스를 설정하여 조회 속도를 높입니다.
    - 동시 로그인 요청과 회원가입 요청에 대한 부하 테스트를 진행 합니다.

- **카카오 OAuth 안정성:** 
	- 카카오 토큰 api와 사용자 정보 api에 연결 타임 아웃을 설정합니다. 
	- 인가 코드는 일회성 토큰이므로 토큰 발급 API를 반복해서 호출하지 않도록 합니다.
	- 카카오 API 호출은 외부 트랜잭션으로 처리하고, 실패 시 회원 생성 트랜잭션을 시작하지 않습니다.

- **데이터 정합성:**
	- 카카오가 보낸 사용자 고유의 id를 provider_user_id로 저장합니다.
	- provider와 provider_user_id를 복합 UNIQUE로 설정해 중복해서 가입되지 않게 합니다.
	- 동시에 같은 요청이 들어오면 UNIQUE 제약조건 처리하고 기존 회원을 돌려보냅니다.
    - DB 트랜잭션이 성공해야만 사용자의 access token과 refresh token 쿠키를 반환 합니다.

- **보안:**
	- refresh token은 원문을 저장하지 않고 hash값을 DB에 저장합니다.
	- `authorizationCode`는 서버에서만 카카오 토큰 API에 전달하고, 클라이언트가 보낸 `providerId`, 닉네임, 프로필 이미지는 신뢰하지 않습니다.
	- 탈퇴나 로그아웃 시, 사용자의 refresh token을 만료, 폐기 합니다.

## Auth

#### controller

- `AuthController`
    
    - `/api/auth`에 속한 회원가입·로그인, state 발급, 토큰 재발급, 로그아웃 요청을 처리한다.
    - 필요한 메서드:
    
    ```
    issueOAuthState();
    oauthLogin();
    reissueToken();
    logout();
    ```
    
    - Service를 호출하고 HTTP 응답을 구성한다.
    - state 발급 시 임시 state 쿠키를 설정하고, state를 응답 Body로 반환한다.
    - 로그인·재발급 성공 시 Access Token을 Body에, Refresh Token을 HttpOnly 쿠키에 담는다.
    - 로그인·재발급 처리가 성공적으로 커밋된 후에만 토큰을 반환한다.
    - 로그아웃 시 Refresh Token 쿠키를 삭제한다.

#### service

- `OAuthStateService`
    
    - state의 생성과 검증을 담당한다.
    - `SecureRandom`으로 난수를 생성하고 Base64 URL 형식으로 인코딩한다.
    - provider와 함께 Redis에 저장하며 TTL은 5분으로 설정한다.
    - 필요한 메서드:
    
    ```
    String issue(Provider provider);
    
    void verifyAndConsume(
        Provider provider,
        String requestState,
        String cookieState
    );
    ```
    
    - 요청의 state와 브라우저의 쿠키 state가 일치하는지 확인한다.
    - Redis에 저장한 provider와 state를 검증한다.
    - Redis에서 검증과 삭제를 원자적으로 처리하여 동일한 state의 중복 사용을 방지한다.
- `OAuthAuthenticationService`
    
    - OAuth 사용자를 우리 서비스에 회원가입 또는 로그인시키는 전체 흐름을 담당한다.
    - 필요한 메서드:
    
    ```
    AuthResult authenticate(
        OAuthLoginRequest request,
        String cookieState
    );
    ```
    
    - 처리 흐름:
        
        1. 요청한 provider가 지원되는지 확인한다.
        2. `OAuthStateService.verifyAndConsume()`으로 state를 검증하고 소비한다.
        3. `OAuthProviderClientFactory.getClient(provider)`로 구현체를 선택한다.
        4. 선택한 구현체를 통해 인가 코드를 외부 서비스의 Access Token으로 교환한다.
        5. 외부 사용자 정보를 조회하고 `OAuthUserInfo`로 변환한다.
        6. `AuthenticationTransactionService.complete()`를 호출한다.
        7. 트랜잭션이 성공적으로 완료되면 인증 결과를 Controller에 반환한다.
    - 외부 OAuth API 호출 동안 DB 트랜잭션을 유지하지 않도록 이 메서드 전체에는 `@Transactional`을 적용하지 않는다.
        
- `AuthenticationTransactionService`
    
    - 외부 인증 완료 후, 회원 조회·생성과 Refresh Token 저장을 하나의 트랜잭션으로 처리한다.
    - 필요한 메서드:
    
    ```
    @Transactional
    public AuthResult complete(OAuthUserInfo userInfo);
    ```
    
    - 처리 흐름:
        
        1. `AccountProvisioningService.findOrCreate()`로 `AccountResult`를 받는다.
        2. 반환된 회원의 ID로 `RefreshTokenService.issueAndStore()`를 호출한다.
        3. `AccessTokenIssuer.issue()`로 서비스용 Access Token을 발급한다.
        4. 회원 정보, `isNewUser`, Access Token, Refresh Token을 내부 결과인 `AuthResult`로 구성한다.
    - 회원 생성이나 Refresh Token 저장에 실패하면 해당 트랜잭션의 DB 변경을 함께 롤백한다.
        
    - 호출받는 DB 서비스는 같은 트랜잭션에 참여해야 하며, 이 흐름에서 `REQUIRES_NEW`로 독립 커밋하지 않는다.
        
    - `AuthResult`의 Refresh Token 원문은 Controller의 쿠키 설정에만 사용하고 응답 Body에 직렬화하지 않는다.
        
- `LogoutService`
    
    - 현재 로그인 세션의 서비스용 Refresh Token을 폐기한다.
    - 필요한 메서드:
    
    ```
    void logout(
        Long userId,
        String rawRefreshToken
    );
    ```
    
    - 전달된 Refresh Token이 현재 사용자의 토큰인지 확인한다.
    - `RefreshTokenService.revoke()`를 호출하여 해당 토큰의 `deletedAt`을 기록한다.
    - 카카오 계정의 로그아웃은 별도 외부 API 연동에 해당한다.
    - 이미 발급한 Access Token은 별도의 폐기 정책이 없다면 만료 전까지 유효하다.
- `RefreshTokenService`
    
    - Refresh Token의 생성, 저장, 검증, Rotation, 폐기를 담당한다.
    - 필요한 메서드:
    
    ```
    IssuedRefreshToken issueAndStore(Long userId);
    
    RotatedRefreshToken rotate(String rawToken);
    
    void revoke(String rawToken);
    
    void revokeAll(Long userId);
    
    Optional<RefreshToken> validate(String rawToken);
    ```
    
    - `issueAndStore()`는 토큰 원문을 생성하고, 해시값과 만료 시간 등 메타데이터를 DB에 저장한다.
    - `validate()`는 토큰의 존재 여부, 만료 여부, 폐기 여부를 확인한다.
    - `rotate()`는 기존 토큰을 검증하고 폐기한 뒤 새로운 Refresh Token을 발급해 저장한다.
    - Rotation에서 기존 토큰 폐기와 새 토큰 저장은 같은 트랜잭션으로 처리한다.
    - 같은 토큰으로 재발급 요청이 동시에 들어와도 한 요청만 성공하도록 잠금 또는 조건부 갱신을 적용한다.
    - 반환하는 내부 결과에는 토큰 소유자인 `userId`와 새 토큰 원문, 만료 정보를 포함한다.
- `TokenReissueService`
    
    - Refresh Token으로 새 Access Token을 발급받는 전체 흐름을 담당한다.
    - 필요한 메서드:
    
    ```
    @Transactional
    public TokenReissueResult reissue(String rawRefreshToken);
    ```
    
    - 처리 흐름:
        
        1. `RefreshTokenService.validate()`로 Refresh Token을 검증하고 소유자의 `userId`를 확인한다.
        2. `UserRepository.findActiveById(userId)`로 현재 인증 가능한 회원인지 확인한다.
        3. 탈퇴했거나 인증이 제한된 회원이면 재발급을 거절한다.
        4. `RefreshTokenService.rotate()`로 기존 토큰을 다시 확인하고 원자적으로 교체한다.
        5. `AccessTokenIssuer.issue()`로 새 Access Token을 발급한다.
        6. 새 Access Token과 Refresh Token을 `TokenReissueResult`로 반환한다.
    - 중간에 실패하면 토큰 교체에 따른 DB 변경을 롤백한다.
        
    - Controller는 새 Access Token을 Body에, 새 Refresh Token을 HttpOnly 쿠키에 담는다.
        

#### client

- `OAuthProviderClient`
    
    - 외부 제공자마다 다른 OAuth API 호출 방식을 통일하는 인터페이스다.
    - 필요한 메서드:
    
    ```
    Provider provider();
    
    OAuthToken exchangeAuthorizationCode(
        String authorizationCode
    );
    
    OAuthUserInfo getUserInfo(String accessToken);
    ```
    
    - `provider()`는 해당 구현체가 담당하는 제공자를 반환한다.
    - `OAuthToken`은 외부 토큰 응답을 처리하기 위한 내부 객체이며, 프론트 응답에 포함하지 않는다.
- `KakaoOAuthClient`
    
    - `OAuthProviderClient`의 카카오 구현체다.
    - `provider()`는 `Provider.KAKAO`를 반환한다.
    - 카카오 인가 코드를 카카오 Access Token으로 교환한다.
    - 카카오 사용자 정보를 조회하여 `OAuthUserInfo`로 변환한다.
    
    ```
    class KakaoOAuthClient implements OAuthProviderClient {
    }
    ```
    
- `OAuthProviderClientFactory`
    
    - provider에 맞는 `OAuthProviderClient` 구현체를 선택한다.
    - 주입받은 구현체들을 각 구현체의 `provider()` 값을 기준으로 등록한다.
    - 필요한 필드와 메서드:
    
    ```
    private final Map<Provider, OAuthProviderClient> clients;
    
    OAuthProviderClient getClient(Provider provider);
    ```
    
    - 현재는 `KAKAO → KakaoOAuthClient`로 연결한다.
    - 추후 Google·Naver 구현체를 추가하면 같은 방식으로 등록한다.
    - 지원하지 않는 provider 요청은 명시적인 오류로 처리한다.
    - 동일한 provider를 담당하는 구현체가 중복 등록되면 애플리케이션 초기화 시 오류로 처리한다.

#### token

- `AccessTokenIssuer`
    
    - Access Token의 발급과 검증 규칙을 정의하는 인터페이스다.
    - 필요한 메서드:
    
    ```
    String issue(Long userId);
    
    AccessTokenClaims validate(String accessToken);
    ```
    
    - 토큰 자체의 유효성을 검증한다.
    - 회원의 현재 탈퇴·정지 상태 확인은 회원 조회 로직에서 수행한다.
- `JwtAccessTokenIssuer`
    
    - JWT 방식으로 Access Token을 발급하고 검증하는 구현체다.
    - 서명, 만료 시간 등 토큰 검증을 담당한다.
    - 인증 Service가 JWT의 구체적인 구현 방식에 의존하지 않도록 한다.

#### dto

- `OAuthStateResponse`
    
    - state 발급 API의 응답이다.
    
    ```
    public record OAuthStateResponse(
        String state,
        Long expiresIn
    ) {
    }
    ```
    
- `OAuthLoginRequest`
    
    - 프론트가 외부 OAuth 인증 완료 후 서버에 전달하는 요청이다.
    
    ```
    public record OAuthLoginRequest(
        Provider provider,
        String authorizationCode,
        String state
    ) {
    }
    ```
    
- `OAuthUserInfo`
    
    - 외부 사용자 정보를 서비스의 공통 형식으로 변환한 내부 객체다.
    
    ```
    public record OAuthUserInfo(
        Provider provider,
        String providerUserId,
        String nickname,
        String profileImageUrl
    ) {
    }
    ```
    
- `AuthResponse`
    
    - 회원가입 또는 로그인 성공 시 프론트에 반환하는 응답이다.
    - `isNewUser`는 `AccountResult`에서 결정된 값을 전달받는다.
    - Refresh Token은 포함하지 않는다.
    
    ```
    public record AuthResponse(
        String accessToken,
        String tokenType,
        Long expiresIn,
        boolean isNewUser,
        UserSummary user
    ) {
    }
    ```
    
- `TokenReissueResponse`
    
    - Access Token 재발급 API의 응답이다.
    - 새 Refresh Token은 HttpOnly 쿠키로 반환한다.
    
    ```
    public record TokenReissueResponse(
        String accessToken,
        String tokenType,
        Long expiresIn
    ) {
    }
    ```
    

#### state

- `OAuthStateStore`
    
    - state 저장 방식에 대한 인터페이스다.
    - Service가 Redis 등 구체적인 저장 기술에 의존하지 않도록 한다.
    - 필요한 메서드:
    
    ```
    void save(
        String state,
        Provider provider,
        Duration ttl
    );
    
    boolean consume(
        String state,
        Provider provider
    );
    ```
    
- `RedisOAuthStateStore`
    
    - `OAuthStateStore`의 Redis 구현체다.
    - state와 provider를 TTL과 함께 저장한다.
    - `consume()`에서 provider 일치 여부 확인과 삭제를 원자적으로 처리한다.
    - state가 없거나 만료되었거나 이미 사용되었으면 검증에 실패한다.

## User

#### controller

- `UserController`
    
    - 사용자 리소스에 대한 HTTP 요청을 처리한다.
    - 인증된 사용자의 ID로 `AccountWithdrawalService`를 호출한다.
    - 필요한 메서드:
    
    ```
    void withdraw();
    ```
    

#### service

- `AccountProvisioningService`
    
    - 외부 계정 정보를 기준으로 기존 회원을 조회하거나 신규 회원을 생성한다.
    - 필요한 메서드:
    
    ```
    AccountResult findOrCreate(OAuthUserInfo userInfo);
    ```
    
    - 처리 흐름:
        
        1. `SocialAccountRepository.findByProviderAndProviderUserId()`로 외부 계정 연결 정보를 조회한다.
        2. 연결 정보가 있으면 해당 `userId`로 `UserRepository.findActiveById()`를 호출한다.
        3. 인증 가능한 기존 회원이면 `AccountResult(user, false)`를 반환한다.
        4. 연결된 회원이 탈퇴했거나 인증 제한 상태라면 로그인 오류로 처리한다.
        5. 연결 정보가 없으면 User와 Social Account를 생성한다.
        6. 신규 회원은 `AccountResult(user, true)`를 반환한다.
    - 탈퇴 회원을 조회하지 못했다는 이유만으로 신규 회원을 생성하지 않는다. 재가입 허용 여부는 별도 정책으로 판단한다.
        
    - `AuthenticationTransactionService`가 시작한 트랜잭션에 참여한다.
        
    - 복합 UNIQUE 제약조건으로 동시 요청에 따른 외부 계정 중복 연결을 방지한다.
        
    - 중복 키 충돌 후 기존 회원으로 로그인 처리를 이어간다면, 실패한 트랜잭션을 롤백한 뒤 새 트랜잭션에서 조회한다.
        
- `AccountWithdrawalService`
    
    - 회원 탈퇴를 처리한다.
    - 필요한 메서드:
    
    ```
    @Transactional
    public void withdraw(Long userId);
    ```
    
    - User의 `deletedAt`을 기록하고 상태를 `WITHDRAWN`으로 변경한다.
    - 사용자의 Refresh Token을 모두 폐기한다.
    - 회원 상태 변경과 토큰 폐기는 같은 트랜잭션으로 처리한다.
    - 재가입 정책에 따라 Social Account를 유지하거나 연결 해제한다.

#### dto

- `AccountResult`
    
    - 회원 조회·생성 결과를 Auth 도메인에 전달하는 내부 객체다.
    - `isNewUser`는 이번 처리에서 신규 회원을 생성했는지를 나타낸다.
    - DB 컬럼으로 저장하지 않는다.
    
    ```
    public record AccountResult(
        User user,
        boolean isNewUser
    ) {
    }
    ```
    

#### entity

- `User`
    
    - 서비스 회원 정보를 나타내는 Entity다.
    - 주요 필드:
    
    ```
    userId
    nickname
    profileImageUrl
    userRole
    userStatus
    createdAt
    updatedAt
    deletedAt
    ```
    
    - 필요한 메서드:
    
    ```
    void withdraw(Instant deletedAt);
    
    boolean isActive();
    
    void anonymize();
    ```
    
    - `isActive()`는 삭제 여부와 회원 상태를 함께 확인한다.
- `SocialAccount`
    
    - 외부 계정과 서비스 User의 연결 정보를 나타내는 Entity다.
    - 주요 필드:
    
    ```
    socialAccountId
    userId
    provider
    providerUserId
    linkedAt
    lastLoginAt
    ```
    
    - 필요한 메서드:
    
    ```
    boolean matches(
        Provider provider,
        String providerUserId
    );
    
    void updateLastLoginAt(Instant loginAt);
    ```
    
- `RefreshToken`
    
    - 서비스의 Refresh Token 정보를 나타내는 Entity다.
    - 주요 필드:
    
    ```
    refreshTokenId
    userId
    tokenHash
    expiresAt
    createdAt
    deletedAt
    ```
    
    - 필요한 메서드:
    
    ```
    void revoke(Instant revokedAt);
    
    boolean isActive(Instant now);
    
    boolean isExpired(Instant now);
    ```
    
    - 현재 필드 구성을 유지하여 폐기 시각은 `deletedAt`에 기록한다.

#### repository

- `UserRepository`
    
    - User Entity의 DB 접근을 담당한다.
    - 필요한 메서드:
    
    ```
    Optional<User> findById(Long userId);
    
    Optional<User> findActiveById(Long userId);
    
    User save(User user);
    ```
    
    - `findById()`는 회원 상태와 관계없이 조회해야 하는 관리·내부 처리에서 사용한다.
    - `findActiveById()`는 `deletedAt IS NULL`과 인증 가능한 `userStatus` 조건으로 조회한다.
    - `findActiveById()` 사용처:
        - `AccountProvisioningService`: 기존 외부 계정으로 로그인할 때.
        - `TokenReissueService`: 토큰 재발급 전에.
        - `JwtAuthenticationFilter`: 인증된 요청을 처리할 때.
    - `findActiveById`라는 이름만으로 활성 조건이 적용되지는 않으므로 `@Query` 또는 사용자 정의 구현으로 조건을 명시한다.
- `SocialAccountRepository`
    
    - Social Account Entity의 DB 접근을 담당한다.
    - 필요한 메서드:
    
    ```
    Optional<SocialAccount> findByProviderAndProviderUserId(
        Provider provider,
        String providerUserId
    );
    
    boolean existsByProviderAndProviderUserId(
        Provider provider,
        String providerUserId
    );
    
    SocialAccount save(SocialAccount socialAccount);
    ```
    
    - `(provider, providerUserId)` 복합 UNIQUE 제약조건으로 동일 외부 계정의 중복 연결을 방지한다.
    - 사전 `exists` 조회만으로는 동시 요청의 중복 생성을 막을 수 없으므로 DB 제약조건을 유지한다.
- `RefreshTokenRepository`
    
    - Refresh Token Entity의 DB 접근을 담당한다.
    - 필요한 메서드:
    
    ```
    Optional<RefreshToken> findActiveByTokenHash(
        String tokenHash
    );
    
    List<RefreshToken> findAllActiveByUserId(Long userId);
    
    void revokeAllByUserId(
        Long userId,
        Instant revokedAt
    );
    
    RefreshToken save(RefreshToken refreshToken);
    ```
    
    - 활성 토큰 조회 시 폐기 여부와 만료 시간을 확인한다.
    - Rotation에서 사용하는 조회·갱신에는 동일 토큰의 동시 사용을 막는 동시성 제어를 적용한다.

## Security

- `JwtAuthenticationFilter`
    
    - 요청 Header의 `Authorization: Bearer {accessToken}`를 확인한다.
    - `AccessTokenIssuer.validate()`로 토큰을 검증하고 `userId`를 추출한다.
    - `UserRepository.findActiveById(userId)`로 현재 인증 가능한 회원인지 확인한다.
    - 활성 회원이 확인된 경우에만 현재 회원 정보와 권한으로 `CurrentUser`를 생성하고 Security Context에 저장한다.
    - 탈퇴하거나 인증이 제한된 회원은 JWT가 만료되지 않았더라도 접근을 차단한다.
    - 필요한 메서드:
    
    ```
    void doFilterInternal(
        HttpServletRequest request,
        HttpServletResponse response,
        FilterChain filterChain
    );
    ```
    
    - 이 설계에서는 인증 요청마다 회원 상태 조회가 발생한다.
- `SecurityConfig`
    
    - Spring Security의 인증·인가 정책을 설정한다.
    - 필요한 메서드:
    
    ```
    SecurityFilterChain securityFilterChain(HttpSecurity http);
    ```
    
    - 접근 정책 예시:
    
    ```
    /api/auth/oauth/kakao/state → PermitAll
    /api/auth/oauth             → PermitAll
    /api/auth/refresh           → PermitAll
    /api/auth/logout            → 인증 필요
    /api/users/me               → 인증 필요
    ```
    
    - `/refresh`의 `PermitAll`은 Access Token 인증을 요구하지 않는다는 의미다. Refresh Token과 회원 상태 검증은 `TokenReissueService`에서 수행한다.
    - 인증·인가 실패 응답도 공통 오류 형식으로 반환하도록 설정한다.
- `CurrentUser`
    
    - 인증 완료 후 현재 사용자 정보를 담는 객체다.
    - 필요한 메서드:
    
    ```
    Long getUserId();
    
    UserRole getRole();
    ```
    

## Common

- `GlobalExceptionHandler`
    
    - Controller와 Service 처리 중 발생한 예외를 공통 API 오류 응답으로 변환한다.
    - 필요한 메서드:
    
    ```
    handleValidationException();
    
    handleAuthenticationException();
    
    handleOAuthException();
    
    handleBusinessException();
    
    handleUnexpectedException();
    ```
    
    - Security Filter 단계의 오류는 Security의 인증·인가 실패 처리에서도 같은 응답 형식을 사용하도록 연결한다.
- `ErrorCode`
    
    - 오류 코드, HTTP 상태 코드, 사용자 메시지를 관리하는 Enum이다.
    
    ```
    BAD_REQUEST
    UNAUTHORIZED
    FORBIDDEN
    NOT_FOUND
    CONFLICT
    INTERNAL_SERVER_ERROR
    UNSUPPORTED_OAUTH_PROVIDER
    INVALID_OAUTH_STATE
    INVALID_REFRESH_TOKEN
    SOCIAL_ACCOUNT_CONFLICT
    USER_ALREADY_WITHDRAWN
    USER_NOT_ACTIVE
    ```
    
- `ApiResponse`
    
    - 모든 API의 공통 응답 형식을 정의한다.
    - `success` 필드는 사용하지 않는다.
    - 성공 시 `data`에 값을 넣고 `error`는 `null`로 반환한다.
    - 실패 시 `data`는 `null`, `error`에 오류 정보를 넣는다.
    - 필요한 메서드:
    
    ```
    static <T> ApiResponse<T> success(T data);
    
    static ApiResponse<Void> error(ApiError error);
    ```
    

성공 응답 예시:

```
{
  "data": {
    "accessToken": "...",
    "isNewUser": true
  },
  "error": null
}
```

오류 응답 예시:

```
{
  "data": null,
  "error": {
    "code": "BAD_REQUEST",
    "message": "요청 값이 올바르지 않습니다.",
    "details": []
  }
}
```
