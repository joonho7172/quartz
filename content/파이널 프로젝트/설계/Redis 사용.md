# websocket simple broker로 단일 인스턴스간 소통을 redis pub.sub으로 구현

현재 websocket으로 발행된 메시지가 이어지는데, 
메시지를 DB에 저장하고 topic을 읽고 소비하는게 하나의 백엔드 인스턴스 내부에서 일어나고 있습니다.

v2에 백엔드 인스턴스가 2개로 늘어나면서, 각 인스턴스간의 소통 장치를 마련해야 하는데, 이 중계를 redis pub.sub으로 구현할 예정입니다.

##### 왜 redis stream이나 kafka 를 쓰지 않고?
redis stream이나 kafka 같은 경우에는 소비해야 하는 메시지가 보존 되어야 하거나, 반드시 보내져야 하는 경우에 사용하기 때문에 이벤트 로그들을 보존하는데, redis pub/sub은 메시지 발송이 실패하면 로그를 보존하거나 기록하지 않기 때문에 실시간으로 빠르게 채팅 전달이 가능합니다.
메시지 저장을 DB에 영구 보관하기 때문에도 로그를 보존할 필요성이 없어 pub.sub을 선택했습니다. 

# caffeine 로컬 캐시를 redis 공유 캐시로 전환

현재 caffeine을 사용해 인스턴스 내부 메모리에 key를 저장해서 캐싱하는데, v2의 2개 인스턴스에서는 서로 다른 메모리를 가지고 있기 때문에 캐싱이 제대로 이루어지지 않을 것을 대비해, 공유 캐시 저장소로 redis를 사용할 예정입니다. 네트워크 왕복 비용 등이 추가돼 응답 시간은 더 늦어질 수 있지만, 캐시를 공유 한다는 점에서 선택했습니다.

# OAuth state 값 redis에 저장

state값은 로그인을 시작한 브라우저가 나중에 돌아온 브라우저인지 확인하기 위한 일회성 값인데, 다중 인스턴스 환경에서 서로 다른 서버로 callback을 받게 된다면 값을 못 알아 볼 수도 있습니다.
현재는 DB에 저장해서 소비하기 때문에 이런 문제는 일어나지 않겠지만, 영구적으로 보존해야 할 데이터도 아닌 뿐더러, 1번만 소비되고 폐기되어야 하며, 일정 시간 이후 만료도 되어야 하기 때문에 redis의 GETDEL이나 hash 후 TTL 적용을 위해서 선택했습니다.
