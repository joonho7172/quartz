구현 1.
현재 조회 이벤트 본문에는 item ID와 user ID가 있다.
	-> 매 이벤트를 Redis에 집계.
추천 consumer가 Redis Hash(java의 map 자료구조와 비슷)에 5분 bucket으로 ItemID를 key로, 조회 횟수를 value로 저장한다.

그리고 저장한 bucket을 Redis sorted Set에 반영.
#### 왜 Redis에 조회수를 집계하는지
초기에는 각각 이벤트를 consumer가 읽을 때마다 DB에 저장하고 item ID 별로 timestamp와 함께 저장을 해서 count 집계를 하려고 했는데, 
1. 쓰기 부하와 아무리 index를 건다고 해도 읽기 부하가 클 것을 예상 (조회수 한 행 마다 저장하므로)
2. 최근으로부터 6시간 실시간 갱신이니 영구적으로 저장될 필요도 없다.

`DB를 쓰면 영속성이나, SQL 측면에서도 편리하게 관리 가능 하긴 하다.`
#### 왜 bucket을 두는지
그냥 단순하게 Sorted Set에다가 item ID별로 조회수를 기록하면, 6시간이 지난 조회수 집계를 걸러내기가 힘들다. 그래서 bucket을 두어, 시간이 만료된 (6시간이 지난) bucket은 집계에 포함하지 않게 하기 위해 bucket을 두었습니다.
#### 왜 bucket을 5분 단위로 하였는지
정확한 집계를 위해 1분 단위로 잡을 수 있었지만, 6시간에 3600개의 bucket을 인메모리 DB인 Redis에 저장하기에는 비싼 비용이라고 생각. 추후에 사용되는 메모리 용량을 보고 bucket 시간대를 조절 할 계획입니다.
#### 왜 자료구조를 Hash 와 Set으로 두었는지
먼저, Set은 중복을 제거하기 때문에 고유한 기본키인 itemId를 담기에 적합하다.
그중에서도 일반 Set이 아닌, SortedSet(ZSET)이 우선순위를 관리해주기 때문에, 빠른 상품 목록을 반환 하기 위해서 사용했습니다.
Hash 같은 경우도 버킷 단위의 redis key에 value로 저장해서, 각 item마다의 count를 추가합니다.

Hash 카운트 증가  -- O(1)
Sorted Set 총 카운트 증가 -- O(log N) 전체 순위 갱신
상위 목록 반환 -- O(log N + K) K개만큼 반환

시간 복잡도 측면에서도 괜찮은 선택이라 판단.
