# Kafka

publisher가 이벤트를 발행하면 토픽이 파티션 단위로 나뉘고, 이를 구독하며 대기하던 consumer가 이벤트를 소비하는 방식입니다.

## 지금 서비스에서 사용할 계획.

1. 교환 상태 변경 후 후속 처리
    1. 교환이 완료, 시작되었다는 시스템 메시지나 알림을 발행하거나
    2. 캐시에 물품 keyword가 등록되어 있지 않다면 외부 AI 서버에 API를 호출하는 과정을 별도 트랜잭션으로 비동기 처리하기 위함입니다.
    3. 우선 물품 저장을 완료한 후, item 테이블의 unit price를 채우는 방식입니다.

## 첫 번째 시나리오: 조회수 처리

1. 현재 조회수는 `GET /items/{itemId}` 상세 조회에서 증가시킵니다. (비관적 락을 통해 조회수 정합성을 강하게 지키고 있습니다.)
2. 아이템 상세 조회와 조회수 증가가 동기적으로 처리되다 보니, 상세 보기에서 조회수 증가 연산이 끝날 때까지 대기하는 상황이 발생합니다.
3. 이를 비동기로 분산하고자 합니다.
4. 처음에는 `@Async`와 `Executor`를 통해 별도 스레드에서 작업하도록 합니다.
5. 그러나 애플리케이션이 갑자기 종료되거나 작업자가 끊기면, 이후 조회수 정합성을 지키기 어렵습니다.
6. 조회수 연산이 많아지면 기존 스레드 풀이 넘칠 수 있습니다.
7. 따라서 조회수 요청을 조절하기 위해 RabbitMQ나 Kafka 같은 메시지 큐를 사용할 수 있습니다.
8. 둘 다 중간에 컨테이너가 중지되거나 작업자가 끊기는 상황에서도 처리를 이어갈 수 있습니다. RabbitMQ는 중단된 작업을 이어서 처리할 수 있고, Kafka는 consumer가 읽은 record의 offset을 저장하기 때문에 재시작 후 이어서 처리할 수 있습니다.

이후에도 조회수 요청량이 부하가 된다면 partition을 늘려 병렬 처리를 고려할 수 있습니다. key를 item 키로 설정하면 서로 다른 물품에 대한 조회수 요청을 병렬 처리할 수 있습니다. 다만 하나의 key(아이템)에 부하가 몰려 행 잠금으로 성능이 떨어진다면 (커넥션 풀의 크기 등등 조절) consumer batch 처리로 대응하려고 합니다.

## 두 번째 시나리오 : 검색 기록 저장
1.  현재 물품 검색은 get API에서 keyword로 물품을 조회하고, 첫 페이지 검색어를 검색 기록에 저장합니다.
2. 현재는 검색 기록 저장도 검색 API 안에서 동기적으로 처리합니다. 상품 목록을 조회하는 동안 검색 기록을 DB에 저장하는 시간까지 응답이 지연될 수 있었습니다.
3. 검색 기록 저장이 끝날 때까지 기다리지 않도록 검색 기록 처리를 검색 결과 조회와 분리했습니다.
4.  검색 API는 SearchHistoryEvent 를 발행하고, `@Async`와 `Executor`를 통해 별도 스레드에서 검색 기록을 저장합니다.
5. 이 방식으로 검색 기록 저장이 끝나기 전에 검색 결과를 반환하여 응답시간을 단축 시킬 수 있습니다.
6. Executor는 프로세스 내부에서 동작하므로, 애플리케이션이 갑자기 종료되면 대기 중인 작업이 유실될 수 있습니다. 현재는 조회수 처리와 같은 스레드 풀을 공유하며, 대기열이 가득 차면 작업을 버리는 설정입니다.
7. 이러한 검색 기록의 유실을 줄여야 한다면 고가용성인 RabbitMQ나 Kafka 같은 메시지 큐를 사용할 수 있습니다. RabbitMQ는 저장된 메시지를 처리 성공 후 확인하도록 하고, Kafka는 DB 저장이 끝난 뒤 offset을 반영하도록 구성해 작업자 중단 후에도 재처리할 수 있습니다.
8. 이후 검색 기록 요청량이 늘어나면 Kafka의 key를 사용자 ID로 설정해, 같은 사용자의 기록은 순서대로 처리하고 서로 다른 사용자의 기록은 병렬 처리하는 방식으로 해결 하려 합니다. 




## 추가 고려 사항
교환 완료 이벤트들이나, 검색 키워드 이벤트등을 재처리 함으로써, 핫 아이템, 핫 키워드 등을 중심으로 추천 집계, 그 후 상품들을 redis에 캐시 저장을 하고 상품 목록 api에 활용할 예정입니다.
