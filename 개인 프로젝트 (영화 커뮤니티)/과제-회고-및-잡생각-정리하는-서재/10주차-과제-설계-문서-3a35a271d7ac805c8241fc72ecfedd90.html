10주차 과제 설계 문서

기존의 js 코드들을 보면서 어떻게 옮길지 구상했습니다.

구현 중에 바뀌거나 AI에게 배운 점들은 전환기에 작성하였습니다.

//코드는 그냥 참고용으로 복붙해놓은거라 안읽으셔도 됩니다.//

API(백엔드 api 요청 함수)

  1. userApi 사용자 수정, 비밀번호 변경, 회원 탈퇴 등
  2. commentApi 댓글 생성 요청, 댓글 수정 요청, 댓글 삭제 및 조회 요청
  3. attachApi 첨부 파일 등록, 조회, 수정, 삭제 요청
  4. postApi 게시글 등록, 조회, 수정 또는 삭제 요청
  5. authAPI 로그인이나 회원가입, 토큰 요청
  6. apiClientApi # 공통 응답이나 공통 예외 처리 요청

Context(여러 페이지가 공유하는 상태)

  2. postLike (게시글 목록에도, 게시글 상세 조회에서도 있는)

  3. CommentList (게시글 상세 조회에 있는 댓글 목록)

  4. LikeButton (

  9. profileMenu 프로필 드롭 다운

  12. ErrorMessage # 오류 메시지 표현

  3. global (body, 입력창 등 전역 디자인)

1. API 분리

먼저 기존 JS에서 가장 기본이 되는 apiClient.js 파일을 마이그레이션 하였습니다.

  • API 주소 관리
  • 로그인 정보와 토큰 조회
  • 요청 헤더 생성
  • JSON 응답 변환
  • 액세스 토큰 만료 시 재발급
  • 요청 실패 처리
  • 이미지 URL 및 날짜 변환
  • 다른 JS 파일에서 사용할 함수 공개

1. apiClient.js

이미 localStorage에 있는 access token으로 부터 userId를 가져오기 때문에 삭제 할 예정입니다.

기존의 loginUser는 localStorage에서 가져왔기 때문에 사용자 정보가 바뀌어도 화면이 렌더링 되지 않았습니다.

→ user를 따로 state로 관리해 login된 user 상태가 바뀌면 그에 맞게 반응하는 구조로 변경할 예정입니다.

로그아웃에 사용되는 clearAuth가 지금은 localStorage에 저장되어 있는 정보를 다 없애는데, react에서는 사용자 상태를 관리하는 useAuth로 책임을 넘기고 apiClient에는 accessToken만 삭제하는 걸로 바꿀 예정입니다.

즉, clearAuth를 별도로 분리하여 apiClient에서 제외시킬 예정입니다.

동시에 setUser(null)를 통해, 로그아웃과 동시에 화면 렌더링도 예정입니다.

withUserId를 사용하지 않으므로 withUserId를 없앨 예정입니다.

json 응답 오류는 전체적으로 냅둘 예정입니다. 나중에 ai에게 오류를 반환하는 react 식 방법을 물어볼 예정입니다.

json이나 파일 요청, 인증 헤더를 추가하는 방식은 그대로 냅둘 예정입니다. 나중에 ai에게 react 식으로 마이그레이션 방법을 물어보고 적용할 계획입니다.

path를 일일히 다 확인해서 지저분한 느낌이라 react 마이그레이션 하면서 바꿔볼 예정입니다.

토큰 재발행 함수입니다. JSON 형태로 응답 받고 만약 재발급에 실패하면 clearAuth(로그아웃) 합니다. clearAuth 에서 state로 user를 관리하기 떄문에 화면이 재렌더링 되면서 로그아웃 상태로 표시 될 것 입니다.

여기서 어떻게 다른 파일로 분리시킨 clearAuth를 가져오고 실행 시키지? 생각했는데 react에서 handleUnauthorezed를 통해 clearAuth에서 useEffect로 선언된 setUnauthorizedHandler를 실행시켜 clearAuth를 실행시키면 되는 것 이었습니다.

날짜 변환은 api와 상관없는 함수로 utils 폴더에 넣어서 관리할 예정입니다.

window.apiClient = {
  request,
  getLoginUser,
  getAccessToken
};

지금은 window를 통해 최상위 전역 변수로 설정해놓은 상태인데 html의 script 순서에 의존하지 않도록. 모듈화해서 export, import 할 예정입니다.

2. Common.js

localStorage에 모든 정보를 확인했다면 useAuth인 AuthContext를 이용해서 간편하게 확인 할 예정입니다.

그러면 자동으로 화면이 리렌더링 될 것입니다.

지금은 document로 불러와 button의 기능을 구현했는데, react에서는 jsx로 button을 하나하나 찝어오지 않고 구현할 예정입니다.

기존에는 ProfileButton을 하나하나 생성해서 디자인을 불러왔다면, react에서는 페이지에서 잦은 횟수로 사용되는 프로필 메뉴이기에 components로 분리하여 작성 할 예정입니다.

똑같이 innerHtml이 아닌 jsx로 변환 할 예정입니다. button과 같이 components에 추가할 예정입니다.

const opened = profileMenu.classList.toggle(‘is-open’);

지금은 toggle로 하고 있는데 state를 사용해 isOpen, setIsOpen으로 두어, 열리면 드롭박스가 보이고 안열리면 감춰지는 형태로 구현하는것이 좋아 보입니다.

결국 리액트에서는 전체적인 Header에서 ProfileMenu 메소드에 props로 { onLogin } 을 내려줍니다. login이 되어 있으면 profileMenu가 보이고, 되어 있지 않으면 로그인 버튼이 보이게 설정 할 예정입니다.

아직 백엔드 기능 구현은 되어 있지 않지만 결국 ProfileMenu가 사용자의 프로필 이미지 이기에,

프로필 이미지 url을 props로 내리고, 프로필 이미지가 있고 없고는 isHasProfileImage 정도의 state로 바꿔주면 좋을 거 같습니다.

profileMenu에서는 state로 isOpen을 설정하여 화면에 적용 할 예정입니다.

처음에 AI가 ProfileMenu에서 user를 props로 가져오려고 하길래 로그인 상태만 가져오면 되지 않을까 해서 바꿨습니다.

login.js

우선 querySelector에 있는 값들은 react가 dom에서 직접 찾지 않으므로, 구조를 바꿔줘야 한다고 생각했습니다.

loginForm은 jsx의 form.. email 입력은 state 등으로.. 바꿀 생각입니다.

우선 emailInput이 없을테니 없애고, email과 password를 onChange를 통해, STATE로 관리하고 Validation 값을 계산해서 보여주면 될 것 같습니다. (useMemo 생각했는데 간단한 계산이라 굳이 싶기도 하고 고민 됩니다.)

localStorage는 없애고, 기존에 location.href 으로 이동하던 경로를 navigate로 이동하게 수정합니다. 그리고 지금은 error를 console에 띄우거나 message.textContent를 통해 오류 메시지를 보여주는데, react에서의 error는 즉시 화면에 렌더링 되어야 하기 때문에 state로 관리를 하면 될 것 같습니다. style.color 같은 경우는 css로 이동..

로그인 화면은 별도 props가 필요 없어보입니다. 응답만 useAuth를 통해 accessToken만 잘 응답받으면 될 것 같습니다. 회원가입은 Link로 이동..

Signup.js

login과 마찬가지로 querySelector는 없애고 username과 email , password, check까지 state, onChange로 둔다.

if문으로 검사하는 것은 util의 validation으로 처리하고, 중복 제출을 방지하기 위해 기존 submitButton을 true와 false로 두던 것을 state로 관리합니다. 나머지 경로 이동은 navigate와 replace 사용해서 경로 이동합니다.

전체적으로 먼저 계획한 login과 비슷한 양상입니다.

PostWrite.js + PostEdit.js

Post칸에서 수정과 작성의 함수가 동일하므로 둘을 합치는 방향으로 고색하였습니다.

위와 같이 querySelector 부분은 없애고 state로 관리할 부분, form으로 관리할 부분, accessToken이나 loginUser는 authApi로 관리합니다.

지금은 전역 변수로 postId에 의존하는 문제점을 해결하고, 매개변수로 받으면서 data까지 매개변수로 전달해 postApi로 이동 시킵니다.

attach 같은 경우도 attachService 로 따로 관리하고 있으니 attachApi로 이동시켜 attachid와 file을 매개변수로 attachAPi로 보냅니다.

파일 검사 함수는 그대로 유지하되, 기능과는 관련 없으므로 util에 validation으로 보내서 처리합니다.

단 fileError 같은 경우는 state로 관리해서 오류 즉시 화면을 반환 할 수 있도록 합니다.

preview는 posts, 게시글 목록의 화면 일부가 되므로 components로 관리합니다. 전달해주는 값들은 props로 imageUrl, alt, removeHandler를 받게 둡니다. removeHandler는 onRemove로 버튼을 눌렀을 때 작동하게 react를 설계합니다.

render 함수는 필요 없을 것 같습니다. currentImage로 remainImage를 state로 관리하고, selectedImage도 state로 관리하면 자동으로 렌더링 될 것입니다. imageCount도 selected된 이미지의 list.length와 remain된 list.length를 더하면 될 것 같습니다.

전부 attachApi에 넣으면 될 것 같습니다. 나중에 post에서 글과 같이 작성하려고 할 때 부분만 성공하는 이슈를 처리해야 할 것 같습니다.

util의 validation에 넣으면 될 것 같습니다. 반환값을 usePostForm으로 돌려보내 state로 관리하면 될 것 같습니다.

useIsSubmitting state로 관리하면 될 것 같습니다.

usePostForm에서 useEffect로 관리하여 postId가 있는 경우에는 수정모드, 없는 경우에는 작성모드로 구분해서 하면 될 것 같습니다.

결론은 usePostForm에서 useEffect로 isEditMode로 수정중인 상태나 작성중인 상태를 관리하며, 게시글 내용과 제목, 이미지, 오류와 제출, 수정 버튼 등을 state로 관리합니다.

UserEdit

전체적인 구조는 userEditPage가 useUserEdit을 호출하고 반환 된 값을 저장하는 식으로 잡았습니다.

마찬가지 querySelector는 사용하지 않으므로 정리합니다.

이전에는 로그인 되어있는지 localStorage에서 확인하고 토큰의 여부를 확인했는데 이제는 useAuth로 관리하기 때문에 필요하지 않을 것 같습니다.

토스트 메시지는 state로 관리하고 일정 시간이 지나면 clear()하게 만들면 될 것 같습니다. 나중에 재사용 할 일이 생기면 useToast로 커스텀 훅으로 만들어도 될 것 같은데 아직 고민 중 입니다.

지금은 dom을 직접 수정하는데 변경되는 nickname을 state로 관리하고 10자 이상은 util의 validation으로 넘기면 될 것 같습니다.

백엔드 api를 불러오는 것뿐이므로 UserApi 파일로 별도 분리만 하면 될 거 같습니다. 이미 Promise 형태로 반환받기 때문에 별도로 async await가 필요할 것 같진 않습니다.

지금 userEditForm 이 하는 일이 중복 수정 방지, nickname 유효성 검사와 error 메시지 띄우기 인데

직접 localStorage에 update하지 않고 useAuth의 state인 user를 변경해 상위 header도 자동으로 다시 렌더링 되게 합니다.

PasswordEdit.js

마찬가지로 querySelector부분은 없애고 로그인 되어있는 상태는 useAuth을 통해서 가져옵니다.

password edit이나 useredit이나 비슷합니다.

validate는 따로 util로 만들어 비밀번호를 확인한 값과 한번 더 입력한 비밀번호 확인을 비교합니다. 비밀번호 유효 검사는 백엔드에서 처리하므로 프론트에서는 비밀번호 일치 불일치만 검사합니다.

비밀번호 변경은 api로 따로 넘깁니다.

입력받은 password와 passwordConfirm은 state로 관리하고 onChange를 통해 보여줍니다. , 그 외 나머지 error도 state로 관리합니다. submitBotton도 중복 제출 방지를 위해 state로 관리해서 props로 내려줍니다. 비밀번호 같은 경우는 isVisible을 통해 버튼을 누르면 비밀번호가 보이고 감춰지는 state도 추가했습니다.

Posts.js

like와 unlike, getPosts는 LikeAPI, postsApi로 각각 분리합니다.

Html을 반환하는 PostCard안에 넣을 예정입니다. 화면 조각중 일부라 컴포넌트로 분리하려고 했지만 PostCard안에만 들어가는 썸네일이라 PostCard안에서 한꺼번에 처리하려고 합니다. imageUrl을 불러오는 resolveImageUrl은 따로 분리할 생각입니다.

기존에 ReviewCard가 좋아요도 담당하고 썸네일도 보여주고, 게시글 내용과 상세페이지 이동 등 많은 기능을 포함하게 했는데 좋아요 기능인 onLikeButton은 STATE로 분리하고 나머지 내용은 postCard로 분리하려고 합니다

renderReview는 postList컴포넌트로 변경하여 posts 배열을 받고, state 관리하여 react에게 렌더링을 맡길 생각입니다.

성공하면 render, 실패하면 오류를 뱉는 기능을 usePosts hook으로 관리할 예정입니다.

posts와 error를 state로 관리하고 초기에는 useEffect로 요청을 보내고 setPosts를 통해서 렌더링 할 예정입니다.

결론 : 크게는 posts와 like를 usePosts에서 state로 관리할 예정입니다. 그리고 Get요청은 abortController로 할 예정입니다.

Post.js

똑같이 querySelector는 없애고,

postId 가져오는건 useParams, user를 가져오는건 useAuth를 사용할 예정입니다.

위와 같은 API호출은 postApi로 변경할 예정입니다. comment도 마찬가지.

지금은 createElement와 appendChild로 불러오는데 PostImageList로 변경할 예정입니다. resolveImageUrl은 유지할 생각입니다.

기존에는 일일히 DOM으로 이미지를 넣었다면 usePost를 통해 Post를 state로 관리하여 렌더링을 맡길 예정입니다.

작성자 검사도 useAuth로 받은 user와 post?user.id를 통해서 검사합니다.

loadPost도 post를 state 관리할 예정으로 렌더링이 필요하지 않습니다. 다만 get 요청 조회이므로 abortController를 통해 구현할 예정입니다.

useLike와 likedButton은 게시글 목록에 만들어놨으니 component와 hook을 재사용 하면 될 것 같습니다.

components로 comment를 분리할 예정입니다. props로 삭제나 수정 상태, comment 내용, user등을 받고 onChange로 state 처리 할 예정입니다.

commentList 컴포넌트를 만들어 처리할 예정입니다.

useComment에서 state로 상태 값을 받아서, 버튼의 문구를 수정 할 예정입니다.

결론은 항상 댓글을 삭제하고 수정하고 추가할때마다 get으로 조회하고 load했는데, react에서는 state로 관리해 렌더링을 맡긴 것 입니다.
