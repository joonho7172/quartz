11주차 과제 회고(고도화)

1. attach 파일의 중복 요청 문제 (10주차 피드백 내용)

프론트에서는 게시글 작성 중 attach 오류가 있을 때 생기는 중복 처리와 게시글 수정 중 생기는 중복 요청을 막긴했는데, 백엔드에서도 그것을 처리 하지 않으면,

ATTACH의 DB 행이 중복 요청 마다 증가 하는 문제가 있었다.

생각 한 해결 방법

  1. 현재 attach db가 id, postid(foreign), attachUrl 이므로 unique값을 설정하면 중복요청을 막지 않을까?
    1. 같은 이미지로 중복 요청이 들어와도 attachUrl이 randomUUID 이므로 계속 추가 되므로 안됨.
  2. 그러면 또 다른 id를 추가해서, 중복 요청을 검사하자, 어차피 프론트에서 selectedImage가 바뀌지 않고 남아서 saveImage 요청을 보내는 것이니, selected의 파일에 전에 들어온 key값이 같으면 그냥 전에 받았던 file을 return 하는 것으로.

ai는 이러한 문제를 해결하기 위해서 위와 같은 방법으로 unique 걸고, key까지 저장하는 것. 그리고 더 나아가 post 중복 요청이 들어올 때를 대비해서 비관적 Lock까지 거는 방법을 추천했다. ( 1. A가 upload key 조회, 2. B가 upload key 조회, 3. A가 없음을 확인하고 저장 시작, 4. B도 없음을 확인하고 저장 시작…..) 과 같은 문제 해결.

근데 프론트에서 for문으로 돌면서 await를 통해 파일을 받는데 동시성 문제가 과연 생길까.. 오버 엔지리어닝이 걱정돼서 빼버렸다. 만약에 생기면 그때 넣는걸로 결정했다.

그치만 백엔드의 unique 제약은 유지하기로 했다. 백엔드에서 프론트로부터 파일을 저장하고 응답을 보내는 도중에 오류가 생기면 프론트는 실패라고 판단하고 isSubmit 버튼을 다시 활성화, 사용자가 다시 요청 할 수 있기 때문에.

결론은 프론트에서 중복 요청의 횟수를 막음 (selected에서 완료된 것만 uploaded로 보내기 때문에) 그리고 만약 프론트로 응답이 가기 전 중복 요청이 된다고 하면 백엔드에서 unique로 데이터 행 추가하지 않고 upload key와 같은 값 전달.

react에서는 단순하게 별점은 사용자의 마우스에 따라 별점을 value로 onChange로 넘기고, 별 모양 기준 왼쪽이 0.5, 오른쪽이 1로 두게끔 한다. 게시글 목록이나 홈 화면에도 나오게 할 예정이라 postEdit에서만 클릭 가능하게, 다른 곳은 readOnly로

기존의 formatDate.js를 바꾸면 되는 것이다. 1분전이면 방금전, 그 외에는 분, 시간, 일, 달, 년도 기준으로 얼마 전인지 표시했다.

4. 프로필 이미지 추가 기능 (내용이 좀 새긴 했습니다)

attachment처럼 그냥 requestParam으로 받고, 저장하는 식으로 가려고 했는데 Ai가 User회원가입이나 수정에서는

email, password, username, 등을 같이 받기 때문에 @ReqeustParam 보다는 @ModelAttribute가 어울린다고 해서 짧게 정리 해봤다.

@ModelAttribute는 multipart/form-data로 전달된 여러 입력값을 하나의 DTO 객체로 묶어주는 역할을 한다.

대신에 ModelAttribute를 사용해 form을 받고 Spring이 그 값들을 빈 객체에 하나씩 넣어주어야 하기 때문에,

@Setter가 필수적이었다, Setter, Getter를 사용하는 것을 지양하는 것이 좋다고 몇주전 회고에 썼었는데

AI에게 간단하게 질문하고 답변 받은 내용이, Entity에 setter를 두는 것만큼 DTO에 프레임워크 바인딩용 Setter를 두는 것이 위험하지 않다는 것. request에 생성자 바인딩과, getter, setter말고 record를 둬보는게 어떻겠냐는 답변을 받았다.

record에 대해서 잘 몰라서 찾아보니까 불변의 dto에 set, get, 생성자 생성을 제공한다고 되어 있다.

생성자를 미리 만들고 값을 주입하던 class와 달리 미리 요청값을 담아서 주는 record의 차이점을 알게 되었다.

그러면 record는 불변이니까 요청값이 이상하면 바꿀 수 없는것 아닌가? (imageUrl이 이상해 null로 바꾸기 등)

  • 애초에 요청값이 이상하면 요청을 거절하면 되고, NotBlank 같은 validation이 있으면 controller 단계에서 걸러지므로 괜찮다는 결론을 받았다.

결론 : request 같이 생성자 바인딩이 필요하고 getter가 필요하며, signUprequest와 같이 modelAttribute로 받아 setter도한 필요한 dto들은 단순 데이터 객체라는 가독성과, 불변성을 강조하기 위해 class에서 record로 바꿨다.

5. 조회수 기능 수정

초기에는 단순하게 post Entity에 viewCount만 담아서 getpost() 요청 할 때마다 +1씩 증가되게 했다.

그로 인해 새로 고침 할 때마다 조회수가 하나씩 늘어나는 단점이 있었다.. 이를 해결하기 위해서

postView entity를 하나 만들고, 그 안에는 post id, user id, viewat 이라는 조회를 한 날짜를 기록했다.

리액트에서 새로 고침 할 때마다 controller를 통해 updatePostView라는 서비스를 부르고, 지금의 날짜가 viewAt 날짜와 다르면 viewCount+1을 하고 viewAt을 수정한다. 만약 viewAt 날짜와 서버 날짜가 같으면 그냥 넘어가는 식이다. 날짜의 기준이 서버이기때문에 해외에서 조회하면 해외의 정각과는 다르겠지만 그건 나중에 생각..

6. 영화 목록 불러오기

먼저 외부 TMDB라는 사이트에서 데이터를 불러오기로 했다. (상업적 목적이 아니라면 무료로 공유)

API키를 받고 데이터를 다운 받고 RDS로 데이터를 json 파일로 저장했다.

저장 기준은 처음에, 제공해주는 데이터에서 popular의 수치를 알려주어서 인기순으로 5000개를 뽑았다가, 최신 영화나 개봉한지 얼마 되지 않은 영화들은 인기순에서 제외되는 사항을 고려해, 인기순 3000, 최신순 3000개 중 중복 데이터를 제거하고 수집하였다. (수집하는 config/MovieDataLoader는 ai에게 부탁했습니다.)

초기 HomePage에서 영화 최신 개봉 순 preview를 제공하는데,

Repository에

List<Movie> findTop4ByOrderByReleaseDateDescIdDesc();

Top4를 반환하는 쿼리 메소드를 작성했다. preview에는 title이랑 posterPath만 있으면 되는데 전체 Movie 엔티티를 반환하는 방식이 마음에 들지 않아, DTO projection을 생각했다가 굳이 영화 4개 때문에 projection까지 만드는 방법이 성능에 큰 영향을 끼칠 것 같지는 않아 냅두기로 했다. (나중에는 5개로 바꿨습니다.)

대신 따로 MoviePreviewResponse로 DTO를 만들어 응답구조는 최소화 시키기로 했다.

프론트에서는 API요청의 도착시 렌더링을 위해 MoviePreview에 포함되는 Movies를 state로 관리했다.
