과제 기능 구현 검색 엔진

먼저 각각의 성능을 비교하기 전에 기준이 되는 검색어를 정하였다.

검색어 1. 공포 영화 (공포 + 영화의 합성어)

검색어 2. 배우 연기가 좋은 영화 (조사와 띄어쓰기가 포함되어 있는 자연어)

검색어 3. 영화 (하나의 단어로 많은 데이터를 얼마나 효율적으로 검색해내는지 확인하기 위함)

먼저 운영 환경이 배포 환경과 같고, AWS의 RDS 와 연결이 되어 있어서, 비용도 그렇고 버전 고정과 벌크 데이터를 넣고 초기화 하기 위해 모든 검색 성능 실험은 따로 도커 환경을 준비 했다.

배포/운영 환경과 같은 환경에서 실험 해야 하므로 버전 8.4.9를 로컬에서 준비했다.

과정은 아래와 같다.

workapi 소스코드 ↓ localhost:3307로 접속만 함 Docker MySQL 8.4.9 ↓ Docker 전용 volume

벤치 마크 전용 사용자 1명을 생성하고, 검색용으로 사용할 게시글 데이터를 10만건 ~ 적재한 후, Like 구현을 해서 explain Analyze로 비교할 계획이다.

  1. 임의의 사용자 만들기

  1. 리뷰 오픈 데이터 셋 가져오기

https://github.com/e9t/nsmc/blob/master/ratings.txt에서 20만건의 자연어 데이터 셋을 가져온다. (나중에 데이터를 복합하고 섞어 50만 건으로 늘릴 예정)

그 중 부정 라벨 50000, 긍정 라벨 50000, 총 10만건의 데이터로 실험 한다.

  1. 현재 운영하고 있는 DB가 MySQL기반이므로 PostRepository에서 검색쿼리를 추가한다.

간단하게 입력값이 제목과 내용에 포함되어 있는지만 검색을 한다 LIKE %입력값%의 성능을 보기 위함.

첫번째 키워드는 “공포 영화”로 like를 통해 값들이 나오는걸 볼 수 가 있다.

그러나 검색어가 조금만 복잡해지면 LIKE로 찾지 못하는 단점이 있다. (예시: “로버트 다우니 주니어가 나오는 액션 영화”, “연기를 잘하고 재밌는 영화”

검색어 1( “공포 영화” ) MySQL LIKE %검색어% 결과.

목록조회, 페이지네이션 까지 정한 조회 결과 이다, 전체 조회까지 67.8ms가 걸린 것을 확인 할 수 있다.

Count 값들만 뽑아낸 조회 결과, 총 59ms가 걸렸다. 전체 조회보다는 조금 더 나은 성능.

API요청과 응답까지의 시간과, p50, p95를 알기 위해

JVM 클래스 로딩, JIT 최적화와 DB 커넥션 풀 준비, DB데이터가 메모리에 올라오는 과정 등. 측정 오류를 줄이기 위해서 워밍업 3회를 거쳤다.

이후에 p50( 요청의 절반 ) 이 108.7ms안에 완료가 되었고, p95(95번쨰 )값이 184.5ms 안에 종료가 되었다.

2번 검색어 “배우 연기가 좋은 영화”

우선 검색 결과는 0이었다. 검색 결과가 없는 상황에서도 성능 비교가 필요하다고 판단해 같은 방법으로 진행 했다.

우선 페이지네이션 등 제약 사항이 있는 필터링 결과는 74.4ms,

그냥 Count만 한 쿼리에는 60.1ms가 나왔다.

똑같이 워밍업 3회, 측정 100회로 p50과 p95의 값을 정했다.

또 다른 대안. MongoDB (NoSQL)

https://liltdevs.tistory.com/213

MongoDB는 데이터를 데이터를 JSON-like documents로 저장하는 NoSQL 데이터베이스이다.

MongoDB 같은 NoSQL은 JSON(BSON) 형태의 유연한 문서 구조를 사용하며, 데이터마다 필드가 달라도 한 문서 안에 계층적으로 담아 한 번에 검색할 수 있다는 이점이 있다. 즉, 비정형된 문서 데이터 검색에 강하다는 결론 하나로 실험을 해볼 가치는 충분 했다.

기존의 MySQL에 있던 데이터를 MongoDB로 복사 한 뒤, 검색 성능을 확인하기 위한 함수를 생성하고,

MySQL의 LIKE %%와 같이 MongoDB의 $regex를 사용해서 측정을 했다. 첫 실행에서만 발생하는 준비 비용을 제외하기 위한, 각자의 워밍업 후에 키워들의 값들을 측정했다.

마지막 대안 : Elastic search

https://trends.builtwith.com/operations/Elasticsearch

결국 또 다른 대안이 없을까 찾아보던 중, BuiltWith 기준으로 현재 가장 많이 사용되고 있는 검색엔진은,

Elastic Search 와, OpenSearch , MeiliSearch 가 있었다.

MeiliSearch는 간단하고 구현이 쉬워 스타트업에서 많이 사용하는 검색 엔진이다. 다만, 한국어 형태소 분석 기능이 없어 한국어의 자연어 기반의 검색에는 약하다는 단점이 있다.

Elastic Search는 Nori라는 한국어 형태소 분석기를 공식적으로 지원한다.

커뮤니티에서 검색 기능은 사실 속도 보다 품질이 더 중요도가 높다고 생각하기에, 이 점은 상당히 매력적이었다.

예를 들면, “마동석이 출연한 액션 영화”라는 문장이 있으면 단순 공백 기준, “마동석이” “출연한” “액션” “영화”가 되겠지만, Nori를 사용하면, “마동석” “출연” “액션” “영화” 와 같이 의미 있는 단어를 추출해 검색해 준다.

OpenSearch는 AWS가 포크해서 만든 검색 엔진으로 AWS가 자동으로 관리해주는 Elastic Search서비스라고 볼 수 있다. 그러나 이번에는 학습을 위해서 OpenSearch 대신 Elastic Search를 사용했다.

먼저 Build.gradle 의존성 파일에 elasticSearch를 도입을 위한 의존성을 추가한다.

elastic search 의 성능을 확인하기 위한 별도의 폴더를 생성하고 elastic search의 nori 형태소 분석기를 설치한다.

위와 같이 형태소 분석이 되는 것을 확인 한 후. 각각의 키워드에 대해서 실험한다.

  • MySQL 같은 경우는 LIKE %검색어%로 Table Scan을 하고
  • MongoDB 같은 경우는 $regex: 검색어로 COLL Scan을 했다.
  • 문서가 JSON 형태라는 이유만으로 NoSQL이 MySQL보다 빠르진 않았다.
