
부하테스트가 처음이기도 하고, 인프라까지 신경써서 운영해보는 것은 처음이라 아쉬웠던 점이 많았다.
우선 좋았던 점은 코드 단계에서의 협업 뿐 아니라, 클라우드 팀과의 협업을 해봄으로써 어느정도 감각이 생겼다는 것.

부하테스트 동안 내가 한 일은 이랬다.
### 1. 백엔드 코드 개선하기
1. Socket.io 메시지 조회 이벤트 개선하기
	기존 socket.io 메시지 조회 이벤트는 MessageLoader.loadMessages()를 통해서
	MongoDB에서 메시지 목록을 조회 한 후, 메시지 마다 사용자와 파일을 조회하고 MessageResponse를 만들어 반환 한다.


```java
sortedMessages.stream()
    .map(message -> {
        User user = findUserById(message.getSenderId());
        return messageResponseMapper.mapToMessageResponse(message, user);
    });
```

findUserById가 userRepository에 findById를 매번 조회하기 때문에,

전체 메시지가 30개, 파일이 20개 라면
전체 메시지 목록 조회 1+ 사용자 조회 30 + 파일 조회 20 : 총 61번의 MongoDB쿼리가 나가는 것을 개선했다.

중복을 제거히는 SET을 사용해서 메시지를 보낸 사용자 별 id를 추리고, Map을 통해 사용자를 한꺼번에 조회해 가져왔다. 

전체 메시지 목록 조회 1+ 사용자 batch 조회 1 + 파일 조회 1 : 총 3번의 쿼리로 개선했다.


2. Page를 Slice로
```java
Page<Message> findByRoomIdAndTimestampBefore(
        String roomId,
        LocalDateTime timestamp,
        Pageable pageable
);
```
기존의 page 방식은 message를 불러올때 현재 페이지의 데이터, 전체 페이지의 수, 전체 메시지의 수, 다음 페이지의 번호 등 불필요한 정보까지 가져온다.
Slice 방식은 현재 조회된 메시지 목록, 다음 메시지가 존재하는지에 대한 여부만 가져오기 때문에
MongoDB의 부하를 줄였다.

3. 메시지 조회용 복합 인덱스 생성
slice 개선 구조로 인해 cursor 방식으로, 기존 OffSet방식과 달리 timestamp를 통해서 roomID를 먼저 확인 후, MessageLoader에서 30개씩 정렬하는 방식이었다.


```java
@CompoundIndex(
        name = "room_timestamp_desc_idx",
        def = "{'room': 1, 'timestamp': -1}"
)
```
저장하는 Message에 오름차순의 방 번호와 내림차순의 Timestamp를 인덱스로 생성하여,
인덱스가 없을 때 Collscan 하는 MondoDB의 부하를 줄이는 법으로 개선했다.
기존의 offset + 인덱스 없이 조회하는 방법보다 mongoDB의 CPU와 api간 연결 성능, 응답 response를 줄일 수 있었다.

4. 방 목록 조회 N+1
기존에는 RoomService 코드에서 방을 전체 조회 하고 (1), 방의 생성자와 참가자를 모두 조회 (n) + 최근 메시지 조회 (n) 식의 n+1 문제를 해결하기 위해,
snapshot에서 MongoDB의 응답 객체를 따로 받아 메시지 생성.
