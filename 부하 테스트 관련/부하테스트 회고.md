
부하테스트가 처음이기도 하고, 인프라까지 신경써서 운영해보는 것은 처음이라 아쉬웠던 점이 많았다.
우선 좋았던 점은 코드 단계에서의 협업 뿐 아니라, 클라우드 팀과의 협업을 해봄으로써 어느정도 감각이 생겼다는 것.

부하테스트 동안 내가 한 일은 이랬다.
### 백엔드 코드 개선하기
1. Socket.io 메시지 조회 이벤트 개선하기
	기존 socket.io 메시지 조회 이벤트는 MessageLoader.loadMessages()를 통해서
	MongoDB에서 메시지 목록을 조회 한 후, 메시지 마다 사용자와 파일을 조회하고 MessageResponse를 만들어 반환 한다.


```java
sortedMessages.stream()
    .map(message -> {
        User user = findUserById(message.getSenderId());
        return messageResponseMapper.mapToMessageResponse(message, user);
    });
```

findUserById가 userRepository에 findById를 매번 조회하기 때문에,

전체 메시지가 30개, 파일이 20개 라면
전체 메시지 목록 조회 1+ 사용자 조회 30 + 파일 조회 20 : 총 61번의 MongoDB쿼리가 나가는 것을 개선했다.

중복을 제거히는 SET을 사용해서 메시지를 보낸 사용자 별 id를 추리고, Map을 통해 사용자를 한꺼번에 조회해 가져왔다. 

전체 메시지 목록 조회 1+ 사용자 batch 조회 1 + 파일 조회 1 : 총 3번의 쿼리로 개선했다.


2. Page를 Slice로
```java
Page<Message> findByRoomIdAndTimestampBefore(
        String roomId,
        LocalDateTime timestamp,
        Pageable pageable
);
```
기존의 page 방식은 message를 불러올때 현재 페이지의 데이터, 전체 페이지의 수, 전체 메시지의 수, 다음 페이지의 번호 등 불필요한 정보까지 가져온다.
Slice 방식은 현재 조회된 메시지 목록, 다음 메시지가 존재하는지에 대한 여부만 가져오기 때문에
MongoDB의 부하를 줄였다.

3. 메시지 조회용 복합 인덱스 생성
slice 개선 구조로 인해 cursor 방식으로, 기존 OffSet방식과 달리 timestamp를 통해서 roomID를 먼저 확인 후, MessageLoader에서 30개씩 정렬하는 방식이었다.


```java
@CompoundIndex(
        name = "room_timestamp_desc_idx",
        def = "{'room': 1, 'timestamp': -1}"
)
```
저장하는 Message에 오름차순의 방 번호와 내림차순의 Timestamp를 인덱스로 생성하여,
인덱스가 없을 때 Collscan 하는 MondoDB의 부하를 줄이는 법으로 개선했다.
기존의 offset + 인덱스 없이 조회하는 방법보다 mongoDB의 CPU와 api간 연결 성능, 응답 response를 줄일 수 있었다.

4. 방 목록 조회 N+1
기존에는 RoomService 코드에서 방을 전체 조회 하고 (1), 방의 생성자와 참가자를 모두 조회 (n) + 최근 메시지 조회 (n) 식의 n+1 문제를 해결하기 위해,
snapshot에서 MongoDB의 응답 객체를 따로 받아 메시지 생성.

기존에 room 당 전체 생성자, 전체 사용자의 목록을 따로따로 가져왔다면,
이번에도 중복을 하용하지 않은 set을 사용해서 사용자의 목록을 일괄적으로 가져오게 했다.
```java
Set<String> userIds = new HashSet<>();

for (Room room : rooms) {
    if (room.getCreator() != null) {
        userIds.add(room.getCreator());
    }

    if (room.getParticipantIds() != null) {
        userIds.addAll(room.getParticipantIds());
    }
}
```
그리고 기존에는 방마다 메시지를 따로 count해서 가져왔다면,
```java
messageRepository.countRecentMessagesByRoomId(roomId, since);
```
이제는
```java
messageRepository.countRecentMessages(roomId);
```
로 전체 방 목록을 보내고 한번에 messages를 Map 형태로 가져온다. - 응답매핑을 가져온 map에서 값을 꺼내서 가져오게 해서 1+n+n 의 쿼리를 1+1+1 총 3회로 줄여 개선했다.

5. Socket.io 방 입장 퇴장 참가자 조회 N+1 성능 개선 
```java
 List<UserResponse> participants = roomOpt.get().getParticipantIds()
                    .stream()
                    .map(userRepository::findById)
                    .filter(Optional::isPresent)
                    .map(Optional::get)
                    .map(UserResponse::from)
                    .toList();
```
기존에는 방에 들어갈때, 참가자의 ID를 하나씩 따로 조회했기 때문에 입, 퇴장 이벤트 한번에 전체 참가자의 목록만큼 mongoDB의  부하가 늘어났다.
userId를 모아 1번의 조회 쿼리를 통해 map 으로 담아서 응답을 map에서 꺼내 쓰는 형태로 개선 했다.

socket 인증 정보에서 userId -> room 조회 -> participantsID 에 현재 사용자 추가 -> 전체를 batch 조회 -> 응답을 생성해서 반환 구조로.

7. 스레드폴 조정
우선 스레드 폴의 size 변경은 내가 직접 한 것이 아닌, 우리 조원이 한 것이다.
```properties
chat.message-read-status.executor.core-pool-size=${MESSAGE_READ_STATUS_CORE_POOL_SIZE:2}
chat.message-read-status.executor.max-pool-size=${MESSAGE_READ_STATUS_MAX_POOL_SIZE:4}
chat.message-read-status.executor.queue-capacity=${MESSAGE_READ_STATUS_QUEUE_CAPACITY:100}
```
위와 같이 applications.properties 파일에 스레드 폴의 크기를 설정해 두어서,
Websocket을 읽었을 때의 이벤트를 발행하는 것과 별개로 MongoDB의 쓰기 지연이 socket의 응답 지연과 분리 했다는 것이다. (완벽한 분리는 아님)

그 외에도 
```properties
server.tomcat.threads.max=${TOMCAT_THREADS_MAX:50}  
server.tomcat.threads.min-spare=${TOMCAT_THREADS_MIN_SPARE:10}  
server.tomcat.accept-count=${TOMCAT_ACCEPT_COUNT:100}  
server.tomcat.max-connections=${TOMCAT_MAX_CONNECTIONS:100}
```
tomcat의 스레드 폴도 늘리고 connection 의 수도 늘려서 처리량을 늘렸다.

8. redis cluster를 통한 redis 병목 완화
기존에는 단일 redis를 통해, 캐시와 세션 저장을 통해 DB의 서버 부하를 분산 시켰다.
그러다 보니 백엔드의 Ec2를 스케일 아웃을 해도 redis가 병목 원인이 되던가, redis의 장애가 socketIO의 pub/sub 기능에도 영향을 주는 걸 알았다.

따라서 EC2 3대를 redis전용으로 1개의 인스턴스에 2개의 노드, master와 replica를 넣어 redis를 3개의 Master와 3개의 replica로 구성했다.
```env
REDIS_CLUSTER_NODES=10.0.101.192:6379,10.0.102.192:6379,10.0.101.118:6379
REDIS_CLUSTER_MAX_REDIRECTS=8
SESSION_REDIS_ENABLED=true
SOCKETIO_REDIS_ENABLED=true
```

이로 인해 Redis의 CPU부하를 줄였고, 네트워크의 병목을 완화시켰다. 
그리고 MongoDB에서 가져오던 로그인, JWT 검증, Socket.IO handshake를 위한 세션을 Redis에서 관리하고, 채팅방 목록, 참여자, 최근 메시지 수, 메시지 브로드 캐스트를 redis에 저장해서 관리했기 때문에 cluster 로 구성한 것이 redis의 부하에도 큰 영향을 미쳤다.


## 아쉬웠던 점
짧은 시간 내에 성능 개선의 효과를 보고, 적용해야 했기에 redis나 n+1 문제등 자세히 알아보지 못했다. 이렇게 회고를 적으면서 돌아보니 어느정도 감은 있지만 자세하게 알지 못했던 거 아쉽다. 회고 7번의 스레드 폴이나, 커넥션 폴 조정, GC 설정 등 욕심은 많았지만 제한적인 시간 내에 하고 싶은걸 다 하기에는 부족했다. 
부하테스트가 끝난 후 Grafana를 통한 성능 개선 수치나, 병목 원인도 자주, 자세히 알고 지점을 찾아내고 싶었는데 현실은 운영과 ai를 통한 기능 구현에 막혔던 거 같아 개인적으로 아쉬웠다.
